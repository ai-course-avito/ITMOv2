## Как объяснить на защите

1. GitHub Trigger слушает `issues`. Code пропускает только `action == "opened"` своего репозитория и извлекает поля Issue.
2. Data Table `processed_issues` проверяет глобальный `issue.id` (строка). Он уникален, в отличие от номера Issue внутри репозитория. Если запись уже есть, выполнение останавливается до вызова модели.
3. Execute Workflow с включённым ожиданием передаёт данные обращения в отдельный сценарий. Классификатор использует только `title` и `body` и возвращает `{type, confidence}`.
4. Basic LLM Chain выбирает тип по тексту. Structured Output Parser требует JSON с допустимым типом и уверенностью от 0 до 1. Code проверяет результат.
5. Если уверенность меньше 0.8 или тип не из `bug/task/feature`, основной сценарий заменяет тип на `unknown`. Switch имеет три правила и запасной выход unknown. Ровно 0.8 относится к известной категории.
6. У каждого типа своя метка. У известных типов есть шаблонный ответ; unknown соединён сразу с записью в таблицу, поэтому комментария нет.
7. При `author_association == "NONE"` известный тип дополнительно получает `first-time-contributor` и приветствие со ссылкой на [CONTRIBUTING.md](CONTRIBUTING.md). Тестовые Issues созданы владельцем (`OWNER`), поэтому эта ветка на них не выполнялась.
8. После успешной обработки сохраняются `issue_id`, `author`, `created_at`. Повторное открытие также отбрасывается проверкой `action`, так как GitHub присылает `reopened`.

## Недельный отчёт и звёздочка

Cron: `0 9 * * MON`. При проверке n8n использовал серверное время UTC+3. В сохранённых JSON дополнительно явно задан `Europe/Moscow`; перед публикацией отчёта выберите его также в Settings → Timezone в n8n. Вручную можно запустить узел «Проверить вручную».

Период — последние семь суток до запуска. В понедельник это неделя до 09:00. Все четыре запроса используют один и тот же рассчитанный период:

```text
GET /search/issues?per_page=100&q=repo:bronY9/ITMOv2 is:issue label:"bug" created:START..END
GET /search/issues?per_page=100&q=repo:bronY9/ITMOv2 is:issue label:"task" created:START..END
GET /search/issues?per_page=100&q=repo:bronY9/ITMOv2 is:issue label:"feature-request" created:START..END
GET /search/issues?per_page=100&q=repo:bronY9/ITMOv2 is:issue label:"needs-triage" created:START..END
```

Считаются созданные за период классифицированные Issues независимо от того, закрыты они сейчас или открыты. GitHub Search индексируется с задержкой: сразу после добавления меток при необходимости запустите отчёт позже. Для учебного репозитория запрашивается до 100 Issues каждой категории. При обрезанном результате сценарий явно падает, чтобы не отправить неверную статистику; для большего репозитория нужна пагинация.

Code группирует данные по типам и авторам и исключает повторы по `issue.id`. Table `weekly_issue_stats` хранит `week_key`, `period_start`, `period_end`, `stats_json`. `week_key` — понедельник недели запуска. Upsert заменяет результат повторного запуска той же недели, а не создаёт дубликат.

Прошлая запись выбирается по `week_key - 7 дней`. Δ — текущее значение минус сохранённое предыдущее. Если прошлых данных нет, письмо пишет «нет данных», а не выдумывает нулевую неделю.

Для проверки разрешённой условием имитации добавлена запись `2026-11-09`: 2 bug, 1 task, 0 feature, 0 unknown, всего 3. В JSON стоит `simulated: true`; письмо и AI-аннотация явно называют сравнение учебным. Реальная запись `2026-11-16`: по одному Issue каждого типа, всего 4, Δ всего +1.

Basic LLM Chain получает реальные текущие числа, предыдущую запись и рассчитанные Δ. Он пишет только краткую аннотацию, не считает метрики самостоятельно. HTML собирается Code node, текст LLM и имена авторов экранируются. В письме две таблицы (типы и авторы), Δ и блок «AI-комментарий недели».

Проверка отчёта: [execution 7357](https://n8n-itmo.cyrweb.ru/workflow/0IDvCDVUSEhmUa5y/executions/7357), 6.243 секунды. Все четыре запроса, группировка, чтение предыдущей недели, AI-аннотация, HTML и сохранение текущей статистики выполнены. Gmail выключен. [Предпросмотр](report-preview.html) воспроизведён тем же кодом HTML по проверенным числам и тексту реального ответа модели; это не полученное письмо.

## Подключение Gmail на учебном сервере

В текущем n8n форма требует **Client ID** и **Client Secret**, поэтому одной кнопки входа Google недостаточно. [Официальная инструкция n8n](https://docs.n8n.io/integrations/builtin/credentials/google/oauth-single-service/).

1. В Google Cloud выбрать или создать проект, включить Gmail API и настроить экран согласия OAuth. При режиме Testing добавить свой Gmail в тестовые пользователи.
2. В Credentials создать OAuth client ID типа **Web application**. В Authorized redirect URIs указать точно:

   ```text
   https://n8n-itmo.cyrweb.ru/rest/oauth2-credential/callback
   ```

3. В n8n открыть «Отправить отчёт Gmail» → **Connect to Gmail**, ввести Client ID и Client Secret из Google Cloud, затем выполнить вход Google и разрешить доступ. Секрет вводить непосредственно в n8n; в GitHub и чат его отправлять не нужно.
4. Далее выполнить пункты проверки письма выше. Доступ к Google Cloud и разрешение почтового доступа выполняет владелец аккаунта.
