| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---|---|---|---|
| Время от открытия PR до первого комментария ревьюера | базовая линия снимается по таймстемпам GitHub (момент открытия PR → момент первого комментария ревьюера) для PR команды до подключения сервиса; текущая оценка — 3–6 часов (`problem.md`, допущение) | сократить с 3–6 до 1–2 часов при условии, что ревьюер получает автоматический разбор рисков в течение 10 сек после открытия PR (`REL-1`, CASE.md/adr.md); конкретное сокращение до 1–2 часов помечено как допущение (`problem.md`) | при каждом открытии PR и при появлении первого комментария ревьюера в GitHub | таймстемпы событий PR в GitHub (открытие PR, первый комментарий ревьюера) |
| Время от получения diff до готового ответа сервиса (`summary`, `risks`, `checks`), сек | базовая линия снимается первым прогоном сервиса на регрессионном наборе из 30 учебных diff (включая `TRAINING_PR.diff`, adr.md «Как проверим риск») сразу после развёртывания | не более 10 сек на вызов — таймаут внешнего LLM (`REL-1`); при ошибке или превышении таймаута — контролируемый ответ вместо зависания (`REL-1`) | на каждом вызове сервиса, начиная с первого прогона регрессионного набора и далее при каждом реальном запросе ревьюера или CI | лог сервиса: `request_id`, длительность, статус (`OBS-1`) |
| Доля рисков из ответа сервиса, с которыми ревьюер согласился | базовая линия снимается на том же первом прогоне регрессионного набора из 30 diff с заранее размеченными ожидаемыми рисками (adr.md «Как проверим риск»): доля согласия = доля рисков в ответе сервиса, совпавших с ожидаемыми (размеченными) рисками этого набора | не менее 80% к третьему прогону расширенного регрессионного набора после доработки фильтра `QA-1`, если порог adr.md был превышен (число 80% — допущение, не выведено из CASE.md/adr.md) | на каждом прогоне регрессионного набора, включая повторные прогоны после доработки фильтра `QA-1` (adr.md «Как проверим риск») | механизм отсутствует для продовой фиксации согласия: сравнение с размеченными ожидаемыми рисками регрессионного набора (adr.md) есть, но отдельного лога или пометки ревьюера «согласен/не согласен» по каждому риску не описано (за пределами `OBS-1`, который логирует только `request_id`, длительность и статус) — нужно добавить такой лог/пометку в интерфейс ревью |
| Доля выдуманных замечаний (риск в ответе не подтверждён строкой diff) | базовая линия снимается первым прогоном регрессионного набора из 30 учебных diff (включая `TRAINING_PR.diff`), описанным в adr.md «Как проверим риск» | не более 1 неподтверждённого риска на 30 прогонов (~3%) — порог согласован в adr.md, раздел «Как проверим риск» | на каждом прогоне регрессионного набора, включая повторные прогоны, которые запускаются, если порог превышен и фильтр `QA-1` дорабатывается (adr.md) | отчёт прогона: для каждого риска в ответе проверяется наличие указанных `file` и `line` в исходном diff |
| Число нарушений правил репозитория, пропущенных при ревью | тем же первым прогоном регрессионного набора из 30 diff с заранее размеченными ожидаемыми рисками (adr.md): считаются нарушения, отмеченные в разметке набора, но не попавшие в `risks` ответа сервиса | не более 1 пропущенного нарушения на 30 прогонов (~3%) — порог перенесён из adr.md для `QA-1` (допущение: adr.md задаёт этот порог для ложных срабатываний, а не для пропусков) | на каждом прогоне регрессионного набора (adr.md «Как проверим риск»), особенно при повторных прогонах после доработки фильтра | механизм отсутствует: разметка ожидаемых рисков в регрессионном наборе есть (adr.md), но шаг сравнения «ожидаемые риски разметки vs фактические `risks` ответа» для подсчёта пропусков не описан — нужно добавить этот шаг к процедуре проверки регрессионного набора |
