# E2E-проверки (few-shot)

| Сценарий | Предусловия | Действие | Наблюдаемый результат | Evidence |
|---|---|---|---|---|
| Позитивный: валидный diff | Сервис запущен; доступен POST `/api/reviews`; LLM замокан; длина diff ≤ 20000 | POST `/api/reviews` с телом `{"diff": "diff --git ..."}` (используем TRAINING_PR.diff) | 200 OK; тело содержит `summary` (строка), `risks` (массив ≤3 элементов), `checks` (массив) | HTTP: статус=200; JSON: ключи `summary`,`risks`,`checks` присутствуют, `len(risks) ≤ 3`; Логи: есть `request_id`, `duration`, `status=200`; подстрока `"diff --git"` в логах отсутствует (OBS-1) |
| Негативный: пустое тело | Сервис запущен; LLM замокан | POST `/api/reviews` с телом `{}` | 422 Unprocessable Entity; ошибка указывает на обязательное поле `diff` | HTTP: статус=422; JSON: сообщение об ошибке содержит указание на отсутствующее поле `diff`; Логи: есть `request_id`, `duration`, `status=422`; содержимое diff не логируется (OBS-1) |
| Граничный: diff > 20000 символов | Сервис запущен; LLM замокан; подготовлен diff длиной 20001+ символ | POST `/api/reviews` с телом `{"diff": "<строка длиной >20000>"}` | 413 Payload Too Large по правилу API-1 | HTTP: статус=413; Логи: есть `request_id`, `duration`, `status=413`; подстрока входного diff отсутствует в логах (OBS-1) |

Примечания к формату:

- На успех ожидается структура согласно OUT-1: `summary`, `risks[]` (максимум три элемента с полями `file`, `line`, `evidence`, `risk`), `checks[]`.
- Для негативных и граничных кейсов проверяем конкретный HTTP-статус из правил CASE и отсутствие утечки содержимого `diff` в логах (OBS-1).
