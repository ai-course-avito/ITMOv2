# Few-shot

- Артефакт Практики 1: [`../practice_01/adr.md`](../practice_01/adr.md) — «Архитектурное решение и взаимодействие сервисов»
- Что хотим улучшить: ADR не задаёт ожидаемой структуры результата. Нет явных критериев выбора альтернатив, trade-offs, NFR с порогами; Mermaid-схема не подкреплена выбором. Через контрастные примеры («хороший» vs «плохой» ADR) зафиксируем шаблон, которому должна соответствовать доработка артефакта.


## Примеры

### Хороший результат

```text
# ADR-2: AI-ревьюер PR как локальный прокси-микросервис
Статус: accepted. Дата: 2026-09-20.

Контекст. Ревью diff ненадёжно: секреты уходят в LLM, нет таймаута (HTTP 500),
ответ неструктурирован. Нужен помощник, который даёт проверяемые замечания,
а решение о merge оставляет человеку.

Решение. Фасад ReviewService перед внешним LLM, публикуется через POST /api/reviews:
SEC-1 фильтр секретов, API-1 длина >20000 → 413, REL-1 timeout 10 с → контролируемый
ответ, OUT-1/QA-1 структура (summary + risks ≤3 + checks), SCOPE-1 границы, OBS-1 логи.
При падении LLM — fallback degraded=true (не 500).

NFR (порог + способ проверки):
- p95 ответа ≤ 10 с (timeout 10 с); падение LLM → degraded-ответ, 0% HTTP 500
  (проверка: tests_integration.md «мок LLM sleep 15 с»).
- 0% утечек секретов; в логах только request_id/длительность/статус (tests_unit.md SEC-1, OBS-1).
- rate limit: при превышении N запросов/мин → 429, без бесконечных ретраев (tests_load.md).

Альтернативы:
- сырой ответ LLM — отклонено (SEC-1/REL-1/OUT-1);
- асинхронная очередь — отложено до >10 000 ревью/день;
- эвристики без LLM — отклонено (нет контекстного анализа);
- локальный прокси — выбран (централизует фильтры, timeout, лимиты).

Архитектурная схема: mermaid flowchart с веткой fallback (ошибка LLM → degraded).
```

### Плохой результат

```text
# Простое решение
Будет делать ревью через ИИ. Используем FastAPI и вызовем модель.
Добавим фильтр ключей и какие-то ограничения. В будущем можно улучшить
и добавить очередь.
```

Почему плохой: нет контекста и критериев, нет альтернатив и trade-offs, NFR без порогов («какие-то ограничения», «в будущем»), схема отсутствует — результат невозможно проверить или воспроизвести.

## Запрос

```text
Вот два примера ADR: ХОРОШИЙ (критерии выбора, компромиссы, NFR с порогами,
Mermaid-схема) и ПЛОХОЙ (без структуры и проверяемости). Доработай
../practice_01/adr.md по структуре ХОРОШЕГО примера: добавь критерии выбора
альтернатив, компромиссы и раздел нефункциональных требований с порогами;
Mermaid-схему сохрани и согласуй с правилами SEC-1/API-1/REL-1/OUT-1/SCOPE-1/QA-1/OBS-1.
```

## Что получили

Модель воспроизвела структуру «хорошего» примера: в ADR появился раздел NFR с порогами и способами проверки, таблица альтернатив дополнена явными критериями и вердиктами, в схему добавлены fallback и rate limit. Порог таймаута 10 с и лимит 20 000 символов взяты из Context Pack, а не выдуманы заново.

## Что изменили в исходном артефакте

- Файл и раздел: `../practice_01/adr.md` — «Решение», «Рассмотренные альтернативы», новая секция «Нефункциональные требования (NFR)»
- Изменение: ADR перестроен по шаблону хорошего примера — добавлены критерии выбора с вердиктами и NFR с порогами
- Как проверили: в `adr.md` присутствует заголовок «Нефункциональные требования (NFR)»; у каждого NFR есть числовой или конкретный порог; Mermaid-блок валиден; `git diff` показывает именно ADR
- Что отклонили: вариант «простое решение» без критериев (сопоставим с плохим примером) и NFR без порогов («высокая надёжность», «быстрая работа»)
