# Few-shot: усиление доказательности problem.md

## Фактический запрос

Применим Few-shot для улучшения доказательности `problem.md`.

Критически важно: в текущем рабочем репозитории каталога `app/` нет. `TRAINING_PR.diff` — это текст учебного patch, а не локальный исполняемый код. Не утверждай, что приложение запускалось, и не создавай отсутствующие файлы.

Задача:

1. Проведи аудит текущего `problem.md` на соответствие хорошему и плохому примеру.
2. Для каждого существенного утверждения укажи: подтверждено diff / не подтверждено / требует runtime-проверки.
3. Исправь `problem.md`, сохранив только доказуемые факты в разделе `## Проблема`.
4. Конкретно исправь утверждения про роль пользователя, `500`, неверный тип тела, задержки, безопасность и бизнес-эффект.
5. Не удаляй саму проблему — сделай её более строгой.
6. `TRAINING_PR.diff` не изменяй.
7. После изменения покажи diff и способ статической проверки.
8. Запиши в `practices/practice_02/few_shot/experiment.md` фактический запрос, фактический результат, принятое изменение и то, что было отклонено.
9. Обнови соответствующую строку в `practices/practice_02/prompts.md`.

Ориентиры Few-shot:

- Хороший результат: «По `TRAINING_PR.diff:35-37` обработчик `POST /api/reviews` получает `payload` и обращается к `payload["diff"]`. Если ключ отсутствует, это статически указывает на возможность `KeyError`. Runtime HTTP-статус этим diff не подтверждается.»
- Плохой результат: «Отправка `{}` сейчас даёт HTTP 500; при неверном типе тела тоже возникает KeyError; большие diff вызывают задержку более 2 секунд; безопасность prompt нарушена.»

## Фактический результат

- Проведён аудит утверждений в `practices/practice_01/problem.md` относительно `TRAINING_PR.diff`.
- Внесена минимальная правка раздела «## Проблема» для сохранения только доказуемых фактов.
- Таблица статуса утверждений подготовлена ниже; подробности проверяемости привязаны к строкам `TRAINING_PR.diff`.

Статус утверждений из исходного `problem.md`:

- «Пользователь: разработчик/ревьюер…» — не подтверждено diff; требует внешнего контекста.
- «Ситуация: обращение к POST /api/reviews…» — подтверждено diff (TRAINING_PR.diff:35–37).
- «При отсутствии ключа diff или неверном типе тела возникает KeyError и ответ 500» — частично: возможность KeyError подтверждается статически (TRAINING_PR.diff:35–37), HTTP-статус и поведение при «неверном типе тела» не подтверждены; требуют runtime-проверки/контекста FastAPI-конфигурации.
- «При больших диффах возможны долгие задержки…» — не подтверждено; синхронный вызов есть (TRAINING_PR.diff:19–22), но метрика задержек требует измерений.
- «Возможны небезопасные промпты» — не подтверждено diff.
- «Почему это мешает бизнесу: нестабильность… риски безопасности…» — неконкретно и частично спекулятивно; из diff следует лишь риск необработанных исключений при некорректном теле запроса.

## Принятое изменение

В `practices/practice_01/problem.md` раздел «## Проблема» обновлён:

- Роль пользователя помечена как «не указан (требует уточнения)».
- Оставлено подтверждённое: доступ `payload["diff"]` без проверки и синхронный вызов `LLM.generate`.
- Убраны недоказуемые утверждения про 500, неверный тип тела, задержки «>2 секунд», «небезопасные промпты».
- Бизнес-эффект конкретизирован как «риск необработанных исключений и неопределённого поведения API при некорректном теле».

## Что отклонено

- Утверждение о гарантированном ответе 500 при `{}`.
- Утверждение о проблеме «неверный тип тела» без схемы/валидации.
- Утверждения о задержках и SLA.
- Утверждения о «небезопасных промптах» без источника.
- Точное определение роли пользователя без подтверждения в источниках.

## Способ статической проверки

1. Открыть `practices/practice_01/TRAINING_PR.diff`.
2. Проверить `app/api.py` добавление обработчика: строки 35–37 содержат `@app.post("/api/reviews")` и `payload["diff"]` — это подтверждает отсутствие проверки ключа и возможность `KeyError`.
3. Проверить `app/review_service.py`: строки 19–22 — формирование промпта и синхронный вызов `LLM.generate`, что подтверждает сам факт синхронности, но не задержки.
4. Отсутствие в diff явной обработки исключений и валидации подтверждает, что HTTP-статус в случае ошибки не определён статически (требует запуска/конфигурации FastAPI).

Статус решения: требует решения студента (подтвердить роль пользователя и целевые метрики на следующих шагах Практики 2).
