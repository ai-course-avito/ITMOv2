# Few-shot

Артефакт Практики 1: `tests_load.md` — нагрузочные проверки для FastAPI-сервиса code review

Что хотим улучшить: добавить 4–5 сценариев вместо двух, инструмент k6, конфигурации для каждого сценария, таблицу интерпретации, инструкцию по запуску, evidence со ссылками на код

## Примеры

Хороший результат

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| **Baseline** — последовательные запросы | 10 rps в течение 60 секунд | Среднее время ответа ≤ 500 мс, 0 ошибок 5xx | Среднее и P95 время ответа, доля успешных ответов | `app/payment.py:34` — sync-блокировка на БД |

Плохой результат

| Сценарий | Нагрузка и длительность |
|---|---|
| Обычный поток | 10 запросов в секунду |

Нагрузочное тестирование пока не требуется.

## Запрос

Напиши нагрузочные проверки для FastAPI-сервиса code review. Инструмент k6, скрипты в tests/load/. Правила: SEC-1 — очистка секретов, API-1 — diff > 20k → HTTP 413, REL-1 — timeout LLM 10 сек, OUT-1 — формат ответа (summary, risks, checks), OBS-1 — лог только request_id, duration, status. 4–5 сценариев: baseline, spike, soak, ramp-up, stress. Каждый сценарий — с конфигурацией k6. Таблица интерпретации метрик. Инструкция по запуску. Evidence со ссылками на строки кода и CASE.md. Раздел «Как использовали AI» в конце.

## Что получили

- 5 сценариев с привязкой к конкретным правилам
- Конфигурации k6 с thresholds для каждого сценария
- Таблица интерпретации: Acceptable / Warning / Failure
- Раздел «Что нельзя тестировать сейчас» — обоснование, почему REL-1 и OBS-1 ещё не измеримы
- Инструкция по запуску (5 команд)
- Evidence со ссылками на `app/review_service.py:20-21`, `app/api.py:36-37`, `CASE.md: REL-1`

## Что изменили в исходном артефакте

Файл и раздел: `practices/practice_01/tests_load.md` — весь файл

Изменение: переписан с нуля. Было: 2 сценария без инструмента, без k6-конфигураций, generic-вывод «нагрузочное тестирование пока не требуется». Стало: 5 сценариев (baseline, spike, soak, ramp-up, stress), k6-конфигурации с порогами, таблица интерпретации, раздел об ограничениях, инструкция по запуску.

Как проверили: Makefile (`make test`) проверяет `test -s tests_load.md` — файл непустой. Отдельно проверили, что thresholds соответствуют REL-1 (≤ 10 секунд) и что каждый сценарий ссылается на конкретный rule из CASE.md.

Что отклонили: вариант с одним сценарий baseline + spike (не покрывал soak для утечек памяти и ramp-up для поиска точки насыщения); вариант с порогом 500 мс вместо 10 сек (невалидно для LLM-依赖ного сервиса с timeout 10 сек).
