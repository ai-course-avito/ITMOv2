## Как использовали AI

- Эксперимент: tree_of_thoughts/experiment.md
- Что проверили и исправили сами: сценарии отражают сравнение альтернатив и критерии выбора; не добавляли новую инфраструктуру.

## Схема дерева

Root → Свободный текст нагрузочных проверок
- Branch A → По типу нагрузки (RPS/latency/soak)
- Branch B → По правилам CASE.md (SEC-1, API-1, REL-1, OUT-1)
- Branch C → По метрикам problem.md (P95, 5xx, утечки)
- Branch D → По типам отказов (timeout, 5xx, деградация, зависимость)

## Оценка веток

| Ветка | Плюсы | Минусы | Покрытие |
|---|---|---|---|
| A | Проста для запуска; ясно задаёт профиль | Может пропустить правила | P95/ошибки покрыты, правила частично |
| B | Привязка к SEC-1/API-1/REL-1/OUT-1 | Требует маппинга метрик | Все правила закрываются |
| C | Ясные KPI из problem.md | Нужен контекст правил | Метрики полностью закрыты |
| D | Фокус на отказах | Может дублировать C | Таймауты/5xx/деградация покрыты |

Выбор: комбинация B+C — привяжем сценарии к правилам и метрикам одновременно.

## Финальный Gherkin

```gherkin
@API-1
Scenario: Проверка границы 413 при смешанном профиле
  Given профиль нагрузки 1 RPS, 100 запросов
  And 50 тел имеют длину diff = 20001 символов, 50 — 20000
  When отправляем POST "/api/reviews"
  Then 100% запросов > 20000 получают 413, остальные 200 получают 200

@REL-1
Scenario: Пиковая нагрузка с контролируемыми таймаутами
  Given профиль нагрузки 5 RPS в течение 10 минут
  And инжект таймаута LLM в 10% запросов (10с)
  When выполняем отправку валидных тел
  Then P95 ≤ 1.5 с и доля 5xx = 0

@SEC-1
Scenario: Редактирование секретов под нагрузкой
  Given профиль нагрузки 2 RPS в течение 5 минут
  And 30% тел содержат фейковые секреты
  When выполняется препроцессинг перед LLM
  Then утечки секретов = 0; доля корректной редакции = 100%

@OUT-1
Scenario: Позитивный путь при базовой нагрузке
  Given профиль нагрузки 2 RPS в течение 5 минут
  When отправляем валидные тела
  Then P95 ≤ 500 мс и ответ соответствует OUT-1
```
