# Tree of Thoughts

- Решение, для которого нужны альтернативы: Как реализовать очистку секретов из diff перед отправкой в LLM (правило SEC-1).
- Критерии выбора:
1. Надежность (низкий риск пропустить секрет).
2. Производительность (не замедляет API).
3. Простота поддержки (легко обновлять правила).


## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| 1) Правила на regex (in-process) | Очень быстрый; минимальные зависимости; легко встраивается в API. | Риск пропуска новых/нестандартных секретов; нужны постоянные ручные апдейты. | Надежность: Средняя, Производительность: Высокая, Поддержка: Средняя |
| 2) Гибрид: regex + готовые сканеры (Gitleaks/TruffleHog) | Высокий recall; регулярные обновления из open-source; меньше ручной поддержки. | Выше нагрузка ЦП; зависимость от внешних бинарников. | Надежность: Высокая, Производительность: Средняя, Поддержка: Высокая |
| 3) Сайдкар/шлюз-сервис (default-deny) | Централизованный аудит; можно обновлять правила без деплоя API. | DevOps-накладные; потенциальная латентность сети. | Надежность: Очень высокая, Производительность: Средняя, Поддержка: Высокая (но сложнее инфраструктура) |

## Выбор

- Выбранная альтернатива: Гибрид (regex + Gitleaks)
- Почему: Максимальный баланс надежности и поддержки за счет готовых, регулярно обновляемых правил, при приемлемой производительности.
- Как проверим: Тесты с известными утечками (токены AWS, GitHub, RSA-ключи) — Gitleaks должен находить то, что простые regex пропускают.
