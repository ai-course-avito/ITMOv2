# Tree of Thoughts

- Решение, для которого нужны альтернативы:
  как переписать `tests_load.md` (Practice 1), чтобы он стал рабочим артефактом,
  а не декларацией. Текущий черновок не содержит сценариев нагрузки, целевых
  метрик, SLO/SLA и evidence; вместо замеров ссылается на `len(diff)`.
- Критерии выбора:
  1. Соответствие API-1 (лимит 20 000 символов; проверка 413 на >20 000).
  2. Соответствие REL-1 (timeout 10 секунд; контролируемый ответ на таймаут).
  3. Воспроизводимость замеров и наличие evidence (k6 summary/Locust отчёты).
  4. Минимальная стоимость проверки на учебном проекте.
  5. Связь с остальными артефактами Практики 1 (метрики, пороги, evidence).

## Запрос

Ты — инженер по производительности. Нужно улучшить файл нагрузочных проверок
для сервиса AI-ревью PR.

Контекст:
- POST /api/reviews, вход {"diff": "..."};
- внешний LLM, timeout 10 секунд (REL-1);
- diff > 20 000 символов → HTTP 413 (API-1);
- ответ: summary, risks (до 3), checks (OUT-1);
- лог: request_id, длительность, статус (OBS-1).

Предложи три внешне описанные альтернативы построения нагрузочных проверок:
A. Минимальный набор: один сценарий на малом diff.
B. Сценарный набор: малый diff, пограничный diff, задержка LLM.
C. Полный профиль: сценарный набор + стресс и soak-тесты.

Для каждой альтернативы:
- опиши плюсы и минусы;
- оцени по критериям выбора (1–5);
- укажи, какие метрики и evidence она даёт;
- укажи, какие риски остаются непокрытыми.

В конце выбери одну альтернативу для учебного проекта, объясни выбор
и предложи, как проверить результат. Не используй скрытые рассуждения,
дай только внешние альтернативы, оценки и вывод.

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. Минимальный набор: один сценарий на малом diff | Быстро, дёшево; один сценарий легко воспроизвести на учебном стенде | Не покрывает API-1 (413 на >20 000 символов); не проверяет REL-1 (timeout 10 с); evidence из одного запуска — недостаточно для вывода о стабильности | A=2/5 (покрытие API-1), B=1/5 (REL-1), C=2/5 (воспр.), D=5/5 (стоимость), E=2/5 (связь) |
| B. Сценарный набор: малый diff, пограничный diff, задержка LLM | S2 проверяет 413 (API-1); S3 индуцирует и проверяет REL-1 (timeout, 0% 500); три воспроизводимых сценария с k6/Locust; evidence — summary/графики по каждому сценарию | Требует настройки k6-скрипта и логирования request_id/duration/status (OBS-1); сложнее, чем A; покрывает, но не глубоко | A=5/5, B=5/5, C=5/5, D=4/5, E=3/5 |
| C. Полный профиль: B + стресс и soak-тесты | Максимальное покрытие: нагрузка выше порогов, длительные soak-тесты выявляют утечки памяти и насыщение CPU | Избыточно для учебного проекта; дорого (хостинг k6/кластер); требует долгой инфраструктуры; не даёт новых insight на текущем этапе | A=3/5, B=4/5, C=4/5, D=2/5, E=2/5 |

## Выбор

- Выбранная альтернатива: B. Сценарный набор.
- Почему: B покрывает ключевые правила (API-1 через S2, REL-1 через S3), даёт
  воспроизводимые метрики и evidence, не перегружает учебный проект. Альтернатива
  A недостаточна — не проверяет ни API-1, ни REL-1. Альтернатива C избыточна —
  стресс и soak требуют инфраструктуры, которой нет на учебном этапе.
- Как проверим: прогон k6 по трём сценариям (S1/S2/S3), проверка p95 < 10 с
  (REL-1) в S2, error rate < 1%, 5xx = 0%, наличие evidence в виде k6 summary/Locust;
  для S3 — проверка 0% 500 и контролируемого таймаута.
