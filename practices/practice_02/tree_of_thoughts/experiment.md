# Tree of Thoughts

- Решение, для которого нужны альтернативы: чем измерять доверие ревьюера к ответам сервиса, если по `OBS-1` в лог пишутся только `request_id`, длительность и статус, а хранилища отметок «согласен / не согласен» нет и ни один из трёх инкрементов `project_management.md` его не создаёт (`problem.md:19`).
- Критерии выбора: 1) стоимость реализации в инкрементах `project_management.md`; 2) соблюдение `OBS-1`; 3) измеряет реальное согласие живого ревьюера, а не только прокси на учебном наборе; 4) можно ли получить первые данные до развёртывания сервиса в реальной работе.

## Запрос

Работай только с файлами practices/practice_01/problem.md, practices/practice_01/project_management.md, practices/practice_01/adr.md и practices/practice_01/CASE.md. Не выполняй никаких git-команд: ни checkout, ни restore, ни reset, ни stash.

Решение, для которого нужны альтернативы: чем измерять доверие ревьюера к ответам сервиса, если по OBS-1 в лог пишутся только request_id, длительность и статус, а хранилища отметок «согласен / не согласен» в системе нет и ни один инкремент project_management.md его не создаёт.

Предложи ровно три альтернативы. Каждая должна быть реализуемой в рамках трёх инкрементов из project_management.md и не нарушать OBS-1, SCOPE-1 и QA-1.

Оцени каждую по четырём критериям:
- стоимость реализации в терминах инкрементов из project_management.md;
- не нарушает ли она OBS-1 (в лог сервиса пишутся только request_id, длительность, статус);
- измеряет ли она согласие живого ревьюера или только прокси на учебном наборе;
- можно ли получить первые данные до развёртывания сервиса в реальной работе.

Формат ответа:
1) таблица с колонками «Альтернатива», «Плюсы», «Минусы», «Оценка по критериям» — ровно три строки, обозначь их A, B, C;
2) выбор: какая альтернатива выбрана, почему, и как проверить, что выбор оказался верным;
3) отдельной строкой — почему отклонены две другие.

Не выбирай альтернативу, которая требует логировать содержимое ответа модели: это нарушает OBS-1. Не вводи фактов за пределами четырёх указанных файлов. Ничего не записывай в practice_01. Сохрани ответ в practices/practice_02/tree_of_thoughts/_raw_output.md.

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. Прокси через размеченный учебный набор (доля рисков, совпавших с разметкой 30 diff) | Уже заложена в проверку Инкремента 2 и в процедуру ADR (`adr.md:41`); не требует нового хранилища; данные доступны с первого прогона. | Не согласие живого ревьюера, а совпадение с разметкой — сам `problem.md:19` отмечает: «Прокси не равна согласию живого ревьюера». | Стоимость минимальная; `OBS-1` не нарушает; измеряет только прокси; данные до развёртывания — да. |
| B. Корреляция лога Инкремента 3 (`request_id`, длительность, статус) с исходом PR в GitHub | Использует уже существующие данные — лог `project_management.md:9` и события GitHub (`problem.md:17`); не требует новых полей ответа сервиса или действий в GitHub. | Даёт лишь косвенный сигнал (быстрое закрытие PR не обязательно значит согласие с риском); данные появляются только после реальной эксплуатации. | Стоимость умеренная; `OBS-1`/`SCOPE-1` не нарушает; измеряет только косвенный прокси по исходу PR; данные до развёртывания — нет. |
| C. Внешний журнал отметок ревьюера вне сервиса, сверяемый по `request_id` из лога Инкремента 3 | Прямо измеряет согласие живого ревьюера с конкретным ответом; не меняет `OUT-1`/лог/код сервиса; ключ сверки (`request_id`) уже логируется по Инкременту 3 (`project_management.md:9`). | Требует дисциплины ревьюера при заполнении; полноценные данные на реальных PR — только после развёртывания, до него доступен лишь ограниченный пилотный сигнал. | Стоимость низкая, новых инкрементов не требует; `OBS-1`/`SCOPE-1`/`QA-1` не нарушает; измеряет реальное согласие живого ревьюера; данные до развёртывания — частично, через пилот на 30 учебных diff. |

## Выбор

- Выбранная альтернатива: C — внешний журнал отметок ревьюера вне сервиса, сверяемый по `request_id` из лога Инкремента 3.
- Почему: единственная из трёх измеряет именно требуемое по `problem.md:19,29` — реальное согласие живого ревьюера, а не прокси-совпадение с разметкой (A) и не косвенный сигнал по исходу PR (B); опирается только на уже логируемый по Инкременту 3 `request_id` (`project_management.md:9`), остальное — процесс вне сервиса, поэтому лог по `OBS-1` не меняется (`CASE.md:70`); запись ведёт человек, а не сервис, поэтому `SCOPE-1` соблюдён; критерий включения риска по `QA-1` альтернатива не затрагивает.
- Как проверим: провести пилот на 30 учебных diff из процедуры `adr.md:41` — привлечь реальных ревьюеров прогнать те же diff через сервис и независимо отметить «согласен / не согласен» по каждому риску во внешнем журнале по `request_id`; если доля согласия живых ревьюеров заметно расходится с прокси-показателем на тех же 30 diff, это подтвердит, что прокси недостаточно и журнал C даёт содержательно другой сигнал; если доли близки — прокси можно временно использовать как приближение, продолжая вести журнал C уже на реальных PR после развёртывания.

## Что изменили в исходном артефакте

- Файл и раздел: `problem.md`, раздел «Метрики», метрика «Доля рисков из ответа сервиса, с которыми ревьюер согласился», ячейка «Источник данных».
- Изменение: указан выбранный способ сбора данных — внешний журнал отметок ревьюера, ведущийся вне сервиса и сверяемый по `request_id` из лога (`OBS-1` не нарушается, так как лог сервиса не меняется).
- Что отклонили: порог расхождения «10–15 процентных пунктов» — число не выведено ни из одного файла; альтернативу A как основной способ измерения, так как совпадение с разметкой не равно согласию живого ревьюера; альтернативу B, дающую косвенный сигнал и не позволяющую получить данные до развёртывания.
