- Решение, для которого нужны альтернативы:
Включить правило API-1 (лимит 20,000) в архитектуру: где реализовать проверку длины.
- Критерии выбора:
  - Простота изменения и минимальность
  - Проверяемость и наблюдаемость
  - Влияние на DX и совместимость

## Запрос


Предложи три альтернативы, где реализовать проверку длины diff (>20,000 -> 413):
- A: На уровне FastAPI endpoint перед вызовом сервиса
- B: В ReviewService.review
- C: В middleware/ASGI слой
Оцени по критериям и предложи выбор с проверкой.

## Внешне описанные альтернативы
## Варианты решения

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A | Ясный контракт API; легко тестировать интеграцией; возвращает 413 без запуска LLM | Дублирование при других входах | Высокая простота, высокая проверяемость, хорошая DX |
| B | Повторное использование в других входах; инкапсуляция | API не документирует 413 напрямую; сложнее тестировать через OpenAPI | Средняя простота, средняя проверяемость |
| C | Унифицированная политика; переиспользование | Сложность, меньше прозрачности; труднее дебажить | Низкая простота, низкая проверяемость |

## Выбор

- Выбранная альтернатива:
  A: проверка на уровне FastAPI endpoint.
- Почему:
  Минимальные изменения, явный контракт и простые интеграционные проверки; соответствует tests_integration/tests_e2e.
- Как проверим:
  Интеграционный тест POST с 20001 символом -> 413; OpenAPI документирует 413.
