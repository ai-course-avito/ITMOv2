# Tree of Thoughts

- Решение, для которого нужны альтернативы: структура плана поставки и порядок инкрементов для исправления слабого артефакта `practice_02/project_management.md`
- Критерии выбора: проверяемость (привязка DoD к tests_* и метрикам problem.md), соответствие CASE.md (OUT-1, API-1, SEC-1, REL-1, QA-1), последовательность зависимостей, минимальность допущений, отсутствие плейсхолдеров

## Запрос

```text
Ты — технический менеджер проекта (delivery lead) учебного сервиса
"AI-помощник ревьюера PR". Пишешь планы поставки в инженерном стиле,
опираешься только на предоставленные источники, не выдумываешь факты.

Источники - артефакты Практики 1:
- CASE.md: правила SEC-1 (redaction секретов), API-1 (лимит 20 000 символов,
  HTTP 413), REL-1 (timeout 10s), OUT-1 (summary/risks<=3/checks),
  SCOPE-1, QA-1;
- problem.md: метрики - доля OUT-1 >=95%, обработка таймаута >=99%,
  отклонение длинных diff = 100%;
- tests_unit.md, tests_integration.md, tests_load.md, tests_e2e.md —
  конкретные проверки;
- prompts.md (P1-02): подтверждённые риски со строками -
  app/api.py:37 (KeyError), app/review_service.py:20 (утечка секретов),
  app/review_service.py:21 (нет таймаута), app/api.py:35-37 (нет лимита),
  app/review_service.py:22 (не OUT-1).
Шаблон — blank_project_management.md. Слабый артефакт — practice_02/project_management.md.

Task: Выполни три шага мышления, затем выдай итоговый артефакт.
1) Сгенерируй минимум 3 альтернативных структуры плана (порядок инкрементов)
   из правил CASE.md: примеры — OUT-1→API-1→SEC-1→REL-1→Документация;
   SEC-1 первым; параллель OUT-1 и API-1. Для каждой укажи плюсы/минусы и
   как каждая проверяется tests_* и метриками problem.md.
2) Оцени альтернативы по критериям: проверяемость, соответствие CASE.md,
   корректность зависимостей, минимальность допущений. Выбери лучшую и
   обоснуй выбор кратко.
3) Сгенерируй итоговый Markdown «План поставки»:
   - Раздел «Инкременты и ответственность» — таблица: наблюдаемый результат,
     роли человека/AI, DoD со ссылками на tests_* и метрики problem.md,
     зависимости. Без колонки владельцев. Без колонки «Риски и меры» (для ToT).

В финальном ответе выведи только тело Markdown без преамбул и
пояснений. PROMPT_ID возьми из входа.
```

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. OUT-1 → API-1 → SEC-1 → REL-1 → Документация | Линейная зависимость, каждое правило проверяется и замыкается на метриках; минимальные допущения | Позднее обнаружение рисков SEC-1/REL-1, если OUT-1 займёт дольше | Проверяемость: высокая; Соответствие CASE.md: полное; Зависимости: последовательные; Простота: высокая |
| B. SEC-1 сначала (SEC-1 → OUT-1 → API-1 → REL-1 → Документация) | Раннее снятие риска утечки секретов | Возможны повторные правки формата OUT-1 под влиянием маскировки; сложнее обосновать DoD без OUT-1 | Проверяемость: средняя; Соответствие CASE.md: полное; Зависимости: риск ревёрсов; Простота: средняя |
| C. Параллель OUT-1 и API-1 (OUT-1 || API-1 → SEC-1 → REL-1 → Документация) | Быстрее старт, часть проверок параллелится | Требует синхронизации контрактов и валидации; выше риск несоответствий | Проверяемость: средняя; Соответствие CASE.md: полное; Зависимости: сложнее; Простота: средняя |

## Выбор

- Выбранная альтернатива: A. OUT-1 → API-1 → SEC-1 → REL-1 → Документация
- Почему: обеспечивает жёсткую проверяемость на каждом шаге с привязкой к tests_* и метрикам problem.md; минимизирует непредусмотренные зависимости; соответствует порядку фиксации контракта до реализации защиты и отказоустойчивости
- Как проверим: каждая строка «Проверка» содержит DoD с ссылками на конкретные tests_* и метрики; ссылки валидируются на существование; mermaid-граф корректно строится; отсутствие плейсхолдеров в финальном файле

## Что изменили в исходном артефакте

- Файл и раздел: `tree_of_thoughts/project_management.md` — все три раздела
- Изменение: выбран линейный порядок инкрементов (OUT-1 → API-1 → SEC-1 → REL-1 → Документация/E2E); добавлены конкретные DoD, связанные с [CASE.md](../../practice_01/CASE.md), tests_* и метриками из [problem.md](../../practice_01/problem.md); диаграмма Ганта без плейсхолдеров, с последовательными задачами
- Что отклонили: параллельный запуск OUT-1 и API-1 (альт. C) из-за повышенного риска несоответствий; постановку SEC-1 первым (альт. B) из-за зависимости от формата OUT-1 и усложнения DoD
