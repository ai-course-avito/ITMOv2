# Tree of Thoughts: Альтернативы подходов к E2E

Альтернатива 1. Контракт + границы + логи (LLM стаб)
- Идея: тесты проверяют контракт ответа OUT-1, граничные условия API-1, обработку таймаута REL-1 и отсутствие утечки diff в логах OBS-1. Внешний LLM заменён управляемым стабом.
- Сценарии: успешный ответ OUT-1; кэп `risks` ≤3; граница 20 000 — OK; 20 001 — 413; таймаут LLM ≤10с — контролируемый ответ; логи не содержат diff.
- Оценка:
  - Полнота: высоко. Все правила CASE из задания (API-1, OUT-1, OBS-1, REL-1) покрыты напрямую.
  - Воспроизводимость: высоко. Стаб LLM делает ответы детерминированными; проверка логов опирается на форматы без чтения diff.
  - Реалистичность: высоко. Нет GitHub/БД/auth, только HTTP и логи.

Альтернатира 2. Генеративные/проперти-тесты поверх API
- Идея: property-based тесты генерируют диффы разной длины, случайные варианты `risks` и `checks`, проверяют инварианты OUT-1 и границу API-1; REL-1 моделируется вероятностной задержкой стаба.
- Сценарии: классы эквивалентности размеров (≤20000 и >20000); генерация массивов `risks` длиной 0..10 и проверка уcечения до 3; стохастический таймаут.
- Оценка:
  - Полнота: средне/высоко. Покрывает правила, но требует больше кода для генераторов.
  - Воспроизводимость: средне. Понадобится фиксированный сид и контроль случайности.
  - Реалистичность: средне. Для учебной практики может быть избыточно.

Альтернатира 3. Минимальный чёрный ящик (smoke)
- Идея: только «счастливый путь» и одна негативная проверка размера; без логов и таймаутов.
- Сценарии: валидный OUT-1; 20 001 -> 413.
- Оценка:
  - Полнота: низко. OBS-1 и REL-1 не покрыты.
  - Воспроизводимость: высоко. Простые сценарии.
  - Реалистичность: высоко, но ценность ограничена.

Выбор
- Лучший подход: Альтернатива 1. Она полно закрывает правила CASE из задания, остаётся детерминированной за счёт стаба LLM, не требует внешних интеграций и остаётся в реалистичном scope.

## E2E-проверки (выбранный подход)

Подход: контрактные проверки ответа и границ с управляемым стабом LLM, проверкой таймаута и логов (без утечки diff).

| Сценарий пользователя | Предусловия | Действие | Наблюдаемый результат | Evidence |
|---|---|---|---|---|
| 1) Успешный обзор PR (OUT-1) | Сервис запущен; доступен POST `/api/reviews`; LLM замокан на детерминированный ответ формата OUT-1 | POST `{"diff": "diff --git a/x b/x\n+line"}` | 200 OK; тело содержит `summary` (str), `risks` (массив длиной ≤3, элементы с `file`, `line`, `evidence`, `risk`), `checks` (массив строк, непустой) | HTTP 200; проверяемые поля: наличие `summary`, `risks`≤3, `checks`≠[]; логи: только метаданные (request_id, длительность, статус), без содержимого diff (OBS-1) |
| 2) Кэп на риски (OUT-1) | Как выше; стаб LLM возвращает 5 рисков | POST валидного небольшого diff | 200 OK; в ответе `risks` усекается до 3 элементов | HTTP 200; проверяемое поле: длина `risks`=3; логи без содержимого diff |
| 3) Граница размера 20 000 (API-1) | Как выше | Отправить diff ровно 20 000 символов | 200 OK; ответ в формате OUT-1 | HTTP 200; проверяемые поля: валидный OUT-1; логи без содержимого diff |
| 4) Превышение размера 20 001 (API-1) | Как выше | Отправить diff длиной 20 001 символ | 413 Payload Too Large | HTTP 413; проверяемое поле: код и сообщение об ограничении; логи без содержимого diff |
| 5) Таймаут LLM 10с (REL-1) | Стаб LLM задерживается >10с | POST валидного небольшого diff | Контролируемый ответ без падения (статус 503/504 или 200 с пометкой — уточнить в реализации) | HTTP 503/504 или 200; проверяемые поля: признак таймаута; логи: длительность запроса ≤10с, без содержимого diff |
| 6) Логи не содержат diff (OBS-1) | Логгер доступен тестам | POST diff с уникальным маркером `DIFF_MARKER_123` | 200 OK | HTTP 200; проверяемые поля: валидный OUT-1; логи не содержат `DIFF_MARKER_123` или фрагментов diff |
