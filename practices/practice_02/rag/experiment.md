# RAG

- Вопрос к источникам: Какие продуктовые правила, ограничения размера запросов, таймауты и требования к ответу из Практики 1 должны лечь в основу сценариев нагрузочного тестирования AI-помощника?

## Разрешённые источники

| Файл или документ | Зачем нужен | Какой фрагмент используем |
|---|---|---|
| `practices/practice_01/context.md` | Правила сервиса, лимиты API, таймауты и контракт ответа | Правила SEC-1 (секреты), API-1 (длина diff < 20k символов, HTTP 413), REL-1 (таймаут LLM 10с), OUT-1 (формат summary/risks/checks), OBS-1 (логирование без утечек) |
| `practices/practice_01/tests_load.md` | Исходная база и пороги нагрузки | 10 rps, diff 5k, p95 < 1.0s, ошибок < 1%, переход к стресс-тестам при > 50 rps |
| `practices/practice_01/CASE.md` | Архитектура и сценарий использования сервиса | Раздел «Как устроен текущий процесс»: Web API -> валидация/маскирование -> внешний LLM -> генерация отчета |

## Запрос

Используя строго факты и правила из разрешённых источников (`context.md`, `tests_load.md`, `CASE.md`):
1. Сформируй план нагрузочного тестирования, привязав каждый сценарий к подтверждённым правилам (API-1, REL-1, SEC-1, OBS-1, OUT-1).
2. Запрещено придумывать сущности, которых нет в источниках (очереди сообщений, распределенные транзакции).
3. Сохрани результат в `practices/practice_02/rag/test_load_new.md` с описанием файла, полной таблицей сценариев, ссылками на правила и критериями приёмки.

## Ответ со ссылками на источники

Сформирован артефакт `practices/practice_02/rag/test_load_new.md`, в котором:
- Вводная часть ссылается на архитектуру из `CASE.md` и правила из `context.md`.
- Сценарии валидируют подтвержденные правила:
  - Baseline и Sustained опираются на параметры из `tests_load.md` (10 и 50 rps, diff 5k, p95 < 1.0s).
  - Сценарий Boundary Payload проверяет ограничение API-1 (diff > 20k символов -> HTTP 413).
  - Сценарий LLM Degradation проверяет правило REL-1 (таймаут 10s и контролируемый ответ при отказе внешнего LLM).
  - Сценарии Masking Overhead и Logging Compliance проверяют SEC-1 и OBS-1 под нагрузкой.
  - Сценарий Response Conformance проверяет сохранение структуры OUT-1 (summary, risks < 3, checks).

## Что изменили в исходном артефакте

- Файл и раздел: `practices/practice_01/tests_load.md` -> переработан в `practices/practice_02/rag/test_load_new.md` (обоснованные сценарии на основе контекста системы, Evidence, критерии приемки).
- Изменение: абстрактный список заменен на сценарии, напрямую верифицирующие продуктовые правила (API-1, REL-1, SEC-1, OBS-1, OUT-1), убрана заглушка, зафиксированы источники требований.
- Как проверили ссылки: каждый пункт таблицы проверен на соответствие цитатам из `practices/practice_01/context.md` и `tests_load.md`.
- Что отклонили как неподтверждённое: отклонили гипотезы об использовании Apache Kafka, очередей фоновых воркеров и сложных распределенных БД, так как в `context.md` зафиксирован синхронный вызов Web API к внешнему LLM.
