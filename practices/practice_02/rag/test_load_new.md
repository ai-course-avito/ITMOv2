# План нагрузочного тестирования AI-помощника ревьюера PR

## Источники требований

- **CASE.md** — архитектура: FastAPI-сервис `/api/reviews` принимает POST с `diff`, вызывает внешний LLM, возвращает `{"summary", "risks", "checks"}`.
- **context.md** — продуктовые правила SEC-1, API-1, REL-1, OUT-1, OBS-1 и формат входа/выхода.
- **tests_load.md** — исходные параметры нагрузки: 10 rps (обычный поток), 50 rps (пик), diff 5k–10k символов, порог p95 < 1.0s, ошибок < 1%.

## Условие запуска

Текущий код не реализует timeout (REL-1) и не логирует длительность (OBS-1). Нагрузочное тестирование проводится после реализации инкремента 2 (timeout + формат ответа OUT-1) и инкремента 3 (логирование request_id, duration, status).

## Порядок выполнения

1. **Сценарий 1 (Baseline)** — устанавливает штатную производительность.
2. **Сценарий 7 (Response Conformance)** — параллельно с Baseline проверяет формат ответов.
3. **Сценарий 5 (Masking Overhead)** — проверяет, что SEC-1 не снижает производительность.
4. **Сценарий 6 (Logging Compliance)** — проверяет OBS-1 при штатной нагрузке.
5. **Сценарий 2 (Sustained)** — пиковая нагрузка после подтверждения baseline.
6. **Сценарий 3 (Boundary Payload)** — edge-case для API-1.
7. **Сценарий 4 (LLM Degradation)** — деградация внешней зависимости.

## Отклонённые гипотезы

Из источников **не подтверждены** и **не включены** в план:

- Использование Apache Kafka, очередей сообщений или фоновых воркеров (в `context.md` зафиксирован синхронный вызов Web API → внешний LLM).
- Распределённые транзакции или базы данных (не упоминаются ни в одном из трёх источников).
- Интеграция с GitHub API (в `context.md` отмечена как неизвестная/не реализованная).
