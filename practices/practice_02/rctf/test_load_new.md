# План нагрузочного тестирования `/api/reviews`

## Назначение документа

Этот файл — регламент нагрузочного тестирования FastAPI-сервиса AI-помощника ревьюера PR. Он заменяет краткую версию из `practices/practice_01/tests_load.md` и отвечает на четыре вопроса:

1. **Что такое «сервис выдержал нагрузку»?** — измеримые пороги в матрице сценариев ниже.
2. **Что и как гонять?** — 15 сценариев от smoke до soak и деградации.
3. **Как доказать результат?** — колонка Evidence: артефакты k6/Locust, дашборды Grafana, трейсы APM.
4. **Когда нагрузочное тестирование можно запускать?** — раздел «Готовность к запуску».

Документ предназначен для инженеров, которые гоняют нагрузку, и для ревьюера, который принимает решение Pass/Fail по чек-листу в конце.

## Регламент работы с документом

1. **Порядок прогона.** Начинать всегда с numbered 1 (smoke) и 2 (baseline). Только после зелёного baseline гнать capacity → peak → spike → stress. Soak запускается после подтверждённого capacity. Сценарии 8–15 (read/write, листинги, деградация) выполняются в любом порядке после baseline.
2. **Фиксация условий.** Каждый прогон записывает: версию сервиса (`git rev-parse HEAD`), окружение (адреса хостов), версию тестового скрипта и дату/время начала. Без этой строки прогон не считается Evidence.
3. **Хранение артефактов.** Результаты сохраняются как `k6/results/<scenario>_<YYYY-MM-DD>.json`, снимки дашбордов как `grafana/<scenario>-<YYYY-MM-DD>.png`. Трейсы выгружаются из APM по `request_id` (OBS-1).
4. **Повторяемость.** LLM-зависимые сценарии (11, 12) гоняются на мок-LLM с детерминированной задержкой; отдельно допускается прогон тех же сценариев на реальном провайдере для валидации мока.
5. **Регрессия.** Любое изменение кода требует повторного прогона baseline и affected-сценариев. Ухудшение p95 более чем на 10% от предыдущего прогона того же сценария → Fail.
6. **Ответственный.** Обновлять матрицу и пороги при изменении правил CASE.md (REL-1, API-1, OUT-1, OBS-1, SEC-1, SCOPE-1, QA-1).

## SLO и допустимые пороги

Пороги применяются ко всем сценариям, если в матрице не указано иное.

| Метрика | SLO/порог | Источник |
|---|---|---|
| Латенция p95 | ≤ 8 секунд | Выведено из REL-1 (timeout 10 с) с запасом |
| Латенция p99 | ≤ 10 секунд | REL-1 — внешний LLM-вызов имеет timeout 10 секунд |
| Ошибки 5xx | 0% за прогон | REL-1 — ошибка LLM превращается в контролируемый ответ |
| Ошибки 4xx | только ожидаемые: 100% HTTP 413 для diff > 20 000 символов | API-1 |
| Пропускная способность | ≥ целевого rps сценария (столбец «Нагрузка») | — |
| CPU | ≤ 70% в пике, без троттлинга | — |
| RAM | рост ≤ 20% от стартовой и стабилизация к концу soak | — |
| Таймауты по REL-1 | 0% при p95/p99 в пределах SLO | REL-1 |
| Логирование | каждый запрос в логе: `request_id`, `duration`, `status` (OBS-1) | OBS-1 |

## Критерии приёмки

### Pass — сценарий принят

- метрики в пределах «Допустимый предел» матрицы; thresholds в k6 зелёные;
- 5xx = 0; 4xx — только ожидаемый 413 из API-1;
- для soak: RAM стабилизировалась к концу прогона;
- для деградации (11–12): 100% контролируемых ответов в формате OUT-1, лог с `request_id`/`duration`/`status`;
- Evidence сохранены: JSON k6/Locust + снимок Grafana + трейс APM для каждого прогона.

### Fail — сценарий отклонён

- любой выход за p95/p99 или рост ошибок 5xx > 0;
- CPU длительно выше 70% или RAM не стабилизируется;
- OOM, падение процесса или срыв соединений;
- нарушение OBS-1: отсутствие `request_id`/`duration`/`status` в логе;
- несохранённые артефакты Evidence;
- регрессия: p95 хуже предыдущего прогона более чем на 10%.

## Готовность к запуску

Намеренная особенность, а не заглушка: текущий код не реализует timeout по REL-1 (`app/review_service.py:20-21`) и не логирует `duration`/`status` по OBS-1 (`app/api.py:36-37`). До реализации инкремента 2 (timeout + контролируемый ответ) и инкремента 3 (лог `request_id`, `duration`, `status`) результаты сценариев 4–15 нельзя интерпретировать — метрик времени ответа просто нет.

Порядок работы:

1. До инкрементов: разрешены сценарии 1–2 и 14 (smoke, baseline, отказ сверхлимитного diff) на мок-LLM — они фиксируют стартовые метрики и проверяют стенд.
2. После инкремента 2 (timeout): сценарии 11–12 (деградация) дают контроль таймаутов.
3. После инкремента 3 (логирование): полная матрица 1–15 по регламенту выше.

## Как использовали AI

- Техника: R.C.T.F. (`practices/practice_02/rctf/experiment.md`).
- Полный запрос и отклонения: строка R.C.T.F. в [`practices/practice_02/prompts.md`](../prompts.md).
- Что проверили и исправили сами: пороги согласованы с правилами CASE.md (п99 ≤ 10 с = REL-1, 100% 413 = API-1, формат ответа = OUT-1, лог = OBS-1); у каждого сценария указаны измеримые SLA и конкретный источник Evidence; заглушек и многоточий в матрице нет.
