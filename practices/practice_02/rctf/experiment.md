# R.C.T.F.

- **Role:** архитектор безопасности и надёжности AI-сервиса ревью PR (FastAPI → внешний LLM)
- **Context:** сервис `../practice_01/adr.md` из Практики 1 со правилами SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1; риск утечки токенов во внешний LLM, падения HTTP 500 при сбое LLM, отсутствия ограничения повторов (rate limit).
- **Task:** сформулировать нефункциональные требования (NFR) к сервису: отказоустойчивость, безопасность, производительность, доступность и наблюдаемость — с проверяемыми порогами и способом проверки, и внести их в ADR.
- **Format:** таблица «Категория | Требование | Порог | Как проверяем»; плюс вложение этой таблицы в `adr.md` без абстрактных метрик.

## Полный запрос

```text
Ты — архитектор безопасности и надёжности AI-сервиса ревью PR. Сценарий:
FastAPI-эндпоинт POST /api/reviews вызывает внешний LLM через ReviewService.
В коде правил: SEC-1 (фильтр секретов), API-1 (длина >20000 → 413),
REL-1 (timeout 10 с, контролируемый ответ), OUT-1 (структура summary+risks+checks),
SCOPE-1 (только советует), QA-1 (риск только с evidence), OBS-1 (лог: request_id,
длительность, статус).
Задача: сформулируй NFR по категориям отказоустойчивость, безопасность,
производительность, доступность, наблюдаемость. Каждое требование обязано иметь
ПОРОГ (число или конкретный критерий) и СПОСОБ ПРОВЕРКИ. Формат ответа:
таблица | Категория | Требование | Порог | Как проверяем |. Без метрик без порога.
```

## Что получили

Таблица NFR из пяти категорий (итог в `../practice_01/adr.md`, раздел «Нефункциональные требования (NFR)»): падение LLM не даёт HTTP 500 (fallback, 0% 500-кодов), 0% утечек секретов и пустые логов OBS-1, p95 ≤ 10 с при timeout 10 с, `/health` = 200 при падении LLM и rate limit → 429, условие перехода на очередь >10 000 ревью/день. Формат «порог + как проверим» обеспечил проверяемость каждого пункта.

## Что изменили в исходном артефакте

- Файл и раздел: `../practice_01/adr.md` — новая секция «Нефункциональные требования (NFR)»
- Изменение: добавлены NFR с порогами и способом проверки, вытекающие из роли архитектора безопасности и правил Context Pack
- Как проверили: для каждого NFR-пункта существует порог и ссылка на тест (`tests_unit.md`, `tests_integration.md`, `tests_load.md`); секция присутствует в `adr.md`
- Что отклонили: формулировки без измерения — «высокая надёжность», «быстрая скорость», «доступность на уровне 99,9%» без источника порога
