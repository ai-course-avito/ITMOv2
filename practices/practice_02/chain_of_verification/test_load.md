# Нагрузочные проверки

Порог включения нагрузки: включаем нагрузочное тестирование при реальном трафике > 10 запросов в минуту или при регулярных REL-1 таймаутах в продакшене.

## SLO/SLA по сценариям

| Сценарий | SLO (цель) | SLA (обяз.) |
|---|---|---|
| S1 — малый diff (<1 000 символов) | p95 < 500 мс; error rate < 1% | TBD (уточнить по данным prod) |
| S2 — пограничный diff (~20 000 символов) | p95 < 10 с (REL-1); timeouts < 1% | TBD |
| S3 — задержка LLM | 0% 500; таймауты обрабатываются контролируемо | TBD |

Примечание: p99, доля 5xx и иные пороги не установлены до получения замеров. Не выдумываем значения — фиксируем как TBD, см. риски/ TODO.

## Сценарии нагрузки

Каждый сценарий описан инструментом, профилем нагрузки (warmup → ramp → steady), целевыми метриками, критериями pass/fail и evidence. Evidence — только результаты замеров (k6 summary, Locust отчёты/графики), без ссылок на строки diff.

### S1 — Малый diff (<1 000 символов)
- Инструмент: k6
- Профиль: warmup 30 с @ 5 RPS → ramp 2 мин до 10 RPS → steady 5 мин @ 10 RPS
- Метрики: p95, p99 (TBD), error rate, 5xx (TBD), timeouts (ожидаются 0)
- Критерии pass/fail:
  - Pass: p95 < 500 мс; error rate < 1%; отсутствие системных 500 (если есть — расследуем)
  - Fail: нарушение порогов или нестабильность на steady-фазе
- Evidence: приложить k6 summary (stdout/JSON) и графики (если есть). Пример: k6 summary с p95, p99, http_req_failed.

Пример запуска: k6 run -e DIFF_SIZE=small ./load/k6_review.js

### S2 — Пограничный diff (~20 000 символов)
- Инструмент: k6
- Профиль: warmup 1 мин @ 2 RPS → ramp 2 мин до 5 RPS → steady 5 мин @ 5 RPS
- Метрики: p95 (< 10 с, REL-1), p99 (TBD), error rate (TBD), 5xx (TBD), timeouts < 1%
- Критерии pass/fail:
  - Pass: p95 < 10 с; timeouts < 1%; отсутствие неожиданных 500
  - Fail: превышение p95 или частые таймауты/5xx
- Evidence: k6 summary/графики с p95 и долей таймаутов; сырой журнал метрик.

Пример запуска: k6 run -e DIFF_SIZE=max ./load/k6_review.js

### S3 — Задержка LLM (индуцированная)
- Инструмент: Locust
- Профиль: warmup 30 с @ 1 RPS → ramp 2 мин до 2 RPS → steady 5 мин @ 2 RPS
- Инъекция задержек: использовать mock/флаг для внешнего LLM, чтобы симулировать ответы > 10 с (REL-1)
- Метрики: p95/p99 (TBD), error rate (TBD), 5xx = 0%, timeouts — фиксируем и проверяем контролируемую обработку (HTTP 200/контролируемый ответ согласно REL-1)
- Критерии pass/fail:
  - Pass: 0% 500; таймауты приводят к контролируемому ответу; отсутствуют деградации на steady
  - Fail: любые 500 или неконтролируемые ошибки/«залипание» запросов
- Evidence: Locust отчёт (stats CSV/скриншоты веб UI) + лог REST статусов (200/timeout-handled)

Пример запуска: locust -f ./load/locust_review.py --host http://localhost:8080
