## Предложение: рабочая версия tests_load.md

1. Для чего
- Проверить выполнение правил: API-1 (413 на diff > 20 000), REL-1 (timeout 10s → контролируемый ответ), OUT-1 (структура ответа), OBS-1 (лог только request_id, duration, status).
- Зафиксировать воспроизводимые замеры под тремя сценариями с evidence.

2. Область и входы
- Endpoint: `POST /api/reviews`
- Вход: JSON `{"diff": "..."}`
- Малый diff: использовать учебный `TRAINING_PR.diff` (фрагмент ≤ 20 000)
- Пограничный diff: синтетический diff длиной ровно 20 000 (валидный) и 20 001 (для проверки 413)

3. Метрики и проверяемые условия
- p95 и p99 времени ответа HTTP (фиксируем значения; пороги не задаём, кроме п. ниже)
- Доля запросов с timeout; условие REL-1: для сценария S2 p95 < 10s
- Доля ответов, соответствующих OUT-1 (summary, risks≤3 с file/line/evidence/risk, checks)
- Количество ответов 5xx (фиксируем; целевых порогов в источниках нет)
- Логи соответствуют OBS-1: только request_id, duration, status; содержимое diff и ответа LLM отсутствует

4. Сценарии
- S1 — Валидный малый diff (на основе TRAINING_PR.diff)
  Цель: проверить долю OUT-1 и базовую латентность на валидных данных.
  Evidence: k6 summary JSON; выборка ответов OUT-1; выдержки логов (3 поля).

- S2 — Пограничный diff ~20 000
  Цель: проверить, что валидный 20 000 проходит; p95 < 10s (REL-1); отдельно 20 001 → HTTP 413 (API-1) до вызова LLM.
  Evidence: k6 summary JSON; отчёт по попыткам с 20 001 (413); выдержки логов (3 поля).

- S3 — Задержка LLM (>10s)
  Цель: при задержке LLM > 10s сервис возвращает контролируемый ответ (без 500).
  Evidence: k6 summary JSON с долей timeout; пример контролируемого ответа; выдержки логов (3 поля).

5. k6: команды для локального прогона
- Общие переменные окружения: `BASE_URL`, `ENDPOINT=/api/reviews`
- Артефакты: `artifacts/k6/<S#>.json`

S1 (малый diff, TRAINING_PR.diff)
```bash
k6 run --summary-export artifacts/k6/S1.json \
  -e BASE_URL="http://localhost:8000" -e ENDPOINT="/api/reviews" \
  -e SCENARIO="S1" -e DIFF_SOURCE="TRAINING_PR.diff" \
  scripts/k6/tests_load.js
```

S2 (пограничный diff: 20 000 и проверка 20 001 → 413)
```bash
# Валидный 20 000
k6 run --summary-export artifacts/k6/S2_valid_20000.json \
  -e BASE_URL="http://localhost:8000" -e ENDPOINT="/api/reviews" \
  -e SCENARIO="S2_VALID" -e DIFF_SIZE="20000" \
  scripts/k6/tests_load.js

# Невалидный 20 001 (ожидаем 413)
k6 run --summary-export artifacts/k6/S2_invalid_20001.json \
  -e BASE_URL="http://localhost:8000" -e ENDPOINT="/api/reviews" \
  -e SCENARIO="S2_413" -e DIFF_SIZE="20001" \
  scripts/k6/tests_load.js
```

S3 (задержка LLM > 10s)
```bash
# Требуется стенд/переключатель, индуцирующий задержку LLM >10s
k6 run --summary-export artifacts/k6/S3_timeout.json \
  -e BASE_URL="http://localhost:8000" -e ENDPOINT="/api/reviews" \
  -e SCENARIO="S3_TIMEOUT" -e LLM_DELAY_SECONDS="12" \
  scripts/k6/tests_load.js
```

6. Evidence (что прикладываем к репорту)
- S1/S2/S3: k6 summary (*.json) с p95/p99, долей ошибок/таймаутов
- OUT-1: выборка 10 ответов с валидацией схемы (summary, risks≤3, checks)
- API-1: журнал S2_413 с HTTP 413 для 20 001
- OBS-1: выдержки логов с полями request_id, duration, status; отсутствие diff/LLM-ответа
