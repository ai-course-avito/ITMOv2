# План нагрузочного тестирования `/api/reviews`

## Назначение документа

Документ — регламент нагрузочного тестирования FastAPI-сервиса AI-помощника ревьюера PR (эндпоинт `POST /api/reviews`, синхронный вызов внешнего LLM). Он перерабатывает черновик `practices/practice_01/tests_load.md`, в котором был только один сценарий и примечание-заглушка, и отвечает на вопросы:

1. **Что считать успехом?** — числовые пороги в матрице сценариев и критериях приёмки (разделы ниже).
2. **Что и как гонять?** — 14 сценариев: от smoke до soak, плюс проверки бизнес-правил под нагрузкой.
3. **Как доказать результат?** — колонка Evidence: артефакты k6/Locust, снимки Grafana, трейсы APM, перехваченные промпты мок-LLM.
4. **Когда тесты можно интерпретировать?** — раздел «Готовность к запуску» с тремя gate-условиями.

Документ предназначен для инженеров, гоняющих нагрузку, и для ревьюера, принимающего Pass/Fail по чек-листу в конце.

## Обоснование сценариев (ReAct: наблюдение → правило → сценарий)

Каждый сценарий прослеживается от дефицита исходного черновика или правила из `context.md`/`CASE.md`.

| Наблюдение (что нашли) | Правило | Что закрывает в матрице |
|---|---|---|
| В `tests_load.md` один сценарий (10 rps × 60 с, diff ~5 000) и заглушка «пока не требуется» | REL-1 | Сценарии 2–8: базовый профиль, sustained, capacity, пик, спайк, стресс, soak |
| Не проверяется граница размера входа | API-1 | Сценарий 9: diff ровно 20 000 символов не отклоняется |
| Не проверяется отказ сверхлимитного входа | API-1 | Сценарий 10: diff > 20 000 → 100% HTTP 413, 0 вызовов LLM |
| Таймаут LLM (10 с) и деградация не проверяются под нагрузкой | REL-1 | Сценарии 11–12: медленный и недоступный LLM, контролируемый ответ |
| Маскирование секретов не проверяется в параллельном потоке | SEC-1 | Сценарий 13: 0 утечек токенов в промпт при 10 rps |
| Формат ответа и контракт логирования не проверяются под нагрузкой | OUT-1, OBS-1 | Сценарий 14: 100% конформных ответов, лог без тел запросов/ответов |

## Регламент работы с документом

1. **Порядок прогона.** Начинать со сценария 1 (smoke) и 2 (baseline). Только после зелёного baseline запускать sustained → capacity → peak → spike → stress → soak. Сценарии 9–14 (бизнес-правила) выполняются в любом порядке после baseline.
2. **Синхронный контур вызова.** `POST /api/reviews` → очистка секретов (SEC-1) → вызов внешнего LLM с timeout 10 с (REL-1) → ответ в формате OUT-1. Сценарии не предполагают фоновых очередей, воркеров и тяжелых SQL-баз — их нет в `context.md`.
3. **Фиксация условий прогона.** Каждый прогон записывает: версию сервиса (`git rev-parse HEAD`), окружение (адреса хостов), версию сценария k6 и дату/время начала. Без этой строки прогон не считается Evidence.
4. **Хранение артефактов.** Результаты — `k6/results/<scenario>_<YYYY-MM-DD>.json`, снимки — `grafana/<scenario>-<YYYY-MM-DD>.png`, трейсы выгружаются из APM по `request_id` (OBS-1), промпты — `mocks/captured_prompts/<scenario>.jsonl`.
5. **Повторяемость.** LLM-зависимые сценарии (11–13) гоняются на мок-LLM с детерминированной задержкой и записью тела запроса. Прогон на реальном провайдере допускается отдельно для валидации мока, но не заменяет его.
6. **Регрессия.** Любое изменение кода требует повторного baseline. Ухудшение p95 более чем на 10% от предыдущего прогона → Fail.
7. **Авторство и обновления.** Матрица и пороги обновляются при изменении правил CASE.md (REL-1, API-1, SEC-1, OUT-1, OBS-1, SCOPE-1, QA-1).

## SLO и допустимые пороги

Применяются ко всем сценариям, если в матрице не указано иное.

| Метрика | SLO/порог | Источник |
|---|---|---|
| Латенция p95 | ≤ 8 секунд | Выведено из REL-1 (timeout 10 с) с запасом |
| Латенция p99 | ≤ 10 секунд | REL-1 — timeout внешнего LLM-вызова 10 секунд |
| Ошибки 5xx | 0% за прогон | REL-1 — ошибка LLM превращается в контролируемый ответ |
| Ошибки 4xx | только ожидаемые 100% HTTP 413 для diff > 20 000 символов | API-1 |
| Пропускная способность | ≥ целевого rps сценария | — |
| CPU | ≤ 70% в пике, без троттлинга | — |
| RAM | рост ≤ 20% от стартовой и стабилизация к концу прогона | — |
| Утечки секретов | 0 вхождений тестовых токенов в перехваченных промптах | SEC-1 |
| Конформность ответа | 100% ответов с полями `summary`/`risks`/`checks`, в `risks` ≤ 3 элемента | OUT-1 |
| Лог приёма запросов | 100% записей содержат `request_id`, `duration`, `status`; 0 вхождений тел diff/ответа | OBS-1 |

## Критерии приёмки

### Pass — сценарий принят

- все метрики в пределах «Допустимый предел» матрицы; thresholds в k6 зелёные;
- 5xx = 0; 4xx — только ожидаемый 413 из API-1 (сценарий 10);
- для сценария 8 (soak): RAM стабилизировалась к концу прогона;
- для сценариев 11–12: 100% контролируемых ответов в формате OUT-1, лог с `request_id`/`duration`/`status`;
- для сценария 13: 0 утечек секретов в `captured_prompts`; для 14: JSON-schema ответов и лог-контракт соблюдены;
- Evidence сохранены: JSON k6/Locust + снимок Grafana + трейс APM для каждого прогона.

### Fail — сценарий отклонён

- любой выход за p95/p99 или рост ошибок 5xx > 0;
- CPU длительно выше 70% или RAM не стабилизируется (сценарии 3, 8);
- OOM, падение процесса или срыв соединений;
- утечка секрета в перехваченном промпте (сценарий 13);
- нарушение OBS-1 или OUT-1 (сценарий 14);
- несохранённые артефакты Evidence;
- регрессия: p95 хуже предыдущего прогона более чем на 10%.

## Готовность к запуску

Текущий код не реализует timeout по REL-1 (`app/review_service.py:20-21`) и не логирует `duration`/`status` по OBS-1 (`app/api.py:36-37`). Это подтверждённое ограничение реализации, а не заглушка: без измеримых метрик времени ответа сценарии 5–8 нельзя интерпретировать. Запуск разделяется на три gate-условия:

| Gate | Условие входа | Какие сценарии разрешены |
|---|---|---|
| 1 (сейчас) | Стенд поднят, мок-LLM доступен | 1, 2, 9, 10, 13 — фиксируют стартовые метрики, лимиты API-1 и маскирование SEC-1 |
| 2 (после инкремента 2: timeout по REL-1) | Реализован timeout 10 с и контролируемый ответ | 3, 4, 5, 6, 7, 8, 11, 12 — деградация LLM и нагрузочные профили |
| 3 (после инкремента 3: логирование по OBS-1) | Лог содержит `request_id`/`duration`/`status` без тел запросов | 14 — полная матрица 1–14 по регламенту выше |

Прогоны gate 1 допустимы уже сейчас и дают интерпретируемые метрики: time-to-413 (API-1), 0 вызовов LLM при сверхлимитном входе, отсутствие утечек секретов.

## Как использовали AI

- Техника: ReAct (`practices/practice_02/react/experiment.md`).
- Полный запрос и отклонения: строка ReAct в [`practices/practice_02/prompts.md`](../prompts.md).
- Что проверили и исправили сами: сопоставили каждую колонку с правилами CASE.md/`context.md` (p99 ≤ 10 с = REL-1, 100% 413 = API-1, маскирование = SEC-1, формат ответа = OUT-1, лог = OBS-1); у каждого сценария есть числовые SLA и источник Evidence; проверили отсутствие многоточий-заглушек и заполненность всех колонок; отклонили сценарии на несуществующий GET-листинг и фоновые очереди, так как `context.md` фиксирует синхронный Web API-вызов.
