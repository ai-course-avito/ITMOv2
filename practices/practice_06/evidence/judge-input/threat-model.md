# Модель угроз Mini Shop

Метод — Microsoft Threat Modeling: описание системы, поиск угроз (STRIDE по
каждому потоку данных), меры защиты, проверка. Объект — учебный магазин
`lab/service.py`; всё запускается только на `127.0.0.1` с синтетическими данными.

[схема: threat-model.puml; её описание — в таблице ниже и в разделе «Границы доверия»]

Исходник схемы: [`threat-model.puml`](threat-model.puml).

## 1. Описание системы

| Элемент | Что это | Что защищаем |
|---|---|---|
| Клиент (`alice`, `bob`) | вошёл по логину, получил токен | свои профиль, заказы, чек; чужие — нет |
| Сотрудник (`staff`) | вошёл по логину | выгрузка профилей — только ему |
| Каталог | `products` | цена задаётся сервером |
| БД | профили (ПДн: имя, e-mail, адрес), заказы | конфиденциальность и целостность |
| Файлы | чеки клиентов, `private/` | чеки — владельцу, `private/` — никому |
| Отзывы | текст от клиентов | попадает в HTML и в prompt модели |
| AI-помощник | модель возвращает `tool` + `arguments`, сервер исполняет | модель не имеет прав больше, чем у вызвавшего |

**Границы доверия.** (1) всё, что приходит от клиента: тело, query,
**заголовки** — недоверенно; (2) процесс магазина; (3) файловая песочница;
(4) модель: её вывод — такие же недоверенные данные, как и ввод пользователя.

**Активы и последствия.** ПДн клиентов (152-ФЗ), целостность цен и заказов,
служебная заметка, доступность учебных файлов.

## 2. Угрозы

Категории STRIDE: **S** подмена, **T** искажение, **R** отказ от действий,
**I** раскрытие, **D** отказ в обслуживании, **E** повышение привилегий.

| ID | STRIDE | Где (поток) | Угроза | Последствие | Мера |
|---|---|---|---|---|---|
| T01 | E | заголовок `X-Role` → `/admin/export` | роль берётся из заголовка клиента, а не из сессии | любой получает выгрузку ПДн | роль только из серверной сессии; нет сессии — 401 |
| T02 | I | `/profile?id=` | нет проверки владельца | чужой профиль (ПДн) | владелец из сессии; чужой `id` — 403/404 |
| T03 | T, I | `/profile`, `/search`, `/assistant/context` | пользовательский ввод подставляется в SQL строкой | чтение и изменение данных БД | параметризованные запросы, проверка типа |
| T04 | I | `GET /orders` | список заказов без аутентификации и фильтра | чужие заказы | только заказы вызвавшего; сотрудник — по роли из сессии |
| T05 | T | `POST /orders`, поле `price` | цена принимается от клиента | покупка за любую цену | цена только из каталога, лишние поля игнорируются |
| T06 | I | `GET /files?user=&path=` | путь собирается из `user` и `path`, владелец не проверяется | чужие чеки и `private/` (граница песочницы не спасает: внутри неё всё доступно) | `user` — из сессии, `path` — один имя файла из разрешённого набора |
| T07 | I | `GET /debug/logs` | журнал с заголовками, в том числе `X-Token`, отдаётся всем | кража чужих сессий | маршрут убрать или только сотруднику, секреты не логировать |
| T08 | T | `POST /reviews`, `/reviews/view` | текст отзыва выводится в HTML без экранирования | сохранённый XSS у любого, кто откроет страницу | экранирование, `Content-Type`, CSP |
| T09 | T, E | отзыв → prompt модели | отзыв попадает в контекст помощника как инструкция | модель выполняет чужие указания (косвенный prompt injection) | данные отдельно от инструкций, пометить как недоверенные; главное — не полагаться на послушание модели (T10–T12) |
| T10 | E | `/assistant/execute` → `read_file` | решение модели исполняется с правами сервера, путь не проверен | чтение чужих чеков и `private/` | авторизация инструмента по сессии вызвавшего, allowlist путей |
| T11 | E, I | `/assistant/execute` → `export_profiles` | любой клиент может вызвать выгрузку ПДн | утечка всех профилей | инструмент доступен только по роли из сессии |
| T12 | D, T | `/assistant/execute` → `delete_tree` | любой клиент может удалить дерево файлов | потеря чеков | деструктивные инструменты не отдавать клиенту; подтверждение человеком |
| T13 | S | `/login`, токены | токен без срока, сессии не отзываются; нет ограничения числа попыток | подбор пароля, долгоживущий токен | срок жизни, лимит попыток |
| T14 | I | любая ошибка | `500` отдаёт текст исключения и его тип | раскрытие внутреннего устройства | общий ответ клиенту, подробности только в журнал |
| T15 | D | тело запроса, пустые поля | `body["product"]` и т. п. без проверки формы; необработанные ошибки | падения, шум в журнале | проверка схемы тела, `400` вместо `500` |
| T16 | R | действия пользователей | нет журнала действий с привязкой к пользователю | не восстановить, кто что сделал | журнал: пользователь, действие, результат (без секретов) |

Порядок проверки: каждая угроза подтверждается воспроизведением на своём
локальном стенде (REPORT_01), затем исправляется с регрессионным тестом и
проверяется повторно (REPORT_02). Угрозы, которые не подтвердились или
остались открытыми, фиксируются там же с причиной.

## 3. Принципы исправления

1. **Идентичность и роль определяет сервер** по сессии, никогда клиентский заголовок.
2. **Права проверяются на сервере для каждого действия**, в том числе действия, которое «предложила» модель.
3. **Недоверенные данные не меняют смысл запроса**: SQL — параметрами, HTML — экранированием, пути — из набора разрешённых.
4. **Модель — не граница безопасности.** Защита работает, даже если модель выполнит любую инструкцию.
5. **Ошибки и журналы не раскрывают секреты и внутренности.**
