# Анализ процесса: AS IS и TO BE

## AS IS

Клиент формирует HTTP‑запрос `POST /api/reviews` с JSON‑телом, содержащим ключ `diff`. FastAPI вызывает обработчик `create_review(payload: dict)`, который без проверки наличия ключа обращается к `review_service.review(payload["diff"])`. `ReviewService.review` формирует prompt:

```
"Review this pull request and find problems:\n" + diff
```

и вызывает `LLM.generate(prompt)`. Ответ строки от LLM оборачивается в словарь `{"comment": answer}` и возвращается клиенту. Ошибки отсутствия ключа `diff` и исключения из `LLM.generate` не перехватываются. Участники: Клиент, FastAPI, ReviewService, LLM.


## TO BE

Малое улучшение без изменения контрактов TRAINING_PR.diff: сохраняем прямой путь, фиксируем проверяемость и наблюдаемость первого сценария. Добавляем только формализованные проверки на уровне тестов (unit/integration/E2E), не меняя код в данном инкременте.

```mermaid
flowchart LR
    A[Клиент: POST /api/reviews с JSON{diff}] --> B[FastAPI: create_review(payload)]
    B --> C[ReviewService.review(diff)]
    C --> D[LLM.generate(prompt)]
    D --> E[Система: {comment: ответ}]
    E --> F[Клиент получает ответ]
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Покрытие проверками | Нет систематических проверок | Есть unit, integration, E2E‑кейсы | Запуск тестов; фиксация ожидаемых падений при отрицательных сценариях |
| Явность рисков | Риски не зафиксированы | Риски описаны и привязаны к строкам diff | Сопоставление с TRAINING_PR.diff |
| Наблюдаемость сценария | Только ручной вызов | Документированные шаги проверки | Выполнение сценариев из tests_* |

## Как использовали AI

- Для чего: описать AS IS/TO BE, не выходя за пределы TRAINING_PR.diff.
- Тип промпта: master prompt по diff и исполняющий промпт P1-03.
- Строка в [`prompts.md`](prompts.md): P1-02, P1-03.
- Что проверили и исправили сами: проверили формулировки против строк diff; убрали любые предположения о внешней инфраструктуре.
