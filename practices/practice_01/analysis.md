# Анализ процесса: AS IS и TO BE

## AS IS

Опишите текущий процесс от события до результата. Укажите участников, задержки, ручные операции и точки потери информации.

Текущий процесс (по `TRAINING_PR.diff`): клиент отправляет `POST /api/reviews` с телом `{"diff": "..."}` (TRAINING_PR.diff:35-36) → `create_review` без валидации читает `payload["diff"]` (TRAINING_PR.diff:37) → `ReviewService.review` формирует промпт `f"Review this pull request and find problems:\n{diff}"` без ограничения длины и санитизации (TRAINING_PR.diff:20) → вызывает `llm.generate(prompt)` без try/except и без timeout (TRAINING_PR.diff:21) → возвращает `{"comment": answer}` клиенту как неструктурированный текст (TRAINING_PR.diff:22).

Участники: клиент эндпоинта (человек или сервис — не указано в diff), FastAPI-приложение (`app/api.py`), `ReviewService` (`app/review_service.py`), внешний `LLM`.

Точки потери информации/риска:
- при отсутствии ключа `diff` — необработанный `KeyError` → 500 без диагностики для клиента (TRAINING_PR.diff:36-37);
- при сбое LLM (таймаут, лимит) — исключение пробрасывается наружу, клиент не получает контролируемый ответ (TRAINING_PR.diff:21);
- ответ LLM не структурирован — теряется машиночитаемость находок (TRAINING_PR.diff:22);
- нет логирования шага вызова LLM — при инциденте невозможно восстановить, что произошло (TRAINING_PR.diff:19-22).

Ручных операций в самом процессе нет — весь путь автоматический, но именно из-за отсутствия проверок и логирования диагностика ошибок требует ручного вмешательства инженера post-hoc.

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Валидация входа | `payload["diff"]` без проверки, `KeyError`→500 (TRAINING_PR.diff:36-37) | Явная проверка наличия и типа `diff`, ответ 4xx при ошибке | integration-тест: запрос без ключа `diff` возвращает 4xx, не 500 |
| Обработка ошибок LLM | `llm.generate` без try/except (TRAINING_PR.diff:21) | Вызов оборачивается в try/except с timeout, ошибка превращается в контролируемый ответ | unit-тест на `ReviewService.review` с падающим/зависающим мок-LLM |
| Наблюдаемость | Нет логирования вызова (TRAINING_PR.diff:19-22) | Логируется факт вызова, длительность, статус (без содержимого diff/ответа) | проверка логов после тестового запроса |

## Как использовали AI

- Для чего: описать AS IS процесс по фактам из diff и предложить минимальный TO BE для устранения проблем валидации и обработки ошибок.
- Тип промпта: master prompt.
- Строка в [`prompts.md`](prompts.md): P1-03.
- Что проверили и исправили сами: TO BE ограничен минимальным сценарием (валидация + обработка ошибок LLM), без добавления функциональности, не подтверждённой diff или явно вытекающей из найденных проблем; конкретные числа (timeout в секундах, лимит длины) не зафиксированы как факт, так как источник с такими правилами (`CASE.md`) не входит в разрешённый список для этого запуска.
