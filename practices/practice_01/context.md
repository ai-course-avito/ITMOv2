## Context Pack для первого рабочего сценария

### Факты и правила

- Помощник анализирует один diff PR за один запрос.
- Результат: краткое описание изменения; не больше трёх рисков; список проверок.
- Каждый риск обязан содержать файл, строку (или функцию) и цитату-доказательство из diff.
- Нет доказательства — риск не включать.
- Недостающие данные помечать как «Открытый вопрос», не выдумывать требования.
- Решение по PR всегда принимает человек.

### Формат входа и результата

- **Вход:** текст diff (учебный файл `TRAINING_PR.diff`).
- **Выход (Markdown):**
  1. Краткое описание изменения (2–4 предложения).
  2. Не больше трёх рисков в формате:  
     `<файл>, <функция/строка> — <что не так>. Доказательство: <цитата из diff>.`
  3. Список проверок (unit / integration / e2e) с ожидаемым результатом.

### Ограничения и запрещённые действия

- Разрешено: анализировать diff, ссылаться на файлы и строки, предлагать проверки.
- Запрещено: approve, merge, менять код, выдумывать требования, доступ к прод-данным.
- Не предлагать merge/approve и не переписывать код в ответе.

### Хороший пример

```text
app/api.py, create_review — обращение payload["diff"] вызывает KeyError,
если в теле запроса нет поля diff. Проверка: POST /api/reviews с пустым JSON.
```

### Плохой пример

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Что пока неизвестно

- SLA ответа API и лимиты размера diff — **Открытый вопрос**.
- Контракт ошибок (4xx/5xx) для невалидного тела — **Открытый вопрос** (в diff не задан).
- Наличие и покрытие существующих автотестов в репозитории продукта — **Открытый вопрос**.
- Конкретная модель LLM в прод-сервисе и её квоты — **Открытый вопрос**.
