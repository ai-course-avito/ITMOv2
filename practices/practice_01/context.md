| Вопрос | Ответ | Источник |

| Продукт | API-помощник для ревью PR: получает diff и возвращает совет человеку | `CASE.md`, `TRAINING_PR.diff` |

## Context Pack

### Факты

- Вход: JSON `{ "diff": "<text>" }` (`TRAINING_PR.diff`, строки 35–37).
- Текущий результат: `{ "comment": "<ответ LLM>" }` (строка 22).
- Diff передаётся в prompt без промежуточной обработки (строки 19–21).

### Правила

- `SEC-1`: удалить токены, пароли и приватные ключи до вызова внешнего LLM.
- `API-1`: diff длиннее 20 000 символов отклонить с HTTP 413.
- `REL-1`: timeout LLM — 10 секунд; ошибку вернуть контролируемо.
- `OUT-1`: ответ содержит `summary`, `risks` и `checks`; в `risks` не более трёх элементов с `file`, `line`, `evidence`, `risk`.
- `SCOPE-1`: сервис не меняет код и не выполняет действия в GitHub.
- `QA-1`: каждый риск подтверждается строкой diff или правилом.
- `OBS-1`: логировать только `request_id`, длительность и статус, без diff и ответа LLM.

### Формат и ограничения

- Использовать только `TRAINING_PR.diff` и релевантные правила `CASE.md`.
- Не включать правила про БД и frontend: они не относятся к кейсу.
- Не утверждать наличие компонентов, которых нет во входных источниках.

### Пример качества

- Хорошо: `app/review_service.py:20 — diff уходит во внешний LLM без удаления секретов, нарушая SEC-1`.
- Плохо: `Код можно улучшить` — нет evidence и воспроизводимой проверки.

## Неизвестно

- Реализация LLM-клиента, инфраструктура, SLA и механизм логирования не показаны.
- Для «контролируемой ошибки» из `REL-1` не заданы точные HTTP-статус и JSON-схема.
- Эти пункты нужно оформить как вопросы, а не как факты.

## Как использовали AI

- Для чего: выделить из `CASE.md` только правила, влияющие на учебный diff.
- Тип промпта: master prompt с Context Pack.
- Строка в [`prompts.md`](prompts.md): `P1-02`.
- Проверка человеком: каждое правило сверено с `CASE.md`, каждый факт — с diff.
