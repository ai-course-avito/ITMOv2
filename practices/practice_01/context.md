## Context Pack для первого рабочего сценария

### Факты и правила

Правила ниже переписал дословно из учебного кейса на момент запусков (тогда это был `CASE.md`; апстрим файл позже удалил, а в новый `README.md` эти правила не переехали — так что этот список сейчас единственный носитель, сверяйте с ним, а не ищите файл).

- `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли, приватные ключи.
- `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
- `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- `OUT-1`: ответ содержит `summary`, массив `risks` (max 3, поля `file`, `line`, `evidence`, `risk`) и массив `checks`.
- `SCOPE-1`: сервис только советует; не пишет код и не выполняет действия в GitHub.
- `QA-1`: риск только если подтвержден строкой diff или правилом репозитория.
- `OBS-1`: в лог только `request_id`, длительность, статус; diff и ответ модели не логируются.
- Факт diff: `app/review_service.py:20` — `prompt = f"Review this pull request and find problems:\n{diff}"` без чистки.
- Факт diff: `app/api.py:36-37` — `payload: dict`, прямой доступ `payload["diff"]` без валидации.

### Формат входа и результата

- Вход: только `TRAINING_PR.diff`; других файлов репозитория не читать.
- Результат: `summary` (1-3 предложения) + `risks` (0-3 шт.) + `checks` (список воспроизводимых проверок).

### Ограничения и запрещённые действия

- Не approve, не merge, не менять код; решает человек.
- Не выдумывать риски без `evidence` (строка diff или правило).
- Не логировать содержимое diff/ответа; не отправлять секреты во внешний LLM.
- Не использовать нерелевантные правила `snake_case`, `i18n` — в исходном кейсе они были явно помечены как дистракторы, я их сюда не тащил.

### Хороший пример (дословно из исходного кейса; номер строки там условный)

```text
app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```
В нашем реальном diff этот же код на строке 20 — смысл тот же, привязывался к нему.

### Плохой пример

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```
Без файла, строки, правила и проверки — так не пишем.

### Что пока неизвестно

- Кто вызывает endpoint (нужны ли auth/rate-limit) — в diff нет.
- Текущие значения метрик ревью (доля доказанных замечаний, latency) — нет данных.
- Реальный размер diff в проде и частота ошибок LLM — нет данных.

## Как использовали AI

- Для чего: прогнал zero-shot по diff и собрал из ответа первую таблицу AS IS
- Тип промпта: zero-shot (`P1-01`)
- Строка в [`prompts.md`](prompts.md): `P1-01`
- Что проверили и исправили сами: прошелся по каждой ячейке и вычеркнул то, чего нет в diff (команды, задержки в проде); нарушение входа заметил по логу — агент подчитал `CASE.md` и тесты, это записал в `P1-01`; `snake_case`/`i18n` выкинул, в `CASE.md` они помечены как мусор
