# Контекст AS IS и Context Pack

## Продукт и команда сейчас

| Вопрос | Ответ | Источник или допущение |
|---|---|---|
| Какой продукт или сервис рассматриваем? | AI-помощник ревьюера PR — сервис `ReviewService`, принимающий diff и возвращающий комментарий через LLM | `TRAINING_PR.diff`, `CASE.md` |
| Кто им пользуется? | Инженер (ревьюер), который открывает PR и хочет получить автоматическую первичную оценку изменений | `CASE.md` — «Решение всегда принимает человек» |
| Как устроен текущий процесс? | Ревьюер вручную читает diff целиком, самостоятельно ищет проблемы и оставляет комментарии без поддержки инструментов | Допущение на основе AS IS (инструмент только добавляется) |
| Где возникает задержка или ошибка? | Ревью занимает много времени; на крупных diff-ах легко пропустить проблемы безопасности или архитектурные риски | Допущение; измеримо через время ревью (нет исторических данных) |
| Какие системы и команды участвуют? | FastAPI-сервис (`app/api.py`, `app/review_service.py`), внешний LLM-провайдер (через протокол `LLM`), инженер-ревьюер | `TRAINING_PR.diff` |

## Context Pack для первого рабочего сценария

### Факты и правила

- `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
- `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ (не 500).
- `OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`. В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.
- `SCOPE-1`: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- `QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
- `OBS-1`: в лог пишутся только `request_id`, длительность и статус. Содержимое diff и ответа модели не логируется.

### Формат входа и результата

- **Вход:** строка `diff` (patch-формат git), не длиннее 20 000 символов.
- **Результат:** JSON-объект с полями:
  - `summary` — строка, краткое описание изменения;
  - `risks` — массив до 3 объектов: `{ file, line, evidence, risk }`;
  - `checks` — массив строк с воспроизводимыми проверками.

### Ограничения и запрещённые действия

- AI не может approve, merge или менять код в репозитории.
- AI не читает файлы репозитория, кроме приложенного diff.
- Риск не включается в ответ без явной ссылки на строку diff или правило (`QA-1`).
- Diff не логируется в целях конфиденциальности (`OBS-1`).
- Содержание ответа LLM не логируется (`OBS-1`).

### Хороший пример

```text
app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```

### Плохой пример

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Что пока неизвестно

- Целевая версия Python (3.8 или 3.9+) — влияет на допустимость `dict[str, str]` vs `Dict[str, str]`.
- Является ли LLM-клиент синхронным или асинхронным — влияет на выбор паттерна (async endpoint vs threadpool).
- Максимальный ожидаемый размер diff на практике (чтобы настроить лимит `API-1`).

## Как использовали AI

- Для чего: формирование Context Pack на основе правил из `CASE.md` и наблюдений zero-shot запуска P1-01.
- Тип промпта: zero-shot (P1-01) — результат использован для выявления недостающего контекста.
- Строка в [`prompts.md`](prompts.md): P1-01.
- Что проверили и исправили сами: сверили каждое правило (`SEC-1`…`OBS-1`) с `CASE.md` построчно; убрали правила, не относящиеся к задаче (`snake_case`, `i18n`); Open Questions из P1-01 перенесены в раздел «Что пока неизвестно».

## Краткая суть изменения в diff

- Добавлен метод `ReviewService.review`, который отправляет текст diff во внешний LLM и возвращает `{"comment": ...}`.
- В API добавлен POST `/api/reviews`, который принимает `payload: dict` и без валидации проксирует `payload["diff"]` в сервис.
