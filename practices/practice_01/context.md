## Context Pack для первого рабочего сценария

### Факты и правила

- В FastAPI тела запросов описывают Pydantic‑моделями для валидации и типобезопасного парсинга.
- Внешние вызовы (LLM, сеть) должны иметь обработку ошибок/таймаутов.
- Любой пользовательский ввод (например, diff) считается недоверенным и может вести к prompt‑injection; нельзя возвращать сырой ответ LLM без пост‑обработки.
- В ревью требуется указывать file:line и подтверждать вывод diff'ом или правилом из этого Context Pack.
- Не придумывать новые правила; опираться только на diff и явные практики выше.

### Формат входа и результата

- Вход: JSON с полем `diff` (строка) для API; для ревью — файл TRAINING_PR.diff.
- Результат ревью: summary и до 3 рисков, каждый с evidence (file:line + цитата) и проверкой (check).

### Ограничения и запрещённые действия

- Запрещено: approve, merge, edit кода в ревью‑ответе.
- Нельзя вводить новые правила; если нет evidence — пункт пропустить.
- Ответ должен соблюдать поток: candidate → evidence → check.

### Хороший пример

Candidate: Нет схемы и валидации входа.
Evidence: app/api.py:35‑37 — `def create_review(payload: dict) ... payload["diff"]`.
Check: Отправить `{}` и ожидать 500/KeyError; корректно — 422 с сообщением валидации.

### Плохой пример

- «Коду не хватает логирования» без ссылок на строки и без правила/проверки.

### Что пока неизвестно

- Требования к аутентификации/лимитам.
- Формат ожидаемого комментария LLM (схема, ограничения длины).

## Как использовали AI

- Для чего: Базовое ревью TRAINING_PR.diff и подготовка Master Prompt.
- Тип промпта: zero‑shot (P1‑01), master prompt (P1‑02).
- Строка в [`prompts.md`](prompts.md): записи P1‑01, P1‑02.
- Что проверили и исправили сами: Негативные кейсы (отсутствие `diff`, нестроковый тип, исключение LLM).
