## Context Pack для первого рабочего сценария

### Факты и правила

- Валидация входа должна выполняться через Pydantic-модели; ошибки тела запроса → 422 Unprocessable Entity.
- Эндпоинт создания ресурса должен возвращать 201 Created и документированный `response_model`.
- Вызовы LLM должны иметь таймаут, базовую обработку исключений и ограничения повторов.
- Пользовательский ввод в промпте должен быть отделён и не менять системные инструкции (харднинг промпта).
- Размер входного `diff` должен быть ограничен; при превышении — отказ (413) или усечение с явным поведением.

### Формат входа и результата

- Запрос: POST `/api/reviews` с телом `{ "diff": string }`.
- Ответ: `{ "comment": string }`.

### Ограничения и запрещённые действия

- Нельзя использовать «сырой» `dict` вместо Pydantic для публичного API.
- Нельзя передавать в LLM невалидированные или слишком большие `diff` без ограничений.
- Нельзя игнорировать исключения/таймауты LLM — нужно маппить на понятные 4xx/5xx.

### Хороший пример

Route с явной схемой и контролем размеров: `@app.post("/api/reviews", response_model=ReviewResponse, status_code=201)` и `def create_review(payload: ReviewRequest) -> ReviewResponse:` с проверкой длины `diff` и обработкой исключений.

### Плохой пример

`def create_review(payload: dict) -> dict[str, str]: return review_service.review(payload["diff"])` — возможен `KeyError`, нет схемы ответа, нет ограничений.

### Что пока неизвестно

- Требуются ли аутентификация и rate limiting.
- Точный максимальный размер `diff` и политика усечения.
- Версия Python/рантайма в проде.

## Как использовали AI

- Для чего: ревью PR и формирование минимальных правок.
- Тип промпта: сначала zero-shot, затем master prompt.
- Строка в [`prompts.md`](prompts.md): записи P1-01 и P1-02.
- Что проверили и исправили сами: сопоставление замечаний с diff по строкам, корректность статусов и схем FastAPI, классификация рисков.
