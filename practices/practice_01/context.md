## Context Pack для первого рабочего сценария

### Факты и правила

- Есть протокол `LLM` с методом `generate(self, prompt: str) -> str`.
- Добавлен метод `ReviewService.review(self, diff: str) -> dict[str, str]`, который формирует строку prompt и вызывает `self.llm.generate(prompt)`.
- Метод `review` возвращает словарь вида `{"comment": answer}`.
- В FastAPI добавлен эндпоинт `POST /api/reviews` с обработчиком `create_review(payload: dict) -> dict[str, str]`, который вызывает `review_service.review(payload["diff"])`.
- Присутствует эндпоинт `GET /health`, возвращающий `{"status": "ok"}`.

### Формат входа и результата

- Вход API: JSON-объект с ключом `diff` (тип строки не проверяется в коде diff).
- Результат API: словарь `{"comment": <ответ LLM>}`.
- Формирование prompt: `"Review this pull request and find problems:\n" + diff`.

### Ограничения и запрещённые действия

- В diff нет явных ограничений по размеру входа, таймаутам, аутентификации или политик по секретам.

### Хороший пример

app/review_service.py — метод `review` вставляет сырой `diff` в prompt без каких-либо преобразований.
Проверка: передать в `review(diff)` тестовую строку и убедиться, что prompt содержит её без изменений.

### Плохой пример

"Нужно добавить лимит размера diff и i18n" — такие выводы не подтверждены содержимым TRAINING_PR.diff.

### Что пока неизвестно

- Есть ли валидация схемы входного JSON на уровне FastAPI (pydantic-модели).
- Как обрабатываются исключения и таймауты вызова LLM.
- Требования к формату ответа API для клиентов.
- Нужна ли аутентификация/авторизация для `/api/reviews`.
- Требования к логированию.

## Как использовали AI

- Для чего: выполнить ревью TRAINING_PR.diff и сформировать выводы.
- Тип промпта: сначала zero-shot, затем master prompt, основанный только на diff.
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02.
- Что проверили и исправили сами: исключили предположения, не подтверждённые diff; привязали риски к цитатам из diff; сформулировали воспроизводимые проверки.
