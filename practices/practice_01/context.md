| Какой продукт или сервис рассматриваем? | HTTP-сервис `review-assistant`: принимает diff пулл-реквеста и возвращает ревью, которое читает человек. Отдельно фиксируем AS IS самого проверяемого кода, потому что он и есть предмет первого сценария. В `app/review_service.py` метод `review()` подставляет diff в промпт без обработки (строка 14), вызывает LLM без таймаута и обработки ошибок (строка 15) и возвращает `{"comment": answer}` (строка 16). Эндпоинт `POST /api/reviews` в `app/api.py` принимает нетипизированный `dict` и обращается к `payload["diff"]` напрямую.

## Context Pack для первого рабочего сценария

Сценарий: помощник получает один diff и возвращает ревью, пригодное для проверки человеком. Пакет собран после запуска `P1-01` под конкретные дефекты baseline и применён в `P1-02`.

### Факты и правила

- `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
- `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- `OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`. В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.
- `SCOPE-1`: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- `QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
- `OBS-1`: в лог пишутся только `request_id`, длительность и статус. Содержимое diff и ответа модели не логируется.
- Решение о merge принимает человек. Помощник не может approve, merge или изменять код.

Правила `snake_case` для таблиц базы данных и обязательный i18n для frontend-строк в пакет **не включены**: в `TRAINING_PR.diff` нет ни миграций, ни frontend-кода, применить их не к чему. Проверено по самому диффу: изменены только `app/review_service.py` и `app/api.py`, оба backend, без работы с БД и без UI.

### Формат входа и результата

- Вход: текст unified diff одного пулл-реквеста. Других источников нет; содержимое файлов вне diff не додумывается.
- Результат: один JSON-объект с полями `summary` (одно-два предложения), `risks` (не более трёх элементов, поля `file`, `line`, `evidence`, `risk`) и `checks` (проверки с описанием входа и ожидаемого результата).

### Ограничения и запрещённые действия

- Не писать код и патчи.
- Не предлагать approve или merge, не выполнять действия в GitHub (`SCOPE-1`).
- Не читать файлы за пределами приложенного diff.
- Не включать риск без подтверждающей строки diff или правила (`QA-1`).
- Не выдавать больше трёх рисков (`OUT-1`).
- Не подавать предположение о нереализованном коде как факт.

### Хороший пример

```text
app/review_service.py:14 - diff подставляется в prompt без удаления секретов,
что нарушает SEC-1. Evidence: prompt = f"Review this pull request and find problems:\n{diff}".
Проверка: передать diff с тестовым токеном и убедиться, что в prompt осталось [REDACTED].
```

### Плохой пример

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Что пока неизвестно

- Кто вызывает `POST /api/reviews`: CI-джоба, GitHub App или человек вручную. От этого зависит модель аутентификации, которой в правилах нет.
- Объём: сколько PR в день проходит через сервис и каково распределение размеров diff. Без этого `API-1` (порог 20 000 символов) нельзя обосновать числом.
- Какой LLM-провайдер используется и какова его реальная задержка относительно таймаута `REL-1` в 10 секунд.
- Как устроено хранение и ротация ключа провайдера: `SEC-1` покрывает только содержимое diff.

## Как использовали AI

- Для чего: получить baseline-ревью diff без контекста (`P1-01`), затем повторить его с собранным Context Pack (`P1-02`), чтобы измерить вклад контекста.
- Тип промпта: zero-shot для `P1-01`, master prompt с Context Pack для `P1-02`.
- Строка в [`prompts.md`](prompts.md): `P1-01`, `P1-02`.
- Что проверили и исправили сами: пересчитали номера строк счётом по телу ханка, потому что заголовки ханков в `TRAINING_PR.diff` завышены (`+1,23` при 16 фактических строках в `app/review_service.py`, `+1,17` при 15 в `app/api.py`). По этому счёту строки 14, 15, 16 подтвердились; пример в `CASE.md` указывает `:16` для нарушения `SEC-1`, что не сходится ни с телом ханка, ни с заголовком. В таблице AS IS оставили свою нумерацию, разбор записан в [`prompts.md`](prompts.md). Из `P1-01` отклонили выводы про блокировку event loop, аутентификацию и rate limiting: они не подтверждаются ни diff, ни правилами, и в раздел «Факты и правила» не попали.
