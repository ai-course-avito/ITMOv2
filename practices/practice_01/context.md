## Context Pack для первого рабочего сценария

### Факты и правила

- Задача помощника: вернуть краткое описание изменения, до 3 рисков с `file`, `line`, `evidence`, `risk`, и список проверок (CASE.md)
- Решение всегда принимает человек; помощник не может approve/merge и не меняет код (SCOPE-1) (CASE.md)
- SEC-1: из diff в запрос к LLM удаляются токены/пароли/ключи (CASE.md)
- API-1: diff > 20 000 символов отклоняется HTTP 413 (CASE.md)
- REL-1: LLM-вызов имеет timeout 10 сек; ошибка превращается в контролируемый ответ (CASE.md)
- OUT-1: ответ содержит `summary`, массив `risks` (≤3), `checks`; поля в `risks`: `file`, `line`, `evidence`, `risk` (CASE.md)
- QA-1: риск включается только при подтверждении строкой diff или правилом репозитория (CASE.md)
- OBS-1: логируются только `request_id`, длительность и статус; содержимое diff/ответа не логируется (CASE.md)

### Формат входа и результата

- Вход: diff Pull Request (текст)
- Результат: JSON-структура с полями `summary`, `risks` (≤3), `checks` в соответствии с OUT-1

### Ограничения и запрещённые действия

- Помощник не выполняет действия в GitHub и не изменяет код (SCOPE-1)
- Нельзя отправлять секреты во внешний LLM (SEC-1)
- Дифы превышающие 20 000 символов должны быть отклонены (API-1)
- LLM-вызовы должны быть ограничены по времени и безопасно обрабатываться (REL-1)

### Хороший пример

```
app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```

### Плохой пример

```
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Что пока неизвестно

- Конкретный механизм редактирования секретов (masking) и перечень паттернов
- Политика аутентификации/авторизации API
- Нефункциональные требования по производительности, кроме REL-1/API-1
- Среда исполнения и деплой
