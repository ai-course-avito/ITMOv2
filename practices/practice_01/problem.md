# Проблема и метрики

## Проблема

- Пользователь: разработчик или CI, вызывающие POST /api/reviews для автоматического ревью PR.
- Ситуация: отправляется diff PR в сервис AI-ревью, ожидается стабильный предсказуемый ответ.
- Что происходит сейчас (AS IS по TRAINING_PR.diff): в новом эндпоинте отсутствует валидация входа и обработка ошибок LLM; весь diff без ограничений уходит в промпт; возвращается только поле `comment`.
- Почему это мешает пользователю или бизнесу: нестабильный API ломает CI, тратит квоту LLM, увеличивает задержки и стоимость, ухудшает доверие к инструменту ревью.
- Что не входит в задачу: полная смена схемы ответа, интеграция аутентификации/квот, выбор конкретного провайдера LLM и его SDK.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте неподтверждённые числа и маркетинговые метрики.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Невалидное тело запроса | Ручной тест: `{}` приводит к KeyError и 500 | Ожидаемый клиентский ответ — 422 Unprocessable Content; 5xx отсутствуют | После внедрения валидации | Интеграционный тест; логи приложения |
| Ошибки внешнего LLM | Необработанное исключение -> 500 | HTTP 502; тело содержит `error.code=LLM_UPSTREAM_ERROR` и безопасное `error.message` без деталей провайдера | После реализации обработки ошибок | Юнит/интеграция с мок LLM; спецификация API |
| Лимит размера diff | Нет лимита | Длина исходного `diff` после декодирования JSON и до redaction: 20 000 символов принимаются, 20 001 — HTTP 413; LLM не вызывается | Сразу после внедрения лимита | Юнит/интеграционный тест; спецификация API |
| Timeout внешнего LLM | Не задан | Таймаут LLM‑вызова — 10 секунд; по таймауту возвращается тот же контракт HTTP 502 | После внедрения таймаута | Юнит/интеграция с искусственной задержкой; спецификация API |
| Пустой diff | Прямой вызов LLM с пустым/пробельным текстом возможен | Пустой или состоящий только из пробелов `diff` отклоняется с HTTP 422; LLM не вызывается | После внедрения валидации | Юнит/интеграционный тест |
| Структура результата | Сейчас возвращается только `comment` | Результат содержит `summary`, `risks` (≤3) и `checks`; каждый риск: `file`, `line`, `evidence`, `risk` | После реализации преобразования ответа | Контракт API; модульные тесты преобразования |
| Логи | Возможен лог чувствительных данных | Diff и ответ LLM не попадают в логи; логируются только безопасные метаданные (`request_id`, длительность, статус) | После добавления логгера | Конфигурация логирования; инспекция логов |
| P95 латентность /api/reviews | Базовый замер отсутствует | Требуется базовый замер на стенде; целевое значение принимается после baseline | После реализации контракта и mock LLM | План нагрузочного теста; отчёт baseline |

## Почему изменение метрики подтвердит решение проблемы

Снижение 5xx на клиентских ошибках подтверждает корректную валидацию и предсказуемость API (422 вместо 500). Преобразование исключений LLM в контролируемый ответ подтверждает устойчивость к сбоям внешнего сервиса. Лимит 20 000 символов исключает избыточные нагрузки и ошибки токенизации. Таймаут 10 секунд ограничивает зависания. Структура результата делает вывод проверяемым (≤3 риска, каждый с file/line/evidence/risk). Исключение diff/ответа модели из логов снижает риск утечек. Для латентности сначала требуется baseline: условия стенда, методика измерений и правило принятия целевого значения после базового замера.
