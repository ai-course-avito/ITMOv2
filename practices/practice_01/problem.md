# Проблема и метрики

## Проблема

- **Пользователь:** инженер-ревьюер, который проверяет Pull Request перед слиянием.
- **Ситуация:** ревьюер открывает diff и вручную ищет проблемы безопасности, архитектурные риски и нарушения правил проекта.
- **Что происходит сейчас:** ревьюер тратит значительное время на первичный просмотр diff; при большом объёме изменений часть проблем (особенно security-риски) пропускается.
- **Почему это мешает пользователю или бизнесу:** пропущенные уязвимости (например, утечка секретов через `SEC-1`) и неконтролируемые LLM-вызовы (`REL-1`) попадают в production, что ведёт к инцидентам и ручным откатам.
- **Что не входит в задачу:** автоматический approve/merge, написание кода вместо ревьюера, ревью файлов за пределами переданного diff.

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля PR с пропущенным нарушением `SEC-1` (секреты в LLM-промпте) | Базовое: 0 из 0 PR с `SEC-1` (данных нет). Способ: за 1 день взять 30 последних закрытых PR, выгрузить их diff, вручную разметить случаи `SEC-1` (двумя людьми) и сравнить с ответом ReviewService по тем же diff; пропуск = есть `SEC-1` в diff, но сервис не пометил нарушение. | 0% пропусков на PR, проверенных сервисом | baseline в первый день (30 PR), далее на каждом PR | diff PR (GitHub UI/gh) + ответы ReviewService (stdout/лог) + ручной аудит |
| Доля LLM-вызовов без timeout, вернувших 500 | Базовое: 0 из 0 вызовов (данных нет). Способ: за 1 день прогнать 200 запросов к ReviewService на фиксированном наборе diff (включая случаи у порога `API-1`), собрать HTTP-коды из access-логов; исключить записи с пометкой timeout по `REL-1`; доля = 500/(все - timeout). | < 1% | в день замера (прогон 200 запросов), далее ежедневно по прод-логам | access-логи сервиса + метки timeout в логах |
| Среднее время первичного ревью одного PR | Базовое: 0 мин по 0 PR (данных нет). Способ: на 30 последних PR измерить время от открытия PR до первого содержательного комментария ревьюера, исключая авто-ответ ReviewService; считать по временным меткам вручную или через `gh`. | -30% относительно базового значения | baseline в первый день (30 PR до запуска), целевое - на 30 PR в следующем спринте | история комментариев PR в GitHub (UI/gh) |

## Почему изменение метрики подтвердит решение проблемы

Сервис вмешивается именно в ту точку, где возникают пропуски: он проверяет diff до того, как ревьюер начинает работу. Если доля нарушений `SEC-1` падает до нуля, значит, автоматическая проверка обнаруживает их раньше человека. Если доля неуправляемых 500-ошибок снижается до целевого значения — правило `REL-1` работает корректно. Если среднее время ревью сокращается — ревьюер тратит меньше времени на поиск очевидных проблем и сосредотачивается на содержательных вопросах.

## Как использовали AI

- Для чего: выявление проблем в diff через zero-shot запрос (P1-01) для формулировки реальной проблемы ревьюера.
- Тип промпта: zero-shot (P1-01).
- Строка в [`prompts.md`](prompts.md): P1-01 (zero-shot, выявление проблемы), P2-02 (RCTF, детализация метрик).
- Что проверили и исправили сами: метрики сформулированы на основе правил из `CASE.md` (`SEC-1`, `REL-1`, `OUT-1`), проверены на соответствие содержимому diff; претензии без подтверждения строками diff не включались; способы замера проверены на реалистичность (30 PR за день).
