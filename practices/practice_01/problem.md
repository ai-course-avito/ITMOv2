# Проблема и метрики

## Проблема

- Пользователь: ревьюер пулл-реквеста в репозитории команды.
- Ситуация: на ревью приходит diff, который должен соответствовать правилам репозитория `SEC-1`…`OBS-1` из [`CASE.md`](CASE.md).
- Что происходит сейчас: ревьюер читает diff целиком и сверяет его с правилами по памяти. Автоматической проверки нет. Попытка заменить это ревью произвольным запросом к LLM даёт результат, который сам нельзя проверить: в запуске `P1-01` модель выдала 7 замечаний, ни одно не содержало номера строки или цитаты, и 5 из 7 не опирались ни на одно правило репозитория.
- Почему это мешает пользователю или бизнесу: непроверяемое замечание стоит ревьюеру ровно столько же времени, сколько чтение diff вручную: его всё равно приходится подтверждать глазами. При этом нарушения, которые выглядят безобидно, пропускаются: в `TRAINING_PR.diff` нарушение `SEC-1` умещается в одну строку `prompt = f"Review this pull request and find problems:\n{diff}"`, и baseline его не нашёл вовсе, подменив другой угрозой (prompt injection).
- Что не входит в задачу: автоматический approve или merge; изменение кода помощником; проверка правил, не относящихся к рассматриваемому diff (`snake_case` для таблиц БД, i18n для frontend-строк); аутентификация и rate limiting эндпоинта, потому что в правилах репозитория их нет и без данных о нагрузке требования к ним не сформулировать.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля рисков с evidence: элементов ответа, содержащих `file`, `line` и дословную строку diff | 0 из 7 (`P1-01`) | не менее 100% элементов `risks` | на каждом контролируемом запуске с фиксированным diff | ответы `P1-01`, `P1-02` в [`prompts.md`](prompts.md) |
| Доля рисков, подтверждённых правилом репозитория: элементов, в тексте которых назван ID из `SEC-1`…`OBS-1` | 2 из 7 частично, ни одного с явным ID (`P1-01`) | не менее 100% элементов `risks` | там же | ответы `P1-01`, `P1-02` |
| Покрытие правил: сколько из пяти нарушаемых этим diff правил названо в ответе | 0 из 5 названо явно, 2 из 5 задето косвенно (`P1-01`) | не менее 3 из 5 при лимите `OUT-1` в три риска | там же | ручная сверка ответа с [`CASE.md`](CASE.md) |
| Доля ответов, соответствующих контракту `OUT-1`: валидный JSON с `summary`, `risks` ≤ 3, `checks` | 0 из 1 (`P1-01`, свободная проза) | 100% ответов | там же | ответы `P1-01`, `P1-02` |
| Число утверждений, не опирающихся ни на одно правило репозитория | 5 из 7 (`P1-01`), из них 3 недоказуемы по diff | не более 0 при трёх рисках | там же | колонка «Что отклонили» в [`prompts.md`](prompts.md) |
| Число секретов, ушедших во внешний LLM: срабатываний правила `SEC-1` на тестовом diff с подставленным токеном | не замерялось, сервис в текущем виде передаёт diff как есть | 0 | при прогоне unit-проверки из [`tests_unit.md`](tests_unit.md) | результат проверки на diff с тестовым токеном |

Знаменатель в метрике покрытия равен пяти, а не семи правилам Context Pack. `QA-1` описывает, каким должен быть ответ помощника, и проверяется по ответу, а не по коду. `SCOPE-1` этим diff не нарушен: сервис только возвращает текст и в GitHub не ходит, найти его нарушенным нельзя. Остаются пять правил, которые код действительно нарушает: `SEC-1` (строка 14), `REL-1` (15), `OUT-1` (16), `API-1` (проверки длины нет) и `OBS-1` (логирования нет вовсе).

Первые пять метрик снимаются с ответа помощника и отвечают на вопрос «можно ли доверять результату». Шестая снимается с самого сервиса и отвечает на вопрос «безопасно ли его вообще запускать».

## Почему изменение метрики подтвердит решение проблемы

Проблема в том, что ответ помощника нельзя проверить, не перечитав diff, а значит он не экономит ревьюеру ничего. Первые две метрики измеряют это напрямую: если у каждого риска есть номер строки, дословная цитата и ID нарушенного правила, ревьюер проверяет утверждение за одно обращение к diff вместо полного прочтения. Пятая метрика закрывает обратную сторону: помощник, который выдаёт правдоподобные, но не привязанные к правилам замечания, увеличивает нагрузку на ревьюера, а не снижает её, поэтому число таких утверждений должно падать одновременно с ростом первых двух.

Третья и четвёртая метрики нужны, чтобы первые две нельзя было улучшить вырождением: ответ из одного тривиального риска с идеальным evidence даст 100% по доле, но пропустит нарушения. Покрытие правил и соответствие контракту `OUT-1` фиксируют, что помощник смотрит на весь набор применимых правил и укладывается в лимит трёх рисков осмысленно, а не случайно.

Шестая метрика проверяет не качество ответа, а само право сервиса работать: пока `SEC-1` нарушается, любые улучшения ревью бессмысленны, потому что каждый вызов утекает содержимое diff во внешний LLM.

Сравнение `P1-01` и `P1-02` на одном diff и одной модели показывает, что все пять метрик ответа сдвигаются от состава входного контекста, а не от формулировки запроса: изменился только Context Pack, инструмент и модель совпадают. Это и есть подтверждение, что решать проблему нужно контрактом и правилами на входе, а не подбором фразы.

## Как использовали AI

- Для чего: получить материал для замера, то есть два ответа на один и тот же diff, различающиеся только составом входного контекста.
- Тип промпта: zero-shot (`P1-01`) и master prompt с Context Pack (`P1-02`).
- Строка в [`prompts.md`](prompts.md): `P1-01`, `P1-02`.
- Что проверили и исправили сами: посчитали значения метрик вручную по тексту обоих ответов, а не со слов модели. Из `P1-01` разобрали 7 пунктов и развели их по трём корзинам. На правила репозитория ложатся два: отсутствие ограничения размера diff (`API-1`) и отсутствие обработки ошибок вызова LLM (`REL-1`), оба без порога и без значения таймаута. Три недоказуемы по diff: блокировка event loop (`llm.generate` объявлен как `Protocol` без тела, блокирующий I/O не показан), отсутствие аутентификации и rate limiting (таких правил в репозитории нет), prompt injection в формулировке «модель это выполнит» (поведение модели по диффу не проверяется). Ещё два доказуемы по diff, но не покрыты ни одним правилом: `KeyError` на `payload["diff"]` и отсутствие схемы у ответа; по `QA-1` они в `risks` всё равно не попадают. Целевое значение по покрытию правил поставили 3 из 5, а не 5 из 5, потому что `OUT-1` ограничивает ответ тремя рисками, и требовать большего значит требовать нарушения собственного контракта.
