# Проблема и метрики

## Проблема

- Пользователь: разработчик и/или CI‑бот, отправляющий дифф PR для автоматического ревью — явно отмечено как допущение в [context.md](context.md) («Кто им пользуется? … Допущение»).
- Ситуация: нужно программно получить комментарий по диффу через HTTP API сервиса.
- Что происходит сейчас:
  - Вход не валидируется: в [app/api.py:36–37](TRAINING_PR.diff) обработчик читает `payload["diff"]` из произвольного `dict`. При отсутствии ключа возникает `KeyError` и 500 Internal Server Error вместо 422 Unprocessable Entity.
  - Нет ограничений размера входа и кода ответа 413 — нарушение правила `API-1` ([CASE.md](CASE.md)).
  - Вызов внешнего LLM синхронный, без таймаута и обработки ошибок — нарушение `REL-1` (таймаут 10 секунд и контролируемый ответ); может блокировать воркер ([context.md](context.md): «обработчик API синхронный (def)»).
  - Дифф отправляется в LLM как есть ([app/review_service.py:20–22](TRAINING_PR.diff)), без редактирования секретов — нарушение `SEC-1`.
  - Формат ответа не соответствует `OUT-1`: сейчас возвращается `{"comment": str}` ([app/review_service.py:19–22](TRAINING_PR.diff)), тогда как требуется `summary`, массив `risks` (≤ 3 с полями `file`, `line`, `evidence`, `risk`) и массив `checks`.
  - Из‑за отсутствия структуры `OUT-1` невозможно соблюсти `QA-1` (риск включается в ответ только при подтверждении строкой diff или правилом репозитория).
- Почему это мешает пользователю или бизнесу (аналитический вывод автора, не дословная цитата источника): нестабильность контракта (5xx вместо предсказуемых 4xx) снижает DX при интеграции в CI; отсутствие маскирования секретов создаёт риск их утечки во внешний LLM; несоответствие `OUT-1` не позволяет автоматически интерпретировать ответ.
- Что не входит в задачу:
  - Помощник только советует и не пишет код / не выполняет действия в GitHub — прямо зафиксировано `SCOPE-1` ([CASE.md](CASE.md)).
  - UI, хранение результатов, троттлинг/квоты, аутентификация/авторизация — в приложенном diff и CASE.md не описаны и не проверялись; считаем вне рамок этого diff, а не формально исключёнными правилом.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля 5xx по POST /api/reviews | Есть 5xx при отсутствии `diff` из‑за `KeyError` ([app/api.py:36–37](TRAINING_PR.diff)) | < 0.5% (ошибки клиента отдаются как 4xx) | Непрерывно, по релизу | Логи/метрики API |
| Валидация входа (422 вместо 500) | Интеграционный тест: тело `{}` должно вернуть 422 со схемной ошибкой | 100% некорректных запросов → 422 | Перед релизом и в проде | Интеграционные тесты, логи |
| Соблюдение `OUT-1` (валидность ответа) | Контрактный тест: ответ содержит `summary`, `risks` (≤3 с `file/line/evidence/risk`), `checks`; сейчас 0% (возвращается `{"comment": str}`) | 100% ответов соответствуют `OUT-1` | Перед релизом и в CI | Схемные/контрактные тесты |
| Соблюдение `API-1` (лимит 20 000 символов, 413) | Интеграционный тест: при `len(diff) > 20000` возвращается 413; сейчас лимит отсутствует | 100% запросов с diff > 20 000 → 413 | Перед релизом и в проде | Интеграционные тесты, логи |
| `REL-1`: P95 латентность /api/reviews | Замер на стенде при типичном диффе; сейчас нет таймаута | P95 ≤ 10s (в пределах SLO LLM) | Непрерывно | APM, трейсинг |
| `REL-1`: обработка таймаутов LLM | Тест с заглушкой LLM (>10s): ответ ≤10s с контролируемой ошибкой | 100% таймаутов → контролируемый ответ | Перед релизом и в CI | Интеграционные тесты |
| `SEC-1`: маскирование секретов в prompt | Инжекционный тест: в diff добавить `token=...`; в отправляемом в LLM prompt секрет заменён на `[REDACTED]` | 100% обнаруженных секретов маскируются | Перед релизом и в CI | Интеграционные тесты |
| `OBS-1`: состав логов | Выборочная проверка логов: только `request_id`, длительность, статус; без содержимого diff/ответа | 100% записей соответствуют `OBS-1` | В проде, периодически | Логи |

## Почему изменение метрики подтвердит решение проблемы

- Снижение доли 5xx и возврат 422 на неверный ввод подтверждают предсказуемый контракт ошибок и улучшение DX.
- Соответствие `OUT-1` гарантирует пригодность ответа для автоматической интерпретации (`summary`/`risks`/`checks`) и соблюдение `QA-1`.
- Применение `API-1` (413 при >20 000 символов) предотвращает злоупотребления и неконтролируемые расходы на LLM.
- Выполнение `REL-1` (P95 ≤ 10s и контролируемая ошибка при таймауте) подтверждает, что сервис не блокируется и выдерживает SLO.
- Маскирование секретов по `SEC-1` снижает риск утечки чувствительных данных.
- Соблюдение `OBS-1` исключает логирование чувствительного содержимого и упрощает аудит.

## Открытые вопросы

- Логирование и `OBS-1`: приложенный diff показывает только `app/review_service.py` и `app/api.py`, ни в одном из них нет вызовов логирования — но diff не доказывает отсутствие логирования во всём сервисе (возможен код вне diff). Нельзя утверждать нарушение `OBS-1` без просмотра остального кода.
- Формат «контролируемого ответа» при таймауте LLM по `REL-1`: статус-код и тело (связан ли с `OUT-1` или отдельным error-форматом).
- Перечень и способ маскирования секретов по `SEC-1` (паттерны, допустимые заменители).
- Точный формат логов по `OBS-1`: единица измерения длительности, представление статуса.

## Как использовали AI

- Для чего: (1) baseline‑генерация комментария по диффу PR; (2) критика и переработка этого файла — привязка проблемы и метрик к конкретным строкам diff и правилам из [`CASE.md`](CASE.md); (3) построчная ReAct-верификация каждого утверждения раздела «Проблема» и каждой строки таблицы «Метрики» против diff/CASE.md/context.md.
- Тип промпта: (1) zero‑shot — P1-01; (2) RCTF (Role–Context–Task–Format) через OpenCode (`agent: plan`, модель `openrouter/openai/gpt-5`) — P1-03; (3) ReAct (Thought/Action/Observation/Conclusion на каждый пункт) через OpenCode (те же agent/модель) — P1-04.
- Строка в [`prompts.md`](prompts.md): записи P1-01 (baseline), P1-03 (RCTF) и P1-04 (ReAct-верификация); полные тексты промптов — в разделах «RCTF prompt для problem.md (P1-03)» и «ReAct prompt для problem.md (P1-04)».
- Что проверили и исправили сами: сверили все ссылки на строки (`app/api.py:36–37`, `app/review_service.py:19–22`, `20–22`) с [`TRAINING_PR.diff`](TRAINING_PR.diff); в ReAct-проходе модель сама предложила заменить `36–37` на `35–37` — перепроверили построчно (`nl -ba TRAINING_PR.diff`) и **отклонили** эту правку как ошибочную (строка 35 — декоратор `@app.post`, не относится к причине `KeyError`); приняли обоснованную находку модели о недостаточности доказательств для утверждения об отсутствии логирования (`OBS-1`) — перенесли в «Открытые вопросы» вместо категоричного утверждения в «Проблеме»; проверили, что каждое упомянутое правило (`SEC-1/API-1/REL-1/OUT-1/QA-1/OBS-1`) действительно определено в [`CASE.md`](CASE.md).
