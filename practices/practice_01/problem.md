# Проблема и метрики

## Проблема

- Пользователь: Разработчик/ревьюер, вызывающий API для автоматического ревью PR по diff.
- Ситуация: В сервисе нет валидации входа и обработки ошибок LLM, а также нет защиты от prompt‑injection. Ответ LLM возвращается клиенту «как есть».
- Что происходит сейчас: При отсутствии поля `diff` или при исключении в LLM API отвечает 500; произвольные инструкции в diff могут повлиять на промпт и итоговый комментарий.
- Почему это мешает пользователю или бизнесу: Нестабильность и небезопасность автоматического ревью — ложные/уязвимые ответы, неожиданные 500, отсутствие воспроизводимой валидации входов.
- Что не входит в задачу: Аутентификация/авторизация, ограничение токенов/квот, интеграции с SCM.

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля запросов 4xx/5xx при некорректном теле | Отправка `{}` → 500 (KeyError) | 422 вместо 500 | До/после фикса | Интеграционный тест API |
| Доля необработанных исключений LLM | Искусственная ошибка в `llm.generate` → 500 | 502/504 с контролируемым сообщением | До/после | Юнит/интеграционный тест ReviewService |
| Воспроизводимость ответа при злонамеренном diff | Diff с инструкцией меняет поведение промпта | Нейтрализация/фильтрация или явное ограничение | После внедрения пост‑обработки | E2E тест с инъекцией |

## Почему изменение метрики подтвердит решение проблемы

- Переход 500 → 422 на неверный ввод подтверждает корректную валидацию.
- Контролируемый ответ на сбои LLM снижает риск падений и улучшает UX.
- Нейтрализация эффектов prompt‑injection повышает надёжность выдачи.

## Как использовали AI

- Для чего: Формулировка проблемы, подбор метрик и сценариев проверки.
- Тип промпта: zero‑shot.
- Строка в [`prompts.md`](prompts.md): P1‑01.
- Что проверили и исправили сами: Пересмотр метрик на измеримость и воспроизводимость в локальном окружении.
