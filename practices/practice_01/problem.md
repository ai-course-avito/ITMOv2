# Проблема и метрики

## Проблема

- **Пользователь**: Backend-разработчики и code reviewers, которые отправляют PR на AI-ревью
- **Ситуация**: PR добавляет эндпоинт `POST /api/reviews` и метод `ReviewService.review`, но diff содержит 5 нарушений репозиторных правил (SEC-1, API-1, REL-1, OUT-1, OBS-1) и не имеет базовой валидации входа и обработки ошибок
- **Что происходит сейчас**: diff передаётся в LLM без очистки секретов, без лимита размера, без таймаута (app/review_service.py:20-21); результат возвращается как сырой текст `{"comment": answer}` (app/review_service.py:16), не соответствуя OUT-1; входной `payload["diff"]` не валидируется (app/api.py:36-37)
- **Почему это мешает**: нарушение SEC-1 — утечка токенов/паролей в LLM; нарушение API-1 и REL-1 — зависание и 500 вместо контролируемого ответа; нарушение OUT-1 — ответ не пригоден для автоматической обработки; отсутствие OBS-1 — невозможность мониторить и отлаживать
- **Что не входит в задачу**: написание новых фич, реализация аутентификации, интеграция с GitHub API (только выявление проблемы и описание требований)

## Метрики

| Метрика | Текущее значение | Целевое изменение | Когда измеряем | Источник данных |
|---|---|---|---|---|
| Количество нарушений репозиторных правил (SEC-1, API-1, REL-1, OUT-1, OBS-1) | 5 из 5 | 0 | После исправления | Code review, grep по TRAINING_PR.diff |
| Количество точек входа без валидации | 1 (payload["diff"], app/api.py:37) | 0 | После исправления | Линтер + code review |
| Доля ответов, соответствующих OUT-1 (summary + risks + checks) | 0 % | 100 % | После исправления | Unit-тест ReviewService.review (tests_unit.md) |
| Количество необработанных исключений LLM | ≥1 (app/review_service.py:21) | 0 | После исправления | tests_unit.md, tests_e2e.md |
| Количество полей логирования, соответствующих OBS-1 | 0 (нет логирования) | = 3 (request_id, duration, status) | После исправления | tests_unit.md |

## Почему изменение метрики подтвердит решение проблемы

Если после исправления: (1) **нарушений правил 0 из 5** — значит найденные проблемы устранены; (2) **валидация входа есть** — `KeyError` заменяется на 422; (3) **ответ 100 % соответствует OUT-1** — его можно парсить автоматически; (4) **исключений LLM 0** — сервис не падает при сбоях LLM; (5) **логирование = 3 поля** — можно мониторить без утечки данных. Каждая метрика измерима и проверяется в тестах из разделов tests_*.md.

## Как использовали AI

- Для чего: формулировка измеримых метрик и проверка связи проблемы с правилами репозитория
- Тип промпта: zero-shot (P1-01), затем уточнение с master prompt (P1-02)
- Строка в `prompts.md`: P1-01, P1-02
- Что проверили и исправили сами: пересчитали количество нарушений правил по CASE.md, сверили с TRAINING_PR.diff
