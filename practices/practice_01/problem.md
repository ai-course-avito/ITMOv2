# Проблема и метрики

## Проблема

- Пользователь: внутренний клиент сервиса ревью (отправляет diff на анализ).
- Ситуация: клиент вызывает POST `/api/reviews` веб‑API, передавая diff pull request.
- Что происходит сейчас: обработчик ожидает наличие ключа `diff` и обращается к `payload["diff"]` напрямую; при отсутствии ключа произойдёт KeyError и вероятный HTTP 500 вместо контролируемой ошибки 4xx.
- Почему это мешает пользователю или бизнесу: нестабильность API и плохой DX — ошибки клиента (пустое тело/неверный формат) превращаются в 500, затрудняя интеграцию.
- Что не входит в задачу: детали реализации `app.dependencies.review_service` и конкретная модель LLM (в diff не представлены).

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля 5xx на POST `/api/reviews` при валидном и невалидном теле | Текущая неизвестна; воспроизводимо, что `{}` вызовет KeyError | Снижение до 0% для клиентских ошибок (должны быть 4xx) | На интеграционных тестах и в логах | Логи сервиса, тест-кейсы практики |
| Наличие валидации входа (тест на отсутствие `diff`) | Отсутствует | Появился тест, проходит | При CI прогоне | tests_integration.md |

## Почему изменение метрики подтвердит решение проблемы

Снижение 5xx при клиентских ошибках и появление явной валидации входа покажут, что API устойчиво обрабатывает неверные запросы и возвращает корректный класс ошибок, не обрушивая сервис.
