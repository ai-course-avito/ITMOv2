# Проблема и метрики

## Проблема

- **Пользователь:** инженер-ревьюер, который проверяет Pull Request перед слиянием.
- **Ситуация:** ревьюер открывает diff и вручную ищет проблемы безопасности, архитектурные риски и нарушения правил проекта.
- **Что происходит сейчас:** ревьюер тратит значительное время на первичный просмотр diff; при большом объёме изменений часть проблем (особенно security-риски) пропускается.
- **Почему это мешает пользователю или бизнесу:** пропущенные уязвимости (например, утечка секретов через `SEC-1`) и неконтролируемые LLM-вызовы (`REL-1`) попадают в production, что ведёт к инцидентам и ручным откатам.
- **Что не входит в задачу:** автоматический approve/merge, написание кода вместо ревьюера, ревью файлов за пределами переданного diff.

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля PR с пропущенным нарушением `SEC-1` (секреты в LLM-промпте) | не измеряется (нет инструмента) | 0% нарушений на PR, проверенных сервисом | после внедрения сервиса, на каждом PR | лог `request_id` + audit diff |
| Доля LLM-вызовов без timeout, вернувших 500 | не измеряется | < 1% (остальное — контролируемый ответ по `REL-1`) | после внедрения сервиса | метрики `app/api.py` |
| Среднее время первичного ревью одного PR | ~N минут (нет исторических данных) | снизить на 30% за счёт автоматического первичного анализа | спринт после запуска | данные GitHub / трекер задач |

## Почему изменение метрики подтвердит решение проблемы

Сервис вмешивается именно в ту точку, где возникают пропуски: он проверяет diff до того, как ревьюер начинает работу. Если доля нарушений `SEC-1` падает до нуля, значит, автоматическая проверка обнаруживает их раньше человека. Если доля неуправляемых 500-ошибок снижается до целевого значения — правило `REL-1` работает корректно. Если среднее время ревью сокращается — ревьюер тратит меньше времени на поиск очевидных проблем и сосредотачивается на содержательных вопросах.

## Как использовали AI

- Для чего: выявление проблем в diff через zero-shot запрос (P1-01) для формулировки реальной проблемы ревьюера.
- Тип промпта: zero-shot (P1-01).
- Строка в [`prompts.md`](prompts.md): P1-01.
- Что проверили и исправили сами: метрики сформулированы на основе правил из `CASE.md` (`SEC-1`, `REL-1`, `OUT-1`), проверены на соответствие содержимому diff; претензии без подтверждения строками diff не включались.
