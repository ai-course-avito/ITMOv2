# Проблема и метрики

## Проблема

- Пользователь: ревьюер/разработчик, использует сервис для анализа PR по diff.
- Ситуация: отправляет diff в POST /api/reviews и ожидает структурированный ответ по правилам репозитория.
- Что происходит сейчас: текущая реализация из TRAINING_PR.diff отправляет diff во внешний LLM без удаления секретов, не ограничивает размер diff, не применяет таймаут/контролируемую обработку ошибок LLM и возвращает нестандартный ответ {"comment": "..."}. Также отсутствует валидация входа (возможен KeyError при отсутствии поля diff).
- Почему это мешает пользователю или бизнесу: нарушаются правила SEC-1, API-1, REL-1, OUT-1, что ведет к риску утечки секретов, нестабильной работе (500 при ошибках), невозможности интеграции из-за несоответствия формату и отсутствию предсказуемых ошибок (413/контролируемые ответы). Ревью-пайплайн становится ненадежным и нефункциональным для потребителей API.
- Что не входит в задачу: внедрение аутентификации и rate limiting (не определено в CASE.md), изменения вне соблюдения правил SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1; любые действия в GitHub и изменения бизнес-процессов.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов, соответствующих OUT-1 (summary, <=3 risks, checks) | 0% (сейчас ответ {"comment": ...}; проверка контрактом) | 100% | Тесты CI на каждый коммит; периодическая выборка в runtime | Автотесты контракта, интеграционные тесты |
| Доля отклонений 413 при diff > 20000 символов (API-1) | 0% (нет проверки длины) | 100% | Интеграционные тесты; метрики API | Тесты, access logs/APM |
| Доля таймаутов/ошибок LLM, превращенных в контролируемый ответ за <=10 с (REL-1) | 0% (нет таймаута/обработки) | 100% | Юнит/интеграционные тесты с моками; runtime метрики | Тесты, логи ошибок/метрики |
| Доля редактирования секретов перед отправкой в LLM (SEC-1) | 0% (diff отправляется как есть) | 100% | Тесты на редактирование; периодические проверки | Тесты prompt-пайплайна |
| Доля 5xx по /api/reviews из-за невалидного payload | >0% (KeyError при отсутствии diff) | 0% | Мониторинг прод; интеграционные тесты | Логи/метрики сервиса |

## Почему изменение метрики подтвердит решение проблемы

Достижение 100% соответствия OUT-1 подтверждает, что потребители API получают ожидаемый формат и могут автоматизировать обработку результатов. Полное соблюдение API-1 (413 на большие diff) защищает ресурсные лимиты и предсказуемость поведения. Выполнение REL-1 устраняет неконтролируемые 500 и повышает надежность сервиса. Выполнение SEC-1 снижает риск утечки секретов при работе с внешним LLM. Снижение 5xx по валидации входа до 0% подтверждает корректную обработку пользовательских ошибок и повышает DX.

## Как использовали AI

- Для чего: сформулировать проблему и метрики на основе context.md, CASE.md и TRAINING_PR.diff.
- Тип промпта: problem statement / metrics.
- Строка в [`prompts.md`](prompts.md): P1-04.
- Что проверили и исправили сами: подтвердили несоответствия правилам SEC-1, API-1, REL-1, OUT-1 по строкам diff; соотнесли метрики с правилами и текущим поведением; исключили нерелевантные правила.
