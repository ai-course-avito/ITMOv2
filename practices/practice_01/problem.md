# Проблема и метрики

## Проблема

- Пользователь: ревьюер PR.
- Ситуация: получает diff и должен найти проблемы безопасности и надёжности.
- Что происходит сейчас: diff уходит во внешний LLM без маскирования секретов, без ограничения длины, без таймаута; ответ не соответствует контракту OUT-1.
- Почему это мешает пользователю или бизнесу: утечка секретов, зависания, неконтролируемые ошибки, несовместимый формат ответа.
- Что не входит в задачу: изменение кода PR, approve/merge, действия в GitHub (SCOPE-1).

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замер | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля диффов с секретами, ушедших во внешний LLM | Замер: тест с `token=TEST_SECRET` в diff; сейчас сырой дифф уходит в `self.llm.generate(prompt)` (`review_service.py:15–16`) | 0 % | На каждом PR-ревью и в CI | Тест unit `SEC-1` из `tests_unit.md` |
| Доля запросов, завершившихся за ≤ 10 с при медленном LLM | Замер: подставить LLM с задержкой > 10 с; сейчас в `review_service.py:16` нет таймаута | 100 % контролируемых ответов; без зависаний | На каждом релизе и в CI | Тест integration `REL-1` из `tests_integration.md` |
| Соответствие ответа контракту `summary/risks/checks` | Замер: ручная проверка полей ответа `POST /api/reviews`; сейчас возвращается `{"comment": ...}` (`review_service.py:17`, `api.py:9`) | 100 % полей присутствуют, `risks` ≤ 3 | На каждом PR-ревью и в CI | Тест E2E `OUT-1` из `tests_e2e.md` |
| Доля диффов длиннее 20 000 символов, принятых сервисом | Замер: отправить diff > 20 000 символов; сейчас в `api.py:9` нет проверки длины и нет ответа 413 | 0 %; сервис возвращает HTTP 413 без вызова LLM | На каждом PR-ревью и в CI | Тест API `API-1` из `tests_integration.md` |
| Доля запросов с невалидным телом, дающих 5xx | Замер: `POST /api/reviews` без `diff`; сейчас `payload["diff"]` даст `KeyError` → 500 | 0 %; невалидный вход → 400/422 | На каждом PR-ревью | Тест E2E негативный сценарий |

## Почему изменение метрики подтвердит решение проблемы

Каждая метрика привязана к конкретному риску из `P1_02.md`:

- **SEC-1** закрывается, когда тест `token=TEST_SECRET` больше не находит секрет в промпте, отправленном в LLM. Это прямой, воспроизводимый замер утечки.
- **REL-1** закрывается, когда тест с медленным LLM (sleep > 10 с) получает ответ ≤ 10 с. Замер отделяет контролируемый ответ от зависания.
- **OUT-1** закрывается, когда ответ `POST /api/reviews` содержит `summary/risks/checks`. Замер не зависит от содержания — только от структуры.
- **API-1** закрывается, когда дифф > 20 000 символов возвращает HTTP 413 без вызова LLM. Замер показывает, что предел входа соблюдается на границе API.
- **Валидация тела** закрывается, когда запрос без `diff` возвращает 4xx, а не 5xx. Замер показывает, что сервис не падает на невалидном входе.

Если хотя бы одна метрика остаётся в текущем значении — соответствующее требование `SEC-1…OUT-1` не выполнено, и решение проблемы не достигнуто.


## Как использовали AI

- Для чего: собрать доказательный список проблем учебного PR и измеримые метрики, подтверждающие их закрытие.
- Тип промпта: master prompt (см. `master_prompt.md`).
- Строка в [`prompts.md`](prompts.md): P1-02.
- Что проверили и исправили сами: сопоставили каждый риск из `P1_02.md` с реальными строками `TRAINING_PR.diff` (`review_service.py:15–17`, `api.py:9`); перенесли приоритеты из «Блока для problem.md»; отклонили нерелевантные замечания zero-shot (Python 3.8, rate limiting) как выходящие за scope практики.
