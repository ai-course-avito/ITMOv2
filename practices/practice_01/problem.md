# Проблема и метрики

## Проблема

- Пользователь: ревьюер PR — получает от сервиса `summary`, до трёх `risks` и список `checks`, сам принимает решение по PR (CASE.md, раздел «Задача помощника»).
- Ситуация: ревьюеру нужно за ограниченное время оценить diff, найти реальные риски (безопасность, надёжность, соответствие правилам репозитория) и решить, какие проверки запустить перед решением по PR.
- Что происходит сейчас: ревьюер вручную читает diff в GitHub и ищет проблемы по памяти без чек-листа; при команде из 5 разработчиков и 10–15 PR в неделю первый комментарий ревьюера обычно появляется через 3–6 часов после открытия PR (допущение).
- Почему это мешает пользователю или бизнесу: без структурированного и подтверждённого набора рисков (`OUT-1`, `QA-1`) ревьюер тратит время на поиск проблем вручную и рискует пропустить нарушение правил репозитория (например, утечку секретов при отправке diff во внешний LLM — `SEC-1`) либо получить неподтверждённые, недоказуемые замечания, которым нельзя доверять.
- Что не входит в задачу: сервис не принимает решение по PR, не делает approve, merge и не меняет код — решение всегда остаётся за человеком (`SCOPE-1`).

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Время от открытия PR до первого комментария ревьюера | 3–6 часов на PR среднего размера (допущение для команды из 5 разработчиков, 10–15 PR в неделю) | автоматический разбор рисков — в течение 10 сек после открытия PR (`REL-1`); первый комментарий ревьюера — сократить с 3–6 до 1–2 часов, так как ревьюер получает готовый список рисков вместо чтения всего diff (допущение) | еженедельно, по данным GitHub (время открытия PR и время первого комментария) | таймстемпы событий PR в GitHub |
| Время от получения diff до готового ответа сервиса (`summary`, `risks`, `checks`), сек | до внедрения сервиса не измерялось (допущение: аналога нет, так как ответ формирует человек) | не более 10 сек на вызов LLM (таймаут — `REL-1`), при ошибке — контролируемый ответ вместо зависания | на каждый вызов сервиса | лог сервиса: `request_id`, длительность, статус (`OBS-1`) |
| Доля рисков из ответа сервиса, с которыми ревьюер согласился | нет данных, метрика вводится вместе с сервисом (допущение: ориентир на старте — 60–70%, пока ревьюер и модель ещё «притираются» друг к другу) | не менее 80% к третьему месяцу использования | еженедельно, по накопленным ответам ревьюеров | ручная отметка ревьюера «согласен / не согласен» по каждому риску в ответе |
| Доля выдуманных замечаний (риск в ответе не подтверждён строкой diff) | нет данных, метрика вводится вместе с сервисом (допущение: цель — как можно ближе к 0%, так как это прямое нарушение `QA-1`) | не более 5% (по `QA-1` идеал — 0%, допуск оставлен на спорные случаи) | на каждый ответ сервиса, выборочная проверка ревьюером | ручная проверка ответа ревьюером против diff |
| Число нарушений правил репозитория, пропущенных при ревью | до внедрения сервиса не отслеживалось системно; допущение — 1–2 пропуска на 10–15 PR в неделю, обнаруживаемые постфактум (например, на следующем ревью или инциденте) | с 1–2 до не более 1 на 15 PR | ежемесячно, по PR за период | ручной разбор инцидентов и повторных ревью, связанных с пропущенными нарушениями |

## Почему изменение метрики подтвердит решение проблемы

Автоматический разбор рисков в течение 10 сек после открытия PR (`REL-1`) подтверждает, что ревьюер получает предварительный анализ почти сразу, а сокращение времени до первого комментария ревьюера с 3–6 до 1–2 часов показывает, что готовый список рисков действительно ускоряет работу человека, а не существует отдельно от неё. Время ответа сервиса не выше таймаута `REL-1` подтверждает, что эта обратная связь предсказуема по времени независимо от поведения внешнего LLM. Рост доли рисков, с которыми ревьюер согласился, до не менее 80% к третьему месяцу использования показывает, что предложения сервиса действительно полезны, а не игнорируются. Снижение доли выдуманных замечаний до не более 5% подтверждает соблюдение `QA-1`: ревьюер может доверять ответу без повторной сплошной проверки, а оставшийся допуск покрывает только спорные случаи. Снижение числа пропущенных при ревью нарушений правил репозитория с 1–2 до не более 1 на 15 PR показывает, что сервис компенсирует неполноту ручной проверки по памяти, а не просто ускоряет прежний процесс с теми же пробелами.

## Как использовали AI

- Для чего: черновик раздела «Проблема» и таблицы метрик по фактам из CASE.md.
- Тип промпта: master prompt (роль, входы, задача и артефакты, формат, границы, шаги, проверка перед выдачей заданы явно).
- Строка в [`prompts.md`](prompts.md): P1-03 (генерация артефактов master prompt'ом).
- Что проверили и исправили сами: убедились, что все метрики продуктовые и связаны со временем обратной связи, качеством замечаний и полнотой проверки правил репозитория; технических метрик оставили одну (время ответа сервиса); отсутствующие текущие значения заменили на явные допущения с пометкой «(допущение)» для команды из 5 разработчиков и 10–15 PR в неделю вместо TODO; не использовали VTG, IRR, WACC, CSAT.
