# Проблема и метрики

## Проблема

- Пользователь: разработчик, который создаёт PR и ждёт ревью; ревьюер, который принимает решение о merge.
- Ситуация: AI-сервис ревью PR (`app/review_service.py`, `app/api.py`) возвращает только произвольный текстовый комментарий и не соблюдает правила репозитория.
- Что происходит сейчас: diff вставляется во внешний LLM без вычитки секретов (SEC-1 нарушен), нет проверки длины (API-1 нарушен), нет таймаута и контролируемой обработки ошибок (REL-1 нарушен), ответ не соответствует требуемой структуре (OUT-1 нарушен), нет валидации входных данных (KeyError → 500).
- Почему это мешает пользователю или бизнесу: ревью ненадёжно — есть риск утечки токенов/ключей во внешний сервис, сервис падает с HTTP 500 и блокирует воркер при медленном LLM, а результат нельзя использовать для принятия решения (нет рисков/проверок).
- Что не входит в задачу: поиск отдельного GitHub PR, сравнение разных агентов, написание кода или merge.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов, соблюдающих OUT-1 (содержат summary + risks ≤3 + checks) | 0% — сервис возвращает только поле `comment` | 100% | на каждый ответ / ревью | ответ сервиса, PR |
| Время ответа на запрос (p95, timeout 10 сек) | не измеряется; нет таймаута — воркер блокируется | ≤10 сек с контролируемым ответом при ошибке | на каждый запрос | логи request_id/длительность/статус (OBS-1) |
| Доля diff с секретами, уходящими в LLM | 100% — diff вставляется без фильтрации (SEC-1) | 0% | на каждый diff | тест с тестовым token → prompt содержит [REDACTED] |
| Доля запросов с HTTP 500 из-за необработанной ошибки | 100% — нет handling, ошибка LLM → 500 | 0% | на каждый запрос | статус-коды ответов сервиса |

## Почему изменение метрики подтвердит решение проблемы

Если доля ответов с полной структурой OUT-1 достигнет 100%, сервис станет пригоден для решения человека. Если ни один diff с секретами не попадает в LLM (SEC-1) и ошибки LLM превращаются в контролируемые ответы (REL-1), уходит главный риск утечки и падений. Метрики измеряются по правилам OBS-1 (только request_id, длительность, статус) и QA-1 (каждый риск подтверждён diff или правилом).

## Как использовали AI

- Для чего: сформулировать пользователя, проблему и измеримые метрики на основе TRAINING_PR.diff
- Тип промпта: zero-shot (P1-01), master prompt (P1-02)
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02
- Что проверили и исправили сами: метрики привязаны к конкретным правилам SEC-1/REL-1/OUT-1, а не выбраны как абстрактные VTG/CSAT
