# Проблема и метрики

## Пользователи и профиль

### Ревьюер (основной пользователь)

- Старший или ведущий разработчик, ответственный за качество кода и решение о merge.
- Работает с очередью PR под давлением дедлайнов; времени на внимательное чтение каждого diff не хватает.
- Принимает решение на основе замечаний; ему нужны точные ссылки на файл и строку и воспроизводимые проверки, а не «код можно улучшить».

### Разработчик, открывающий PR

- Ждёт быстрого и понятного ревью, хочет получить список конкретных замечаний и расправиться с ними до ревью человеком.
- Не хочет, чтобы его токены/ключи из diff утекали во внешние сервисы.

## Проблема

- **Основная проблема:** ручное ревью долгое и невнимательное — критичные нарушения (секреты в diff, отсутствие обработки ошибок, неверный формат ответа) пропускаются, а замечания в лучшем случае хранятся в голове ревьюера.
- **Почему сервис-помощник сейчас не решает её:** `app/review_service.py` вставляет diff во внешний LLM без вычитки секретов (SEC-1 нарушен), не проверяет длину diff (API-1 нарушен), зовёт LLM синхронно без таймаута и без обработки ошибок (REL-1 нарушен) и возвращает только произвольное поле `comment` вместо структуры `summary` + `risks` + `checks` (OUT-1 нарушен).
- **Что происходит сегодня при попытке использовать сервис:** slow-LLM блокирует воркер и падает с HTTP 500; секреты из diff уходят во внешний LLM; ревьюер получает общий текст без `file:line` и без воспроизводимых проверок.
- **Почему это мешает бизнесу:** риск утечки токенов и ключей; ненадёжный вывод — сервис нельзя использовать для принятия решения о merge; ревьюер тратит время на ручной разбор.
- **Что не входит в задачу:** поиск отдельного GitHub PR, написание кода, merge; сравнение разных агентов между собой.

## Метрики

| Метрика | Текущее значение или способ замера | Целевое значение | Когда измеряем | Источник данных |
|---|---|---|---|---|
| Время ревью одного PR от открытия до решения человека (p95) | нет замеров; сервис отвечает без таймаута и может висеть | заметное сокращение цикла; ответ сервиса p95 ≤ 10 с | после каждого ревью | трекинг PR, логи `request_id`/длительность/статус (OBS-1) |
| Доля ложных срабатываний (замечаний без evidence или правила) | ~100% — сырой ответ LLM не проверяется по QA-1 | ≤ 10% | на каждый ответ | сверка каждого риска со строкой diff или правилом |
| Доля пропущенных критичных нарушений (секреты, 500-ошибки) | высокая — проверки нет, секреты уходят в LLM | 0% по SEC-1/REL-1 | на каждый diff и вызов | тест с тестовым token → в prompt `[REDACTED]`; статус-коды ответов |
| Доля ответов, соблюдающих OUT-1 (`summary` + `risks` ≤3 + `checks`) | 0% — сервис возвращает только `comment` | 100% | на каждый ответ | ответ сервиса, PR |
| Доля запросов с HTTP 500 из-за необработанной ошибки LLM | ~100% — ошибка LLM не перехватывается | 0%; ошибка превращается в контролируемый ответ | на каждый запрос | статус-коды ответов сервиса |

## Почему изменение метрики подтвердит решение проблемы

- Если время ответа сервиса станет предсказуемым (p95 ≤ 10 с при timeout по REL-1) и доля 500-ок упадёт до 0 %, ревью перестанет блокироваться зависшим LLM — это снижает время ревью.
- Если доля рисков без evidence упадёт (QA-1) и каждый риск будет иметь `file:line` + `check`, ревьюер сможет быстро подтверждать или отклонять замечание — это снижает ложные срабатывания и делает вывод пригодным для решения.
- Если ни один diff с секретами не уходит во внешний LLM (SEC-1) — устраняется главный риск утечки.

## Как использовали AI

- Для чего: сформулировать пользователей, проблему и измеримые продуктовые метрики (время ревью, доля ложных срабатываний) на основе TRAINING_PR.diff
- Тип промпта: zero-shot (P1-01), master prompt (P1-02)
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02
- Что проверили и исправили сами: метрики привязаны к конкретным правилам SEC-1/REL-1/OUT-1/QA-1/OBS-1, а не выбраны как абстрактные VTG/CSAT; целевые значения согласованы с таймаутом 10 с и форматом OUT-1
