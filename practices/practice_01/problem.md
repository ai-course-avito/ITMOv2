# Проблема и метрики

## Проблема

- Пользователь: в предоставленных материалах не указан (context.md:10–11). Если роль важна, требуется уточнение — не подтверждено доступными источниками.
- Ситуация: реализован обработчик `POST /api/reviews`, принимающий тело запроса как `dict` (TRAINING_PR.diff:35–37).
- Что происходит сейчас: в обработчике выполняется доступ `payload["diff"]` без проверки наличия ключа (TRAINING_PR.diff:35–37); при отсутствии ключа это может приводить к `KeyError` — факт HTTP-статуса при этом не подтверждён доступными источниками. Метод `ReviewService.review` формирует промпт и вызывает `LLM.generate` синхронно (TRAINING_PR.diff:19–22).
- Почему это мешает пользователю или бизнесу: возможны необработанные исключения и неопределённое поведение API при некорректном теле запроса — не подтверждено доступными источниками, требует согласования формулировки и последствий.
- Что не входит в задачу: идеи по будущим улучшениям (валидация, очереди, защита) — предложенные направления, требуют согласования; не подтверждено доступными источниками.

## Метрики

В этом разделе разделены подтверждённые наблюдения (AS IS), способы проверки и предлагаемые цели (TO BE). Цели помечены как требующие согласования и не содержат неподтверждённых чисел.

### AS IS: подтверждённые наблюдения и источники

- Ошибка при отсутствии `diff`:
  Доступ к `payload["diff"]` без проверки (TRAINING_PR.diff:35–37). Фактический HTTP-статус неизвестен — не подтверждено доступными источниками.

- Обработка некорректного входа:
  Явной схемы запроса/ответа нет в предоставленном diff; поведение при неверном типе/контент-тайпе неизвестно (TRAINING_PR.diff:35–37). Другие источники не подтверждают детали схем.

- Время обработки большого diff:
  Вызов `LLM.generate` синхронный (TRAINING_PR.diff:19–22); таймауты/лимиты в предоставленных источниках не показаны. Фактическая латентность не подтверждена доступными источниками.

- Обработка исключения `LLM.generate`:
  Исключения не оборачиваются в видимых фрагментах (TRAINING_PR.diff:19–22; 35–37); результат на уровне API неизвестен — не подтверждено доступными источниками.

### Как измеряем (будущие проверки)

- Ошибка при отсутствии `diff`:
  Интеграционный тест POST `/api/reviews` с телом `{}`; зафиксировать статус и тело ответа. Статическая проверка подтверждает риск `KeyError`.

- Обработка некорректного входа:
  Набор интеграционных тестов: не-JSON, неверный `Content-Type`, JSON с неверным типом поля `diff`; зафиксировать статусы и сообщения об ошибке.

- Время обработки большого diff:
  Нагрузочные тесты: согласовать диапазон размеров диффа; измерять p50/p95 latency (без фиксации целевых значений на текущем этапе).

- Обработка исключения `LLM.generate`:
  Интеграционный тест с мок-LLM, выбрасывающим исключение; проверить, что ответ контролируемый и без трассировки.

### TO BE: цели (требуют согласования)

- Ошибка при отсутствии `diff`:
  Явная валидация входа и возврат клиентской ошибки с описанием отсутствующего поля. Статус-код согласовать.

- Обработка некорректного входа:
  Ввести схему запроса; при несоответствии — предсказуемая клиентская ошибка. Статусы и формат ошибки согласовать.

- Время обработки большого diff:
  Определить цели по задержке и лимиты размера/таймаута. Численные пороги — предложенный target, требует согласования.

- Обработка исключения `LLM.generate`:
  Контролируемый ответ сервиса без трассировки стека. Конкретная стратегия и статус-коды согласовать.

### Неизвестно/требует согласования

- Роль пользователя сервиса.
- Точные статус-коды и формат ошибок для клиентских случаев.
- Диапазон «больших» diff, численные пороги задержки и SLA — не подтверждено доступными источниками, требуется согласование.
- Требования к Content-Type, типу и максимальному размеру поля `diff`.

## Почему изменение метрики подтвердит решение проблемы

Снижение доли ошибок сервера за счёт валидации входа и предсказуемая клиентская ошибка при некорректном входе демонстрируют, что ошибки пользователя не приводят к падению сервиса. Ограничение времени и размера позволит удерживать задержки в согласованных пределах. Контролируемая обработка исключений LLM повысит надёжность интеграции.
