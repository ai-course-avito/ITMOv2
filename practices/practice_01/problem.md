# Проблема и метрики

## Проблема

- Пользователь: разработчик, открывающий PR в репозитории
- Ситуация: при ревью PR разработчик тратит время на ручной поиск проблем безопасности, архитектурных нарушений и ошибок в коде
- Что происходит сейчас: сервис.review() отправляет raw diff в LLM без валидации, очистки секретов и обработки ошибок. Ответ LLM возвращается как есть без структурирования по правилам OUT-1
- Почему это мешает пользователю или бизнесу: сервис не защищён от инъекций промпта, утечки секретов и падения при недоступности LLM. Результат ревью неструктурирован и не соответствует ожидаемому формату (summary, risks, checks)
- Что не входит в задачу: интеграция с GitHub API, автоматический approve/merge, изменение кода через сервис

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля PR с утечкой секретов через diff | 100% (секреты не фильтруются, SEC-1 не реализован) | 0% (секреты удаляются перед отправкой в LLM) | После реализации SEC-1 | Логи отправки промпта в LLM |
| Среднее время ответа сервиса | Не замеряется (нет timeout, REL-1 не реализован) | ≤ 10 секунд с контролируемым ответом при ошибке | Нагрузочный тест | Метрики FastAPI |
| Доля ответов с соблюдением формата OUT-1 | 0% (возвращается raw текст LLM) | 100% (summary, risks[≤3], checks) | После реализации OUT-1 | Валидация ответа через JSON-схему |
| Количество инцидентов безопасности из-за сервиса | Не отслеживается | 0 | Ежемесячно | Sentry / логи |

## Почему изменение метрики подтвердит решение проблемы

- Снижение утечек секретов подтверждает, что SEC-1 работает и diff очищается
- Соблюдение SLA по времени ответа подтверждает, что REL-1 реализован и timeout работает
- 100% формат ответа подтверждает, что OUT-1 соблюдается и клиент получает предсказуемую структуру
