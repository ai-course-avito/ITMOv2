# Проблема и метрики

## Проблема

- Пользователь: ревьюер PR — получает от сервиса `summary`, до трёх `risks` и список `checks`, сам принимает решение по PR (CASE.md, раздел «Задача помощника»).
- Ситуация: ревьюеру нужно за ограниченное время оценить diff, найти реальные риски (безопасность, надёжность, соответствие правилам репозитория) и решить, какие проверки запустить перед решением по PR.
- Что происходит сейчас: ревьюер вручную читает diff в GitHub и ищет проблемы по памяти без чек-листа; при команде из 5 разработчиков и 10–15 PR в неделю первый комментарий ревьюера обычно появляется через 3–6 часов после открытия PR (допущение: числа нет в CASE.md, описание AS IS реконструировано в analysis.md — см. rag/experiment.md).
- Почему это мешает пользователю или бизнесу: без структурированного и подтверждённого набора рисков (`OUT-1`, `QA-1`) ревьюер тратит время на поиск проблем вручную и рискует пропустить нарушение правил репозитория (например, утечку секретов при отправке diff во внешний LLM — `SEC-1`) либо получить неподтверждённые, недоказуемые замечания, которым нельзя доверять.
- Что не входит в задачу: сервис не принимает решение по PR, не делает approve, merge и не меняет код — решение всегда остаётся за человеком (`SCOPE-1`).

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Время от открытия PR до первого комментария ревьюера | базовая линия снимается по таймстемпам GitHub (открытие PR → первый комментарий) до подключения сервиса; текущая оценка 3–6 часов (допущение) | сократить с 3–6 до 1–2 часов при условии автоматического разбора рисков в течение 10 сек (`REL-1`); число 1–2 часа — допущение: в adr.md его нет, там формулировка качественная | при каждом открытии PR и появлении первого комментария | таймстемпы событий PR в GitHub |
| Время от получения diff до готового ответа сервиса (`summary`, `risks`, `checks`), сек | базовая линия снимается первым прогоном регрессионного набора из 30 учебных diff (включая `TRAINING_PR.diff`) после развёртывания | не более 10 сек на вызов — таймаут `REL-1`; при ошибке контролируемый ответ вместо зависания | на каждом вызове сервиса, начиная с первого прогона набора | лог сервиса: `request_id`, длительность, статус (`OBS-1`) |
| Доля рисков из ответа сервиса, с которыми ревьюер согласился | до появления продовых данных используется прокси: доля рисков, совпавших с размеченными ожидаемыми рисками набора из 30 diff (`adr.md`, «Как проверим риск»). Прокси не равна согласию живого ревьюера | не менее 80% к третьему прогону расширенного набора после доработки фильтра `QA-1` (число 80% — допущение, не выведено из `CASE.md` и `adr.md`) | на каждом прогоне регрессионного набора, включая повторные после доработки `QA-1` | механизм отсутствует: пометка ревьюера «согласен / не согласен» нигде не хранится, так как по `OBS-1` в лог пишутся только `request_id`, длительность и статус. Ни один инкремент project_management.md такого хранилища не создаёт, поэтому измерять метрику пока нечем. Выбранный способ (tree_of_thoughts/experiment.md) — внешний журнал отметок ревьюера вне сервиса, сверяемый по request_id |
| Доля выдуманных замечаний (риск в ответе не подтверждён строкой diff) | базовая линия снимается первым прогоном регрессионного набора из 30 учебных diff (`adr.md`, «Как проверим риск») | не более 1 неподтверждённого риска на 30 прогонов (~3%) — порог согласован с `adr.md`, раздел «Как проверим риск» | на каждом прогоне набора, включая повторные при превышении порога | отчёт прогона: для каждого риска проверяется наличие указанных `file` и `line` в исходном diff |
| Число нарушений правил репозитория, пропущенных при ревью | считаются нарушения, отмеченные в разметке набора из 30 diff, но не попавшие в `risks` ответа сервиса | не более 1 пропущенного нарушения на 30 diff (допущение: собственный порог; в adr.md порог задан только для неподтверждённых рисков и требует отдельного согласования перед использованием как критерий приёмки) | на каждом прогоне регрессионного набора | механизм отсутствует: шаг сравнения «размеченные ожидаемые риски против фактических `risks`» в процедуре прогона не описан. Нужно добавить его в проверку набора; ни один инкремент project_management.md не создаёт этот шаг сравнения — нужно добавить его как отдельную задачу до начала измерения метрики |

## Почему изменение метрики подтвердит решение проблемы

Сокращение времени от открытия PR до первого комментария ревьюера с 3–6 до 1–2 часов подтверждает, что автоматический разбор рисков в течение 10 сек (`REL-1`) действительно ускоряет работу ревьюера, а не существует отдельно от неё. Источник данных — таймстемпы событий PR в GitHub, поэтому достижение порога проверяется по объективным меткам времени, а не по субъективной оценке.

Удержание времени от получения diff до готового ответа сервиса не более 10 сек на вызов подтверждает соблюдение таймаута `REL-1`: обратная связь ревьюеру предсказуема по времени независимо от поведения внешнего LLM, а при сбое сервис выдаёт контролируемый ответ вместо зависания. Источник — лог сервиса (`request_id`, длительность, статус, `OBS-1`), то есть порог проверяется по факту на каждом вызове, начиная с первого прогона регрессионного набора.

Рост доли рисков, с которыми ревьюер согласился, до не менее 80% к третьему прогону расширенного набора должен показывать, что предложения сервиса после доработки фильтра `QA-1` совпадают с ожиданиями ревьюера, а не игнорируются. Однако источник данных для этой метрики помечен как «механизм отсутствует»: пометка ревьюера «согласен / не согласен» нигде не хранится, поэтому до появления отдельного хранилища таких отметок эта метрика не может подтвердить решение проблемы — доступен только прокси-показатель совпадения с разметкой набора, а не согласие живого ревьюера.

Снижение доли выдуманных замечаний до не более 1 неподтверждённого риска на 30 прогонов (~3%) подтверждает соблюдение `QA-1`: порог задаёт требуемый уровень подтверждённости рисков. Порог согласован с adr.md, а источником служит отчёт прогона, в котором для каждого риска проверяется наличие указанных `file` и `line` в исходном diff, что делает проверку порога воспроизводимой на каждом прогоне регрессионного набора.

Снижение числа нарушений правил репозитория, пропущенных при ревью, до не более 1 пропущенного нарушения на 30 diff должно показывать, что сервис компенсирует неполноту ручной проверки по памяти, а не просто ускоряет прежний процесс с теми же пробелами. Но источник данных для этой метрики тоже помечен как «механизм отсутствует»: шаг сравнения размеченных ожидаемых рисков с фактическими `risks` в процедуре прогона не описан, поэтому до появления такого шага сравнения эта метрика не может подтвердить решение проблемы — число пропусков просто неоткуда взять.

## Как использовали AI

- Для чего: черновик раздела «Проблема» и таблицы метрик по фактам из CASE.md.
- Тип промпта: master prompt (роль, входы, задача и артефакты, формат, границы, шаги, проверка перед выдачей заданы явно).
- Строка в [`prompts.md`](prompts.md): P1-03 (генерация артефактов master prompt'ом).
- Что проверили и исправили сами: в Практике 2 раздел «Метрики» и текст под ним доработаны шестью техниками (few-shot, R.C.T.F., chain of verification, tree of thoughts, RAG, ReAct); значения «нет данных» заменены способом снятия базовой линии; порог доли выдуманных замечаний согласован с adr.md (~3% вместо 5%); для метрик без механизма сбора это указано прямо; числа без источника помечены как допущения. Подробности в practices/practice_02/prompts.md.
