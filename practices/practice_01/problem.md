# Проблема и метрики

## Проблема

- Пользователь: разработчик/CI, отправляющий diff в API для автоматического ревью.
- Ситуация: в PR добавлены эндпоинт POST `/api/reviews` и метод `ReviewService.review`, вызывающий LLM без валидации и устойчивости.
- Что происходит сейчас: API принимает произвольный `dict` и обращается к LLM синхронно; промпт строится из необработанного diff. Возвращается `{"comment": answer}` без структуры.
- Почему это мешает пользователю или бизнесу: повышенный риск 500/422 из‑за отсутствия схемы и проверок; блокировка event loop на I/O; уязвимости и утечки при инъекции через diff; нестабильный формат ответа усложняет интеграции.
- Что не входит в задачу: выбор конкретного LLM-провайдера, тонкая настройка промпта.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля запросов 422/500 на POST /api/reviews | базовая: измерить в тестовом стенде | < 1% | на каждом релизе | логи FastAPI |
| P95 времени ответа POST /api/reviews | базовая: измерить | ≤ 500 мс (без LLM) / ≤ 1.5 с (с таймаутами LLM) | на каждом релизе | APM |
| Доля инцидентов из‑за инъекции в промпт | 0 в регрессе | 0 | после релиза | тесты и багтрекер |

## Почему изменение метрики подтвердит решение проблемы

Снижение 422/500 и P95 укажет на корректную валидацию и неблокирующую обработку; отсутствие инцидентов по инъекциям — на безопасную обработку diff.

Главные проблемы по важности с подтверждением строками diff

1. Отсутствие валидации входа и схемы данных в API.
   Подтверждение: `app/api.py:36–37` — `def create_review(payload: dict) -> dict[str, str]: return review_service.review(payload["diff"])`. FastAPI рекомендует Pydantic‑модели для тел запросов.
2. Синхронный эндпоинт и вызов LLM могут блокировать event loop.
   Подтверждение: `@app.post("/api/reviews")` + `def create_review(...)` без `async`; LLM вызывается напрямую в `review_service.review` (стр. 19–22). Для I/O следует использовать `async def` или `run_in_threadpool`.
3. Уязвимость промпта к инъекциям через raw diff и отсутствие нормализации.
   Подтверждение: `prompt = f"Review this pull request and find problems:\n{diff}"` (`app/review_service.py:20`). Нет экранирования, усечения, маркеров контекста.
4. Неструктурированный ответ LLM проксируется наружу без контракта.
   Подтверждение: `return {"comment": answer}` (`app/review_service.py:22`). Нет схемы и полей для ссылок/важности; усложняет потребление в CI.
