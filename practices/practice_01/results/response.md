Ниже — результаты ревью PR. Сначала — проблемы по убыванию серьёзности с привязкой к файлам и строкам из диффа, затем вопросы и краткое резюме изменений.

Проблемы и риски
- Высокая — Отсутствие валидации входа в API, возможен 500 на клиентской ошибке (app/api.py:35-38). В хендлере `create_review(payload: dict)` извлечение `payload["diff"]` без проверки приведёт к `KeyError`, если поле отсутствует или тип не строка. Это выдаст 500 вместо предсказуемого 422/400 с описанием ошибки. Рекомендация: ввести Pydantic-модель запроса с полем `diff: str` и, при необходимости, модель ответа.
- Высокая — Нет обработки ошибок LLM (app/review_service.py:19-22). Любое исключение из `self.llm.generate(prompt)` поднимется наверх и превратится в 500 без контролируемого формата. Рекомендация: перехватывать ошибки, логировать, возвращать структурированную ошибку либо пробрасывать как HTTPException с корректным кодом.
- Средняя — Потенциальная блокировка потока в FastAPI (app/api.py:35-38). Эндпоинт синхронный, а `llm.generate` с высокой вероятностью сетевой/IO-bound. В синхронном виде будет блокировать воркер и снижать пропускную способность. Рекомендация: сделать обработчик `async` и/или обернуть вызов LLM в `run_in_threadpool`, либо предоставить асинхронную реализацию клиента LLM.
- Средняя — Требование к версии Python из-за аннотаций (оба файла). Использование `dict[str, str]` требует Python 3.9+, `typing.Protocol` — 3.8+. Если проект целится в 3.8, то `dict[str, str]` сломается (нужен `Dict[str, str]` из `typing`). Уточнить целевую версию рантайма.
- Средняя — Нестабильная/нечёткая схема ответа (app/review_service.py:21-22, app/api.py:35-38). Возвращается `{"comment": answer}` без формального контракта. Клиентская сторона может ожидать иную структуру. Рекомендация: закрепить response model, формат и ограничения (например, список находок с полями severity/message/path/line).
- Средняя — Уязвимости по качеству/безопасности контента. Прямой возврат сырых ответов LLM без пост-обработки/фильтрации может приводить к длинным, нерелевантным или потенциально небезопасным сообщениям. Рекомендация: нормализовать вывод (лимиты, формат, фильтры), задать строгий промпт с требованиями к структуре и языку.
- Низкая — Качество промпта (app/review_service.py:20). Запрос слишком общий: “Review this pull request and find problems”. Нет указаний на формат, краткость, сортировку по важности, ссылки на строки. Это снизит полезность ответа и затруднит последующую обработку.
- Низкая — Неконсистентность локали. Промпт на английском, а проектная документация/контекст — на русском. Если продукта придерживается единой локали, стоит явно выбрать язык ответа.
- Низкая — Отсутствие тестов для новой функциональности. Нет юнит-тестов на `ReviewService.review` (включая обработку ошибок), и интеграционных тестов на POST `/api/reviews` (валидный запрос, отсутствие `diff`, неверный тип, поведение при ошибке LLM).
- Низкая — Стиль/прочее. Изменение объявления `Protocol` на многострочный формат — косметика, но польза сомнительна; можно оставить, не ошибка.

Вопросы
- Какая целевая версия Python? От этого зависит допустимость `dict[str, str]`.
- `llm.generate` синхронный или асинхронный? Есть ли таймауты/ретраи? Допустима ли блокировка воркера?
- Какой контракт ожидает клиент для ответа? Достаточен ли один текстовый комментарий или нужны структурированные находки (severity, file, line, message)?
- Есть ли требования к локали ответа LLM (RU/EN)?
- Нужна ли аутентификация/авторизация на эндпоинте сейчас или это учебный/внутренний сервис?

Краткое резюме изменений
- Добавлен метод `ReviewService.review(diff: str) -> dict[str, str]`, который формирует промпт и возвращает результат LLM как `{"comment": ...}`.
- Добавлен POST эндпоинт `/api/reviews` в FastAPI, который вызывает `review_service.review` с полем `diff` из тела запроса.
- Незначительное стильовое изменение объявления `LLM.generate` в `Protocol`.

Рекомендованный минимум исправлений
1. Ввести Pydantic-модель запроса/ответа и вернуть 422 при отсутствии/неверном типе `diff`.
2. Обернуть вызов LLM в обработку исключений и вернуть контролируемую ошибку.
3. Уточнить/зафиксировать версию Python; при необходимости заменить `dict[...]` на `Dict[...]`.
4. Улучшить промпт и/или формат ответа (структура, сортировка, ограничения).
5. Добавить базовые тесты для сервиса и эндпоинта, включая негативные кейсы.
