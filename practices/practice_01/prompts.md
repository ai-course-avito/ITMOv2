## Запуск 1 (P1-01) — сырой ответ

### Запрос

> Ниже diff учебного PR. Посмотри PR и найди проблемы.

Передан только `TRAINING_PR.diff` — без контекста репозитория и без инструкций.

### Сырой ответ

> По итогам ревью diff видно, что добавляются метод `review` в `ReviewService` и REST-эндпоинт `POST /api/reviews`, который вызывает этот метод.
>
> Проблемы и замечания:
>
> 1. **Нет обработки ошибок.** Вызов `self.llm.generate(prompt)` не обёрнут в try/except. Если LLM недоступен или ответит ошибкой, клиент получит HTTP 500 вместо осмысленного сообщения.
> 2. **Нет валидации входных данных.** `create_review(payload: dict)` сразу обращается к `payload["diff"]`. Если ключа `diff` нет, будет `KeyError`; тип и размер не проверяются.
> 3. **Риск prompt injection.** Содержимое `diff` вставляется в prompt через f-string без экранирования. Вредоносный diff может подменить инструкцию модели.
> 4. **Долгий синхронный вызов.** LLM-вызов выполняется прямо в обработчике запроса, из-за чего возможна блокировка воркера и высокие задержки. Лучше выносить в асинхронную очередь.
> 5. **Ответ неструктурированный.** Возвращается только `{"comment": answer}` — без summary, списка рисков и проверок. Данные неудобно потреблять программно.
> 6. **Нет лимита на размер diff.** Огромный diff приведёт к расходу токенов и, возможно, к переполнению контекста LLM.
> 7. **Нет логирования и метрик.** Не пишутся длительность выполнения и статус каждого ревью.
>
> Рекомендации: добавить try/except с таймаутом вокруг LLM-вызова, ввести схему валидации (Pydantic), экранировать diff, вынести вызов в фоновую задачу, структурировать ответ и ограничить длину diff.

### Критика

- **Ответ слишком общий.** Замечания на уровне «добавьте try/except», «используйте Pydantic», «вынесите в очередь» не оценивают конкретный код ревью-сервиса: не сказано, что именно нарушено относительно правил репозитория и какой бизнес-риск из этого следует.
- **Нет точных привязок к строкам.** Ни один пункт не имеет `file:line` из diff (реальные строки: `review_service.py:19-22`, `api.py:36`). Без привязки замечания невозможно проверить и нельзя применять к конкретному месту.
- **Галлюцинации по архитектуре.** Утверждения про асинхронную очередь/воркеров, расход токенов, метрики и ограничение длины не опираются на diff — этих деталей в коде нет, они придуманы «в духе» типового ревью.
- **Нет воспроизводимых команд для валидации.** Ни для одного бага не указано, как воспроизвести проверку: например, отправить diff >20 000 символов и ожидать HTTP 413; передать diff с тестовым токеном и убедиться, что в prompt `[REDACTED]`; вызвать сервис с упавшим LLM и ожидать контролируемый ответ вместо 500.

## Master Prompt v1

Контракт второго запуска. Сюда из `context.md`/`CASE.md` перенесены только материалы, меняющие выполнение задачи: роль, входы, формат, запреты и Context Pack.

### 1. Цель и роль

- Роль: **AI-ассистент ревьюера PR**.
- Цель: проанализировать diff учебного PR, найти нарушения правил репозитория и вернуть структурированный отчёт, по которому ревьюер принимает решение.
- Границы роли: ассистент только советует; решение всегда принимает человек.

### 2. Входы и источники

- Обязательный вход: только `TRAINING_PR.diff` (файл `practices/practice_01/TRAINING_PR.diff`).
- Разрешённые источники: сам diff и правила из секции «## Context Pack» ниже. Внешние источники не искать.

### 3. Задача и артефакты

- Что сделать: отобрать риски, подтверждённые строкой diff или правилом Context Pack (QA-1); для каждого пройти candidate → evidence → check; вернуть отчёт.
- Что вернуть: `summary` + не более 3 критических рисков + массив `checks`.

### 4. Формат результата

- Строгий формат ссылок: `[файл:строка]` (например, `review_service.py:19-20`).
- `risks`: массив ≤3 объектов с полями `file`, `line`, `evidence`, `risk`; у каждого риска обязательная воспроизводимая проверка (команда/запрос).
- `checks`: массив воспроизводимых проверок (curl/запрос), по одной на каждый риск.

### 5. Полномочия и запреты

- Разрешено: анализировать diff, ссылаться на `[файл:строка]`, предлагать проверки.
- Запрещено: approve, merge, редактирование кода (SCOPE-1); придумывать правила, которых нет в Context Pack; использовать что-либо, кроме diff и Context Pack.

### 6. Рабочий процесс и остановка

- Шаги:
  1. candidate — список потенциальных рисков;
  2. evidence — строка diff или правило для каждого кандидата;
  3. cap — оставить не более 3 самых критических с evidence (QA-1);
  4. check — сформулировать воспроизводимую команду/запрос для каждого;
  5. собрать ответ по формату п.4.
- Когда остановиться и запросить человека: для риска нет evidence → пропустить; для ответа нужны факты вне diff/Context Pack → остановиться и уточнить.

### 7. Проверки и evidence

- Каждый риск сверяется со строкой `[файл:строка]` из diff или с текстом правила из Context Pack.
- Evidence сохраняется в ответе; риск включается только при наличии evidence и воспроизводимой проверки.

### 8. Definition of Done

- Задача закончена, когда: есть `summary`; до 3 рисков, у каждого `[файл:строка]` + evidence + воспроизводимая проверка; границы SCOPE-1 соблюдены; придуманных правил нет.

## Context Pack

Факты, правила, примеры и ограничения для этой задачи (подробно в [`context.md`](context.md)).

### Правила репозитория (только влияющие на этот PR)

- `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
- `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- `OUT-1`: ответ содержит `summary`, массив `risks` (≤3, поля `file`/`line`/`evidence`/`risk`) и массив `checks`.
- `SCOPE-1`: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- `QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
- `OBS-1`: в лог пишутся только `request_id`, длительность и статус; содержимое diff и ответа модели не логируется.

### Ограничения задачи

- Вход: только diff; другие файлы и внешние источники не используются.
- Не более 3 критических рисков; строгий формат ссылок `[файл:строка]`.
- Запрещено: approve, merge, редактирование кода.
- Каждый риск обязан иметь воспроизводимую проверку (команду/запрос).

### Формат ответа

- `summary` — краткое описание изменения.
- `risks` — массив ≤3 объектов с полями `file`, `line`, `evidence`, `risk`.
- `checks` — массив воспроизводимых проверок.

### Примеры комментария

Хороший:

```text
review_service.py:19-20 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```

Плохой:

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Почему второй результат качественнее, точнее и инженерно воспроизводим

- **Точность.** P1-01 даёт общие советы («добавьте try/except», «используйте Pydantic», «вынесите в очередь») без привязки к коду. P1-02 ссылается на конкретные `[файл:строка]`, совпадающие с фактом: `review_service.py:19-22` и `api.py:36`.
- **Доказуемость.** Каждый пункт P1-02 проходит QA-1: есть evidence из строки diff или правила контекста. Галлюцинации P1-01 (архитектурные домыслы про воркеры и метрики) во втором запуске просто не могут быть выдвинуты — для них нет правила.
- **Инженерная воспроизводимость.** К каждому риску приложена команда или запрос, который другой инженер выполняет без пояснений: diff с тестовым token → в prompt `[REDACTED]`; мок LLM со sleep 15 с → контролируемый ответ, а не 500; diff 25 000 символов → HTTP 413 и LLM не вызван. В P1-01 таких команд нет вообще.
- **Пригодность для решения.** Лимит ≤3 рисков + структура `summary`/`risks`/`checks` превращают вывод в рабочий контракт для ревьюера (SCOPE-1: решает человек), а не в эссе — как показывает свойство «количество и приоритизация рисков».
