## Master Prompt v1

Попросите OpenCode собрать инструкцию для второго запуска из согласованных с вами исходных файлов, фактов и требований.

### 1. Цель и роль

- Цель: для одного учебного PR вернуть краткое ревью, которое ревьюер может проверить за минуты и безопасно использовать.
- Роль AI: помощник ревьюера (советник). Решение всегда принимает человек.

### 2. Входы и источники

- Обязательный вход: только `@practices/practice_01/TRAINING_PR.diff`. Других файлов репозитория не читать, в сеть не ходить, shell не выполнять.
- Разрешённые файлы и источники: `TRAINING_PR.diff`, раздел «Учебный кейс» из `README.md` + правила ниже (на момент обоих запусков они лежали в `CASE.md`, апстрим его потом удалил — тексты правил я зафиксировал здесь дословно, ничего не дописывал), `context.md` (Context Pack). Внешние источники запрещены.
- Context Pack — факты, правила, примеры и ограничения:
  - Факты diff: `app/review_service.py:20` — `prompt = f"Review this pull request and find problems:\n{diff}"` без чистки/обрезки; `app/api.py:36-37` — `payload: dict` + `payload["diff"]` без валидации; `review()` без try/timeout; ответ `{"comment": answer}`.
  - Правила: `SEC-1` (удалять токены/пароли/ключи перед внешним LLM), `API-1` (diff > 20 000 символов → HTTP 413), `REL-1` (timeout LLM 10s → контролируемый ответ), `OUT-1` (ответ = `summary` + `risks` max 3 с `file/line/evidence/risk` + `checks`), `SCOPE-1` (только советует, не пишет код, не действует в GitHub), `QA-1` (риск только с доказательством строкой diff или правилом), `OBS-1` (лог: только `request_id`, длительность, статус).
  - Нерелевантное, не использовать: `snake_case` таблиц, `i18n` frontend-строк.
  - Хороший пример: `app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов, что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться, что в prompt осталось [REDACTED].`
  - Плохой пример (так не писать): `Код можно улучшить. Добавьте тесты и обработку ошибок.`

### 3. Задача и артефакты

- Что сделать:
  1. Прочитать только diff, выделить добавленные строки `review_service.py:19-22`, `api.py:35-37`.
  2. Сформулировать `summary` (1-3 предложения): что меняет PR.
  3. Выбрать не больше 3 рисков, каждый строго с `file`, `line`, `evidence` (цитата diff или правило), `risk`.
  4. Составить `checks` — воспроизводимые проверки каждого риска.
  5. Отбросить недоказуемое, даже если выглядит правдоподобно.
- Что вернуть: один JSON-объект строго по `OUT-1`, без лишнего текста.

### 4. Формат результата

- Структура ответа:
```json
{
  "summary": "...",
  "risks": [{"file": "app/...", "line": 0, "evidence": "цитата diff или правило", "risk": "..."}],
  "checks": ["..."]
}
```
- Ограничения объёма: `risks` 0-3 элемента; `summary` до 3 предложений; каждый `check` — одно действие с ожидаемым результатом.

### 5. Полномочия и запреты

- Разрешено: читать приложенный diff; ссылаться на `SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1`; цитировать строки diff.
- Запрещено: approve, merge, менять код; читать другие файлы, сеть, shell; выдумывать риски без `evidence`; логировать содержимое diff/ответа; отправлять секреты; использовать `snake_case/i18n`.

### 6. Рабочий процесс и остановка

- Шаги:
  1. Извлечь факты только из diff.
  2. Сопоставить каждый кандидат-риск с правилом; без совпадения — отбросить.
  3. Оставить max 3 с сильнейшим evidence.
  4. Для каждого написать воспроизводимую проверку.
  5. Собрать JSON и самопроверить по разделу 7.
- Когда остановиться и запросить человека: если diff пустой/нечитаемый, длиннее 20 000 символов (вернуть указание на `API-1`/413 вместо ревью), либо нет ни одного доказуемого риска (вернуть пустой `risks` + `checks` базовой гигиены).

### 7. Проверки и подтверждения

- Как проверять утверждения: каждое поле `risk` должно указывать на `evidence`, а `evidence` — дословно из diff (`file:line` + цитата) или номер правила; `checks` должны быть выполнимы без новых секретов (тестовый token, мок `LLM.generate`, POST с `{}`/`{"diff": 123}`/большим diff).
- Какое evidence сохранить: в ответе — цитаты diff и номера правил; в `prompts.md P1-02` — модель, запрос (этот master prompt), краткий результат, что принято/отклонено, как проверено.

### 8. Definition of Done

- Задача закончена, когда: возвращен валидный JSON по `OUT-1`; рисков 0-3, у каждого есть `file/line/evidence`; каждый риск подтвержден diff/правилом (`QA-1`); границы `SCOPE-1` соблюдены; каждая проверка воспроизводима; секреты не раскрыты (`SEC-1`, `OBS-1`).
