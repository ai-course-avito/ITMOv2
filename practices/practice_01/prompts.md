## Master Prompt v1

Попросите OpenCode собрать инструкцию для второго запуска из согласованных с вами исходных файлов, фактов и требований.

### 1. Цель и роль

- Цель: сгенерировать каркас бэкенда AnimeMap API (DDD модульный монолит) и покрыть его тестами по стратегиям из practice_01.
- Роль AI: ведущий генератор кода и тестов, соблюдающий архитектурные правила и контракты.

### 2. Входы и источники

- Обязательный вход: файлы из practices/practice_01/*.md (problem, context, product_management, adr, analysis, project_management, tests_*), стек и ограничения из Context Pack.
- Разрешённые файлы и источники: текущий репозиторий; официальная документация FastAPI/SQLAlchemy/Alembic/Redis/httpx/Pydantic при необходимости синтаксиса.
- Context Pack — факты, правила, примеры и ограничения:
  - Архитектура: модульный монолит по DDD со слоями interfaces/application/domain/infrastructure
  - Принципы: ООП, SOLID; Presentation — Pydantic; Domain/Application — dataclasses(slots=True)
  - Данные: PostgreSQL; доступ через SQLAlchemy; миграции Alembic (до первой dev-версии допустим рефактор первой миграции)
  - Кэш: Redis для частых запросов координат и поиска; TTL и инвалидация
  - Интеграции: httpx для внешнего геокодера; тайм-ауты/ретраи
  - Идентификаторы: UUIDv4 первичные ключи, генерируются на уровне domain
  - Запрет: реализация фронтенда в этом репозитории

### 3. Задача и артефакты

- Что сделать: создать каркас каталогов и модулей по слоям; определить domain entities и value objects; порты репозиториев; маппинг ORM; Alembic миграции; Redis-кэш-адаптер; httpx-клиент; FastAPI endpoints; тесты unit/integration/e2e/load по стратегиям.
- Что вернуть: изменения в кодовой базе; инструкции по запуску; подтверждение прохождения тестов (если возможно локально).

### 4. Формат результата

- Структура ответа: краткое описание изменений, перечисление созданных файлов/папок, команды запуска, заметки по конфигам.
- Ограничения объёма: избегать избыточной болтовни; код и структуры — по делу.

### 5. Полномочия и запреты

- Разрешено: создавать/редактировать файлы в рамках бэкенда; добавлять зависимости в requirements; писать миграции; конфиг Redis/httpx.
- Запрещено: добавлять фронтенд; менять выбраный стек; нарушать DDD-границы (domain не зависит от infrastructure).

### 6. Рабочий процесс и остановка

- Шаги:
  1. Прочитать файлы practice_01, зафиксировать ключевые требования.
  2. Создать структуру модулей DDD.
  3. Добавить доменные сущности и порты.
  4. Реализовать инфраструктуру: ORM-модели/маппинг, миграции, Redis, httpx-клиент.
  5. Добавить FastAPI endpoints.
  6. Написать тесты по tests_unit/integration/e2e/load планам.
  7. Прогнать тесты, зафиксировать результаты.
- Когда остановиться и запросить человека: неопределённость в контракте API, миграциях схемы или политике модерации.

### 7. Проверки и подтверждения

- Как проверять утверждения: соответствие коду архитектурным правилам (импорт-границы), прохождение тестов, статический анализ типов.
- Какие результаты проверки сохранить: вывод тестов, список файлов, выдержки из конфигов.

### 8. Definition of Done

- Задача закончена, когда: структура DDD создана; UUIDv4 используется в domain и БД; работают базовые CRUD и поиск; кэш Redis подключён; httpx-клиент подключён с тайм-аутами; миграции применимы; тесты реализованы согласно планам и проходят локально/в CI.
