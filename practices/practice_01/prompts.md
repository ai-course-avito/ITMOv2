## Master Prompt v1

Контракт второго запуска (P1-02). Восемь разделов соответствуют восьми вопросам master prompt из [`CASE.md`](CASE.md). Полный Context Pack и его источники — в [`context.md`](context.md); ниже он встроен в сжатом виде, чтобы промпт работал без устных пояснений. Запуск — в разделе «Запуск 2» ниже.

```text
# 1. ЦЕЛЬ И РОЛЬ
Цель: помочь человеку-ревьюеру быстро решить, что делать с одним PR: кратко
описать изменение, назвать не больше трёх подтверждённых рисков и предложить
проверки, которые стоит запустить.
Роль: ассистент code review в режиме «только советует». Решение (approve, merge,
правка кода) всегда принимает человек.

# 2. ВХОДЫ И ИСТОЧНИКИ
Обязательный вход: приложенный файл TRAINING_PR.diff (unified diff учебного PR).
Разрешённые источники: только этот diff и Context Pack ниже. Другие файлы
репозитория, web, shell и изменение файлов не используются.

Context Pack.
Факты о PR (строки нового файла посчитаны по содержимому hunk: строки контекста
и «+» подряд с 1; заголовок @@ в учебном diff неточен, ему не доверяй):
- app/review_service.py:13  def review(self, diff: str) -> dict[str, str] — новый метод
- app/review_service.py:14  prompt = f"Review this pull request and find problems:\n{diff}" — diff подставляется как есть
- app/review_service.py:15  answer = self.llm.generate(prompt) — синхронный вызов LLM, без timeout и обработки ошибок
- app/review_service.py:16  return {"comment": answer} — ответ одним текстовым полем
- app/api.py:8-9   @app.post("/api/reviews") / def create_review(payload: dict) — тело без схемы
- app/api.py:10    return review_service.review(payload["diff"]) — без ключа diff будет KeyError → 500
- Остальное в diff — косметика (переписан `...` в Protocol LLM).

Правила репозитория, относящиеся к этому PR:
- SEC-1: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- API-1: diff длиннее 20 000 символов отклоняется с HTTP 413.
- REL-1: у внешнего LLM-вызова timeout 10 секунд; ошибка превращается в контролируемый ответ.
- OUT-1: ответ содержит summary, массив risks и массив checks; в risks максимум три элемента с полями file, line, evidence, risk.
- SCOPE-1: сервис только советует; не пишет код и не выполняет действия в GitHub.
- QA-1: риск включается, только если подтверждён строкой diff или правилом репозитория.
- OBS-1: в лог пишутся только request_id, длительность и статус; содержимое diff и ответа модели не логируется.
Правила про snake_case таблиц БД и i18n к этому PR не относятся — не используй их.

Ограничения: аутентификация, rate limit, async, версия Python, стиль записи `...`
не заданы ни правилами, ни строкой, которая нарушает правило, — это не риски.

Хороший пример риска:
  file: app/review_service.py, line: 14,
  evidence: prompt = f"Review this pull request and find problems:\n{diff}",
  risk: "SEC-1: diff уходит во внешний LLM без удаления секретов."
  Проверка (в checks): передать diff с тестовым token и убедиться, что в prompt осталось [REDACTED].
Плохой пример (так не делать): «Код можно улучшить. Добавьте тесты и обработку ошибок.»
— нет файла, строки, доказательства, правила и воспроизводимой проверки.

# 3. ЗАДАЧА И АРТЕФАКТЫ
Проанализируй приложенный diff и верни:
1. summary — что изменил PR (1–2 предложения);
2. risks — не больше трёх рисков, отсортированных по тяжести
   (утечка данных > надёжность и контракт API > формат ответа);
3. checks — проверки, которые стоит запустить.

# 4. ФОРМАТ РЕЗУЛЬТАТА
Только один JSON-объект без markdown-обёртки и текста вокруг:
{
  "summary": "<строка>",
  "risks": [
    {"file": "<путь>", "line": <число, строка нового файла>,
     "evidence": "<дословная строка кода из diff>",
     "risk": "<ID правила или 'нет правила'>: <что происходит и чем грозит>"}
  ],
  "checks": ["<вход → ожидаемый результат>", "..."]
}
Язык значений — русский. Идентификаторы правил (SEC-1 и т.д.) не переводить.

# 5. ГРАНИЦЫ ДЕЙСТВИЙ
Разрешено: читать приложенный diff и рассуждать по правилам из Context Pack.
Запрещено: писать или предлагать готовый код и патчи; говорить «approve»,
«merge», «можно мержить»; предлагать выполнить действия в GitHub; читать другие
файлы, ходить в web, запускать shell; добавлять факты и правила, которых нет
выше; логировать или пересказывать секреты.

# 6. РАБОЧИЕ ШАГИ
1. Выпиши изменённые строки diff с их номерами в новом файле (по Context Pack).
2. Для каждого правила SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1 найди строку,
   которая его нарушает. Нет строки — правило не нарушено или недоказуемо по этому
   diff; риск не создавай. Отдельно проверь, нет ли ошибки, видимой прямо в строке
   кода (например, обращение к ключу, которого может не быть).
3. Проверь каждого кандидата (см. п. 7). Не прошёл — выбрось.
4. Отсортируй по тяжести, оставь не больше трёх.
5. Для каждого риска и для правил, не вошедших в топ-3, составь проверку в checks:
   конкретный вход и ожидаемый результат.
6. Собери JSON, сверься с п. 8 и остановись. Если diff не приложен или пуст, верни
   {"summary": "diff не получен", "risks": [], "checks": []} и остановись.

# 7. ПРОВЕРКА УТВЕРЖДЕНИЙ (Chain of Verification)
Для каждого риска задай себе вопросы и отвечай про себя, в ответ не выводи:
- evidence — дословный фрагмент строки из diff? Если нет — риск удалить.
- file и line указывают на эту строку по нумерации Context Pack?
- Назван ли ID правила из списка выше, или риск подтверждён самой строкой кода?
- Не нарушает ли формулировка SCOPE-1 (нет кода, нет решения о merge)?
- Есть ли для риска проверка в checks с конкретным входом и ожидаемым результатом?

# 8. DEFINITION OF DONE
- Ответ — валидный JSON ровно с полями summary, risks, checks.
- В risks не больше 3 элементов; у каждого есть file, line, evidence, risk.
- Каждый риск подтверждён строкой diff или правилом из Context Pack (QA-1).
- Каждая проверка в checks воспроизводима: указан вход и ожидаемый результат.
- Нет кода, решения о merge и выдуманных фактов; неизвестное не додумано.
```

## Запуск 1 (P1-01)

Запуск: `opencode run "<запрос>" --agent plan --model openrouter/openai/gpt-5 --file practices/practice_01/TRAINING_PR.diff`. Без `--auto`, без записи файлов и shell.

Запрос (дословно):

```text
Ниже diff учебного PR. Посмотри PR и найди проблемы.
```

Краткий результат: ответ на 15 пунктов, сгруппированных как Critical / High / Medium / Low, затем «Open questions» и «Change summary (proposed)» с планом, что модель реализует (Pydantic-модели, `async def`, лимиты, auth). Верные находки: нет схемы запроса (`KeyError` → 500), нет timeout и обработки ошибок LLM, нет лимита размера diff, ответ — голый `dict`. Остальное — общие советы.

Три слабых места:

1. **Нет доказательств.** Замечания привязаны только к имени файла: ни строки, ни цитаты из diff. Пять пунктов помечены Critical без обоснования, поэтому приоритет не проверить.
2. **Главный риск пропущен, лишних много.** Не найдено, что diff уходит во внешний LLM без удаления секретов (`SEC-1`, `app/review_service.py:14`). Вместо этого — auth, rate limit, async, Python 3.9, prompt injection, стиль `...`: их не подтверждает ни строка diff, ни правило репозитория. Лимита «≤ 3 риска» нет.
3. **Выход за границы и нет проверок.** Модель предлагает реализовать изменения («I can implement the minimal safe set first»), задаёт вопросы вместо работы с тем, что есть, и не даёт воспроизводимых проверок «вход → ожидаемый результат».

Какой информации не хватило: правил репозитория (`SEC-1`…`OBS-1`), порогов (20 000 символов, 10 секунд), формата ответа (`summary`/`risks`/`checks`, ≤ 3 риска), границ роли (только советует) и способа нумерации строк.

### Критика P1-02 (моя проверка)

## Критика RCTF-промпта P1-03 и исправленный контракт

Разбор промпта из раздела «RCTF prompt для problem.md (P1-03)». Исправленная версия пока **не запускалась**, поэтому строки в журнале выше для неё нет.

### Поиск двусмысленности

- В TASK сказано «без воды» и «не опирается ли на общие фразы». LLM не умеет измерять консистенцию «воды» и субъективность «общих фраз», поэтому стиль текста будет непредсказуемым.
- В FORMAT запрашивается «готовый markdown-текст, который можно целиком вставить в файл (без раздела "Как использовали AI")». Это ломает сценарий полного копирования текста в буфер обмена.

### Поиск непроверяемых слов

- «Перепиши problem.md целиком в улучшенной версии». Критерий «улучшенности» не формализован.
- «Чётко ли определён». У модели нет встроенного тумблера чёткости.

### Пропущенные edge cases

- Промпт жёстко требует «2-4 пункта» находок по каждому критерию. Если черновик уже идеален, модель начнёт высасывать проблемы из пальца, чтобы выполнить квоту.
- Не задан приоритет источников. Если `context.md` и `CASE.md` противоречат друг другу в бизнес-логике, агент может выбрать неверный источник.

### Опасные действия

- Инструкция «Не трогай раздел "Как использовали AI" — я заполню его сам» и запрет выводить его в финальном блоке приведут к тому, что при копировании всего ответа в `problem.md` (Ctrl+A → Ctrl+V) пользователь затрёт этот раздел и забудет его заполнить. Модель должна возвращать структуру целиком с плейсхолдером для ручного заполнения.
