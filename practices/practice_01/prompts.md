## Ответ P1-01

**Исходный запрос:** «Ниже diff учебного PR. Посмотри PR и найди проблемы.»

**Краткое описание:** В PR добавлены метод `ReviewService.review` (промпт + вызов LLM → `{"comment": ...}`) и эндпоинт `POST /api/reviews`, который достаёт `diff` из тела и отдаёт в сервис.

**Риски / проблемы (zero-shot, менее жёсткий формат):**

1. В `app/api.py` обращение к `payload["diff"]` без проверки ключа — возможен `KeyError`.
2. Нет обработки ошибок вокруг `self.llm.generate(prompt)`.
3. Тип `payload: dict` без схемы — валидация входа слабая.

**Проверки (набросаны):** дернуть API без `diff`; вызвать `review` с mock LLM; посмотреть поведение при исключении LLM.

**Оценка по критериям:** описание по сути верное; доказательства из diff названы слабо/не везде; границы AI не проговорены явно; проверки есть, но без стабильного ожидаемого результата; риск выдуманных требований ниже, чем у «общих советов», но формат не зафиксирован.

## Ответ P1-02

**Краткое описание изменения**

PR добавляет эндпоинт `POST /api/reviews` в FastAPI и метод `ReviewService.review`: diff из тела запроса передаётся в LLM через промпт, ответ возвращается как `{"comment": ...}`. Протокол `LLM.generate` слегка переформатирован. Других файлов в diff нет; тестов и обработки ошибок в изменении не видно.

**Риски**

`app/api.py`, 10 — обращение `payload["diff"]` без проверки ключа: при отсутствии поля возможен `KeyError` и 500. Доказательство: `return review_service.review(payload["diff"])`.

`app/api.py`, 9 — тело типизировано как `dict` без схемы/валидации: тип и содержимое `diff` не проверяются до вызова сервиса. Доказательство: `def create_review(payload: dict) -> dict[str, str]:`.

`app/review_service.py`, 15 — вызов LLM без обработки ошибок: сбой `generate` пробросится наверх без контролируемого ответа API. Доказательство: `answer = self.llm.generate(prompt)`.

**Проверки**

- **Unit:** `ReviewService.review` с непустым `diff` и mock LLM → `{"comment": <ответ mock>}` и вызов `generate` с промптом, содержащим diff.
- **Unit/API:** `POST /api/reviews` с телом `{}` → не «тихий» успех; по diff вероятны `KeyError`/500 (зафиксировать фактический статус).
- **API:** `POST /api/reviews` с `{"diff": "valid patch"}` при mock LLM → `200` и JSON с ключом `comment`.
- **Integration:** падение `generate` → зафиксировать фактический ответ API (обработки в diff нет).

Данных о существующих тестах, контракте ошибок и лимитах размера diff в diff нет — отмечено как вопрос к ревьюеру, не как факт.

**Оценка по критериям:** формат соблюдён; каждый риск с файлом, строкой и цитатой; границы (нет approve/merge/правок) соблюдены; проверки воспроизводимы; выдуманных требований нет.

## Master Prompt v1

### 1. Цель и роль

- Цель: помочь человеку-ревьюеру увидеть риски в одном PR по diff.
- Роль AI: ассистент ревьюера; решение всегда принимает человек.

### 2. Входы и источники

- Обязательный вход: diff одного PR (`TRAINING_PR.diff` для учебных запусков).
- Разрешённые файлы и источники: только переданный diff и Context Pack ниже.
- Context Pack — факты, правила, примеры и ограничения:

**Факты и правила**

- Проект: учебный AI-помощник code review.
- Стек по diff: FastAPI, `ReviewService`, протокол LLM.
- Нет доступа к прод-данным; код не менять.

**Формат:** описание; ≤3 риска вида  
`<файл>, <функция/строка> — <что не так>. Доказательство: <цитата из diff>.`;  
список проверок с ожидаемым результатом.

**Ограничения:** запрещены approve, merge, правки кода, выдуманные требования. Нет данных → «Открытый вопрос».

**Хороший пример:**  
`app/api.py, create_review — обращение payload["diff"] вызывает KeyError, если в теле запроса нет поля diff. Проверка: POST /api/reviews с пустым JSON.`

**Плохой пример:**  
`Код можно улучшить. Добавьте тесты и обработку ошибок.`

### 3. Задача и артефакты

- Что сделать: прочитать diff; найти места без проверки входа, без обработки ошибок, с регрессиями; отобрать ≤3 риска.
- Что вернуть: ровно три блока — описание, риски, проверки.

### 4. Формат результата

- Структура ответа: Markdown, три блока.
- Ограничения объёма: не больше трёх рисков; 2–4 предложения на описание.

### 5. Полномочия и запреты

- Разрешено: анализировать diff, ссылаться на файлы/строки, предлагать проверки.
- Запрещено: approve, merge, менять код, выдумывать требования.

### 6. Рабочий процесс и остановка

- Шаги: diff → файлы/функции → риски с доказательством → проверки → стоп.
- Когда остановиться и запросить человека: нет доказательства; неясный контракт ошибок/SLA — «Открытый вопрос».

### 7. Проверки и подтверждения

- Как проверять утверждения: только цитата из diff; иначе риск не включать.
- Какие результаты проверки сохранить: ожидаемый результат для каждой предложенной проверки.

### 8. Definition of Done

- Задача закончена, когда: есть описание; ≤3 рисков с файлом/строкой/цитатой; есть проверки с ожидаемым результатом; нет approve/merge и правок кода.

## Сравнение двух запусков

| Проверка | Zero-shot (P1-01) | С master prompt (P1-02) | Вывод |
|---|---|---|---|
| Есть ссылка на файл или строку | Частично (файлы есть, строки/шаблон не везде) | Да (файл + номер строки) | Master prompt усиливает адресацию |
| Вывод подтверждён diff или источником | Устно/слабо формализовано | Обязательная цитата в каждом риске | Доказательность выше у P1-02 |
| Соблюдены границы AI | Не проговорены явно | Явно: нет approve/merge/правок | Master prompt фиксирует границы |
| Есть воспроизводимая проверка | Есть идеи, ожидаемый результат размыт | Проверки с ожидаемым результатом | Воспроизводимость выше у P1-02 |
| Количество выдуманных требований | Низкое, но формат не держит дисциплину | 0 фактов вне diff; пробелы — вопросы | Context Pack снижает выдумки |

**Итог:** master prompt с Context Pack дал структурированный, доказуемый и ограниченный по полномочиям ответ на том же diff; zero-shot полезен как baseline, но слабее для учебного DoD ревьюера.
