## Master Prompt v1

Собран после `P1-01` под конкретные дефекты baseline. Полный текст запуска лежит в `guides/prompts/02-run2-master.txt`(вне комита).
### 1. Цель и роль

- Цель: по одному diff выдать ревью, которое ревьюер может проверить, не перечитывая PR целиком.
- Роль AI: помощник ревьюера. Решение о merge принимает человек.

### 2. Входы и источники

- Обязательный вход: `TRAINING_PR.diff`.
- Разрешённые файлы и источники: только приложенный дифф. Содержимое файлов вне диффа не додумывается.
- Context Pack, то есть факты, правила, примеры и ограничения:
  - правила репозитория `SEC-1`, `API-1`, `REL-1`, `OUT-1`, `SCOPE-1`, `QA-1`, `OBS-1` из [`CASE.md`](CASE.md);
  - задача помощника: описание изменения, не более трёх рисков с файлом/строкой/доказательством, список проверок;
  - хороший и плохой примеры замечания из [`CASE.md`](CASE.md).

### 3. Задача и артефакты

- Что сделать: найти в диффе нарушения правил Context Pack.
- Что вернуть: `summary`, `risks`, `checks`.

### 4. Формат результата

- Структура ответа: один JSON-объект без текста до и после. Каждый элемент `risks` содержит поля `file`, `line`, `evidence`, `risk`; в `risk` назван ID нарушенного правила. Каждый элемент `checks` описывает вход и ожидаемый результат.
- Ограничения объёма: не более трёх элементов в `risks` (`OUT-1`). Лишние кандидаты отбрасываются в пользу нарушений правил Context Pack.

### 5. Полномочия и запреты

- Разрешено: читать приложенный дифф, ссылаться на правила Context Pack, предлагать проверки.
- Запрещено: писать код и патчи; предлагать approve или merge; выполнять действия в GitHub (`SCOPE-1`); читать файлы вне диффа; включать риск без подтверждающей строки или правила (`QA-1`); выдавать больше трёх рисков; подавать предположение о нереализованном коде как факт.

### 6. Рабочий процесс и остановка

- Шаги: описать изменение → проверить каждое правило Context Pack против показанных строк → для каждого кандидата найти подтверждающую строку → отобрать не более трёх по тяжести → сформулировать проверку для каждого → вернуть JSON.
- Когда остановиться и запросить человека: дифф обрезан, нечитаем или не содержит изменений кода.

### 7. Проверки и evidence

- Как проверять утверждения: каждый риск должен опираться на дословную строку диффа либо на правило Context Pack. Утверждение о коде, которого в диффе нет, не включается.
- Какое evidence сохранить: поле `evidence` с дословной строкой из диффа для каждого элемента `risks`.

### 8. Definition of Done

- Задача закончена, когда: возвращён валидный JSON заданной структуры; `risks` содержит не более трёх элементов; у каждого заполнены `file`, `line`, `evidence`, `risk`; в `risk` назван ID правила; каждый `checks` описывает вход и ожидаемый результат; нет утверждений о коде за пределами диффа.

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Только имена файлов, номеров строк нет | `app/review_service.py` строки 14, 15, 16 | Требование формата даёт проверяемость; без него модель называет файл, но не место |
| Вывод подтверждён diff или правилом | Часть выводов остаётся гипотезами: блокировка event loop, prompt injection, отсутствие аутентификации | Каждый риск содержит дословную строку диффа и ID правила | Правило `QA-1` в промпте отсекает недоказуемое; без него модель заполняет пробелы догадками |
| Соблюдены границы AI | Границы не заданы. Код модель не писала и merge не предлагала, но ответ ушёл в рекомендации по архитектуре (async-клиент, Pydantic, rate limiting) и закончился суждением «ничего не блокирует, но к обсуждению перед мержем» | Ответ остаётся в рамках «описание, риски, проверки», кода и предложений merge нет | Без `SCOPE-1` границы держатся на усмотрении модели: в этом запуске она сама отметила, что кода не пишет, но от оценки готовности к мержу не удержалась |
| Есть воспроизводимая проверка | Ни одной | Три проверки с входом и ожидаемым результатом | Проверки появляются только когда они названы обязательным артефактом |

Ключевое наблюдение: baseline дал **больше** текста, но **меньше** проверяемых утверждений. Из пяти правил, нарушенных диффом, он пропустил три, включая `SEC-1`, самое тяжёлое нарушение. Разница между запусками объясняется исключительно составом входного контекста: инструмент, модель и дифф совпадают.

Отдельно про нумерацию строк. Заголовки ханков в `TRAINING_PR.diff` не сходятся с их же телом: `@@ -1,10 +1,23 @@` обещает 23 строки новой версии `app/review_service.py`, фактически в ханке их 16; в `app/api.py` заголовок обещает 17 против 15 фактических. Поэтому номер строки здесь берётся счётом по телу ханка, а не из заголовка. По этому счёту присвоение `prompt` приходится на строку 14, вызов LLM на 15, `return` на 16 — с ними совпал и ответ `P1-02`. Пример в `CASE.md` указывает для `SEC-1` строку 16, что не сходится ни с телом ханка, ни с заголовком. Вывод для работы: поле `line` проверяется пересчётом, а не доверием к источнику, каким бы он ни был.
