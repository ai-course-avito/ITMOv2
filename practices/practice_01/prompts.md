## P1-01 Result

Ниже — ревью изменений в TRAINING_PR.diff с фокусом на баги, риски и пропуски в тестах. Указываю файлы и фрагменты по диффу.

Проблемы и риски
1) Отсутствие валидации входных данных и неуправляемые 500
- Файл: app/api.py, строки 35–38 (создание эндпойнта)
- Код: create_review(payload: dict) -> dict[str, str]: return review_service.review(payload["diff"])
- Проблема: если в теле запроса нет ключа "diff" или он не строка, будет KeyError/TypeError и 500 Internal Server Error.
- Риск: нестабильность API; плохой DX для клиентов.
- Рекомендация: использовать Pydantic-модель для запроса (например, class ReviewRequest(BaseModel): diff: str) и/или явно проверять наличие/тип и возвращать 422 Unprocessable Entity через HTTPException. Также прописать response_model для схемы ответа.

2) Отсутствие обработки ошибок LLM и таймаутов
- Файл: app/api.py, строки 35–38; app/review_service.py, строки 19–22
- Проблема: ошибки/таймауты из llm.generate пробросятся наружу как 500. Нет ограничений по времени выполнения.
- Риск: зависания воркеров, деградация SLA.
- Рекомендация: установить таймаут на генерацию и перехватывать исключения с маппингом в 5xx/4xx по ситуации; опционально логировать и возвращать дружелюбное сообщение.

3) Уязвимость к "denial-of-wallet"/abuse и отсутствуют лимиты входа
- Файл: app/api.py, строки 35–38; app/review_service.py, строки 19–22
- Проблема: любой может отправлять огромные диффы, LLM будет дорогим/долгим. Нет аутентификации/квот/лимитов размера.
- Риск: рост затрат, DoS.
- Рекомендация: добавить аутентификацию/авторизацию, rate limiting, максимальный размер диффа, усечение/суммаризацию входа.

4) Prompt injection / слабая формализация промпта
- Файл: app/review_service.py, строки 19–22
- Код: prompt = f"Review this pull request and find problems:\n{diff}"
- Проблема: дифф включён без разграничителей и указания формата ответа; контент диффа может «переписать» инструкции (prompt injection).
- Риск: нестабильный/непредсказуемый ответ LLM.
- Рекомендация: использовать явные маркеры секций (<diff>...</diff>), «системные» инструкции, фиксированный формат ответа (например, JSON со списком issues), валидацию/парсинг ответа.

5) Схемы запрос/ответа не типизированы для OpenAPI
- Файл: app/api.py, строки 35–38
- Проблема: вход — сырой dict; выход — dict[str, str] без response_model.
- Риск: бедная документация OpenAPI/Swagger, сложнее интеграция клиентов.
- Рекомендация: Pydantic-модели для запроса/ответа и указание response_model в декораторе.

6) Синхронный вызов LLM в веб-эндпойнте
- Файл: app/api.py, строки 35–38
- Проблема: endpoint синхронный (def), llm.generate тоже синхронный. В FastAPI sync-handlers уходят в threadpool, но если generate блокирующий/сетевой и тяжёлый, можно занять пул.
- Риск: снижение пропускной способности под нагрузкой.
- Рекомендация: рассмотреть async-эндпойнт и обёртку в asyncio.to_thread или явно оставить sync, но контролировать пул и таймауты. Либо сделать LLM-обёртку асинхронной.

7) Совместимость типов с версией Python
- Файл: оба
- Проблема: используются dict[str, str] и typing.Protocol. Это ОК с Python ≥3.9 (Protocol — с 3.8), но сломается на 3.8 для dict[...] без from __future__ import annotations.
- Риск: падение при более старых рантаймах.
- Рекомендация: зафиксировать минимальную версию Python (например, 3.10+) в pyproject/poetry/requirements или использовать typing.Dict и/или from __future__ import annotations.

8) Жёсткая зависимость через модульный импорт вместо DI
- Файл: app/api.py, строки 30–37
- Код: from app.dependencies import review_service; прямое использование в хендлере.
- Проблема: сложно мокать/переопределять в тестах; слабая гибкость конфигурации.
- Рекомендация: использовать Depends для внедрения ReviewService, чтобы в тестах подменять зависимость.

9) Неопределённость статуса ответа
- Файл: app/api.py, строки 35–38
- Проблема: эндпойнт именуется как «create» и висит на POST, но возвращает 200 без явного статуса. Если это «операция над ресурсом без сохранения», 200 нормально; если «создание», обычно 201.
- Рекомендация: явно указать status_code в декораторе и договориться о семантике.

10) Тесты отсутствуют
- Файлы: новые фичи в app/review_service.py и app/api.py
- Проблема: нет юнит-тестов на ReviewService.review и интеграционных тестов на POST /api/reviews.
- Риск: регрессии не будут пойманы.
- Рекомендация: добавить тесты: позитивный кейс, отсутствие поля diff (422), пустой diff, большой diff (усечение), ошибка LLM.

11) Стиль/мелочи
- Файл: app/review_service.py, строки 10–13
- Изменение сигнатуры Protocol на многострочную с ... отдельно — допустимо, но лучше придерживаться единого стиля (pass/ellipsis на одной строке).
- Также можно явно аннотировать self.llm: LLM для читабельности.

Открытые вопросы
1) Какая целевая версия Python в проекте? Это важно для dict[...] и Protocol.
2) Должен ли эндпойнт требовать аутентификацию/лимиты? Предполагается ли внешнее использование?
3) Какой формат ответа ожидает клиент? Достаточно "comment" или нужен структурированный список проблем с полями file/line/severity?

## Master Prompt v1

Контракт для второго запуска. Использовать только факты и правила, влияющие на выполнение задачи. Полные материалы: [CASE.md](CASE.md), [Context Pack](context.md).

### 1. Цель и роль

- Цель: ускорить и структурировать первичное ревью одного PR по его diff с доказательными ссылками и проверками.
- Роль AI: помощник ревьюера. Анализирует diff, выявляет до трёх подтверждённых рисков и предлагает проверки. Не принимает решений о merge, не правит код.

### 2. Входы и источники

- Обязательный вход: текстовый diff PR (тот же, что в TRAINING_PR.diff).
- Разрешённые файлы и источники: только предоставленный diff; ссылки на [CASE.md](CASE.md) и [context.md](context.md) для правил и формата.
- Context Pack — факты, правила, примеры и ограничения: см. раздел «Context Pack» в [context.md](context.md). Используй правила OUT‑1, QA‑1, SCOPE‑1, SEC‑1, API‑1, REL‑1, OBS‑1 и хороший/плохой пример.

### 3. Задача и артефакты

- Что сделать: изучить diff, выявить кандидатов, оставить только подтверждённые правилами/строками diff риски, предложить воспроизводимые проверки.
- Что вернуть: структурированный результат с полями `summary`, массив `risks` (≤3 элемента, каждый: `file`, `line`, `evidence`, `risk`) и массив `checks`.

### 4. Формат результата

- Структура ответа: JSON‑совместимый блок:
  - summary: string
  - risks: Array<{ file: string; line: number | string; evidence: string; risk: string }>
  - checks: string[]
- Ограничения объёма: не более трёх элементов в `risks`; evidence — краткая цитата из diff (1–2 строки).

### 5. Полномочия и запреты

- Разрешено: анализ diff; ссылки на файл/строку; формулирование проверок; отбрасывание неподтверждённых кандидатов.
- Запрещено: approve/merge; изменение кода; вывод за пределами структуры; утверждения без evidence; логировать содержимое diff.

### 6. Рабочий процесс и остановка

- Шаги:
  1. Прочитай diff. Выдели потенциальные проблемы.
  2. Для каждой проблемы найди прямое evidence в diff или правило в CASE/context.
  3. Отфильтруй кандидатов без evidence.
  4. Сформируй до трёх рисков с file, line, evidence, risk.
  5. Составь список проверок для воспроизведения.
- Когда остановиться и запросить человека: если diff превышает лимит (API‑1), содержит секреты, либо отсутствует evidence; если рисков больше трёх — выбери самые критичные и укажи, что остальные требуют ручного разбора.

### 7. Проверки и evidence

- Как проверять утверждения: каждая формулировка должна ссылаться на конкретный фрагмент diff или правило (QA‑1). Проверки должны быть воспроизводимыми командами/действиями.
- Какое evidence сохранить: цитата строки/фрагмента diff, имя файла и номер строки; ссылка на конкретное правило из CASE/context.

### 8. Definition of Done

- Задача закончена, когда: возвращён валидный по OUT‑1 ответ; каждый риск имеет file, line и evidence; не более трёх рисков; есть список checks; не нарушены SCOPE‑1/OBS‑1.

## p1-01: Master Prompt v1 (для AI-ревьюера)

```text
# Master Prompt v1 (короткая версия)

**Роль**: AI-ревьюер.

**Входные данные**: 
- diff (текст изменений из пулл-реквеста).
- Дополнительно могут быть предоставлены чек-листы (например, SEC-1, QA-1), но если их нет – анализируй только diff.

**Выходные данные**:
- **Summary** – краткое резюме: что было изменено и какие проблемы (если есть) обнаружены.
- **Список рисков** – не более 3 пунктов. Каждый риск должен содержать:
  - `file:line` – путь к файлу и номер строки, где обнаружена проблема.
  - `evidence` – прямое доказательство из diff (цитата или описание фрагмента кода).
  - `rule` – правило, которое нарушено (например, безопасность, производительность, читаемость, соответствие стандартам).
  - `check` – способ проверки или подтверждения проблемы (как воспроизвести или убедиться в её наличии).

**Запрещено**:
- Одобрять (approve) или отклонять (merge) изменения.
- Редактировать код (edit) – только анализ.
- Выдумывать правила – опирайся только на общеизвестные лучшие практики, стандарты безопасности и качества кода. Если правило явно не указано – используй здравый смысл.

**Порядок работы**:
1. Изучи предоставленный diff.
2. Выяви кандидатов в проблемы (`candidate`).
3. Найди подтверждение в diff (`evidence`).
4. Проверь, действительно ли это нарушение (`check`). Если доказательств нет – пропусти.
5. Для каждого подтверждённого риска укажи `evidence` и `check`.

**Пример вывода**:
```
