## P1-01 Полный результат

Контекст и команда запуска:
- Использовали только приложенный diff `practices/practice_01/TRAINING_PR.diff`, другие файлы не читались.
- Команда: `opencode run --agent plan --file practices/practice_01/TRAINING_PR.diff "Используй только приложенный diff. Не читай другие файлы репозитория. Посмотри PR и найди проблемы."`

Findings (по важности):
- High: app/api.py:35-38 — отсутствие валидации тела запроса. Используется `payload: dict` и прямой доступ `payload["diff"]`. Если ключ отсутствует или тип не строка, будет KeyError и 500 вместо 422. Нужно Pydantic-модель или хотя бы проверка с явной 422/400.
- High: app/review_service.py:19-22 — отсутствие обработки ошибок LLM. Любая ошибка `llm.generate` приведет к 500. Нужен try/except с осмысленным ответом и логированием.
- High: app/review_service.py:19-22 — риск DoS/переполнения токенов: весь diff без ограничений попадает в prompt. Большие диффы могут уронить производительность или вызвать ошибки у LLM. Нужны лимиты, усечение, чанкинг или суммаризация.
- Medium: app/api.py:35-38 — sync endpoint вызывает потенциально долгий/сетевой вызов `llm.generate`. Если реализация LLM блокирующая, это может ухудшать throughput. Возможно стоит сделать `async` и/или использовать фоновые задачи, очередь.
- Medium: app/api.py:35-38 — нет аутентификации/авторизации и защиты от злоупотреблений. Публичный POST, который тратит ресурсы LLM.
- Medium: app/api.py:35-38 — нет явной схемы ответа (`response_model`) и контрактов; это ухудшает OpenAPI-документацию и валидацию ответа.
- Medium: app/review_service.py:19-22 — структура ответа фиксирована как `{"comment": <str>}`. Для реальных ревью часто нужен список находок с типами/ссылками; текущая форма ограничивает клиентов.
- Low: app/api.py:36 — аннотации `dict[str, str]` требуют Python 3.9+. Если проект <3.9, будет RuntimeError при импорте. Альтернатива: `Dict[str, str]` из `typing` или `from __future__ import annotations`.
- Low: app/review_service.py:9-13 — косметическая смена стиля объявления метода в Protocol; функционально без изменений, но не несет пользы.
- Low: Сообщение-промпт на английском, возможно несоответствие ожиданиям команды/потребителей.

Открытые вопросы:
- Какая версия Python в проекте? Это влияет на использование `dict[str, str]`.
- Реализация `llm.generate` синхронная или асинхронная? Нужна ли поддержка async.
- Какие ограничения по размеру diff и ожидания по формату результата? Нужны ли множественные комментарии/категории/ссылки на строки?
- Требуется ли аутентификация для эндпоинта и лимиты запросов?

Краткая рекомендация изменений:
1. Ввести Pydantic-модель для запроса и ответа; валидировать наличие и тип `diff`; возвращать 422 при нарушении.
2. Ограничить размер входного `diff` и/или реализовать разбиение/суммаризацию.
3. Обернуть вызов LLM в обработку ошибок, логировать, возвращать контролируемые ответы.
4. Рассмотреть `async`-обработчик или фоновые задачи, если LLM-запросы долгие.
5. Добавить `response_model` для документации/валидации, тесты на happy-path и ошибки (нет `diff`, большой `diff`, ошибка LLM).
6. При необходимости — аутентификация и базовые лимиты/квоты.

## Master Prompt v1

Соберите здесь контракт второго запуска. Не копируйте все документы целиком — ставьте ссылки на файлы и переносите только необходимый для задачи контекст.

### 1. Цель и роль

- Цель: провести ревью PR по diff и выделить максимум 3 проверяемых риска с привязкой к правилам.
- Роль AI: AI‑reviewer.

### 2. Входы и источники

- Обязательный вход: `TRAINING_PR.diff`.
- Разрешённые файлы и источники: только предоставленный diff и список правил SEC‑1…QA‑1.
- Context Pack — факты, правила, примеры и ограничения: см. `context.md` раздел «Context Pack…»; следовать потоку candidate -> evidence -> check; не придумывать правила; запрет approve/merge/edit.

### 3. Задача и артефакты

- Что сделать: на основе diff сформировать кандидатов проблем, оставить только те, где есть evidence в diff; сопоставить с правилами.
- Что вернуть: summary изменений + ≤3 риска с file:line, evidence (цитата) и ссылкой на правило + для каждого риск — check (как воспроизвести/проверить).

### 4. Формат результата

- Структура ответа: Summary; Risks: список элементов {file:line, evidence, rule, check}.
- Ограничения объёма: не более 3 рисков.

### 5. Полномочия и запреты

- Разрешено: использовать только diff и правила, выносить проверяемые выводы.
- Запрещено: approve, merge, edit; придумывать правила; ссылаться на файлы вне diff.

### 6. Рабочий процесс и остановка

- Шаги: 1) Прочитать diff. 2) Сформировать кандидатов. 3) Для каждого найти evidence. 4) Сопоставить правило. 5) Сформулировать check. 6) Оставить ≤3. 7) Вернуть результат.
- Когда остановиться и запросить человека: если нет ни одного риска с evidence или правила недостаточны для однозначной проверки.

### 7. Проверки и evidence

- Как проверять утверждения: для каждого риска предоставить шаги проверки, воспроизводимые локально (запрос/мок/границы входа).
- Какое evidence сохранить: точные цитаты строк diff с file:line.

### 8. Definition of Done

- Задача закончена, когда: выдан summary, до 3 рисков, у каждого есть file:line, evidence и правило, и описан check. Нет запретных действий и выдуманных правил.
