# Integration-проверки

| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Ссылка на источник |
|---|---|---|---|---|
| `FastAPI` → `ReviewService` → `LLM` | Дифф с токенами/паролями уходит во внешний LLM без очистки | Отправить `POST /api/reviews` с diff, содержащим `token=abc123` и блок `-----BEGIN PRIVATE KEY-----`; использовать заглушку LLM | В prompt вместо секретов стоят `[REDACTED]`, исходные значения отсутствуют | `CASE.md` — правило SEC-1 |
| `FastAPI` → `ReviewService` | Ответ не соответствует контракту OUT-1 (возвращается `comment` вместо структуры) | Отправить `POST /api/reviews` с коротким валидным diff; проверить JSON-структуру ответа | Ответ содержит поля `summary`, `risks` (не более 3), `checks` | `TRAINING_PR.diff:22` (`return {"comment": answer}`) |
| `FastAPI` → `ReviewService` | Нет отклонения слишком длинного diff; запрос проходит в LLM | Отправить `POST /api/reviews` с payload.diff длиной > 20 000 символов | HTTP 413, `ReviewService`/`LLM` не вызываются | `CASE.md` — правило API-1 |
| `ReviewService` → `LLM` | Нет таймаута 10 сек; зависание или необработанное исключение | Внедрить LLM-заглушку, которая отвечает >10 сек или бросает timeout | Завершение за ~10 сек и контролируемый ответ в формате OUT-1 (summary описывает таймаут) | `CASE.md` — правило REL-1 |

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): P1-01 (zero-shot, baseline), P2-05 (RAG, привязка интеграционных тестов к источникам).
- Что проверили и исправили сами: добавлен тест на `SEC-1`; указаны конкретные HTTP-коды ответа согласно правилам `CASE.md`; с помощью RAG (P2-05) каждый тест-кейс жёстко привязан к документу с требованиями или конкретной строке в diff, где сейчас допущена ошибка.
