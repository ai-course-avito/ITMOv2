# Integration-проверки

Проверяются стыки, на которых unit-тесты ничего не ловят: у каждого компонента по отдельности контракт соблюдён, а на границе теряется. Внешний LLM по-прежнему замокан — граница с провайдером проверяется в [`tests_load.md`](tests_load.md) и [`tests_e2e.md`](tests_e2e.md).

| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Evidence |
|---|---|---|---|---|
| `POST /api/reviews` → `ReviewService` | тело запроса не содержит ключ `diff`: `payload["diff"]` даёт `KeyError` и голый HTTP 500 | POST с телом `{}` | HTTP 4xx с внятным сообщением, трассировки в ответе нет, LLM не вызван | тело ответа, `mock.call_count == 0` |
| отсечка длины → редактор секретов | порядок перепутан: секрет успевает попасть в промпт до отказа по длине | дифф в 20 001 символ с токеном внутри | HTTP 413; редактор и LLM не вызывались | порядок вызовов на моках |
| редактор секретов → LLM-клиент | наружу уходит исходный дифф вместо очищенного | дифф с токеном, мок клиента сохраняет полученный промпт | в промпте `[REDACTED]`, токена нет | сохранённый моком аргумент |
| редактор секретов → сверка evidence | сверка идёт с очищенным диффом, из-за чего риск на строке с секретом отбрасывается как невоспроизводимый | дифф с токеном; ответ модели цитирует строку, попавшую под редакцию | риск сохранён: сверка выполняется с исходным диффом | список `risks` до и после сверки; пунктирная связь на схеме в [`adr.md`](adr.md) |
| LLM-клиент → валидатор | сырой текст модели уходит клиенту в обход схемы | мок возвращает `"Код выглядит нормально"` | контролируемая ошибка, текста модели в HTTP-ответе нет | тело ответа |
| LLM-клиент → валидатор | ответ проходит схему, но содержит четыре риска | мок возвращает валидный JSON с `risks` из четырёх элементов | ответ отклонён по `OUT-1`, наружу не уходит | код причины отклонения |
| валидатор → HTTP-слой | причина отклонения теряется, клиент получает 500 без контекста | те же два входа, что выше | стабильный код ответа и различимая причина отказа | сравнение двух ответов между собой |
| таймаут → HTTP-слой | таймаут внутри клиента отрабатывает, но наружу выходит как 500 | мок засыпает на 11 секунд | контролируемый ответ не позднее 10 секунд | замер времени запроса целиком, код ответа |
| сквозной путь → лог | запись лога формируется на слое, который видит дифф, и содержимое утекает в лог | один запрос с токеном в диффе, перехват логгера | в записи только `request_id`, длительность, статус | перехваченные записи за время запроса |

Ключевая проверка здесь четвёртая. Редакция секретов и сверка evidence по отдельности корректны, но если сверку подключить к очищенному тексту, сервис начнёт молча выбрасывать именно те риски, ради которых написан: нарушение `SEC-1` живёт ровно на той строке, которую редактор и затирает.

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): `P1-02`.
- Что проверили и исправили сами: первую строку таблицы взяли из разбора `P1-01` — замечание про `KeyError` на `payload["diff"]` доказуемо по диффу, но не покрыто ни одним правилом репозитория, поэтому в `risks` оно не пошло, а в integration-проверки пошло. Четвёртую строку нашли при разборе схемы в [`adr.md`](adr.md), а не из ответа модели: в первом варианте схемы сверка шла с очищенным диффом, и связь заметили только когда стали рисовать поток данных.
