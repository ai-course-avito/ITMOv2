# Integration-проверки

Проверяются стыки между компонентами. Внешний LLM заменён управляемой заглушкой, всё остальное работает по-настоящему.

| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Evidence |
|---|---|---|---|---|
| HTTP-слой → валидатор размера → клиент LLM | Проверка размера выполняется после внешнего вызова, и большой diff всё равно уходит наружу | `POST /api/reviews` с diff на 25000 символов, заглушка LLM считает обращения | HTTP 413, счётчик обращений к заглушке равен нулю | `API-1`, строка «Размер входа» в [`analysis.md`](analysis.md) |
| Удаление секретов → клиент LLM | Секрет вычищается из копии, а в промпт уходит исходный текст | Запрос с diff, содержащим тестовый токен, заглушка сохраняет полученный промпт | В сохранённом промпте есть `[REDACTED]` и нет исходного токена | `SEC-1`, строка «Секреты внутри diff» в [`analysis.md`](analysis.md) |
| Клиент LLM → внешний провайдер | Таймаут не доходит до HTTP-слоя, наружу выходит HTTP 500 | Заглушка отвечает через 11 секунд | Ревьюер получает контролируемый ответ об ошибке, код ответа не 500 | `REL-1`, сценарий «Негативный, внешний вызов не уложился в таймаут» в [`product_management.md`](product_management.md) |
| Хранилище правил → фильтр рисков | Фильтр опирается на зашитый список, а не на хранилище | Правило удалено из набора, заглушка возвращает риск с ссылкой на него | Риск в ответ не попадает | `QA-1`, хранилище D1 на схеме в [`analysis.md`](analysis.md) |
| Сборка ответа → HTTP-слой | Ответ отдаётся в форме, не соответствующей контракту | Обычный запрос, ответ проверяется валидатором схемы | Ответ содержит `summary`, `risks` и `checks`, каждый риск с `file`, `line`, `evidence`, `risk` | `OUT-1` в [`CASE.md`](CASE.md) |
| Весь путь запроса → журнал | В журнал попадает содержимое diff или ответ модели | Запрос с секретом внутри diff, после него читается журнал | В журнале только `request_id`, длительность и статус | `OBS-1`, инкремент 3 в [`project_management.md`](project_management.md) |
