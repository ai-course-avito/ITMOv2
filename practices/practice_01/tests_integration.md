| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Evidence |
|---|---|---|---|---|
| Сервис ↔ внешний LLM | Таймаут вызова LLM (10 секунд) не превращается в контролируемый ответ, а приводит к зависанию или необработанному исключению | Мок внешнего LLM, который не отвечает дольше 10 секунд (например, засыпает на 15 секунд); отправляем в сервис diff в пределах лимита `API-1` | Сервис завершает обработку запроса не позднее ~10 секунд с момента вызова LLM и возвращает контролируемый ответ об ошибке (HTTP-статус ошибки, а не 200); необработанное исключение или зависание процесса отсутствует | REL-1; время ответа сервиса ≤ 10 с (замер по времени вызова, допуск до 10.5 с на накладные расходы); тело ответа содержит поле статуса ошибки, а не поля `summary`/`risks`/`checks` |
| Сервис ↔ внешний LLM | Ошибка провайдера (HTTP 500) или невалидный JSON в ответе LLM приводит к необработанному исключению вместо контролируемого ответа | Мок внешнего LLM: первый прогон возвращает HTTP 500; второй прогон возвращает тело `"{not valid json"` вместо ожидаемого JSON. Diff в пределах лимита | В обоих прогонах сервис возвращает контролируемый ответ об ошибке (не 200, без стектрейса в теле ответа); процесс не завершается аварийно | REL-1; HTTP-статус ответа сервиса — код ошибки (не 2xx) в обоих прогонах; в теле ответа отсутствует текст трассировки исключения (`Traceback`) |
| Сервис ↔ вызывающая сторона (HTTP API) | Diff свыше лимита 20 000 символов всё равно уходит на обращение к LLM, вместо отказа до вызова | Отправляем запрос с diff длиной 20 001 символ; мок внешнего LLM настроен так, чтобы фиксировать факт вызова (счётчик обращений) | Сервис возвращает HTTP 413 без обращения к LLM; счётчик обращений к моку LLM остаётся равным 0 | API-1; HTTP-статус ответа `413`; счётчик вызовов мока LLM `== 0` после запроса |
| Сервис ↔ подсистема логирования | После обработки запроса в лог попадает содержимое diff или текст ответа модели вместо только `request_id`, длительности и статуса | Отправляем в сервис diff с уникальной меткой в тексте, например `"UNIQUE_DIFF_MARKER_9f3a"`, и настраиваем мок LLM так, чтобы он возвращал ответ с меткой `"UNIQUE_MODEL_MARKER_7b2c"`; после запроса читаем полную лог-запись, созданную для этого `request_id` | Лог-запись содержит только поля `request_id`, длительность и статус; строки `"UNIQUE_DIFF_MARKER_9f3a"` и `"UNIQUE_MODEL_MARKER_7b2c"` в ней отсутствуют | OBS-1; отсутствие подстрок `"UNIQUE_DIFF_MARKER_9f3a"` и `"UNIQUE_MODEL_MARKER_7b2c"` в тексте лог-записи; набор ключей лог-записи равен `{"request_id", "duration_ms", "status"}` |

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): P1-03.
- Что проверили и исправили сами: убедились, что каждая строка проверяет именно стык между двумя компонентами (сервис и мок внешнего LLM, сервис и вызывающая сторона, сервис и логирование), а не изолированную функцию — это отличает файл от `tests_unit.md`; для каждого сценария зафиксировали конкретный наблюдаемый результат (HTTP-статус, счётчик вызовов, конкретные строки-метки в логе), а не общую формулировку «обработал корректно»; сверили каждую строку с кодом правила из `CASE.md` (`REL-1`, `API-1`, `OBS-1`); проверили, что сценарий с превышением лимита `API-1` явно доказывает отсутствие обращения к LLM (счётчик = 0), а не только код ответа.
