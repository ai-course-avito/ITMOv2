# Integration-проверки

| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Подтверждение |
|---|---|---|---|---|
| FastAPI `create_review` → `review_service.review` | `KeyError`, если в теле нет `diff` | `POST /api/reviews` с телом `{}` | Не «тихий» 200 с валидным ревью; зафиксировать фактический статус (сейчас по diff вероятен необработанный `KeyError`/500). Желаемый контракт 4xx — **Открытый вопрос** | HTTP-тест / TestClient |
| API → сервис → LLM | Падение `llm.generate` пробрасывается без контролируемого ответа | Mock LLM бросает исключение; `POST` с `{"diff": "..."}` | Зафиксировать фактический ответ. Целевой контролируемый 5xx/ошибка клиенту — **Открытый вопрос** | Integration-тест с mock |
| Валидный путь API → сервис → LLM | Неверный ключ ответа или пустой comment | `POST /api/reviews` с `{"diff": "valid patch"}`, mock возвращает `"nits found"` | HTTP 200, тело содержит ключ `comment` со значением от mock | Integration-тест |
| Помощник ревьюера ↔ вход только diff | Выдуманные требования вне diff | Прогон master prompt на `TRAINING_PR.diff` | Нет утверждений о прод-SLA/тестах как о фактах; пробелы — «Открытый вопрос» | Разметка ответа P1-02 |

## Как использовали AI

- Для чего: integration-сценарии API ↔ сервис ↔ LLM и проверка границ промпта.
- Тип промпта: master prompt / test design.
- Строка в [`prompts.md`](prompts.md): P1-01 и P1-02.
- Что проверил студент и какие исправления поручил агенту: ожидаемые HTTP-коды ошибок без контракта в diff не навязаны как факт.
