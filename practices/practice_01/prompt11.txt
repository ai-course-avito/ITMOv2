Ниже — обзор PR с фокусом на риски, регрессии и недостающие проверки. Ссылки даны на изменённые файлы и строки из диффа.
Findings (по убыванию критичности)
- app/api.py:35-38 — Нет валидации входа, используется сырой dict и прямой доступ к ключу. payload["diff"] при отсутствии ключа приведёт к KeyError и 500 вместо 422. Нужно явное описание схемы запроса через Pydantic-модель и автоматическая валидация.
- app/api.py:35-38 — Нет response_model. Описание ответа в OpenAPI будет расплывчатым (arbitrary object), что ухудшит DX и может сломать автогенерацию клиентов.
- app/api.py:35-38 — Нет обработки ошибок LLM. Любое исключение из review_service.review/llm.generate даст 500 без понятной диагностики. Для внешнего API стоит маппить на 4xx/5xx с контролируемыми сообщениями.
- app/api.py:35-38 — Нет аутентификации/авторизации на новом эндпоинте. Если сервис публичный/многоарендный, это прямой риск.
- app/review_service.py:19-22 — Нет ограничений на размер diff. Прямое включение всего диффа в prompt может превысить лимиты токенов LLM или резко удорожить запрос. Нужны ограничения/усечение, возможно разбиение на чанки.
- app/review_service.py:19-22 — Формат промпта и результата нефиксирован. LLM возвращает произвольный текст, а сервис оборачивает его в {"comment": ...}. Это делает контракт неустойчивым: клиенты не смогут надёжно парсить/структурировать замечания. Нужен стабильный формат ответа (список замечаний, типы, ссылки на файлы/строки).
- app/api.py:35-38 — Синхронный хендлер и синхронный вызов LLM. Если LLM — сеть/IO, то это блокирует воркер-потоки Uvicorn/Starlette. В FastAPI синхронные роуты гоняются в threadpool, но лучше явное async с неблокирующей реализацией клиента или отдельный воркер.
- app/dependencies.review_service — Сопряжение по контракту. Новый API вызывает метод review. Если в app.dependencies экспортируется именно экземпляр ReviewService, всё ок; если ранее там был другой тип (функция/обёртка) — будет AttributeError. Дифф не показывает изменения в dependencies, это зона риска.
- app/review_service.py:9-13 — Изменение сигнатуры LLM.generate формально не произошло, но стиль тела метода в Protocol поменян с однострочного на многострочный. Это не ошибка, но лишний шум в диффе; придерживайтесь одного стиля.
- app/api.py:35-38 — Нет логирования входящих запросов/исключений. Труднее будет расследовать сбои и эксплуатационные инциденты.
- Общий контракт — Нет тестов на новый эндпоинт и сервис: минимально нужны юнит-тесты на ReviewService.review (мокаем LLM) и интеграционный тест на /api/reviews с валидным и невалидным телом.

Рекомендованные изменения (кратко)
1. Ввести Pydantic-модели:
- ReviewRequest { diff: str }
- ReviewResponse { comment: str } или лучше структурированный список findings; указать response_model.
2. Валидация и обработка ошибок:
- Проверка наличия поля diff, возврат 422 при невалидном теле.
- Обёртка вокруг вызова LLM с преобразованием ошибок в HTTPException 502/503.
3. Управление размером входа:
- Ограничить размер diff (например, до N символов/строк) и явно усекать/чанкать.
4. Контракт результата:
- Договориться о стабильной схеме (например, список {file, line, severity, message}), чтобы клиенты могли автоматизировать отображение.
5. Технически:
- Убедиться, что app.dependencies.review_service — это экземпляр ReviewService.
- Добавить базовое логирование.
- Добавить тесты на сервис и эндпоинт.
