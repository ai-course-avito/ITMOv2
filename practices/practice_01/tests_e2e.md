# E2E-проверки

| Сценарий пользователя | Предусловия | Действие | Наблюдаемый результат | Evidence |
|---|---|---|---|---|
| Позитивный — ревьюер получает структурированный отчёт | Сервис запущен; LLM-стаб возвращает валидный ответ; diff без секретов, длина < 20 000 символов | `POST /api/reviews` с `{ "diff": "<валидный diff>" }` | HTTP 200; тело содержит `summary` (строка), `risks` (массив ≤ 3 элементов с `file`, `line`, `evidence`, `risk`), `checks` (массив строк) | Проверить схему ответа через `pydantic.parse_obj_as(ReviewResponse, body)` |
| Негативный — diff содержит секрет | Сервис запущен; diff содержит строку `SECRET_KEY=abc123` | `POST /api/reviews` с `{ "diff": "...SECRET_KEY=abc123..." }` | HTTP 400; LLM-стаб не вызывался (`assert not llm_mock.called`); тело содержит описание ошибки `SEC-1` | Проверить вызов LLM через мок; проверить статус ответа |
| Граничный — LLM недоступен | Сервис запущен; LLM-стаб бросает `TimeoutError` через 10 с | `POST /api/reviews` с валидным diff | HTTP 503; тело содержит поле `error` с читаемым описанием (`REL-1`); ответ получен не позже 11 с | Измерить wall-clock время ответа; проверить статус и поле `error` |

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): P1-01 — Open Questions из zero-shot (что происходит при ошибке LLM, при большом diff) стали основой для граничного и негативного сценариев.
- Что проверили и исправили сами: добавлено измерение wall-clock времени для проверки `REL-1`; позитивный сценарий использует Pydantic-валидацию ответа, а не сравнение строк — это надёжнее.
