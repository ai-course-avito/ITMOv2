# E2E-проверки

| Сценарий пользователя | Предусловия | Действие | Наблюдаемый результат | Evidence |
|---|---|---|---|---|
| Позитивный | Сервис доступен; внешний LLM отвечает в пределах таймаута; на вход подаётся `TRAINING_PR.diff` (1102 символа, в пределах лимита `API-1`) | Ревьюер отправляет `TRAINING_PR.diff` в эндпоинт сервиса (`POST /api/reviews`) и получает ответ | Ответ содержит `summary` (непустая строка), массив `risks` из не более трёх элементов, каждый с непустыми полями `file`, `line`, `evidence`, `risk`, и массив `checks`; ревьюер не видит в ответе действий approve/merge/изменения кода | OUT-1, QA-1, SCOPE-1; тело ответа с ключами `summary`, `risks` (`len(risks) <= 3`, у каждого элемента заполнены `file`/`line`/`evidence`/`risk`), `checks`; в ответе отсутствуют поля или действия вида `approved`, `merged`, `patched_files` |
| Негативный | Сервис доступен; на вход подаётся diff длиной 20 001 символ (искусственно дополненный `TRAINING_PR.diff`) | Ревьюер отправляет этот diff в эндпоинт сервиса | Сервис отклоняет запрос до какого-либо обращения к внешнему LLM; ревьюер получает ответ, а не зависание | API-1; HTTP-статус ответа `413`; тело ответа не содержит полей `summary`/`risks`/`checks`, характерных для успешного разбора |
| Граничный | Сервис доступен; внешний LLM намеренно не отвечает 10 секунд (симулируется задержкой провайдера); на вход подаётся `TRAINING_PR.diff` | Ревьюер отправляет `TRAINING_PR.diff` в эндпоинт сервиса и ждёт ответ | Ревьюер получает контролируемый ответ об ошибке в пределах ~10 секунд, а не зависший запрос без ответа; сервис не выполнил approve, merge и не изменил код в GitHub | REL-1, SCOPE-1; время ответа ≤ 10 с (замер от отправки запроса до получения ответа, допуск до 10.5 с); HTTP-статус ответа — код ошибки (не 200); в GitHub у тестового PR отсутствуют новые approve/merge/коммиты от сервиса за период проверки |

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): P1-03.
- Что проверили и исправили сами: сверили позитивный сценарий с полями `summary`/`risks`/`checks` и ограничением на три риска из `OUT-1`, а также с `QA-1` (риск не попадает без подтверждения); проверили, что негативный сценарий воспроизводится конкретным числом символов (20 001) и конкретным HTTP-статусом (413) по `API-1`; для граничного сценария зафиксировали, что ожидаемый результат — контролируемая ошибка в пределах таймаута `REL-1`, а не факт «сервис не завис»; отдельно добавили проверку `SCOPE-1` в граничном сценарии (отсутствие approve/merge/изменений кода в GitHub), как того требует задача; убедились, что структура таблицы (три строки: позитивный/негативный/граничный) совпадает с заготовкой.
