Ниже — ревью по диффу. Сначала проблемы (по убыванию серьезности), затем вопросы и краткое резюме изменений.
Проблемы
Высокая серьезность
1. app/api.py:create_review — отсутствие валидации входа и неграциозные ошибки
- Используется тип payload: dict без Pydantic-модели. При отсутствии ключа "diff" будет KeyError и 500 вместо ожидаемого 422 Unprocessable Entity.
- Нет явной схемы тела запроса в OpenAPI.
Риск: нестабильное поведение API и плохой DX.
Решение: ввести Pydantic-модель запроса/ответа, автоматически получите валидацию и корректные 422.
2. app/review_service.py:ReviewService.review — отсутствие ограничений на размер diff
- Весь diff без ограничений включается в промпт. Большие патчи приведут к превышению токенов/таймаутам/взрывам стоимости.
Решение: ограничить размер входного diff (обрезка, чанкинг, суммаризация), возвращать 413 или обрабатывать асинхронно.
Средняя серьезность
3) app/api.py:create_review — отсутствие обработки ошибок LLM
- Исключения/ошибки от self.llm.generate приведут к 500 без пояснений.
Решение: перехватывать ошибки провайдера, маппить на 503/502/504 с понятным сообщением и логированием.
4. app/api.py:create_review — синхронный эндпоинт, потенциальная блокировка воркера
- Вызов LLM может быть долгим; синхронная функция блокирует обработчик запросов.
Решение: сделать async-эндпоинт и вызывать LLM в threadpool/async-клиенте, либо перевести на фоновые задачи (BackgroundTasks/очередь).
5. app/api.py:create_review — отсутствие response_model
- Возврат «сырого» dict ухудшает спецификацию и валидацию ответа.
Решение: задать Pydantic-модель ответа и response_model в декораторе.
Низкая серьезность
6) app/review_service.py:LLM Protocol — стиль объявления метода
- Перенос с «... в той же строке» на многострочный вариант не несет пользы и снижает читабельность. Нефункционально, но стилистически спорно.
7. app/review_service.py:ReviewService.review — формат промпта
- Для устойчивости и читаемости промпта полезно обрамлять diff в тройные кавычки/блок кода, указывать краткую инструкцию и формат ответа.
Решение: добавить явные маркеры и инструкцию, чтобы снизить «дрейф» ответа.
8. Отсутствуют тесты
- Нет юнит-теста на ReviewService.review и интеграционного теста эндпоинта POST /api/reviews (валидный/невалидный вход, большие дифы, ошибка LLM).
Открытые вопросы
1. Целевая версия Python? Использование dictstr, str требует 3.9+. Если проект на 3.8 — потребуется from future import annotations или typing.Dict.
2. Ожидаемый контракт API: только поле diff? Нужны ли метаданные (repo, автор, язык, лимиты)?
3. Предполагаемый максимум размера diff и SLA времени ответа? Нужны ли асинхронные задачи/очередь?
4. Требуются ли аутентификация/квоты/лимиты для этого эндпоинта?
Краткое резюме изменений
- Добавлен ReviewService.review, который формирует промпт и вызывает LLM.
- Добавлен POST /api/reviews, принимающий dict и возвращающий ответ ReviewService.
Рекомендации по минимальным правкам
1. Ввести Pydantic-модели:
- ReviewRequest { diff: str }
- ReviewResponse { comment: str }
И использовать их в эндпоинте с response_model.
2. Обработать отсутствие diff и ошибки LLM (422/5xx).
3. Ограничить размер diff (обрезка/413) или сделать асинхронную обработку.
4. Небольшой рефактор промпта: обрамить diff в блок кода и дать четкую инструкцию формата ответа.
5. Добавить базовые тесты.
