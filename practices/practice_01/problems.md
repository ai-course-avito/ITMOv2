# Проблемы и риски по результатам ревью P1-01/P1-02

## Критичные

- app/api.py:35-38 — Невалидированный body и небезопасный доступ к `payload["diff"]`, возможен 500 вместо 4xx.
- app/api.py:35-38 — Нет обработки ошибок на пути к LLM; любые исключения приводят к 500 без контролируемого ответа.
- app/review_service.py:19-22 — Риск prompt‑инъекций: сырой diff вставлен в промпт без изоляции и инструкций.
- app/review_service.py:19-22 — Неограниченный размер входа: большие диффы могут переполнить контекст модели и увеличить задержку/стоимость.

## Значимые

- app/api.py:35-38 — Нет Pydantic‑схем запроса/ответа; контракт API неформализован.
- app/api.py:35-38 — Отсутствует аутентификация/авторизация и базовые лимиты, возможна злоупотребление сервисом.
- app/review_service.py:19-22 — Неструктурированный вывод (`{"comment": str}`) затрудняет постобработку и визуализацию.
- app/api.py:35-38 — Риски по задержке/конкурентности из‑за синхронного хендлера при сетевом `llm.generate`.
- app/review_service.py:9-13 — Совместимость типов: `dict[str, str]` требует Python ≥3.9.

## Минорные

- app/review_service.py:9-13 — Косметическая правка сигнатуры `LLM.generate` без функциональной необходимости.
- app/api.py:35-38 — Семантика статуса ответа для создания обзора (200 vs 201) не определена.
- Отсутствуют логи/метрики вокруг запросов обзора (размер diff, latency, коды ошибок).
- Нет тестов на валидацию входа и базовый путь с мок‑LLM.

## Открытые вопросы

- Гарантированная версия Python в рантайме/CI.
- Требуется ли аутентификация/авторизация и какой механизм выбрать.
- Максимальный допустимый размер `diff` и ожидаемая SLA генерации.
- Нужен ли структурированный формат ответа (с перечнем находок) вместо одного текста.

## Предлагаемые шаги (без имплементации)

- Ввести Pydantic‑модели `ReviewRequest` и `ReviewResponse` для API.
- Добавить обработку ошибок вокруг вызова `review_service.review` с логированием и корректными кодами 4xx/5xx.
- Усилить промпт: системные инструкции и явные разделители `<<BEGIN_DIFF>>`/`<<END_DIFF>>`; ограничить размер входа.
- Рассмотреть структурированный JSON‑вывод с валидацией схемы.
- Подумать об аутентификации и rate limiting, если сервис не внутренний.
- Добавить базовые тесты и наблюдаемость.
