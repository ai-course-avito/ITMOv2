Ниже — результаты кодаудита по диффу practices/practice_01/TRAINING_PR.diff. Сначала — проблемы по важности с ссылками на файлы/участки, затем вопросы и краткие рекомендации.

Проблемы (по важности)
- app/api.py ("/api/reviews", строки 35-38)
  - Отсутствие валидации входа. Параметр объявлен как `payload: dict`, доступ к `payload["diff"]` без проверки. Если поля нет или тип не строка, будет KeyError/500 вместо 422. В FastAPI лучше использовать Pydantic-модель входа.
  - Нет схемы ответа (`response_model`). Сейчас возвращается произвольный `dict[str, str]`, что усложняет контракт и валидацию/документацию (OpenAPI).
  - Нет обработки ошибок. Исключения из `review_service.review`/LLM приведут к 500 без дружелюбного ответа.
  - Без аутентификации/авторизации. Публичный POST-эндпоинт, который вызывает LLM, открывает возможность злоупотребления, накручивания затрат и DoS.
  - Потенциальный DoS по объему. Нет ограничения размера `diff`, он напрямую отправляется в LLM. Большие диффы перегрузят модель, приведут к таймаутам/расходам.
  - Синхронный вызов длительной операции. `create_review` синхронный, LLM вызов может занять секунды/десятки секунд. Под нагрузкой это блокирует воркеры (хоть FastAPI и вынесет sync в threadpool), лучше явный контроль: таймауты, очереди, фоновая задача, или асинхронная реализация.
- app/review_service.py (метод ReviewService.review)
  - Нет нормализации/ограничения входа. Принимает `diff` как есть, без проверки пустых/слишком больших значений, без усечения/санитайза. Риск инжекции подсказки (prompt injection) и утечки системных инструкций LLM.
  - Нет таймаутов/ретраев/логирования. Любая ошибка/подвисание LLM приведет к 500 наверху.
  - Возвращаемая структура слишком примитивна: `{"comment": answer}`. Для обзора PR обычно нужны множественные замечания с привязкой к файлам/строкам; текущая форма не масштабируется и плохо совместима с UI.
- Совместимость типов
  - Использование `dict[str, str]` в аннотациях требует Python 3.9+. Если проект/окружение на 3.8, это упадет без `from __future__ import annotations` или без `typing.Dict`. В repo не видно pin’а версии.
- Стиль/архитектура DI
  - app/api.py: `from app.dependencies import review_service` импортирует singleton/глобал. В FastAPI предпочтительнее `Depends` для явного управления жизненным циклом, подмен/тестирования.
- Мелкие замечания
  - LLM Protocol: перевод метода к многострочному виду с `...` — нейтрально, но изменения ради стиля без функциональной ценности. Если проект на 3.8, может потребоваться `typing_extensions.Protocol`.
  - Текст промпта хардкодом на английском; если продукт русскоязычный, стоит унифицировать язык или параметризовать.

Открытые вопросы
- Какая целевая версия Python? (важно для `dict[str, str]`, `Protocol`)
- Требуются ли аутентификация и квотирование для этого эндпоинта?
- Какой ожидаемый формат результата обзора? Одна строка или список замечаний с контекстом (файл/строка/уровень)?
- Какие ограничения по длине diff и по времени ответа LLM допустимы?

Рекомендации (кратко)
- Ввести Pydantic-модели: вход `ReviewRequest(diff: constr(min_length=1, max_length=...))`, выход `ReviewResponse(...)`; добавить `response_model` в роут.
- Обработать ошибки: валидация отсутствия ключа, типы, исключения LLM; возвращать 4xx/5xx с понятными сообщениями.
- Ограничить размер `diff`, усекать/суммаризировать до лимита токенов; добавить таймаут и ретраи LLM.
- Добавить аутентификацию, rate limiting/квоты, базовый анти-спам.
- Перейти на DI через `Depends`, чтобы легче мокать в тестах.
- Подумать над более структурированным ответом (список findings с привязкой к файлам/линиям).
- Зафиксировать версию Python или использовать совместимые аннотации (`typing.Dict`, `typing_extensions.Protocol`) при необходимости.

Если нужно, могу переписать эндпоинт на Pydantic и добавить базовую обработку ошибок и лимиты прямо сейчас.
