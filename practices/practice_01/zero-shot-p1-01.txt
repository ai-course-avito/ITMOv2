
Ниже список проблем по диффу TRAINING_PR.diff, отсортировано по важности, с привязкой к файлам/строкам.

Критичные
- app/api.py:35-38 — Нет валидации входного тела запроса. Аннотировано как `payload: dict`, затем без проверки обращение к `payload["diff"]`. При отсутствии ключа будет KeyError и 500 вместо корректного 422. В FastAPI правильнее использовать Pydantic-модель с обязательным полем `diff: str`.
- app/api.py:35-38, app/review_service.py:19 — Используются аннотации вида `dict[str, str]` (PEP 585). Это требует Python ≥ 3.9. Если проект на 3.8 (что вероятно, учитывая использование `typing.Protocol`, часто встречаемое в 3.8-проектах), модуль упадет при импорте с ошибкой “type 'dict' is not subscriptable”. Либо перейти на 3.9+, либо заменить на `Dict[str, str]` из `typing` (и/или добавить `from __future__ import annotations` для избежания ранней оценки аннотаций).
- app/api.py:35-38 — Отсутствует схема ответа (`response_model`). OpenAPI-спека будет неполной/нестрогой, и клиенты не получат контракт. Лучше объявить Pydantic-модель ответа.

Значимые
- app/api.py:35-38 — Тип `payload: dict` слишком общий, теряется типобезопасность, статическая проверка не ловит проблемы. C Pydantic-моделью получите и типизацию, и авто-валидацию, и документацию.
- app/api.py:35-38 — Отсутствует обработка ошибок вызова LLM/сервиса (таймауты, исключения). Любой сбой приведет к 500 без понятного сообщения. Стоит оборачивать в try/except и возвращать контролируемую ошибку/статус.
- app/review_service.py:19-22 — Возвращаемая структура из сервиса смешивает доменную логику и форму API-ответа (`{"comment": answer}`). Сервис лучше возвращает доменную сущность/строку, а формирование JSON-оболочки делать на уровне API.
- app/review_service.py:20 — Подсказка для LLM хардкожена и на английском. Если продукт русскоязычный — несоответствие локали; стоит вынести в конфиг/шаблон, предусмотреть i18n.
- app/api.py:35-38 — Эндпоинт открытый, без аутентификации/авторизации. Если сервис предполагает ограничения, нужно предусмотреть безопасность (зависимости, токены и т.д.).

Замечания поменьше
- app/review_service.py:11-12 — Изменение сигнатуры Protocol на многострочную с `...` — окей, но чисто стилистика, функционально без разницы.
- app/review_service.py:20 — Риск prompt injection: дифф вставляется напрямую в промпт. В реальной системе стоит как минимум отделять системные инструкции от пользовательского текста, эскейпить или ограждать маркерами, а лучше — использовать структурированный промпт.
- app/api.py:35-38 — Синхронный эндпоинт и синхронный LLM-вызов допустимо, но если LLM блочит поток долго, имеет смысл подумать об асинхронности/очереди/таймаутах.

Открытые вопросы
- Какая целевая версия Python? Если 3.9+, вопрос с `dict[str, str]` снимается; если 3.8 — обязательно поправить аннотации.
- Есть ли модуль `app.dependencies` с `review_service`? В диффе он не показан — важно, чтобы импорт не падал и зависимость корректно инициализировалась (включая LLM).

Рекомендованные правки (кратко)
- Ввести Pydantic-модели:
  - Request: `class ReviewRequest(BaseModel): diff: str`
  - Response: `class ReviewResponse(BaseModel): comment: str`
  - В эндпоинте: `def create_review(payload: ReviewRequest) -> ReviewResponse: ...`
- Заменить PEP 585 аннотации на совместимые с 3.8 (`from typing import Dict`) или зафиксировать Python ≥ 3.9.
- Добавить обработку ошибок вокруг вызова LLM, вернуть контролируемые ответы.
- По возможности вынести шаблон промпта и локализацию в конфиг, продумать защиту от prompt injection.
- В сервисе возвращать доменную сущность (строку), а формирование JSON делать в слое API.
