# Нагрузочные проверки

Нагрузочные проверки нужны уже на первом сценарии, и причина конкретная: вызов внешнего LLM синхронный и удерживает воркер до 10 секунд по `REL-1`. Это ограничение записано как последствие в [`adr.md`](adr.md), и вопрос о переходе на очередь возвращается к рассмотрению именно по результатам этих замеров.

## Профиль нагрузки

Раньше все сценарии опирались на величину «номинальная нагрузка», которая нигде не была определена, поэтому запустить нельзя было ни один. Здесь она определена через ёмкость самого сервиса, а не через частоту открытия пул-реквестов: частота не измерена, а ёмкость выводится из уже принятых решений.

При синхронном вызове каждый запрос удерживает один воркер на время обслуживания. По закону Литтла при полной занятости число запросов в системе равно числу воркеров, а предельная пропускная способность равна

```text
λ_max = W / t_s
```

где `W` — число воркеров сервера приложений, `t_s` — время обслуживания одного запроса. В худшем случае `t_s` равно таймауту `REL-1`, то есть 10 секундам, и тогда `λ_max = W / 10` запросов в секунду.

Номинальная нагрузка — **закрытый контур из `N = W` клиентов**: каждый клиент отправляет следующий запрос только после ответа на предыдущий. Такой контур сам выводит сервис на границу ёмкости, и задавать частоту запросов числом не требуется.

| Параметр | Что это | Откуда берётся | Значение на сегодня |
|---|---|---|---|
| `W` | число воркеров сервера приложений | конфигурация развёртывания | читается из конфигурации перед прогоном |
| `t_timeout` | таймаут внешнего вызова | `REL-1` в [`CASE.md`](CASE.md) | 10 секунд |
| `t_обвязка` | время сервиса без внешнего вызова: разбор запроса, удаление секретов, отбор рисков, сборка ответа | калибровочный прогон на той же сборке с заглушкой LLM, отвечающей мгновенно | измеряется, числом не задаётся |
| `t_stub` | фиксированная задержка ответа заглушки LLM | назначается прогоном. Ограничение задаётся сценарием: `t_stub < t_timeout` там, где проверяется штатный путь, и `t_stub > t_timeout` в сценарии деградации. На приёмку конкретное значение не влияет, потому что предел выражен относительно него | 1 секунда для трёх сценариев, 11 секунд для сценария деградации |
| `payload` | длина diff в запросе | проверка инкремента 1 в [`project_management.md`](project_management.md) | 4000 символов |
| `N` | число клиентов закрытого контура | `N = W` для номинала, `N = 2W` для запаса | вычисляется |

Заглушка LLM во всех сценариях отвечает с фиксированной задержкой `t_stub`: так `t_s` детерминирован и результаты сравнимы между прогонами. Конкретное значение `t_stub` ничем не выводится и выводиться не должно — оно задаётся прогоном. Приёмку оно не искажает, потому что пределы выражены относительно него, а не абсолютным числом секунд: требуется лишь, чтобы для трёх сценариев задержка укладывалась в таймаут, а для сценария деградации выходила за него.

| Номинальная работа команды | Закрытый контур `N = W`, заглушка LLM отвечает за `t_stub`, `payload` 4000 символов, 10 минут | p95 полного времени ответа не выше `t_обвязка + t_stub`, ни одного HTTP 500 | p50 и p95 полного времени ответа, коды ответов, занятость воркеров | Запрет HTTP 500 выводится из `REL-1`: отказ обязан превращаться в контролируемый ответ. | Двукратный запас | Закрытый контур `N = 2W`, остальное как в номинальном сценарии, 5 минут | Ни одного HTTP 500, ни одного ответа вне контракта `OUT-1` | Доля отказов, распределение времени ответа, занятость воркеров, поведение при исчерпании пула | `REL-1` и `OUT-1`. Ряд RSS сохраняется как наблюдение, порога на него нет, см. «Открытые вопросы» |

## Откуда взялся каждый предел

Предыдущая редакция содержала четыре числа, поданных как выведенные из правил. Проверка показала, что выводятся не все.

| Утверждение прежней редакции | Статус | Что сделано |
|---|---|---|
| p95 не выше 12 секунд | Не выводится. `REL-1` фиксирует таймаут 10 секунд, надбавка в 2 секунды на обвязку не зафиксирована нигде | Заменено на `t_обвязка + t_timeout`, где обвязка измеряется калибровочным прогоном |
| Доля отказов не выше 1 процента | Не выводится. Ни одно правило и ни одно решение [`adr.md`](adr.md) не называет допустимую долю отказов | Порог убран. Доля отказов измеряется, но не служит критерием приёмки до замера базовой линии |
| Потребление памяти не растёт линейно со временем | Не проверяется в такой формулировке: не заданы ни окно наблюдения, ни величина допустимого роста | Перенесено из пределов в наблюдения. Сохраняется ряд RSS по минутам |
| Длительности прогонов 10 и 5 минут | Не выводятся ни из одного источника | Оставлены как явно названное допущение, а не как следствие правил |
| Отсутствие HTTP 500 | Выводится из `REL-1`: «ошибка превращается в контролируемый ответ» | Оставлено как предел |
| Отсутствие ложного HTTP 413 | Выводится из `API-1` от противного: порог отсечения — «длиннее 20000», значит 19900 символов проходит | Оставлено как предел |

## Открытые вопросы

- Поведение сервиса при исчерпании пула воркеров не задано ни одним правилом и ни одним решением: неизвестно, должен ли лишний запрос ждать в очереди, получать отказ с кодом или отбрасываться. Пока это не решено, доля отказов в сценарии двукратного запаса не может быть критерием приёмки — неизвестно, какое её значение считать правильным. Вопрос адресуется в [`adr.md`](adr.md) вместе с решением про очередь.
- Абсолютной частоты открытия пул-реквестов здесь по-прежнему нет, и это осознанно: она не измерена, о чём сказано в разделе «Что пока неизвестно» в [`context.md`](context.md). Профиль выражен через ёмкость сервиса, поэтому проверки исполнимы уже сейчас. После замера базовой линии, который в [`project_management.md`](project_management.md) идёт первым этапом, добавляется отдельный сценарий с измеренным пиковым потоком — он ответит на вопрос, хватает ли ёмкости, тогда как нынешние четыре отвечают на вопрос, как сервис ведёт себя на своей границе.
