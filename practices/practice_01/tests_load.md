# Нагрузочные проверки

| Сценарий | Профиль нагрузки | Допустимый предел | Что измеряем | Evidence/правило |
|---|---|---|---|---|
| Baseline | 10 rps, 2 мин warm-up + 5 мин стабильной нагрузки | p95 ≤ 10с; при симулированном таймауте LLM — 100% контролируемых ответов (REL-1) | p50/p90/p95 latency, error_rate, controlled_timeout_ratio | REL-1 |
| Step | 10 rps 3 мин → 30 rps 3 мин → 60 rps 3 мин → 90 rps 3 мин → 120 rps 3 мин | На каждом шаге p95 ≤ 10с (REL-1); стабилизация — наблюдение (не критерий) | p95, error_rate, backlog_trend (рост очереди) | REL-1 |
| Spike | 20 rps 3 мин → 200 rps 60с → 20 rps 3 мин | Во время спайка p95 ≤ 10с (REL-1); восстановление — наблюдение (без порогов) | p95, error_rate, recovery_time | REL-1 |
| Soak | 30 rps, 5 мин warm-up + 30 мин стабильной нагрузки | p95 ≤ 10с на всём интервале | p95 over time, error_rate, drift | REL-1 |
| API-1 длинный diff | 20 rps, 2 мин; diff ≈ 30000 символов | 100% запросов возвращают HTTP 413 (API-1). Отсутствие вызовов LLM — дополнительная проверка, если длина проверяется до обращения к модели (не критерий) | share_413; при наличии трассировки — trace_no_llm; проверка логов на отсутствие содержимого diff | API-1; OBS-1 |

## Методика

- Окружение и допущения:
  - Однотипные машины и стабильная сеть; отсутствуют сторонние фоновые нагрузки.
  - LLM-заглушка с контролируемой задержкой для проверки REL-1: должна уметь симулировать задержки > 10с. При превышении таймаута (10с) сервис обязан вернуть контролируемый ответ (REL-1).
  - Генератор нагрузки и сервис запускаются в повторяемой конфигурации; фиксируйте версии и параметры запуска.
- Прогрев и стабилизация:
  - Перед каждой основной фазой — warm-up 2–5 минут (см. профиль в таблице), пока p95 и error_rate не стабилизируются.
  - Для Step подтверждайте стабилизацию на каждом шаге (переход после стабилизации без роста очереди).
- Данные/генерация diff:
  - Короткий diff: ≤ 5000 символов — для Baseline/Step/Spike/Soak.
  - Близко к лимиту: 19000–19999 символов — для проверки границы в любых сценариях.
  - Длинный diff: ≈ 30000 символов — для сценария API-1 (ожидаем HTTP 413; отсутствие обращения к LLM — если проверка длины выполняется до вызова модели).
  - Во все варианты данных добавляйте маркер SECRET_MARKER для проверки OBS-1 (не должен появляться в логах/метриках).
- Сбор метрик:
  - Латентность p50/p90/p95 по завершённым запросам; error_rate (5xx/неуспехи); share_413 для длинных diff; controlled_timeout_ratio = доля контролируемых ответов среди запросов, где заглушка симулировала таймаут > 10с.
  - Фиксируйте backlog/очередь (рост времени ответа/невыполненные ко времени шага) для Step/Spike.
  - Логи проверяются на соблюдение OBS-1: содержат только request_id, длительность, статус; отсутствие содержимого diff и маркера SECRET_MARKER.
- Отчётность и артефакты:
  - Сырые метрики в машиночитаемом формате (JSON/CSV) и графики времени против латентности/ошибок.
  - Сводная таблица по сценариям (профиль, p95, error_rate, share_413, controlled_timeout_ratio, pass/fail).
  - Один отчёт .md с выводами и ссылками на сырые данные.

## Критерии приёмки (pass/fail)

- REL-1: во всех сценариях Baseline/Step/Spike/Soak p95 ≤ 10с. При симулированных таймаутах LLM — 100% контролируемых ответов (каждый таймаут → контролируемый ответ, REL-1).
- API-1: для входов с diff > 20000 символов доля ответов HTTP 413 = 100% (API-1); отсутствие вызовов LLM подтверждается, только если проверка длины выполняется до вызова модели.
- OBS-1: во всех сценариях логи содержат только request_id, длительность, статус; отсутствуют содержимое diff и маркер SECRET_MARKER.

## Риски и интерпретация

- Деградация производительности: рост p95 или error_rate выше порогов на ступенях/во время спайка без нарушений OBS-1 — это предел до деградации. Зафиксируйте rps и условия, при которых это произошло.
- Нарушение OBS-1: появление содержимого diff или SECRET_MARKER в логах/метриках при любых нагрузках — это ошибка независимая от производительности и должна быть исправлена отдельно.
- Ложная деградация: отсутствие warm-up или нестабильная сеть может завысить p95. Повторите прогон после стабилизации.
