# Нагрузочные проверки

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| 50 одновременных запросов к POST `/api/reviews` с валидным небольшим `diff` | 50 параллельных запросов; окно 10 секунд (burst) | 5xx ≤ 1% (problem.md); p95 латентности ≤ 10s (REL-1) или контролируемые ответы 422/413/502/503 | p95/p99 latency, доля 5xx, отсутствие деградации сервиса, отсутствие необработанных исключений | TRAINING_PR.diff: app/api.py L35-38 — синхронный вызов ReviewService; app/review_service.py L21 — блокирующий вызов LLM; problem.md «Метрики»: цель 5xx ≤1%; CASE.md: REL-1 (timeout 10s) |
| Медленный LLM (таймаут) | 1 запрос; LLM задержка > 10s | Ответ ≤ 10s; код 502/503; без утечки diff в тексте ошибки | время ответа, HTTP‑код, отсутствие зависаний на уровне API | CASE.md: REL-1; TRAINING_PR.diff: app/review_service.py L21 — нет обработки таймаута сейчас |
| Большой diff | 1 запрос с `len(diff)=20001` | HTTP 413 без вызова LLM | доля 413, число обращений к LLM = 0 | CASE.md: API-1 — лимит 20 000 символов; TRAINING_PR.diff: app/api.py L35-38 — отсутствие проверки размера сейчас |

Если нагрузочное тестирование пока не требуется, обоснуйте это и назовите условие, после которого оно понадобится.

На этапе текущего diff полноценное нагрузочное тестирование даёт ограниченную пользу: отсутствуют реализация API-1 (лимит размера) и REL-1 (таймаут/обработка ошибок), поэтому результаты будут отражать известные дефекты (500 при отсутствии `diff`, зависания). Полноценные прогоны нужны после внедрения API-1 и REL-1; до этого — ограничиться короткими sanity‑burst (до 50 запросов) для подтверждения контролируемых ответов.

- Тип промпта: master prompt (QA‑инженер)
