# Нагрузочные проверки

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| Обычный анализ со stub LLM | 20 одновременных пользователей, 5 минут; diff 5–10 тыс. символов; задержка LLM 0,5 с | Предварительный baseline: p95 ≤2 с, ошибок ≤1%, нет необработанных 5xx | RPS, p50/p95/p99, доля ответов по OUT-1, CPU и память | Отчёт k6/Locust и метрики сервиса |
| Медленный LLM | 20 одновременных запросов, 2 минуты; stub отвечает дольше 10 с | 100% вызовов завершаются контролируемо; p95 ≤11 с; процесс не исчерпывает workers/connections | Длительность, число timeout, 5xx, активные соединения | Отчёт генератора нагрузки, счётчики timeout и ресурсов |
| Быстрое отклонение больших diff | 50 RPS, 2 минуты; каждый diff длиной 20 001 | 100% ответов — HTTP 413; LLM-вызовов 0; предварительно p95 ≤500 мс | RPS, latency, коды ответа, счётчик вызовов stub LLM | Отчёт нагрузки и журнал stub LLM |
| Смешанный поток | 80% допустимых, 10% слишком больших, 10% невалидных; 20 пользователей, 5 минут | Корректный статус для каждого класса; нет необработанных 5xx; память не растёт монотонно | Распределение статусов, latency по классам, CPU/память | Отчёт нагрузки и графики ресурсов |

Численные пределы, кроме обязательного timeout 10 секунд, являются стартовыми гипотезами: в CASE.md нет SLA, профиля трафика и характеристик инфраструктуры. Их нужно заменить после первого baseline и согласования SLO. Полноценный тест с реальным LLM понадобится перед production-релизом или после появления целевого RPS/SLO; до этого используется управляемый stub, чтобы не отправлять секреты и не смешивать производительность приложения с вариативностью провайдера.
