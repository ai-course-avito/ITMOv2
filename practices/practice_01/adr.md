# ADR: решение для первого рабочего сценария

- Статус: accepted
- Дата: 2026-09-05
- Ответственные: Студент (единственный исполнитель)

## Контекст

AI‑помощник code review принимает текстовый diff на POST /api/reviews и возвращает совет. В текущем состоянии (см. problem.md, context.md) выявлены проблемы:

- SEC-1: отсутствует редакция секретов перед вызовом внешнего LLM — риск утечки токенов, ключей и приватных данных.
- API-1: нет жёсткого лимита 20 000 символов и корректного ответа 413 для больших диффов.
- REL-1: нет таймаута 10 секунд и контролируемого ответа при сбое/задержке LLM.
- OUT-1: ответ не имеет гарантированной JSON‑схемы (summary, risks<=3, checks) для автоматической обработки.
- OBS-1: недостаточная наблюдаемость — нет стандартизированных полей request_id, длительности и статуса; риск логирования содержимого diff/LLM payload.

## Решение

Принять минимально достаточные изменения для первого рабочего сценария:

1. SEC-1: перед вызовом LLM всегда выполнять санитацию diff. Детектировать и заменять на [REDACTED] как минимум:
   - токены GitHub (ghp_), AWS ключи (AKIA...), строки Bearer ...,
   - приватные ключи (-----BEGIN PRIVATE KEY----- ...),
   - password=..., api_key=..., секреты формата key=...,
   - иные явные токен‑паттерны. Санитайзер не должен ломать структуру diff.
2. API-1: отклонять вход длиной > 20000 символов (измерение по символам), возвращать HTTP 413. Ровно 20000 — допускается.
3. REL-1: обернуть вызов LLM таймаутом 10 секунд. При таймауте/ошибке возвращать контролируемый ответ HTTP 200 с JSON того же формата: лаконичный summary на русском, указывающий на деградацию; risks=[], checks — воспроизводимые шаги ручной проверки/повторного запуска.
4. OUT-1: нормализовать и валидировать ответы по схеме: summary:string; risks — массив не более 3 элементов {file:string, line:int, evidence:string, risk:string}; checks: array[string]. Сценарии с >3 рисками — обрезать/фильтровать до 3, риски без evidence исключать (QA-1).
5. OBS-1: логировать только request_id, duration, status; не логировать diff и payload модели. Логи — на английском, плейн‑текст или JSONL, без содержимого.

Язык пользовательского результата — русский (summary и checks), логи и системные поля — английский. Формат числа «20 000» унифицирован во всех документах.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Асинхронные очереди и ретраи | Усложняют архитектуру и эксплуатацию, выходят за SCOPE первого сценария; таймаут 10с и контролируемый ответ достаточно для MVP |
| Стриминговый ответ (SSE/WebSocket) | Не требуется по целям; повышает сложность клиента и совместимости |
| Увеличение лимита >20k | Повышает стоимость и риск утечки; для учебного сценария 20k достаточно |
| Логирование полного запроса/ответа | Нарушает OBS-1 и повышает риск утечек |
| Отказ от санитайзера (ответственность на пользователе) | Не соответствует SEC-1; неприемлемо по безопасности |
| Сохранение результатов и аудита в БД | Вне SCOPE-1; добавляет инфраструктурные зависимости |

## Последствия и главный риск

- Положительные последствия:
  - Снижение риска утечек, предсказуемые задержки, структурированный результат, улучшенная поддерживаемость.
- Ограничения:
  - Отсечение больших диффов, ограничение рисков до 3, возможная потеря части контекста из‑за санитайзера.
- Главный риск:
  - Перередакция (ложные срабатывания) или недоредакция (утечки) секретов; чрезмерно общие проверки при деградации.
- Как проверим риск:
  - Юнит и интеграционные тесты санитайзера; проверка логов на отсутствие контента; e2e сценарии деградации; нагрузочные проверки таймаутов.

    LLMClient -- ok --> Normalize[Normalize & Validate (OUT-1, QA-1)]

    Normalize --> Response[HTTP 200 JSON]
