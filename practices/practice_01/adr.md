# ADR: решение для первого рабочего сценария

- Статус: accepted
- Дата: 2026-09-10
- Ответственные: команда ревью-сервиса

## Контекст

Сервис помогает ревьюеру PR: принимает diff и возвращает структурированный результат. По правилам репозитория (CASE.md) необходимо:
- SEC-1: перед отправкой во внешний LLM удалять секреты из diff;
- API-1: отклонять diff длиной > 20 000 символов с HTTP 413;
- REL-1: ограничивать вызов внешнего LLM таймаутом 10 секунд и превращать ошибку в контролируемый ответ;
- OUT-1: формировать ответ как summary, массив risks (до 3, с file, line, evidence, risk) и массив checks;
- QA-1: включать в ответ только риски, подтвержденные строкой diff или правилом;
- OBS-1: логировать только request_id, длительность и статус, не логируя содержимое diff и ответы модели.

Текущая реализация (TRAINING_PR.diff) нарушает SEC-1, API-1, REL-1 и OUT-1: diff отправляется в LLM как есть, нет ограничения длины, нет таймаута/контролируемой ошибки, ответ — {"comment": "..."}.

## Решение

Внести минимально необходимые изменения сервиса и API для соответствия правилам:

1) Валидация и ограничение размера (API-1)
- Явная схема входа и проверка наличия поля diff.
- При длине diff > 20 000 символов возвращать HTTP 413.

2) Редакция секретов (SEC-1)
- Перед вызовом LLM редактировать diff, замещая обнаруженные токены/пароли/ключи на [REDACTED].
- Не логировать исходный diff (OBS-1).

3) Надежность LLM-вызова (REL-1)
- Вызывать LLM с таймаутом 10 секунд.
- Исключения/таймауты преобразовывать в контролируемый ответ с предсказуемой структурой.

4) Формат ответа (OUT-1, QA-1)
- Возвращать объект с полями: summary, risks[<=3] и checks.
- Каждый risk содержит file, line, evidence, risk; включается только при подтверждении строкой diff/правилом.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Свободный текст {"comment": "..."} | Нарушает OUT-1; потребители не получают структурированный результат |
| Не ограничивать размер diff | Нарушает API-1; риск сбоев/затрат и превышения контекста LLM |
| Не редактировать секреты | Нарушает SEC-1; риск утечки конфиденциальных данных |
| Делать всю обработку на клиенте | Усложняет интеграцию, не гарантирует соблюдение SEC-1/API-1/REL-1 на сервере |

## Последствия и главный риск

- Положительные последствия:
  - Соответствие правилам SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1.
  - Предсказуемый контракт ответа, удобный для автоматизации.
  - Повышение надежности за счет таймаутов и контролируемых ответов.
- Ограничения:
  - Большие diff (> 20 000 символов) будут отклоняться.
  - Редакция секретов может скрывать часть контекста; требуется аккуратный дизайн.
  - Вызовы LLM ограничены 10 секундами.
- Главный риск:
  - Неполная или избыточная редакция секретов: либо утечка, либо потеря доказательств в evidence.
- Как проверим риск:
  - Тесты на SEC-1 с синтетическими токенами/секретами, проверка [REDACTED] в prompt.
  - Интеграционные тесты на API-1 (HTTP 413) и REL-1 (таймауты/контролируемые ответы).
  - Контрактные тесты OUT-1/QA-1 (<=3 риска, каждый с file/line/evidence/risk).
