# ADR: решение для первого рабочего сценария

- Статус: proposed / accepted
- Дата: 2026-09-08
- Ответственные: Технический аналитик, Архитектор

## Контекст

Эндпоинт POST `/api/reviews` принимает `payload: dict` и извлекает ключ `diff` напрямую. При отсутствии ключа возникает `KeyError`, что ведёт к 5xx. Нет проверки размера входа, нет нормализации ответа и редакции секретов.

## Решение

Использовать Pydantic-модель для валидации входа и описания контракта ответа (без изменения текущего кода в diff; решение для следующего инкремента).

- Вход: модель `ReviewRequest` с полем `diff: constr(strip_whitespace=True, min_length=1, max_length=20000)`.
- Безопасность: предобработка `diff` для удаления/редакции секретов (SEC-1).
- Надёжность: обёртка вызова LLM с таймаутом 10 секунд (REL-1) и контролируемой ошибкой.
- Выход: модель `ReviewResponse` с полями `summary: str`, `risks: list[Risk] (<=3)`, `checks: list[str]` (OUT-1).

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Сырая dict без схемы | Нет автоматической 4xx-валидации, сложнее поддерживать контракт, выше риск 5xx |
| Ручные проверки в обработчике | Дублирование логики, нет автогенерации схем, выше шанс пропустить случай |
| Marshmallow/другие валидации | Доп. зависимости; Pydantic встроен в экосистему FastAPI |

## Последствия и главный риск

- Положительные последствия:
  - Стабильные 4xx при ошибках клиента, снижение 5xx.
  - Прозрачный контракт и автодокументация.
  - Возможность централизовать SEC-1/API-1/REL-1.
- Ограничения:
  - Дополнительные модели и обёртки увеличивают кодовую базу.
  - Ограничение длины может требовать конфигурации.
- Главный риск:
  - Неверная редакция секретов может спрятать полезный контекст или пропустить секрет.
- Как проверим риск:
  - Юнит-тесты на шаблоны секретов; интеграционный тест, что [REDACTED] попадает в prompt; ручная проверка граничных случаев.
