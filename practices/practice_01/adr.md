# ADR: решение для первого рабочего сценария

- Статус: accepted
- Дата: 2026-09-17
- Ответственные: команда практики (студент, ревьюер)

## Контекст

Учебный сервис AI-ревью PR получает diff и возвращает рекомендации. По TRAINING_PR.diff текущая реализация принимает произвольный словарь, напрямую обращается к `payload["diff"]`, отправляет весь diff во внешний LLM и возвращает только `comment`. Нет валидации и обработки ошибок.

Целевой контракт задаётся правилами CASE.md: SEC-1 (redaction секретов), API-1 (лимит 20 000 символов и 413), REL-1 (таймаут 10с и контролируемая ошибка), OUT-1 (структура summary/risks/checks, ≤3 риска), SCOPE-1 (решение за человеком), QA-1 (риск только с evidence), OBS-1 (безопасное логирование).

## Решение

Принять архитектуру слоями защиты и преобразования:

1) FastAPI endpoint с валидацией входа и явной схемой ответа.
2) Проверка размера diff на границе (≤ 20 000 символов), возврат 413 при превышении.
3) Redaction секретов до передачи в LLM (замена на `[REDACTED]`).
4) Review service формирует ограниченный prompt, вызывает внешний LLM с таймаутом 10 секунд и преобразует исключение или timeout в HTTP 502 с `error.code=LLM_UPSTREAM_ERROR` и безопасным `error.message`.
5) Преобразование ответа в структуру `summary/risks/checks` (≤3), каждый риск с `file`, `line`, `evidence`, `risk`.
6) Безопасное логирование только метаданных (без diff и ответа LLM).

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Проверка лимита только в review service | Поздняя отбраковка, тратятся ресурсы на создание зависимостей; хуже ясность контракта на границе |
| Автоусечение/суммаризация больших diff вместо 413 | Нарушает API-1 (контракт); повышает сложность и риски потери контекста |

## Последствия и главный риск

- Положительные последствия:
    - Предсказуемый API, воспроизводимые коды 422/413, структурированный ответ.
    - Снижение риска утечки секретов и логирования чувствительных данных.
    - Ограничение затрат и латентности за счёт лимита и таймаута.
- Ограничения:
    - Большие diff (> 20 000 символов) отклоняются — требуется клиентская адаптация.
    - Обработка ошибок LLM возвращает обобщённый ответ без деталей.
- Главный риск:
    - Неправильная классификация ошибок внешнего LLM и спор по статусу ответа.
- Как проверим риск:
    - Интеграционный тест с мок LLM, поднимающим исключения и таймауты; проверка соответствия выбранному статусу и отсутствию 5xx из‑за необработанных исключений.

## Архитектурная схема

```mermaid
flowchart LR
    Client[Клиент/CI] --> API[FastAPI endpoint]
    API --> VAL[Валидатор запроса]
    VAL -->|422| Client
    VAL --> SIZE[Проверка размера]
    SIZE -->|413| Client
    SIZE --> RED[Redaction секретов]
    RED --> RS[Review Service]
    RS --> LLM[Внешний LLM (timeout 10s)]
    LLM --> TR[Преобразование ответа]
    LLM --> ERR[Контролируемая ошибка]
    TR --> LOG[Безопасное логирование]
    ERR --> LOG
    TR --> Human[Человек принимает решение]
    ERR --> Human
    Human --> OUT[summary + ≤3 risks + checks]
```
