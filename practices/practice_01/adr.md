## Контекст

MVP «AnimeMap API» — бэкенд для поиска и выдачи координат локаций из аниме, с кэшированием часто повторяющихся запросов, верификацией координат и избранным. Стек: Python, FastAPI, PostgreSQL (SQLAlchemy + Alembic), Redis, httpx; деплой за Nginx в Docker Swarm. Требования: DDD, ООП/SOLID; presentation слой — Pydantic; domain/application — dataclasses с `slots=True`; в infrastructure используются ORM-модели с маппингом в domain entities и обратно; первичный ключ — UUIDv4 (создание сущностей в domain без `flush`).

## Tree of Thoughts: выбор архитектуры

Вариант A — Микросервисы

- Мысли 1: Разделение по bounded contexts (Locations, Geocoding, Favorites, Moderation) снижает связность и улучшает масштабируемость по командам.
- Мысли 2: Для MVP возрастут накладные расходы: сетевые границы, контрактные тесты, observability, развёртывание нескольких сервисов в Swarm, управление транзакционной согласованностью.
- Мысли 3: Геокодинг — внешняя зависимость; вынесение в отдельный сервис не даёт выигрыша в скорости для MVP, но добавляет очереди/ретраи.
- Критика: Сверхсложно для 1 инженера и AI-агентов, высокие операционные риски, дублирование моделей, распределённые транзакции, усложнение DDD сквозь сервисные границы на старте.

Вариант B — Модульный монолит (DDD)

- Мысли 1: Чёткие модули/контексты внутри одного репозитория/процесса (interfaces/presentation, application, domain, infrastructure) позволяют применять DDD и соблюдать SOLID без сетевых overhead.
- Мысли 2: Простая транзакционность (одна БД), быстрые итерации, легче верифицировать схемы и миграции. Redis-кэш и httpx остаются адаптерами в infrastructure.
- Мысли 3: Готов к будущей экстракции сервисов: стабильные границы модулей, явные порты/адаптеры, DTO и маппинги между ORM и domain.
- Критика: Ограниченная независимая масштабируемость модулей; риск «разрастания» слоя infrastructure без код-ревью; единый деплой может стать узким местом при росте.

Решение: Для MVP выбираем модульный монолит (DDD). Он минимизирует операционные риски, ускоряет поставку и оставляет путь к микросервисам при росте.

## Решение

- Слои и модули: `interfaces` (FastAPI + Pydantic DTO), `application` (use-cases, сервисы, CQRS), `domain` (entities на dataclasses `slots=True`, value objects, репозитории/интерфейсы), `infrastructure` (SQLAlchemy ORM, маппинги ORM<->domain, Redis-кэш, httpx-клиенты, Alembic).
- Идентификаторы: UUIDv4 как PK/ID в domain и БД; генерация ID в domain до сохранения (без `flush`).
- Кэширование: Redis как read-through для поиска/координат; TTL и инвалидация по событиям изменения локаций/верификации.
- Геокодинг: httpx-клиент с тайм-аутами/ретраями; нормализация JP/EN; троттлинг запросов.
- Деплой: единый сервис FastAPI за Nginx в Docker Swarm; PG и Redis как сервисы кластера.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Микросервисная архитектура | Высокая сложность эксплуатации и интеграции для команды из 1 инженера; дополнительные скоупы: контрактные тесты, трассировка, очереди, согласованность данных |
| Модульный монолит (DDD) | Выбран как подход MVP; оставляет возможность выделения сервисов позже |

## Последствия и главный риск

- Положительные последствия: ускорение MVP, упрощение тестирования и миграций, единые транзакции, предсказуемая латентность.
- Ограничения: общие ресурсы процесса, единый релизный цикл, необходимость дисциплины модульных границ.
- Главный риск: эрозия модульных границ и утечка инфраструктурных зависимостей в domain.
- Как проверим риск: lint/арх-чеки (import-layers), code review, unit-тесты на маппинги ORM<->domain, ADR-контроль.
