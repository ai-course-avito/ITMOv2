# ADR: решение для первого рабочего сценария

- Статус: proposed
- Дата: 2026-09-08
- Ответственные: Команда разработки

## Контекст

Из TRAINING_PR.diff следует:

- Добавлен эндпоинт FastAPI `POST /api/reviews`, который принимает произвольный `dict` и обращается к `payload["diff"]` без валидации (evidence: app/api.py:35-38).
- Сервис `ReviewService.review(diff)` формирует промпт, напрямую вставляя пользовательский `diff`, и вызывает `LLM.generate` (evidence: app/review_service.py:19-22). Возвращается `{"comment": answer}`.

Проблемы текущего подхода:
- Отсутствует валидация входа и ограничение размера, возможен `KeyError` и DoS большими входами (evidence: app/api.py:36-38).
- Промпт-инжекции и неограниченная вставка пользовательского текста в LLM (evidence: app/review_service.py:19-22).
- Нет обработки ошибок LLM и явного контракта ответа.

## Решение

Минимально инвазивный дизайн «валидация на границе + guardrails для промпта + обработка ошибок»:

1. Pydantic-схема запроса с обязательным строковым полем `diff` и верхним лимитом размера; при нарушении — 422/413.
2. Перед вызовом LLM: усечение/очистка `diff`, добавление статических инструкций в промпт.
3. Таймаут и перехват исключений при `LLM.generate`, преобразование в контролируемые ответы 4xx/5xx.
4. Сохранить текущий формат ответа `{comment: str}` для совместимости; рассмотреть расширение схемы в следующем инкременте.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Полная перестройка API (асинхронные очереди, вебхуки) | Слишком тяжёлая для первого инкремента; diff не требует асинхронщины напрямую |
| Немедленный переход к структурированному ответу (issues[]) | Полезно, но потребует большего изменения контракта и тестов; отложено до инкремента 2 |
| Фильтрация на уровне LLM без валидации входа | Не решает 500/DoS; необходима валидация на входе API |

## Последствия и главный риск

- Положительные последствия:
  - Снижение 500 из-за KeyError; контролируемые ответы при ошибках LLM; предсказуемые затраты за счёт лимита входа.
- Ограничения:
  - Усечение `diff` может ухудшить качество ревью; дополнительная задержка на валидацию/санитизацию.
- Главный риск:
  - Промпт-инжекции остаются возможными без дополнительных контекстных фильтров.
- Как проверим риск:
  - Интеграционный тест с «злонамеренным» diff; проверка, что промпт содержит усечённую/очищенную версию (evidence-сценарии см. tests_integration.md, опираются на app/review_service.py:19-22 как исходный риск).

## Архитектурная схема

```mermaid
flowchart LR
    Client[POST /api/reviews] --> API[FastAPI handler]
    API -->|Validate & Limit| Guard{Valid?}
    Guard -- No --> Err[422/413]
    Guard -- Yes --> Service[ReviewService]
    Service -->|Prompt (guardrails)| AI[LLM.generate]
    AI --> Map{Error?}
    Map -- Yes --> E5xx[Handled 5xx/4xx]
    Map -- No --> Out{"{comment: str}"}
```

## Как использовали AI

- Для чего: Сформулировать решение и альтернативы, вытекающие из рисков, подтверждённых строками diff.
- Тип промпта: master prompt.
- Строка в [`prompts.md`](prompts.md): P1-02.
- Что проверили и исправили сами: Привязали все проблемы к конкретным строкам diff; исключили варианты, не подтверждённые diff; оставили минимально инвазивное решение для первого инкремента.
