# ADR: решение для первого рабочего сценария

- Статус: proposed / accepted
- Дата: 2026-09-16
- Ответственные: ИТ-архитектор, команда backend

## Контекст

По учебному diff добавлен HTTP‑эндпоинт и сервис вызова LLM:

- В `app/api.py` реализован `POST /api/reviews` и функция `create_review(payload: dict)`, которая без валидации берёт `payload["diff"]` и проксирует в сервис (app/api.py L35-38).
- В `app/review_service.py` добавлен метод `review(self, diff: str)`, формирующий промпт `"Review this pull request and find problems:\n{diff}"`, вызывающий `self.llm.generate(prompt)` и возвращающий `{"comment": answer}` (app/review_service.py L19-22). Вызов LLM синхронный, без обработки ошибок (L21).
- Интерфейс LLM определён через `Protocol` с методом `generate(self, prompt: str) -> str` (app/review_service.py L11-13).

## Решение

Принять минимальные архитектурные изменения для первого рабочего сценария API‑ревью:

1. Ввести явный контракт API: модель запроса `{"diff": str}` и ответ в формате OUT-1: `summary`, `risks` (не более 3 элементов с полями `file`, `line`, `evidence`, `risk`), `checks`. На уровне FastAPI валидировать наличие и тип `diff`; некорректный ввод — контролируемая клиентская ошибка (422). Основание: текущий доступ по ключу без проверки (`payload["diff"]`) в app/api.py L35-38 может привести к `KeyError` и 500; OUT-1 определяет целевой контракт ответа.
2. Обработать ошибки LLM: обернуть вызов `llm.generate(prompt)` try/except и маппировать исключения в контролируемые ответы сервера (например, 502/503). Основание: прямой вызов без обработки в app/review_service.py L21.
3. Изолировать пользовательский `diff` в промпте: добавлять явные делимитеры и формулировать инструкцию модели так, чтобы содержимое `diff` трактовалось как данные, а не команды. Основание: сейчас `diff` включается в инструкцию напрямую (app/review_service.py L20).
4. Ограничить размер входного `diff` на уровне API, отклонять чрезмерно большие запросы с клиентской ошибкой. Основание: параметр `diff: str` принимается без ограничений (app/review_service.py L19-22), что чревато высокой стоимостью и латентностью.
5. Рассмотреть неблокирующий вызов LLM (async/фон) для долгих операций, чтобы не блокировать воркеры HTTP. Основание: синхронный путь запроса `create_review(...)` → `llm.generate(...)` (app/api.py L36-38; app/review_service.py L21).

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Оставить `payload: dict` без схемы | Риск 500 при отсутствии ключа `diff` (app/api.py L35-38), непредсказуемый контракт |
| Продолжать синхронный вызов LLM без обработки ошибок | Любая ошибка `llm.generate` (app/review_service.py L21) превращается в 500 и портит стабильность API |
| Оставить ответ `{"comment": str}` вместо OUT-1 — отклонено, так как нарушает OUT-1 | Такой ответ не содержит `summary`, структурированных `risks` (≤3 с `file`, `line`, `evidence`, `risk`) и `checks`; затрудняет проверяемость и расширение |

## Последствия и главный риск

- Положительные последствия:
  - Предсказуемость API и снижение 5xx благодаря валидации и обработке ошибок.
  - Снижение влияния недоверенного ввода на модель (делимитеры в промпте).
  - Контроль затрат/латентности за счёт ограничения размера `diff`.
- Ограничения:
  - Ограничение размера `diff` может отклонять редкие большие PR.
  - Дополнительные проверки на пути запроса немного увеличивают латентность.
- Главный риск:
  - Длительные или нестабильные ответы LLM всё ещё могут деградировать UX, если неблокирующий вызов отложен.
- Как проверим риск:
  - Интеграционный тест: `POST /api/reviews` с пустым телом `{}` → 422 (вместо текущего 500 из‑за `payload["diff"]`, app/api.py L35-38).
  - Юнит‑тест: заставить `llm.generate` выбрасывать исключение → контролируемый ответ (не 500) (основание: app/review_service.py L21).
  - Тест безопасности промпта: добавить в `diff` инструкции → модель должна игнорировать содержимое как команды (основание: включение `diff` в промпт, app/review_service.py L20).
  - Нагрузочный тест: большой `diff` → запрос отклоняется клиентской ошибкой; сервер не уходит в дорогостоящую обработку (основание: отсутствие ограничений, app/review_service.py L19-22).
  - Проверка структуры OUT-1: ответ 200 содержит `summary`, `risks` (≤3, элементы с `file`, `line`, `evidence`, `risk`) и `checks`.
