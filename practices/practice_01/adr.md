# ADR: API для ревью diff через LLM

Статус: Proposed


## Решение

- Добавить публичный POST-эндпоинт `/api/reviews`, принимающий JSON с полем `diff` и возвращающий результат анализа модели в стандартизированном виде.
- В сервисном слое `ReviewService` формировать промпт и вызывать `LLM.generate`, при этом сервис возвращает доменный результат (строку), а API-слой отвечает за структуру JSON.
- Ввести валидацию, ограничение размера входа, маскирование секретов и таймаут вызова LLM.

## Обоснование

- TRAINING_PR.diff показывает направление: уже добавлен эндпоинт и сервис, но отсутствуют валидация, ограничения и разделение ответственности. Это приводит к рискам 5xx и проблемам безопасности. Принятое решение устраняет эти риски без изменения общей архитектуры.

## Схема (Mermaid)

```mermaid
flowchart TD
    C[Client] -->|POST /api/reviews {diff}| A[FastAPI Controller]
    A -->|Validate, limit, redact| S[ReviewService]
    S -->|prompt| L[LLM]
    L -->|answer| S
    A -->|JSON response| C
```

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| Отправлять diff как есть, без валидации | Минимум кода | 5xx при ошибках входа, риски безопасности |
| Валидация только в сервисе | Не меняется сигнатура контроллера | Смешение слоёв, слабая контрактность API |
| Синхронный вызов без таймаута | Проще реализация | Риск подвисания запроса, деградация SLA |

## Главный риск

- Отсутствие редактирования секретов и ограничения размера входа при интеграции с внешним LLM.

## Последствия

- Плюсы: снижается доля 5xx за счёт валидации; соблюдение правил API-1, SEC-1, REL-1; улучшается поддерживаемость за счёт разделения слоёв.
- Минусы: требуется внедрить модель запроса и обработку ошибок; небольшое усложнение контроллера и тестов.
