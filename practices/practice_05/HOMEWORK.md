# ДЗ 5. Две команды, одна фича

Проект: warhammerMap, ветка practice-5-spec-driven. Фреймворк: GitHub Spec Kit. Фича: администратор скачивает все события карты одним JSON-файлом.

Артефакты лежат в папке speckit: constitution, спека UI (001-events-export-ui), спека логики (002-events-export-api), общий контракт (events-export-contract.md). В каждой папке спеки есть spec-before.md (до согласования), spec.md (после), spec.diff, plan.md и tasks.md.

## Как работали

Две команды изображали два отдельных агента Codex, у каждого свой контекст. Читать чужую папку им было запрещено. Команда UI читала только клиент и описала кнопку, состояния и тексты ошибок. Команда логики читала только сервер и описала endpoint, поля файла, сортировку, доступ и коды ошибок.

При сверке нашлось четыре расхождения. UI ждал массив, логика отдавала объект с exportedAt. UI сам называл файл events.json, логика отдавала имя с датой в заголовке. Событие с удалённой планетой у логики роняло весь экспорт с ошибкой 500. Лимит у логики был и по числу событий, и по размеру, и ещё отдельный код 503, а UI знал только 401 и 403. Решили так: объект с exportedAt, имя файла из заголовка с запасным events.json, для удалённой планеты place: null, лимит только 10 000 событий с кодом 413. Обе команды обновили свои спеки под контракт, потом по Spec Kit составили plan и tasks и написали код.

Главная находка на этапе спек: глобальный AdminGuard пропускает все GET-запросы без проверки сессии. Команда UI считала, что экспорт и так закрыт. Без спеки логики эндпоинт оказался бы открыт всем. Исправили декоратором RequireAdmin, который guard читает до того, как пропустить чтение.

## Проверки

Сервер: npx jest, 42 из 42 тестов. Отдельные тесты есть на сортировку, place: null, пустой список, 413 до загрузки данных и на guard для GET с RequireAdmin. Клиент: tsc и next build без ошибок.

На запущенном стеке: без сессии 401, обычный пользователь получает 403, администратор получает 200, заголовок attachment с events-20261029.json и 7 событий по порядку дат. Обычный GET /events остался открытым.

Демо: войти как admin@warhammer.local, нажать «Экспорт событий» в панели поиска, скачается файл. После выхода кнопки нет, прямой запрос к /api/backend/events/export возвращает 401.

## Сравнение с OpenSpec

OpenSpec строится вокруг изменения: proposal, delta к текущей спеке, после приёмки archive вливает её в главную спеку. Это удобно в существующем проекте, где важно, что именно меняется. Spec Kit строится вокруг фичи: каждая фича получает свою папку со spec, plan и tasks, а над всем стоит constitution с принципами проекта. Плана в отдельном шаге OpenSpec нет, у Spec Kit он есть, и в нём явно проверяется соответствие constitution.

Spec Kit тяжелее: больше шаблонов и команд, init ставит в проект десяток файлов команд. Шаблон спеки подробный: user stories с приоритетами, FR, success criteria. Для небольшой фичи часть разделов оказалась лишней. Скрипт создания фичи по умолчанию хочет новую git-ветку, а для работы двух команд в одном дереве это мешало, папки пришлось создавать руками. У OpenSpec есть validate и archive, у Spec Kit аналога нет: актуальность спек после реализации никто не проверяет.

Для brownfield-изменений я бы выбрал OpenSpec. Spec Kit удобнее для новой фичи, которую делят несколько команд: constitution задаёт им общие правила.

## Рефлексия

Самое полезное в задании: две спеки, написанные независимо. Каждая команда честно выписала свои предположения о другой стороне, и все расхождения стали видны до кода, а не на интеграции. Дыра в доступе нашлась именно так: одна команда считала её закрытой, другая прочитала код и увидела, что нет.

Решения в контракте принимал человек, агенты только предлагали варианты. Так и должно быть: например, вопрос, падать ли экспорту на битых данных, это продуктовое решение, а не техническое.

Ещё вывод: отчёт агента не равен проверке. Один из запусков Codex сообщил, что всё готово, хотя из-за песочницы не смог записать ни одного файла. Другой упёрся в лимит до финальных тестов. Каждый результат пришлось сверять с диском и запускать проверки самому.
