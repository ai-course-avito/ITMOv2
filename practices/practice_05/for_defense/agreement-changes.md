# Что изменилось после согласования контракта

Сравниваются предоставленная заказчиком версия [до согласования](<before согласование/spec.md>) и [согласованная версия](<after согласование/spec.md>). Полные контракты: [до](<before согласование/contract.md>) и [после](<after согласование/contract.md>). Изменения сверены с присланным diff трёх файлов.

## Принятые решения

| Вопрос | До согласования | После согласования |
| --- | --- | --- |
| Как искать город | Контракт предлагал совпадение фрагмента названия; точное правило оставалось открытым. | Сравнение без учёта регистра и пробелов по краям, **только с начала названия**: `Мос` находит Москву, `оск` — нет. |
| Что делать с прежним результатом при отправке | Было зафиксировано сохранение результата при редактировании; поведение после неудачной отправки ещё обсуждалось. | При попытке отправки прежний результат, заголовок маршрута и сравнение цен сразу очищаются. При ошибке проверки, сети или сервиса показывается ошибка без прежнего результата. При простом редактировании результат по-прежнему остаётся. |

## Как обновились три файла

### Спецификация `spec.md`

- Статус изменён с «контракт ожидает согласования» на «общий контракт согласован 2026-10-28».
- В сценарий выбора добавлен проверяемый пример `Мос` / `оск`; требование `FR-003` и раздел алгоритма теперь однозначно задают поиск с начала названия.
- В сценарий исправления маршрута добавлена ошибочная отправка с очисткой прежнего результата. `FR-004` уточняет границу его сохранения, а `FR-011` — очистку результата, заголовка и сравнения цен до проверки формы.
- Раздел состояний UI и граничный случай ошибки сервиса уточнены: выбранные аэропорты сохраняются для повтора, прежний результат — нет. Добавлен критерий `SC-007` для проверки ошибочной отправки.

### Общий контракт `contract.md`

- Статус и последний раздел изменены с проекта на согласованные решения.
- Шаг фильтрации справочника закрепляет совпадение только с начала названия города.
- Порядок отправки закрепляет очистку прежнего результата **перед** проверкой двух выбранных аэропортов, дат и фильтров. Только после успешной проверки выполняется один POST.
- Таблицы состояний и ошибок уточняют отсутствие прежнего результата при некорректном маршруте и ошибке поиска.

### Чеклист `requirements.md`

- В [версии до](<before согласование/checklists/requirements.md>) примечание говорит, что контракт ещё требует согласования. В [версии после](<after согласование/checklists/requirements.md>) отмечены два принятых решения. Оценка качества текста осталась 16/16; это не оценка работающего кода.

## Что осталось прежним

Справочник локален, подсказки не вызывают поиск, а форма отправляет выбранные IATA-коды через существующие `POST /api/fares/one-way` и `POST /api/fares/round-trip`. Даты и фильтры сохраняют прежний формат. Позднее расширение справочника до 48 городов и 58 аэропортов было отдельным изменением UI и не относится к двум решениям этого согласования.

Эти папки фиксируют содержимое версий для защиты. Они сами по себе не устанавливают порядок создания документов и кода; его нужно подтверждать историей чатов и коммитов.
