# Как выглядят спецификации OpenSpec и Spec Kit на одной фиче

**Фича:** выбор конкретного аэропорта по названию города в `practice_05`. Сравнение основано на файлах этого репозитория, а не на общих описаниях фреймворков.

## Артефакты

| OpenSpec | Spec Kit |
| --- | --- |
| [proposal.md](../../../openspec/changes/city-airport-selection/proposal.md) — зачем нужна фича, что меняется, охват | [spec.md](../../../specs/001-city-airport-selection/spec.md) — пользовательские истории, требования, критерии успеха, допущения |
| [spec delta](../../../openspec/changes/city-airport-selection/specs/city-airport-selection/spec.md) — добавленные требования и сценарии `WHEN/THEN` | [contract.md](../../../specs/001-city-airport-selection/contract.md) — отдельно согласованные данные, правила, вызовы, состояния и ошибки |
| [design.md](../../../openspec/changes/city-airport-selection/design.md) — решения, альтернативы, риски, схема взаимодействия | [checklist](../../../specs/001-city-airport-selection/checklists/requirements.md) — проверка качества текста спецификации |
| [tasks.md](../../../openspec/changes/city-airport-selection/tasks.md) — шаги реализации и проверки | `plan.md` и `tasks.md` для этой Spec Kit фичи отсутствуют |

Версия Spec Kit **до согласования** сохранена из предоставленных заказчиком материалов: [spec.md](<before согласование/spec.md>), [contract.md](<before согласование/contract.md>) и [чеклист](<before согласование/checklists/requirements.md>). Согласованная версия также сохранена в [папке «after согласование»](<after согласование/spec.md>) и основном каталоге `specs/001-city-airport-selection/`. Разница описана в [отдельном файле](agreement-changes.md).

## Разница в форме требований

| Аспект | OpenSpec | Spec Kit в этой работе |
| --- | --- | --- |
| Единица описания | Изменение к существующему продукту: `ADDED Requirements` для capability `city-airport-selection` | Самостоятельная feature specification с приоритетными пользовательскими историями P1–P3 |
| Проверяемый сценарий | Под требованием дано условие и результат: `WHEN` вводят «Москва» → `THEN` показаны три аэропорта | В истории дано `Given/When/Then` и отдельный `Independent Test`; требования имеют ID `FR-001`–`FR-012` |
| Ценность | Кратко в `Purpose` и `proposal.md` | Для каждой истории явно записано `Why this priority`; отдельно даны измеримые `SC-001`–`SC-007` |
| Проектные решения | Локальный справочник, отделение текста от кода, альтернативы и риски находятся в `design.md` | В `spec.md` описаны UI и логика, а точные данные и API вынесены в `contract.md` |
| Контроль полноты | Требования и сценарии читаются вместе с design и tasks | Отдельный чеклист отмечает 16 критериев качества спецификации |

Например, OpenSpec формулирует требование «Подтверждённый выбор для поиска» и сценарий, где изменение текста сбрасывает выбор. Spec Kit раскладывает это на историю исправления маршрута, проверяемые случаи и `FR-005`/`FR-006`. Общий контракт уточняет представление поля (`text` и `selected`), порядок проверки и отсутствие POST при неподтверждённом выборе.

## Что пришлось согласовать между UI и логикой

1. **Совпадение города:** только с начала названия после удаления пробелов по краям и без учёта регистра. `Мос` находит Москву, `оск` — нет. OpenSpec требовал нечувствительность к регистру, но не фиксировал режим поиска по части названия.
2. **Предыдущий результат:** ввод и выбор его не меняют; попытка отправки очищает его до проверки полей. При ошибке показывается сообщение без старого результата. OpenSpec фиксировал сохранение результата лишь до нажатия кнопки.
3. **Граница API:** UI хранит отображаемый текст отдельно от выбранного аэропорта; логика передаёт существующим `POST /api/fares/one-way` и `POST /api/fares/round-trip` только IATA-коды и прежние параметры. Новый серверный endpoint подсказок не нужен.

Согласованные правила записаны в [общем контракте](../../../specs/001-city-airport-selection/contract.md). Реализация использует [компонент UI](../frontend/src/AirportField.tsx) и [модуль подготовки запроса](../frontend/src/fareSearch.ts); сервер сохранил существующий API.

## Наблюдения и ограничения сравнения

- OpenSpec в этой работе удобен для точечного изменения: proposal, delta spec, design и tasks показывают, как новая функция встроится в уже работающий поиск.
- Spec Kit делает более явными пользовательский путь, приоритет и критерии результата; отдельный контракт помог разделить работу UI и логики. При этом для этой фичи не были созданы `plan.md` и `tasks.md`, поэтому сравнение полного цикла Spec Kit провести нельзя.
- Общая Spec Kit спецификация и контракт сохранены **до** и **после** согласования. Они не разделены на два самостоятельных документа UI и логики. Архивные версии «до» предоставлены заказчиком позднее; коммит согласованной Spec Kit спецификации (`d0543ab`) сделан после коммитов реализации UI (`ab22f11`, `2ee8608`). Сами файлы не подтверждают требование задания «согласовать до генерации кода»; порядок коммитов здесь указан открыто.
- OpenSpec design и Spec Kit contract описывают исходный справочник из 4 городов и 6 аэропортов. Позднее UI расширен до 48 городов и 58 аэропортов без отдельного обновления этих двух документов. Фактический состав приведён в [документации фичи](../docs/features/city-airport-selection.md).

## Проверяемое состояние реализации

[Отчёт проекта](../verification/flight-features.md) содержит backend-тесты, сборку и офлайн-сценарий поиска с подменённым Ignav. [Тесты логики формы](../frontend/src/fareSearch.test.mjs) покрывают выбор аэропорта, поиск по началу города, формирование POST, неподтверждённый выбор и ошибки. Отдельного зафиксированного браузерного демо в этих артефактах нет.
