# Задачи: [НАЗВАНИЕ ФИЧИ]

**Входные данные**: Дизайн-документы из `/specs/[###-feature-name]/`

**Предварительные условия**: plan.md (обязателен), spec.md (обязателен для пользовательских историй), research.md, data-model.md, contracts/

**Тесты**: Примеры ниже включают тестовые задачи. Тесты НЕОБЯЗАТЕЛЬНЫ — включайте их только если явно запрошены в спецификации фичи.

**Организация**: Задачи сгруппированы по пользовательским историям для независимой реализации и тестирования каждой истории.

## Формат: `[ID] [P?] [Story] Описание`

- **[P]**: Можно выполнять параллельно (разные файлы, нет зависимостей)
- **[Story]**: К какой пользовательской истории относится задача (например, US1, US2, US3)
- Указывайте точные пути к файлам в описаниях

## Конвенции путей

- **Один проект**: `src/`, `tests/` в корне репозитория
- **Веб-приложение**: `backend/src/`, `frontend/src/`
- **Мобильное**: `api/src/`, `ios/src/` или `android/src/`
- Пути ниже предполагают один проект — корректируйте по структуре из plan.md

## Зависимости и порядок выполнения

### Зависимости фаз

- **Подготовка (Фаза 1)**: Нет зависимостей — можно начинать сразу
- **Базовая (Фаза 2)**: Зависит от завершения Подготовки — БЛОКИРУЕТ все истории
- **Пользовательские истории (Фаза 3+)**: Все зависят от завершения Базы
  - Истории можно вести параллельно (при наличии ресурсов)
  - Или последовательно в порядке приоритетов (P1 → P2 → P3)
- **Полировка (финальная фаза)**: Зависит от завершения всех нужных историй

### Зависимости пользовательских историй

- **Пользовательская история 1 (P1)**: Можно начинать после Базовой (Фаза 2) — без зависимостей от других историй
- **Пользовательская история 2 (P2)**: Можно начинать после Базовой (Фаза 2) — может интегрироваться с US1, но должна быть тестируема независимо
- **Пользовательская история 3 (P3)**: Можно начинать после Базовой (Фаза 2) — может интегрироваться с US1/US2, но должна быть тестируема независимо

### Внутри каждой пользовательской истории

- Тесты (если включены) ДОЛЖНЫ быть написаны и ПАДАТЬ до реализации
- Модели — перед сервисами
- Сервисы — перед эндпоинтами
- Ядро реализации — перед интеграцией
- История завершена — прежде чем переходить к следующему приоритету

### Возможности параллельной работы

- Все задачи Подготовки с пометкой [P] можно выполнять параллельно
- Все Базовые задачи с пометкой [P] можно выполнять параллельно (в рамках Фазы 2)
- После завершения Базы все пользовательские истории можно начинать параллельно (если хватает ресурсов)
- Все тесты пользовательской истории с пометкой [P] можно выполнять параллельно
- Модели внутри истории с пометкой [P] можно выполнять параллельно
- Разные пользовательские истории могут выполняться параллельно разными участниками команды

## Стратегия реализации

### Сначала MVP (только Пользовательская история 1)

1. Завершить Фазу 1: Подготовка
2. Завершить Фазу 2: Базовая (КРИТИЧНО — блокирует все истории)
3. Завершить Фазу 3: Пользовательская история 1
4. ОСТАНОВИТЬСЯ и ПРОВАЛИДИРОВАТЬ: Протестировать Пользовательскую историю 1 независимо
5. Деплой/демо при готовности

### Инкрементальная поставка

1. Завершить Подготовку + Базу → База готова
2. Добавить Пользовательскую историю 1 → Тестировать независимо → Деплой/Демо (MVP!)
3. Добавить Пользовательскую историю 2 → Тестировать независимо → Деплой/Демо
4. Добавить Пользовательскую историю 3 → Тестировать независимо → Деплой/Демо
5. Каждая история добавляет ценность, не ломая предыдущие

### Параллельная стратегия команды

При наличии нескольких разработчиков:

1. Команда совместно завершает Подготовку + Базу
2. После завершения Базы:
   - Разработчик A: Пользовательская история 1
   - Разработчик B: Пользовательская история 2
   - Разработчик C: Пользовательская история 3
3. Истории завершаются и интегрируются независимо

## Примечания

- [P] задачи = разные файлы, нет зависимостей
- Метка [Story] привязывает задачу к конкретной пользовательской истории для трассируемости
- Каждая пользовательская история должна завершаться и тестироваться независимо
- Убедитесь, что тесты падают до реализации
- Коммит после каждой задачи или логической группы
- Останавливайтесь на любой контрольной точке для независимой валидации истории
- Избегайте: расплывчатых задач, конфликтов в одном файле, кросс-историйных зависимостей, ломающих независимость
