# Practice 05 Subscription Service Constitution

## Core Principles

### I. Project Structure (service/ui/tests)
Все компоненты проекта обязаны соблюдать следующую структуру директорий:
- backend‑сервис на Python размещается в каталоге `service/` и поднимается локально (localhost);
- пользовательский интерфейс размещается в каталоге `ui/`;
- все авто‑тесты размещаются в каталоге `tests/`.
Рationale: единая структура упрощает запуск, навигацию и автоматизацию CI/CD.

### II. Spec-Driven Development (SDD) & Approval
Работа ведется строго по SDD:
- перед реализацией создается спецификация (spec);
- спецификация явно согласуется с человеком‑ревьюером; исполнитель не имеет права
  выставлять статус «согласовано» самостоятельно;
- все неизвестные и допущения помечаются явно; реализация не начинается, пока
  критичные неизвестные не разрешены.
Rationale: снижает риск неверных реализаций и укрепляет предсказуемость разработок.

### III. Unit Tests for Every Feature
Каждая новая фича должна сопровождаться юнит‑тестами, покрывающими ключевые сценарии.
Тесты пишутся и поддерживаются вместе с кодом фичи. Тесты должны быть стабильными,
детерминированными и запускаться локально и в CI. Отсутствие тестов для новой фичи
рассматривается как блокер к слиянию.
Rationale: обеспечивает регрессионную устойчивость и документирует поведение.

### IV. Production-Ready Quality (No Stubs)
Код базы должен оставаться работоспособным в любой момент. Запрещены заглушки и
незавершенные фрагменты, оставляющие систему в нерабочем состоянии. Любые временные
ограничения явно документируются и обоснованы, но не нарушают работоспособность.
Rationale: поддерживает качество и сокращает технический долг.

### V. Language Policy (RU comments, EN code/commits)
Комментарии и ответы (в переписке, спецификациях, PR‑обсуждениях) ведутся на русском.
Код, идентификаторы, сообщения коммитов и логи — на английском.
Rationale: облегчает коммуникацию в команде и совместимость инструментов.

## Additional Constraints

- Технологический стек backend: Python.
- Приложение сервиса запускается на localhost в режиме разработки; детали порта и
  профилей запуска документируются в README соответствующих модулей.
- UI из `ui/` взаимодействует с сервисом из `service/` через явно описанные контракты.

## Development Workflow

- Спецификация → явное согласование человеком → реализация → ревью → слияние.
- Любая реализация без согласованной спецификации запрещена.
- В каждый PR включаются соответствующие тесты из `tests/`.
- CI обязан запускать юнит‑тесты и сигнализировать о несоответствии принципам.
- Неизвестные в задачах помечаются и трекаются до разрешения; реализация блокируется,
  если неизвестные критичны для дизайна/контракта.

## Governance

- Настоящая Конституция имеет приоритет над иными практиками.
- Процедура поправок: изменения оформляются как PR, включают описание, причину и план
  миграции (если требуется). Поправки вступают в силу после явного согласования
  человеком‑ревьюером (утверждающий ревьюер: Пользователь).
- Версионирование Конституции: Semantic Versioning
  MAJOR — несовместимые изменения принципов или удаление разделов;
  MINOR — добавление новых принципов/разделов или значимое расширение;
  PATCH — редакционные уточнения без изменения смысла.
- Compliance: каждое ревью проверяет соблюдение принципов. PR, нарушающие принципы,
  не могут быть слиты без обоснованного исключения, одобренного человеком‑ревьюером.
