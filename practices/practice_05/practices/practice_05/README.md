Практика 05 — Subscription Service и серверный поиск по нику (username)

Кратко

- Минимальный сервис подписок со статическим UI и двумя вариантами бэкенда:
  - stdlib HTTP server (server.py) — точка входа по умолчанию, без внешних зависимостей
  - FastAPI (service/app.py) — альтернативная реализация, используется в тестах
- Одна кросс-командная фича реализована на двух сторонах (бэкенд и UI): серверный поиск по нику (username) среди подписчиков.
- Спецификации написаны и сведены по SDD-процессу с использованием GitHub SpecKit.

Как запустить

- Сервер и UI:
  - make -C practices/practice_05 run
  - открыть http://localhost:8000/

Фича: Поиск по нику (только среди подписчиков)

- Область: поиск только по множеству подписчиков текущего пользователя
- Поле сопоставления: username (регистронезависимый поиск по подстроке)
- Длина запроса: 2..100 (строка нормализуется trim)
- Пагинация: page/page_size; сервер возвращает total
- Сортировка: username ASC, затем id ASC
- Поля элемента ответа: id, username, status (чувствительные поля не возвращаются)
- Поведение UI: отправляет запросы с debounce ~300 мс, показывает результаты в порядке сервера, отображает total и число элементов на странице

Контракт API

- Endpoint: GET /api/subscribers/search
- Auth: обязателен (в этой практике через заголовок X-Auth-User)
- Параметры запроса:
  - query: строка 2..100; регистронезависимый substring по username
  - page: число ≥ 1 (по умолчанию 1)
  - page_size: 1..50 (по умолчанию 20)
- Ответ 200 (application/json):
  - { total: number, page: number, page_size: number, items: Array<{ id: string, username: string, status: 'active'|'blocked' }> }
- Ошибки:
  - 401 Unauthorized — отсутствует аутентификация
  - 422 Unprocessable Entity — ошибки валидации (длина запроса и т.п.)
  - 429/5xx — по стандартам проекта

SDD с GitHub SpecKit

- Процесс:
  - Раздельные спеки для бэкенда (001) и UI (002)
  - Сведение решений в разделах «Согласование (v1)»
  - Явно зафиксированный контракт API (путь, параметры, ответ, ошибки)
- Артефакты SpecKit лежат в .specify/ и .opencode/ (чек-листы, таски, воркфлоу)
- Результат: спеки направляют разработку и тесты; контракт обеспечивает согласованность команд

Сравнение: SpecKit vs OpenSpec

- GitHub SpecKit (использован здесь):
  - Markdown‑first, SDD прямо в репозитории; лёгкие чек-листы и воркфлоу
  - Удобно для быстрых итераций и согласования фич в одном репо
  - Компромисс: меньше формальной валидации; опора на дисциплину и тесты
- OpenSpec (контракт‑фёрст, например, OpenAPI):
  - Строго типизированные контракты; генерация клиентов/серверов
  - Силен для многосервисных систем и API‑первого подхода
  - Компромисс: более тяжёлая настройка; для гибких UI/UX итераций нужен процесс
- Когда что выбирать:
  - SpecKit — для фич‑уровня SDD и быстрого сведения (как в этой практике)
  - OpenSpec — для больших, разделяемых API, где важны инструменты и генерация

Принятые решения

- Поиск ограничен подписчиками; сопоставление по username
- Мин. длина 2, макс 100 (trim)
- Серверная пагинация с total
- Элементы: id, username, status; UI рендерит username и статус в режиме поиска
- display_name убран из API и UI для однозначности
- Дальше: унифицировать серверные реализации, расширить тесты для stdlib‑сервера, рассмотреть OpenAPI при выносе API
