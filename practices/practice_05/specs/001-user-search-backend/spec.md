# Спецификация функциональности: Поиск пользователя по имени (бэкенд)

**Ветка фичи**: n/a

**Создано**: 2026-11-01

**Статус**: Черновик

**Входные данные**: Описание пользователя: "Нужно уметь делать поиск по имени пользователя в сервисе. Сгенерируй спеку ТОЛЬКО под часть бэкенда, не трогая юай."


## Согласование (v1)

- Область: серверный поиск используется во всех сценариях; UI обращается к API поиска. Поиск ограничен множеством подписчиков текущего пользователя.
- Поле сопоставления: username (регистронезависимо; подстрочное совпадение).
- Минимальная длина запроса: 2 символа; пустой ввод/пробелы — снятие фильтра на UI, запросы <2 сервер не принимает.
- Максимальная длина запроса: 100 символов; сервер отклоняет превышение; UI ограничивает ввод/обрезает.
- Сортировка/пагинация: по умолчанию сервер сортирует по username ASC и возвращает страницы (page/page_size) и общее количество total. UI отображает результаты постранично в порядке сервера.

Примечание: UI выводит результаты в порядке, возвращённом сервером; дополнительных параметров сортировки на v1 не предусматривается.

## Сценарии пользователей и тестирование (обязательно)

### Пользовательская история 1 - Поиск по имени (Приоритет: P1)

Как аутентифицированный пользователь сервиса, я хочу искать пользователей по их имени/никнейму (username), чтобы быстро находить нужного пользователя.

**Почему этот приоритет**: Поиск — ключевая функция навигации по пользователям и необходимое основание для многих сценариев.

**Независимый тест**: При вводе запроса длиной не менее 2 символов сервис возвращает список кратких карточек пользователей, соответствующих запросу, с пагинацией.

**Сценарии приемки**:

1. Дано аутентифицированный пользователь и существующий пользователь с username "ivan", Когда выполнен запрос с query="iva", Тогда результат содержит пользователя "ivan" и список отсортирован по username по возрастанию.
2. Дано аутентифицированный пользователь и несколько совпадений, Когда выполнен запрос с query длиной ≥2, Тогда возвращается не более 20 результатов на страницу, присутствует информация для перехода к следующей странице.

---

### Пользовательская история 2 - Валидация и пустые результаты (Приоритет: P2)

Как пользователь, я хочу получать понятные сообщения об ошибках при некорректном запросе и корректный пустой ответ, когда совпадений нет, чтобы понимать, что делать дальше.

**Почему этот приоритет**: Улучшает предсказуемость и снижает обращения в поддержку.

**Независимый тест**: Запрос длиной <2 символов приводит к предсказуемой ошибке валидации; запрос корректной длины без совпадений возвращает пустой список и нулевые счетчики.

**Сценарии приемки**:

1. Дано аутентифицированный пользователь, Когда выполнен запрос с query длиной <2 символов, Тогда возвращается ошибка валидации с описанием ограничения по длине.
2. Дано аутентифицированный пользователь, Когда выполнен запрос с корректной длиной и без совпадений, Тогда возвращается пустой список результатов и корректные метаданные пагинации.

---

### Пользовательская история 3 - Доступ и безопасность (Приоритет: P3)

Как владелец сервиса, я хочу, чтобы поиск был доступен только аутентифицированным пользователям и возвращал только безопасные поля, чтобы исключить утечку персональных данных.

**Почему этот приоритет**: Соответствие требованиям безопасности и приватности.

**Независимый тест**: Неаутентифицированный запрос отклоняется; ответы содержат только разрешенные поля (идентификатор, username, отображаемое имя, статус), без e-mail, телефонов и пр.

**Сценарии приемки**:

1. Дано неаутентифицированный клиент, Когда выполняет запрос поиска, Тогда доступ запрещен.
2. Дано аутентифицированный клиент, Когда выполняет корректный запрос, Тогда в ответе присутствуют только разрешенные поля и отсутствуют чувствительные данные.

---

### Краевые случаи

- Пустой или состоящий из пробелов запрос — трактуется как некорректный (ошибка валидации).
- Слишком длинный запрос — ограничение по максимальной длине (например, 100 символов) приводит к ошибке валидации.
- Запрос с разным регистром — поиск нечувствителен к регистру.
- Юникод/кириллица — поиск корректно обрабатывает символы за пределами ASCII.
- Большое количество совпадений — результаты пагинируются, время ответа остается в целевом SLA.

## Требования (обязательно)

### Функциональные требования

- FR-001: Сервис ДОЛЖЕН предоставлять серверную возможность поиска среди подписчиков текущего аутентифицированного пользователя по полю username посредством текстового запроса (query).
- FR-002: Сопоставление ДОЛЖНО быть нечувствительным к регистру и поддерживать частичное совпадение подстроки (substring match).
- FR-003: Минимальная длина query — 2 символа; запросы длиннее 100 символов отклоняются. Пробелы по краям игнорируются (trim).
- FR-004: Результаты ДОЛЖНЫ пагинироваться. Значения по умолчанию: размер страницы 20, максимальный размер 50. Ответ содержит информацию для запроса следующей страницы и общее количество результатов (total).
- FR-005: Порядок результатов по умолчанию — по username по возрастанию. При равенстве — по идентификатору по возрастанию.
- FR-006: Ответ ДОЛЖЕН возвращать только следующие поля для каждого пользователя: уникальный идентификатор, username, статус (активен/заблокирован). Поля с чувствительной информацией (e-mail, телефон, токены и т.п.) НЕ ДОЛЖНЫ возвращаться.
- FR-007: Запросы поиска ДОЛЖНЫ требовать аутентификации. Неаутентифицированные запросы отклоняются.
- FR-008: Валидационные ошибки ДОЛЖНЫ возвращать четкое описание причины (например, ограничение по длине) в пользовательском-ориентированном виде.
- FR-009: Сервис ДОЛЖЕН корректно обрабатывать имена с буквами не-ASCII (включая кириллицу) при поиске и сопоставлении.
- FR-010: Сервис ДОЛЖЕН фиксировать попытки доступа без аутентификации и критические ошибки поиска для последующего аудита.

### Контракт API

- Endpoint: GET `/api/subscribers/search`
- Аутентификация: обязательна (JWT/сессия по стандартам проекта)
- Query-параметры:
  - `query` — строка, trim; длина 2..100; регистронезависимый substring по `username`
  - `page` — целое число ≥1; по умолчанию 1
  - `page_size` — целое число 1..50; по умолчанию 20
- Ответ 200 (application/json):
  - `{ total: number, page: number, page_size: number, items: Array<{ id: string, username: string, status: 'active'|'blocked' }> }`
  - Порядок `items`: по умолчанию `username` ASC; при равенстве — `id` ASC
- Ошибки:
  - 401 Unauthorized — неаутентифицированный запрос
  - 422 Unprocessable Entity — ошибка валидации (например, `{ error: { code: 'validation_error', message: 'query length must be between 2 and 100' } }`)
  - 429 Too Many Requests — согласно лимитам
  - 5xx — по стандартам проекта

### Ключевые сущности (если фича связана с данными)

- User (сводная модель ответа):
  - id (уникальный идентификатор)
  - username (строка)
  - display_name (строка)
  - status (enum: active, blocked)

- Search Query (логическая сущность запроса):
  - query (строка, 2..100 символов)
  - page (натуральное число ≥1)
  - page_size (натуральное число 1..50, по умолчанию 20)

## Критерии успеха (обязательно)

### Измеримые показатели

- SC-001: 95% валидных поисковых запросов возвращают результаты (или пустой ответ) менее чем за 700 мс при типичном объеме данных.
- SC-002: 100% запросов длиной <2 символов приводят к валидационной ошибке с понятным пояснением; 100% запросов без совпадений возвращают пустой список без ошибок.
- SC-003: 100% точных совпадений (полный username) присутствуют на первой странице результатов при стандартном размере страницы.
- SC-004: В ответах отсутствуют чувствительные данные; это подтверждается ревью безопасности и автотестами на состав полей.

## Предположения

- Фича включает интеграцию UI с сервером; UI использует данный контракт API.
- Все клиенты обращения к поиску — аутентифицированные пользователи сервиса.
- В доменной модели присутствует поле username, пригодное для поиска по подстроке.
- Пагинация требуется для контроля объема ответа и времени отклика; значения по умолчанию: page_size=20, max=50.
- Сортировка по username удовлетворяет текущим бизнес-требованиям; расширенные варианты релевантности могут быть рассмотрены отдельно.
