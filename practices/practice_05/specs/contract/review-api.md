# Контракт стыка: страница ↔ HTTP API ревью диффа

Единый межкомандный контракт по Принципу V конституции
(`.specify/memory/constitution.md`). Описывает только стык между страницей
и HTTP-слоем сервиса: адрес, маршруты, формат запроса/ответа, HTTP-коды,
ошибки, тайм-ауты, демо-режим. Не описывает внутреннее устройство страницы
(вёрстка, состояния интерфейса) и внутреннее устройство сервера
(обработчики, модули) — это зона каждой команды по отдельности.

Любая правка этого файла — согласованное изменение, видимое обеим
командам, прежде чем реализация начинает от него зависеть (Принцип V).

## 1. Процесс, адрес, маршруты

- Страницу и API обслуживает один процесс на одном origin:
  `127.0.0.1:<порт>`.
- Порт по умолчанию — `8055`. Переопределяется переменной окружения
  `REVIEW_PORT`.
- Адрес прослушивания фиксирован — `127.0.0.1` (Принцип VI конституции),
  не входит в конфигурацию.
- CORS не используется: страница и API всегда на одном origin.

| Маршрут | Метод | Назначение | Отвечает за содержимое |
|---|---|---|---|
| `/` | `GET` | HTML-страница | команда UI (файл страницы) |
| `/app.js` | `GET` | Скрипт страницы | команда UI (файл скрипта) |
| `/api/review` | `POST` | Ревью диффа | команда логики (обработчик) |

Маршрутизация запросов и отдача файлов страницы по `/` и `/app.js` —
ответственность команды логики (сервер отдаёт статические файлы, которые
предоставляет команда UI). Содержимое HTML/JS — ответственность команды UI.

## 2. Формат запроса

```
POST /api/review
Content-Type: application/json

{"diff": "<текст диффа>"}
```

- Единственное обязательное поле — `diff` (строка, весь текст диффа
  целиком).
- Незнакомые поля в теле запроса игнорируются, а не считаются ошибкой.

## 3. Формат ответа `review_diff`

HTTP-слой передаёт поля, которые вернула `review_diff` (см.
`docs/requirements.md`), без изменений состава и без добавления полей.

| `status` | HTTP-код |
|---|---|
| `"ok"` | 200 |
| `"rejected"` | 400 |
| `"error"` | 502 |

## 4. Ошибки HTTP-слоя (до вызова `review_diff`)

Отдельная от `review_diff` категория — запрос не дошёл до `review_diff` и
модель не вызывалась. Формат тела:

```
{"status": "request_error", "code": "<код>", "message": "<текст>"}
```

| `code` | HTTP-код | Условие |
|---|---|---|
| `invalid_request` | 400 | тело не является корректным JSON, либо JSON без поля `diff`, либо `diff` не строка |
| `request_too_large` | 413 | заявленный или фактический размер тела запроса больше 1 МиБ (`1048576` байт); отказ до чтения тела по `Content-Length`, не дожидаясь полной загрузки в память |
| `method_not_allowed` | 405 | запрос к `/api/review` методом, отличным от `POST` |
| `not_found` | 404 | запрос к пути, который сервис не обслуживает |

Все ответы сервиса (успех, отказ, ошибка запроса, ошибка модели, 404, 405)
— корректный JSON с `Content-Type: application/json`, без текста
трассировки исключения.

## 5. Правило разбора ответа на стороне клиента

1. Клиент всегда сначала пытается разобрать тело ответа как JSON и
   посмотреть на поле `status`.
2. HTTP-код — вторичный сигнал, используется только как подсказка, а не
   единственный источник решения.
3. Клиент считает это «ошибкой сети/сервера» (без статистики, с
   предложением повторить попытку) только в одном из трёх случаев:
   - ответа нет вовсе (сеть недоступна, обрыв, тайм-аут на уровне
     страницы);
   - тело ответа не является корректным JSON;
   - значение `status` не входит в известный набор
     (`"ok"`, `"rejected"`, `"error"`, `"request_error"`).

## 6. Текст для пользователя: `message` vs код

- `message` в ответах `review_diff` и в ответах `request_error`
  предназначен для разработчика и может содержать технические детали.
- Пользовательский текст, который видит человек на странице, страница
  выбирает сама по значению `code` (и `status`), а не копирует `message`
  напрямую.
- `message` допускается показывать в свёрнутом блоке «подробнее» —
  опционально, не как основной текст сообщения.

## 7. Размер диффа

- Единственное бизнес-правило ограничения размера диффа —
  `MAX_DIFF_BYTES = 8192` внутри `review_diff`, дающее отказ
  `diff_too_large`.
- `request_too_large` (413) — исключительно техническая защита
  транспортного уровня HTTP-слоя, не замена и не дублирование бизнес-правила.
- Клиент показывает пользователю один и тот же пользовательский текст и
  для `diff_too_large`, и для `request_too_large` — с точки зрения
  пользователя оба означают «дифф слишком большой».

## 8. Тайм-ауты

- Ожидание ответа модели на сервере ограничено `REVIEW_TIMEOUT_SECONDS = 30`
  (контракт `review_diff`, `docs/requirements.md`).
- Страница ждёт ответа от `/api/review` не больше **45 секунд**. По
  истечении этого времени страница показывает «ошибку сети/сервера» и не
  остаётся в состоянии загрузки бесконечно.
- Ответ сервера, пришедший после истечения этих 45 секунд, клиентом
  игнорируется.

## 9. Демо-режим

- Запуск сервера с флагом `--fake-model` подставляет встроенный клиент
  модели вместо обращения к настоящей Ollama.
- Формат ответов `/api/review` в демо-режиме идентичен обычному режиму —
  отличается только содержимое поля `review` при успехе. Клиенту не нужно
  менять логику разбора ответа.

## 10. Сводная таблица: исход → HTTP-код → тело → что видит страница

| Исход | `status` | `code` | HTTP-код | Поля тела | Что показывает страница |
|---|---|---|---|---|---|
| Успех | `ok` | — | 200 | `review`, `stats` | текст ревью + статистика |
| Отказ: пустой дифф | `rejected` | `empty_diff` | 400 | `code`, `message` | сообщение об отказе, без текста ревью и без статистики |
| Отказ: дифф больше лимита | `rejected` | `diff_too_large` | 400 | `code`, `message` | сообщение об отказе «дифф слишком большой», без текста ревью и без статистики |
| Ошибка модели: тайм-аут | `error` | `model_timeout` | 502 | `code`, `message`, `stats` | сообщение об ошибке модели + статистика, без текста ревью |
| Ошибка модели: нет соединения | `error` | `model_unavailable` | 502 | `code`, `message`, `stats` | сообщение об ошибке модели + статистика, без текста ревью |
| Ошибка модели: HTTP-ошибка модели | `error` | `model_http_error` | 502 | `code`, `message`, `stats` | сообщение об ошибке модели + статистика, без текста ревью |
| Ошибка модели: плохой ответ | `error` | `model_bad_response` | 502 | `code`, `message`, `stats` | сообщение об ошибке модели + статистика, без текста ревью |
| Ошибка запроса: невалидный JSON/нет `diff`/`diff` не строка | `request_error` | `invalid_request` | 400 | `code`, `message` | обобщённое сообщение об ошибке сети/сервера, без статистики |
| Ошибка запроса: тело больше лимита транспорта | `request_error` | `request_too_large` | 413 | `code`, `message` | тот же текст, что для `diff_too_large` (п. 7), без статистики |
| Ошибка запроса: неподходящий метод | `request_error` | `method_not_allowed` | 405 | `code`, `message` | обобщённое сообщение об ошибке сети/сервера, без статистики |
| Ошибка запроса: путь не обслуживается | `request_error` | `not_found` | 404 | `code`, `message` | обобщённое сообщение об ошибке сети/сервера, без статистики |
| Сеть/сервер: нет ответа, обрыв, тайм-аут страницы, тело не JSON, незнакомый `status` | — (ответа нет или не распознан) | — | — | — | сообщение об ошибке сети/сервера, без статистики, с предложением повторить попытку |

## 11. Решения и причины

Дата: 2026-10-22.

- **Коды 200/400/502 для `ok`/`rejected`/`error`.** Отказ (`rejected`) —
  ошибка на стороне запроса (невалидный вход), поэтому 4xx; ошибка модели
  (`error`) — сбой зависимости сервера, а не клиента, поэтому 5xx (502
  как «сервер получил корректный запрос, но вышестоящая зависимость не
  ответила корректно»). Различать исходы по HTTP-коду было бы менее
  надёжно, чем по телу: отсюда правило п. 5 — код вторичен, тело первично.
- **Лимит тела запроса 1 МиБ.** Выбран заметно больше
  `MAX_DIFF_BYTES = 8192`, чтобы корректное JSON-тело с диффом на границе
  бизнес-лимита не отклонялось транспортной защитой из-за накладных
  расходов JSON-обёртки и экранирования строк. Запас по размеру (1 МиБ
  против 8 КиБ) достаточен, чтобы не требовать точного расчёта экранирования
  на каждый символ, но всё ещё защищает сервер от буферизации действительно
  больших тел в память.
- **`request_too_large` показывается тем же текстом, что `diff_too_large`.**
  Пользователь не должен различать, на каком именно уровне (бизнес-правило
  `review_diff` или транспортная защита HTTP-слоя) отклонён его слишком
  большой дифф — для него это один и тот же практический вывод: «нужно
  уменьшить дифф».
- **Свой пользовательский текст на странице, а не прямой показ `message`.**
  `message` пишется для разработчика и может меняться по форме без
  согласования со страницей (например, включать значения переменных);
  устойчивый контракт для пользовательского текста — код (`status`+`code`),
  а не содержимое `message`. Это также снимает риск показать пользователю
  случайно непригодную для показа строку.
