# Спецификация функциональности: Поиск по нику (username) среди подписчиков (UI)

**Ветка фичи**: `[ui-user-name-search]`

**Создано**: 2026-11-01

**Статус**: Черновик

**Входные данные**: Описание пользователя: "Хочу добавить функцию поиска подписчиков по имени. Сгенерируй спеку для этой фичи ТОЛЬКО на стороне ui, не думая про бэкенд."

## Согласование (v1)

- Область: серверный поиск используется во всех сценариях; UI обращается к API поиска. Поиск ограничен множеством подписчиков текущего пользователя.
- Поля поиска: сопоставление выполняется по полю username (регистронезависимо, подстрочное совпадение).
- Минимальная длина запроса: 2 символа; пустая строка/пробелы — снятие фильтра, запросы <2 не отправляются.
- Сортировка: UI выводит результаты в том порядке, в котором возвращает сервер.
- Пагинация: используется серверная пагинация (page/page_size); сервер возвращает total; UI отображает результаты постранично.
- Максимальная длина запроса: 100 символов — ограничение применяется на уровне UI (обрезка/предотвращение ввода) и валидируется сервером.
- Триггер: отправка запроса c debounce ~300 мс; отмена предыдущих незавершённых запросов.
- Аватар: в рамках v1 не обязателен; отображение ограничивается безопасными данными.
- Счётчик: отображает общее число результатов (total) из ответа сервера и количество на текущей странице.

## Сценарии пользователей и тестирование (обязательно)

### Пользовательская история 1 - Быстрый поиск по нику (Приоритет: P1)

Как пользователь списка подписчиков, я хочу ввести ник (username) в поле поиска и сразу видеть результаты, чтобы быстро найти нужного человека.

**Почему этот приоритет**: Это основной сценарий использования поиска; обеспечивает мгновенную ценность и сокращает время на навигацию по списку.

**Независимый тест**: Открыть список подписчиков, ввести фрагмент ника; убедиться, что список обновляется результатами сервера без перезагрузки страницы; отображается total и количество на текущей странице.

**Сценарии приемки**:

1. Дано, что список подписчиков отображён и поле поиска пустое, Когда пользователь вводит фрагмент ника (например, "iv"), Тогда список показывает элементы, где username содержит этот фрагмент (регистр игнорируется), и количество элементов обновлено.
2. Дано активный фильтр, Когда пользователь очищает поле поиска (иконка очистки или клавиша Esc), Тогда отображается исходный список без фильтра.

---

### Пользовательская история 2 - Пустые результаты и пустой ввод (Приоритет: P2)

Как пользователь, я хочу получать ясную обратную связь при отсутствии совпадений и понятное поведение при пустом вводе, чтобы не теряться.

**Почему этот приоритет**: Улучшает UX, предотвращает путаницу и снижает количество поддерживающих обращений.

**Независимый тест**: Ввести запрос, заведомо не соответствующий ни одному имени; убедиться в показе состояния "нет результатов" с рекомендациями. Очистить ввод; убедиться в восстановлении полного списка.

**Сценарии приемки**:

1. Дано введён запрос без совпадений, Когда пользователь завершает ввод, Тогда отображается пустое состояние с текстом "Совпадений не найдено" и подсказкой очистить фильтр.

---

### Пользовательская история 3 - Доступность и управление с клавиатуры (Приоритет: P3)

Как пользователь с клавиатурой или скринридером, я хочу корректные подписи и фокусировку поля поиска, чтобы использовать поиск без мыши.

**Почему этот приоритет**: Соответствие доступности и базовая инклюзивность.

**Независимый тест**: Перемещать фокус Tab до поля поиска; ввести запрос; нажать Esc для очистки; убедиться в озвучивании метки и изменений списка.

**Сценарии приемки**:

1. Дано фокус в поле поиска, Когда пользователь нажимает Esc, Тогда поле очищается и список сбрасывается.

---

### Краевые случаи

- Ввод пустой строки или только пробелов — трактуется как отсутствие фильтра, список полный.
- Лишние пробелы в начале/конце — игнорируются при сравнении.
- Разный регистр символов — поиск регистронезависимый.
- Многословные отображаемые имена — не влияют на поиск; сопоставление выполняется по username.
- Некорректные/редкие символы (дефисы, апострофы, эмодзи) — воспринимаются как часть строки; совпадения находят точные подстроки.
- Очень длинные имена — UI не ломается; текст усечён визуально согласно текущим правилам списка.
- Большой объём результатов — UI корректно обрабатывает серверную пагинацию; обновления остаются плавными; total может быть большим числом.
- Запрос длиной <2 символов — фильтр не применяется; UI может подсветить подсказку о минимальной длине.
- Запрос длиной >100 символов — ввод ограничивается/обрезается до 100 символов.

## Требования (обязательно)

### Функциональные требования

- **FR-001**: UI ДОЛЖЕН содержать видимое поле поиска над списком подписчиков с меткой "Поиск по нику (username)" и плейсхолдером "Введите ник".
- **FR-002**: Поиск выполняется через серверный API; UI отправляет запросы только при длине запроса ≥2 символов; предыдущие незавершённые запросы отменяются (debounce ~300 мс).
- **FR-003**: Совпадение определяется как "содержит" подстроку (containment), регистр игнорируется; лишние пробелы в начале/конце запроса отбрасываются; поиск выполняется по полю username.
- **FR-004**: UI отображает доступные поля карточки; в режиме поиска отображается ник (username) и статус.
- **FR-005**: Обновление результатов происходит по мере ввода (as-you-type) с debounce ~300 мс; визуальное обновление списка должно происходить без заметной задержки.
- **FR-006**: ДОЛЖЕН быть доступен быстрый сброс фильтра: иконка очистки внутри поля и клавиша Esc при фокусе на поле; пустая строка/пробелы полностью снимают фильтр.
- **FR-007**: При отсутствии совпадений отображается явное пустое состояние: заголовок "Совпадений не найдено" и краткая подсказка "Измените запрос или очистите фильтр".
- **FR-008**: Количество найденных элементов (badge/счётчик) отображается рядом с заголовком списка или полем поиска и обновляется при каждом изменении запроса; отображает общее число результатов (total) и число элементов текущей страницы.
- **FR-009**: Сортировка и выбранные режимы отображения списка не изменяются при применении поиска; UI выводит элементы в том порядке, в котором их вернул сервер.

- **FR-010a**: Серверный ответ включает total (общее число результатов), page, page_size и список элементов текущей страницы.

- **FR-013**: UI ДОЛЖЕН поддерживать серверную пагинацию (page/page_size) и навигацию между страницами согласно стандартам проекта.
- **FR-010**: Поле поиска имеет связанный label для скринридеров; фокусное кольцо видимо; контраст по гайдлайнам проекта.
- **FR-011**: Локализация текста меток, плейсхолдеров и пустых состояний соответствует текущему языку интерфейса (по умолчанию — русский).
- **FR-012**: Состояние фильтра не сохраняется между страницами/перезагрузками; при повторном открытии список отображается без фильтра.

### Ключевые сущности (если фича связана с данными)

- **Subscriber (UI)**: Элемент списка; отображает display_name (обяз.), опц. аватар и статус. Поиск выполняется по username.
- **Search Query (UI)**: Текст запроса по username; нормализуется (тримминг пробелов, приведение регистра для сравнения); ограничен 2..100 символами; не сохраняется.

### Контракт API (UI ожидания)

- Endpoint: GET `/api/subscribers/search`
- Параметры запроса:
  - `query` — строка, trim; длина 2..100; регистронезависимый substring по `username`
  - `page` — целое число ≥1; по умолчанию 1
  - `page_size` — целое число 1..50; по умолчанию 20
- Ответ 200 (application/json):
  - `{ total: number, page: number, page_size: number, items: Array<{ id: string, username: string, status: 'active'|'blocked' }> }`
  - Порядок `items` соответствует сортировке сервера (по умолчанию `username` ASC; при равенстве — `id` ASC)
- Ошибки:
  - 401 Unauthorized — неаутентифицированный запрос
  - 422 Unprocessable Entity — ошибка валидации (например, `{ error: { code: 'validation_error', message: 'query length must be between 2 and 100' } }`)
  - 429 Too Many Requests — согласно лимитам
  - 5xx — по стандартам проекта

## Критерии успеха (обязательно)

### Измеримые показатели

- **SC-001**: 95% серверных ответов по поиску возвращаются менее чем за 700 мс при типичном объёме данных; 95% UI-отрисовок после получения ответа завершаются менее чем за 300 мс.
- **SC-002**: 99% операций поиска завершаются без визуальных артефактов (мигания, скачков макета) на стандартных устройствах.
- **SC-003**: 90% пользователей успешно находят нужного подписчика по имени в рамках 10 секунд при первом использовании функции (по результатам тестирования с пользователями или внутреннего UAT).
- **SC-004**: Среднее время нахождения подписчика по имени сокращается минимум на 30% по сравнению с сценарием без поиска (базовая метрика до включения фичи).

## Предположения

- UI использует серверный поиск по username среди подписчиков; список может обновляться по мере получения страниц.
- Email/логины и иные поля вне объёма; поиск только по username.
- Поддержка мобильных и десктопных разрешений входит в объём; отдельной оптимизации для очень больших списков (10000+) не требуется в v1.
- Текущие правила отображения сохраняются; пагинация и сортировка определяются сервером по умолчанию.
