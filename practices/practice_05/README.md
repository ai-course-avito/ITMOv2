# Практика 5. SDD в существующем проекте

На занятии проведите одну небольшую фичу своего проекта через полный цикл OpenSpec: исследование → требования → обсуждение → реализация → проверки → обновление спецификаций и архив. Затем настройте правило проекта для будущих спецификаций и проверьте его на одном фрагменте. Рассчитывайте примерно на 90 минут.

OpenSpec CLI выдаёт инструкции, показывает статус и проверяет структуру документов. Содержание спецификаций и код пишет агент в вашем coding client. Цель, границы изменения и приёмку результата определяет человек.

Для работы здесь подготовлена [отдельная копия приложения «Билетик»](PROJECT_README.md) из практики 4. Описание фичи для части 1 — [выбор порядка сортировки билетов](docs/features/price-sort.md); она пока не реализована. Запуск и проверки описаны в документации проекта.

## Подготовка

Работайте в корне существующего проекта; сохраните его код, правила, инструменты и тесты. Команды презентации рассчитаны на Node.js **не ниже 20.19.0** и OpenSpec **1.14.1**:

```sh
node --version
npm install -g @fission-ai/openspec@1.14.1
openspec --version
openspec init --profile core
```

При инициализации выберите свой coding client и перезапустите его. Попросите агента проверить `openspec --version`, `openspec list --json` и корень проекта. В примерах ниже `/opsx-*` — команды OpenCode; в Codex используйте соответствующие `$openspec-*` skills.

## Часть 1. Одна фича через полный цикл

Выберите небольшое улучшение существующего проекта: например, фильтр или сортировку списка, проверку ввода, экспорт видимых данных или локальную настройку. Новый продукт или фреймворк для этой части не нужен.

1. **Исследуйте код.** Через `/opsx-explore` (Codex: `$openspec-explore`) попросите агента прочитать затронутый код и тесты, найти команду проверки и запустить исходную проверку. Зафиксируйте 3–5 условий приёмки и прежнее поведение, которое нужно сохранить. На этом шаге код не меняйте.
2. **Подготовьте предложение.** Через `/opsx-propose my-feature` (Codex: `$openspec-propose`) опишите цель, условия, ошибки, границы и то, что не входит в изменение. Прочитайте созданные документы до разрешения на реализацию.
3. **Проверьте спецификацию.** В отдельном чате или с отдельным агентом проверьте предложение на пробелы, допущения и совместимость с кодом без правки файлов. Разберите замечания. Если нужно уточнение, обновите изменение через `/opsx-update my-feature` (Codex: `$openspec-update-change`) и примите итоговый план.
4. **Реализуйте согласованное.** После принятия спецификации запустите `/opsx-apply my-feature` (Codex: `$openspec-apply-change`). Просмотрите изменения и фактические результаты проверок. Если обнаружились новые требования, сначала обсудите их и обновите документы.
5. **Проверьте и примите результат.** В отдельном проверяющем чате запустите настоящую команду проверки проекта. Для основного, ошибочного и прежнего сценариев запишите ожидание, факт и доказательство. Человек сопоставляет результат с условиями приёмки.
6. **Обновите спецификации и архивируйте.** Только после приёмки выполните `/opsx-sync my-feature`, проверьте diff текущей спецификации, затем `/opsx-archive my-feature`. В Codex соответствующие skills — `$openspec-sync-specs` и `$openspec-archive-change`. Убедитесь, что текущая спецификация отражает принятое поведение, а изменение осталось в архиве.

Для просмотра документов используйте реальные имена изменений и спецификаций из списков:

```sh
openspec list
openspec list --specs
openspec show CHANGE --type change
openspec validate CHANGE --type change --strict --no-interactive
openspec view
```

Если спецификация уже есть, её можно открыть командой `openspec show SPEC --type spec`. Пустой список основных спецификаций до первого архивирования допустим.

## Часть 2. Правило проекта для OpenSpec

1. Создайте черновик следующего изменения через `/opsx-propose my-next-feature` и сохраните фрагмент документа **до** изменения. Остановитесь до реализации.
2. Дополните существующий `openspec/config.yaml` правилом для будущих `design`, не создавая второй ключ `rules`:

   ```yaml
   rules:
     design:
       - Объясни взаимодействие диаграммой Mermaid.
   ```

3. Получите свежие инструкции командой `openspec instructions design --change my-next-feature --json` и убедитесь, что в них есть ваше правило. Через `/opsx-update my-next-feature` (Codex: `$openspec-update-change`) предложите применить его к сохранённому фрагменту. Просмотрите diff, подтвердите правку и проверьте, что смысл и границы не изменились. Код на этом шаге не меняйте.

Если у изменения нет `design`, используйте `rules.specs` и правило для существующей спецификации, например формат Given/When/Then. Итог: правило остаётся в конфигурации для следующих изменений, а его действие видно на сравнении фрагмента до и после.

## Домашняя работа: две команды — одна фича

Выберите **другой SDD-фреймворк** и сравните его применение с OpenSpec. Эмулируйте две команды в двух чатах:

- Команда 1 готовит спецификацию UI: экраны, действия, состояния и ошибки.
- Команда 2 готовит спецификацию логики: данные, алгоритм, правила и API.

**До генерации кода** согласуйте общий контракт: данные, вызовы, ошибки и состояния. Примите решения и обновите обе спецификации. Затем реализуйте UI и логику, проверьте сквозной сценарий и ошибку или граничный случай.

### Что сдать

- Обе спецификации до и после согласования, а также общий контракт.
- Код работающих UI и логики, результаты проверок и короткое демо.
- Краткую рефлексию: что пришлось согласовать и чему вы научились; сравнение выбранного SDD-фреймворка с OpenSpec.
