# Spec Delta

## Purpose

Единые правила HTTP API Argon: формат ошибок, соответствие статусов и идентификация клиента, чтобы все остальные capability вели себя предсказуемо.

## ADDED Requirements

### Requirement: Единый формат ошибок
Система SHALL возвращать любую ошибку в формате `application/problem+json` с полями `status`, `title`, `detail` и машинным полем `code` (snake_case). Ошибки валидации SHALL дополнительно содержать `errors` с перечнем полей.

#### Scenario: Ресурс не найден
- **WHEN** клиент запрашивает несуществующий товар
- **THEN** ответ имеет статус 404 и `code` равен `product_not_found`

#### Scenario: Невалидное тело запроса
- **WHEN** клиент отправляет товар с пустым `name`
- **THEN** ответ имеет статус 400, `code` равен `validation_failed`, а `errors` содержит поле `name`

### Requirement: Статусы бизнес-конфликтов
Система SHALL возвращать 409 с кодом конфликта, когда запрос корректен по форме, но нарушает бизнес-правило (дубликат, удаление используемой сущности, нехватка остатков, недопустимый переход статуса). Система SHALL NOT менять данные при отказе.

#### Scenario: Отказ не меняет данные
- **WHEN** запрос завершается ответом 409
- **THEN** состояние каталога, складов, резервов и заказов совпадает с состоянием до запроса

### Requirement: Идентификация клиента
Клиентские ручки `/api/me/*` SHALL требовать заголовок `X-User-Id` с идентификатором существующего пользователя. Иначе система SHALL вернуть 401 с кодом `user_unauthorized`. Прочие ручки заголовок не требуют.

#### Scenario: Заголовок отсутствует
- **WHEN** клиент вызывает `GET /api/me/orders` без `X-User-Id`
- **THEN** ответ имеет статус 401 и `code` равен `user_unauthorized`

#### Scenario: Пользователь не существует
- **WHEN** клиент передаёт `X-User-Id` несуществующего пользователя
- **THEN** ответ имеет статус 401 и `code` равен `user_unauthorized`
