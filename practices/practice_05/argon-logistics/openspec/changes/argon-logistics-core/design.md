# Design

## Context

Проект с нуля (greenfield), требования в `proposal.md` и `specs/`. Окружение: .NET 10 SDK, Windows, без внешней инфраструктуры. Нужен работающий backend, который можно запустить одной командой и проверить тестами.

## Goals / Non-Goals

**Goals:**
- Чистая доменная логика планирования без зависимостей от БД и HTTP, чтобы её можно было тестировать как функцию.
- Атомарное резервирование остатков без перепродажи.
- Запуск без внешних сервисов (SQLite-файл).

**Non-Goals:**
- Горизонтальное масштабирование (несколько инстансов API), распределённые блокировки.
- Аутентификация, пагинация, миграции схемы БД (используется `EnsureCreated`).

## Decisions

### Структура solution
`Argonum.Logistics.Core` (сущности, `DeliveryPlanner`, без пакетов) → `Argonum.Logistics.Api` (EF Core, сервисы, minimal API endpoints) → `Argonum.Logistics.Tests` (xUnit: unit для планировщика, интеграционные через `WebApplicationFactory`).
Альтернатива: один проект. Отвергнута: планировщик хочется держать чистым и покрывать unit-тестами отдельно от EF.

### Граф и алгоритм планирования
Узлы: склады и ПВЗ. Рёбра: пути склад → склад и привязки склад → ПВЗ. ПВЗ не имеет исходящих рёбер, поэтому транзитным быть не может.
Один запуск Dijkstra по **обратному** графу от ПВЗ даёт время и следующий узел для всех складов за один проход (вместо запуска из каждого склада). Стоимость сравнивается кортежем `(минуты, пересадки)`, при равенстве побеждает меньший `id` следующего склада, что делает результат детерминированным.
Выбор источников: для каждого товара жадно по складам в порядке `(минуты, id)`. Для одного товара это минимизирует время самого дальнего источника. Альтернатива «минимум числа отправок» (задача покрытия) отвергнута как избыточная.

### Отправка = склад-источник
Позиции с одного склада группируются в одну отправку. Отправки заказа считаются параллельными, поэтому `estimatedMinutes` равно максимуму. Консолидация на транзитных складах не делается (Non-Goal пропозала).

### Резерв остатков
В строке остатка две величины: `Quantity` (физически на складе) и `Reserved`. Доступно = `Quantity - Reserved`. Резерв ставится при создании заказа, снимается при отмене, списывается вместе с `Quantity` при отгрузке. Инвариант `0 <= Reserved <= Quantity` проверяется в сервисах.
Альтернатива: списывать сразу при заказе. Отвергнута: невозможна честная отмена и непонятно, что физически лежит на складе.

### Конкурентность
Все операции, меняющие остатки (создание/отмена заказа, отгрузка, правки остатков), выполняются под одним `SemaphoreSlim` и в одной транзакции БД. Это корректно для одного инстанса. Альтернативы (оптимистичный токен, `BEGIN IMMEDIATE`) сложнее для SQLite и не нужны при Non-Goal про масштабирование.

### Уникальность без учёта регистра
SKU, названия складов и email сравниваются по нормализованному ключу (`TextKey.Of`: trim + `ToUpperInvariant`) в отдельной колонке с уникальным индексом.
Альтернатива: коллация `NOCASE` в SQLite. Отвергнута: она сворачивает регистр только для ASCII, и «Склад Север» с «склад север» считались бы разными (поймано тестом).

### Снимки в заказе
Заказ хранит название/SKU товаров, названия складов и маршрут (список участков) как данные на момент планирования, без внешних ключей на каталог и граф. Поэтому удаление товара/склада/пути не ломает историю, а изменения графа не пересчитывают старые планы (spec `logistics-network`).

### Хранилище и API
EF Core + SQLite (`argon.db`), `EnsureCreated`. Целочисленные `id`. Minimal API с группами по ресурсам. Бизнес-ошибки: исключение `DomainException(code, status)` → единый обработчик → `application/problem+json` с `code`. Валидация тел запросов выполняется вручную в одном месте, чтобы коды и формат `errors` были едиными.
Клиент определяется заголовком `X-User-Id` (middleware-фильтр группы `/api/me`).

### Время и статусы
Статусы хранятся как строки-enum. Время берётся через `TimeProvider`, чтобы тесты могли его подменять.

## Risks / Trade-offs

- [Один семафор сериализует все изменения остатков] → Для масштаба практики достаточно; при росте нагрузки заменить на блокировки по строкам складов.
- [Нет авторизации: админские ручки открыты] → Явно вне scope; описано в proposal и docs.
- [`EnsureCreated` не умеет миграции] → При смене схемы удалить `argon.db`; миграции добавить при выходе за практику.
- [Жадный выбор складов не минимизирует число отправок] → Осознанный компромисс в пользу времени доставки.
- [Заказ либо выполняется целиком, либо отклоняется] → Простое и понятное поведение; частичные заказы вне scope.
