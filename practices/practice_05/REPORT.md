## 2. Spec Kit: две команды — одна фича

Фича — веб-страница ревью и HTTP API над `review_diff`.

1. **Конституция** (`3fa9ab8`): 6 принципов, в том числе «стык команд — один
   общий контракт» и «`check.sh` нельзя менять без отдельного поручения».
2. **Две спеки независимо** — две сессии, у каждой свой
   `SPECIFY_FEATURE_DIRECTORY`; команды не читали друг друга и OpenSpec-proposal.
   Спеки до согласования — `61ea041`.
3. **Сверка стыка** — третья сессия «архитектор» + мои решения. Расхождения:

   | Тема | UI считал | Логика считала | Решение |
   |---|---|---|---|
   | HTTP-коды | `error` → 200 | 200 / 400 / **502** | 200/400/502, страница решает по `status` в теле |
   | кто отдаёт страницу | тот же origin | один эндпоинт, остальное 404 | один процесс: `GET /`, `GET /app.js`, `POST /api/review` |
   | очень большой дифф | «дифф слишком большой» | `request_too_large` до `review_diff` | лимит тела 1 МиБ, на странице тот же текст |
   | `message` | без технических деталей | «готовый текст для показа» (а в нём `[Errno 111]`) | текст страницы по `code`, `message` — в «подробнее» |
   | ошибки HTTP-слоя | неизвестный ответ → «сеть» | свои коды, форма не определена | `{"status":"request_error", code, message}` |
   | числа | — | — | порт 8055, тайм-аут страницы 45 с, флаг `--fake-model` |

   Архитектор нашёл первые две и пробелы по числам, но пропустил «большой
   дифф» и `message` — оба видны только если проиграть сценарий
   пользователя, а не сверять формат обмена.
4. **Контракт** `specs/contract/review-api.md` (`6da0de3`), затем
   `/speckit.clarify` в обеих командах — спеки после согласования `a89f206`.
5. **Plan → tasks → analyze** (`d65d0d5`, `evidence/speckit-analyze.md`),
   **implement** по очереди: логика (`cf43533`), UI (`2ff8360`).

## 3. Сравнение OpenSpec и Spec Kit (на этой работе)

| | OpenSpec 1.14.1 | Spec Kit 1.2.2 |
|---|---|---|
| Единица работы | change: delta к текущим specs | папка фичи `specs/NNN-*`: spec → plan → tasks |
| Brownfield | delta + archive дают **живую** main spec `review-diff` — описание текущего поведения системы | у каждой фичи своя спека; общей «текущей спеки системы» нет, после implement спеки фиксируют намерение, а не состояние |
| Проверка формы | `openspec validate --strict` детерминированно: поймал требование без SHALL и описание > 500 символов | детерминированно — только наличие файлов (`check-prerequisites.sh`); качество — чек-лист и analyze, которые делает модель |
| Постоянные правила | `config.yaml`: `context` и `rules` по артефактам — CLI сам подмешивает в инструкции (доказано файлами) | конституция — модель читает и проходит Constitution Check в плане; сработала: правка `check.sh` потребовала явного поручения |
| Несколько команд | change именуются, параллельные changes в одной папке не мешают | текущая фича — один `.specify/feature.json` на checkout: вторая команда перетёрла указатель первой; спасла переменная `SPECIFY_FEATURE_DIRECTORY` |
| Объём | change `diff-stats` — 296 строк на маленькую фичу | 1655 строк документов на фичу с двумя командами; спеки по 337 строк |
| Где плохо | валидатор подталкивает «чинить форму»: агент вынес правило подсчёта из требования в пояснение сценария, чтобы уложиться в 500 символов | спеки многословны и дублируют контракт; поддерживать их после кода дорого |
| Вывод | лучше для потока небольших изменений существующей системы | лучше, когда до кода надо договориться нескольким сторонам и нужны plan/research/contracts |

## 4. Рефлексия

Согласовали до кода шесть вещей, в которых команды разошлись бы при
интеграции: коды ответов, кто отдаёт страницу, поведение на очень большом
диффе, что показывать пользователю вместо `message`, форму ошибок
HTTP-слоя и числа (порт, тайм-аут, флаг демо). Каждая спека по отдельности
была разумной — противоречия видны только при сверке «допущений о
другой стороне», поэтому раздел допущений оказался самым полезным в
спеке.

Чему научился: документ и валидатор не доказывают поведение — в обоих
фреймворках все галочки стояли, а дыры нашлись мутациями (две ветки
`except` без проверки `stats`, тайм-аут, защищённый только `abort`).
Независимая проверка находит другое, чем автор: ревьюер OpenSpec нашёл
сломанный старый тест, архитектор — протокол, но не пользовательские
сценарии. И правило в конфиге работает, только если доказать, что агент
его получил, — это видно по выводу CLI, а не по ответу агента.

## Оговорки

- С этапа plan Spec Kit шлюз модели (VseLLM) отвечал `HTTP 402` (лимит
  ключа курса), OpenCode показывал это как `Request failed`. Plan, tasks,
  analyze и implement обеих команд выполнил другой агент-исполнитель вне
  OpenCode по тем же инструкциям `.opencode/commands/speckit.*.md` и
  скриптам `.specify/` с `SPECIFY_FEATURE_DIRECTORY` каждой команды и теми
  же границами файлов. Поэтому analyze — не независимая проверка; независимой
  служат мутации и сквозные проверки.
- `openspec/changes/review-web-ui/` намеренно не реализован в OpenSpec — это
  фрагмент для части 2 и для сравнения с той же фичей в Spec Kit.
