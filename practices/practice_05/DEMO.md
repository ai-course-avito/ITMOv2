# Рассказ и показ ДЗ 5

Сценарий примерно на 4 минуты. Цитаты можно читать почти дословно;
строки «Показать» — действия на экране. Пути ниже относительно этой папки.

## Подготовить до защиты

В терминале:

```bash
cd /home/kate/Documents/ITMO/AI/ITMOv2
git branch --show-current
REVIEW_MODE=demo make -C practices/practice_05/project run
```

Должна быть ветка `practice_05`. Если сервер уже работает на порту 8000,
повторно запускать его не нужно. Открыть http://127.0.0.1:8000.
Скопировать весь [TRAINING_PR.diff](inputs/TRAINING_PR.diff), чтобы быстро
вставить его во время показа. Открыть в редакторе FRAMEWORK.md,
RECONCILIATION.md, CONTRACT.md и evidence/final-check.txt.

## 1. Задача и продукт — 20 секунд

> В пятом домашнем задании нужно было смоделировать работу двух команд над
> одной функцией: отдельно описать интерфейс и логику, согласовать их до кода,
> затем реализовать и проверить. Для этого я выбрала AI-помощника ревью PR:
> пользователь вставляет diff — текст изменений кода — и получает описание,
> возможные риски с цитатами и список проверок.

**Показать:** страницу приложения с полем ввода. Условие при необходимости —
[презентация, страница 16](prenetation.pdf).

## 2. Фреймворк и две команды — 40 секунд

> Вместо OpenSpec использован GitHub Spec Kit. В нашей работе у каждой части
> есть спецификация, план и задачи, а общие правила вынесены в constitution.
> В OpenSpec работа организована вокруг изменения: proposal, specs, design
> и tasks, с последующим обновлением спецификаций и архивированием.
> Сравнение сохранено отдельно.
>
> Две команды эмулировали два независимых агента: один подготовил спецификацию
> интерфейса, второй — логики. Координатор сопоставил предложения, а итоговые
> решения до начала реализации одобрила я.

**Показать:** таблицу в [FRAMEWORK.md](FRAMEWORK.md), затем два файла:
[UI spec](project/specs/001-review-ui/spec.md) и
[logic spec](project/specs/002-review-logic/spec.md).
Достаточно показать структуру, читать документы целиком не нужно.

## 3. Что согласовали до кода — 50 секунд

> Исходные предложения отличались. Например, UI допускал пустой список проверок,
> а логика требовала хотя бы одну. Также логика допускала замечание по правилу
> без координат строки, а интерфейс ожидал привязку к коду.
> Мы приняли общий контракт: хотя бы одна проверка, а каждый риск содержит
> файл, номер строки и точную цитату из diff. Ещё согласовали формат ошибок,
> ограничения результата и время ожидания.
> Обе спецификации обновлены до реализации; версии до и после сохранены.

**Показать:** строки checks и evidence в [RECONCILIATION.md](RECONCILIATION.md),
соответствующие поля в [CONTRACT.md](CONTRACT.md), затем папки
[before](evidence/before/) и [after](evidence/after/).
Если попросят доказательство порядка работ: commit `5301bc5` содержит
согласованные документы, но ещё не содержит `project/app/` и `project/static/`.

## 4. Работа приложения и ошибка — 60–80 секунд

> Сейчас показан деморежим: вместо внешней модели работают воспроизводимые
> правила. Сам путь через интерфейс, HTTP API, обработку diff и вывод результата
> настоящий. Адаптер внешней модели реализован, но реальный вызов провайдера
> в этой работе не проверялся.

**Сделать:** вставить учебный diff → нажать «Проверить diff» → прокрутить результат.

> Здесь три возможных риска. У каждого есть файл, строка и цитата, поэтому
> замечание можно проверить. Ниже — предлагаемые проверки. Совпадение цитаты
> подтверждает её наличие в diff, но не доказывает правильность самого риска.

**Показать:** маркер ДЕМО, одну карточку риска и список проверок.
Затем нажать «Очистить», ввести `это не diff` и отправить.

> Некорректный diff отклоняется с понятной ошибкой. После исправления ввода
> можно повторить запрос.

**Сделать:** заменить текст учебным diff и снова получить результат.

## 5. Проверки и вывод — 40 секунд

> Пройдено 37 тестов логики и API и 10 браузерных тестов. Проверены успешный
> сценарий, ошибки, лимит 20000 символов, повторная отправка и поздний ответ.
> Основной браузерный сценарий проходит через настоящий локальный сервер
> в деморежиме; отдельные сбои моделируются управляемыми ответами.
>
> Мне помогли общий контракт и таблица расхождений: они сделали понятными
> данные и позиции обеих команд. Самым важным было связать каждый риск
> с конкретной строкой. Мой вывод: спецификация полезна, когда по ней можно
> проверить поведение приложения. Дальше я хотела бы проверить настоящую
> модель на разных PR и добавить загрузку diff из файла или по ссылке.

**Показать:** в [final-check.txt](evidence/final-check.txt) два итога:
`Ran 37 tests … OK` и `Ran 10 tests … OK`. Полная рефлексия —
[REFLECTION.md](REFLECTION.md).
