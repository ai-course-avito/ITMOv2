# Правила работы над практикой 5

Эти правила действуют для `practices/practice_05/` и изменений проекта, выполняемых в рамках практики 5. При работе с кодом другого каталога учитывай также его локальный `AGENTS.md`.

## Контекст проекта

- Рабочий проект находится в `practices/practice_05`: это отдельная копия «Билетика» из практики 4. Основная документация — [PROJECT_README.md](PROJECT_README.md), план фичи сортировки — [docs/features/price-sort.md](docs/features/price-sort.md), история изменений — [CHANGELOG.md](CHANGELOG.md).
- React/TypeScript/Vite вызывает только FastAPI. Ключ `IGNAV_API_KEY` хранится на сервере в окружении или `backend/.env`; не передавай его в браузер, код, логи и коммиты.
- Поиск выполняется только по кнопке: успешные запросы Ignav могут тарифицироваться. Сохраняй трёхминутный кеш одинаковых запросов, валидацию IATA-кодов и полных дат, поведение пустых ответов и ошибок.
- API поиска — `POST /api/fares/one-way` и `POST /api/fares/round-trip`. Для прямых рейсов Ignav получает `max_stops: 0`, для бюджета — `max_price` в валюте рынка. Валюту показывай из ответа без пересчёта.
- SQLite в `backend/price_history.sqlite3` локальная. Сравнивай только одинаковые параметры поиска и одинаковые валюты, используя общий расчёт `backend/app/price_math.py`. Пустые ответы сохраняются без цены и не используются как числовая точка сравнения.
- OpenSpec инициализирован в корне репозитория. В артефактах явно указывай целевой проект `practices/practice_05`. Документ фичи остаётся планом до реализации и приёмки; соблюдай этапы из README практики.

## Skills и проверки

- Перед изменением FastAPI читай `.agents/skills/fastapi-python/SKILL.md`, сложных схем — `pydantic/SKILL.md`, React — `vercel-react-best-practices/SKILL.md`.
- Для общей проверки читай `.agents/skills/verify-flight-features/SKILL.md` и запускай из `practice_05`: `backend/.venv/bin/python .agents/skills/verify-flight-features/scripts/run.py --report verification/flight-features.md`.
- Проверки используют подменённый Ignav и временную SQLite. Старые отчёты не подтверждают актуальный результат. Для сортировки отдельно проверяй порядок карточек, граничные случаи и отсутствие нового запроса при переключении.
- `opencode.json` подключает Context7 и MCP `flight-history`; инструкции — в [MCP_README.md](MCP_README.md). Hook `.opencode/plugins/verify-after-edit.js` действует в OpenCode. В Codex запускай проверки явно.

## Новые фичи и документация

- При добавлении каждой фичи обновляй документацию проекта в рамках того же изменения.
- Описывай новое поведение, способ использования и ограничения. Если меняются запуск, настройки или API, обновляй соответствующие инструкции и примеры.
- Фиксируй, что изменилось, в разделе истории изменений документации проекта либо в его `CHANGELOG.md`, если такой файл уже используется.
- Документация должна соответствовать реализованному и проверенному поведению. Не описывай запланированные возможности как готовые.

## Коммиты

- После завершения и проверки новой фичи оформляй её отдельным коммитом по Conventional Commits вместе с обновлённой документацией.
- Формат сообщения: `<type>(<scope>): <краткое описание>`. Область `scope` можно опустить, если она не помогает понять изменение.
- Для новых фич используй `feat`, для исправлений — `fix`, для самостоятельных изменений документации — `docs`. По необходимости используй `refactor`, `test`, `build`, `ci` и `chore`.
- Для несовместимых изменений добавляй `!` после типа или области и пояснение `BREAKING CHANGE:` в теле коммита.
- Объединяй в коммит одну законченную задачу. Добавляй файлы явно и не включай посторонние или незавершённые изменения пользователя.
- Перед коммитом выполни проверки, требуемые проектом, и проверь diff. Если проверки не удалось выполнить, сообщи причину и не представляй их как успешные.

Пример:

```text
feat(practice-05): добавить новую возможность и обновить документацию
```
