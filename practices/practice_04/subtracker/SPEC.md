# SPEC — subtracker

## 1. Продукт

**Проблема.** Люди забывают, за что платят (стриминг, облака, VPN, приложения): списания приходят неожиданно, общая сумма в месяц и в год неизвестна.

**Ценность.** Один экран показывает расход за месяц и за год и заранее предупреждает о списаниях.

**Аудитория.** Физлица с 5–20 подписками. Разработка — соло, ролей и командных тарифов нет.

## 2. Тарифы

| | Free | Pro |
|---|---|---|
| Количество подписок | без лимита | без лимита |
| Список подписок, расход за месяц/год | да | да |
| Реклама | да (показывает фронт) | нет |
| Перетаскивание (ручной порядок подписок) | нет | да |
| Интеграция с календарём (дата списания) | нет | да |
| Прогноз расходов | нет | да |
| Оценка необходимости подписки (рейтинг) | нет | да |
| Подсказки по экономии / оптимизации расходов | нет | да |

Статус реализации: **ни одна Pro-фича пока не реализована.** Реализован только признак `plan` (`free` по умолчанию) и его выдача через `GET /api/auth/me`. Реклама — задача фронта: бэкенд лишь сообщает план. Оплата (Stripe) не делается; тариф переключается вручную в БД. Лимита подписок на Free нет.

## 3. Модель данных

- **User**: `id`, `email` (уникален, хранится в нижнем регистре), `hashed_password` (argon2), `default_currency` (3 буквы; одна валюта на пользователя), `plan` (`free` | `pro`, по умолчанию `free`).
- **Subscription**: `id`, `owner_id` → User, `name` (1–255), `amount` (`Decimal`, > 0, 2 знака, до 99 999 999.99), `billing_cycle` (`monthly` | `yearly` | `weekly` | `custom_days`), `custom_interval_days` (обязателен только для `custom_days`, от 1 до 3650, иначе запрещён), `is_active`, `start_date`, `next_billing_date` (обе даты в диапазоне 2000-01-01…2100-12-31), `note` (до 500, необязательно).
- Правила на `amount`, `billing_cycle`, `custom_interval_days` и диапазон дат дублируются CHECK-ограничениями в БД; в этих границах расчёт дат не может переполниться. Категорий нет.

Следующие этапы добавят поля для Pro-фич (порядок, оценка необходимости).

## 4. API

Все эндпоинты, кроме `/health` и `/api/auth/*`, требуют `Authorization: Bearer <access_token>`.

**Реализовано**
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`, `GET /api/auth/me`
- `GET /health`
- `GET /api/stats/summary` — расход за месяц/год по активным подпискам текущего пользователя.
- `GET /api/stats/breakdown` — разбивка месячных расходов по подпискам и по циклам оплаты (для диаграмм).
- `POST /api/subscriptions` (201), `GET /api/subscriptions` (параметры списка — ниже), `GET /api/subscriptions/{id}`, `PATCH /api/subscriptions/{id}`, `DELETE /api/subscriptions/{id}` (204).
- `GET /api/subscriptions/upcoming?days=N` — ближайшие списания.

Чужая подписка неотличима от несуществующей: 404 на чтение, изменение и удаление. Поля `id` и `owner_id` в запросе игнорируются. Невалидные данные — 422. Лимита подписок на Free нет.

Пример создания:
```json
POST /api/subscriptions
{"name": "Netflix", "amount": "15.49", "billing_cycle": "monthly", "start_date": "2026-01-05"}
```
Ответ содержит `amount` строкой с двумя знаками (`"15.49"`) и `next_billing_date`. Если дата не передана, она считается как ближайшая дата списания не раньше сегодняшнего дня от `start_date` по циклу.

**Список подписок.** Параметры `GET /api/subscriptions`: `is_active`, `billing_cycle`, `q` (поиск по названию и примечанию без учёта регистра и пробелов по краям, работает и для кириллицы, до 100 символов; `%` и `_` ищутся как обычные символы), `sort` (`id` по умолчанию, `name`, `amount`, `monthly_cost`, `charge_date`), `order` (`asc` по умолчанию, `desc`), `limit` (1–500, по умолчанию 100), `offset`. Порядок: сначала фильтры, потом поиск, сортировка и только затем выдача страницы; при равенстве ключей порядок по `id`; подписки без `charge_date` (неактивные) всегда в конце. `sort=amount` сортирует по сумме платежа как она указана, а для сравнения затрат используйте `monthly_cost`. Неизвестные значения — 422. Каждый элемент списка, помимо полей подписки, содержит `monthly_cost` (месячный эквивалент, строка с двумя знаками), `charge_date` (ближайшая реальная дата списания, считается от сохранённой `next_billing_date` вперёд по циклу; для неактивных `null`) и `days_until` (дней до списания; для неактивных `null`). В ответах на создание, чтение одной подписки и PATCH этих полей нет. Поиск, сортировка и выдача страницы выполняются в приложении после фильтрации в БД: для личного списка до нескольких сотен подписок этого достаточно, для очень больших списков потребуется сортировка в SQL.

**Разбивка расходов** (`/api/stats/breakdown`). Ответ: `currency`, `monthly_total` (равен `monthly_total` из summary), `by_subscription` (`id`, `name`, `billing_cycle`, `monthly_cost`, `share_percent`; по убыванию стоимости, затем по названию) и `by_cycle` (`billing_cycle`, `subscription_count`, `monthly_cost`, `share_percent`; все `custom_days` в одной группе). Только активные подписки. Проценты округляются до двух знаков, поэтому их сумма может отличаться от 100 из-за округления; если общий итог равен 0.00, все доли 0.00. Топ-5 фронт берёт срезом из `by_subscription`.

**PATCH** — частичное обновление: итоговая подписка проверяется целиком. Если меняются `billing_cycle`, `custom_interval_days` или `start_date` и `next_billing_date` не передан, дата пересчитывается; при переходе с `custom_days` на другой цикл интервал сбрасывается сам.

**Ближайшие списания (напоминания).** `days` от 1 до 365, по умолчанию 7. Возвращаются свои активные подписки, у которых дата списания попадает в промежуток от сегодня до сегодня + `days` включительно. Элемент: `id`, `name`, `amount`, `billing_cycle`, `charge_date`, `days_until`; сортировка по `charge_date`, затем по `name`. Если сохранённая `next_billing_date` уже в прошлом, `charge_date` считается от неё вперёд по циклу (месяц и год — с обрезкой до последнего дня месяца без накопления сдвига: 31 января -> 28 февраля -> 31 марта; 29 февраля + год -> 28 февраля). Запрос ничего не записывает в БД. «Сегодня» — дата по UTC, поэтому у пользователей в других часовых поясах возможен сдвиг на день около полуночи UTC. Напоминаний по email нет: это список для экрана.

**Планируется:** Pro-эндпоинты (прогноз, рейтинг, подсказки).

## 5. Дорожная карта (этапы, один этап = один change и коммит)

1. `backend-foundation` — миграции, auth, `plan`, запуск без Docker, seed, `/health`, CORS. **Готово.**
2. `subscriptions-crud` — CRUD подписок, изоляция пользователей, `next_billing_date`, ближайшие списания (напоминания считаются по запросу, планировщик не нужен). **Готово.**
3. `frontend-mvp` — фронтенд для Free: дизайн, вход, подписки, дашборд (см. раздел 8). **Идёт планирование.**
4. Pro-фичи: прогноз, календарь, рейтинг необходимости, подсказки, drag-and-drop.
5. Оплата (Stripe) и реклама.

## 6. Известные ограничения (TODO)

- Нет защиты от перебора паролей (ограничения частоты на вход и регистрацию) — сделать до публичного запуска.

- Refresh-токены не хранятся и не отзываются (stateless JWT) — для продакшена нужен список/ротация.
- Напоминаний по email/push нет: ближайшие списания считаются при запросе. Когда понадобятся уведомления вне приложения, потребуется планировщик (очередь задач или cron + таблица статусов); APScheduler внутри процесса не годится для продакшена (теряется при перезапуске, не масштабируется на несколько инстансов). В `AGENTS.md` он пока значится в стеке — устарело.
- «Сегодня» для напоминаний — UTC, персональных часовых поясов нет.
- Docker/compose пока нет (в `AGENTS.md` они указаны как планируемые); запуск локальный (см. раздел 7).

## 7. Локальный запуск

Нужны: Python-окружение через `uv`, запущенный PostgreSQL и база из `DATABASE_URL`.

```bash
cd backend
uv sync
cp .env.example .env          # один раз; задайте SECRET_KEY (обязателен)
./scripts/dev.sh --seed       # проверка БД -> миграции -> демо-данные -> uvicorn на :8000
```

- Swagger: http://localhost:8000/docs, проверка живости: http://localhost:8000/health
- `--seed` отказывается работать при `APP_ENV=production` (демо-пароль публичный), и тогда сервер не запускается.
- Демо-пользователь после `--seed`: `demo@example.com` / `demo-password` (план `free`, 5 подписок). Повторный запуск не создаёт дубликатов.
- Без демо-данных: `./scripts/dev.sh`.
- Перевести пользователя на Pro вручную: `UPDATE users SET plan = 'pro' WHERE email = '...';`
- Тесты: `uv run pytest`. Тест миграций на реальном Postgres включается переменной `TEST_POSTGRES_URL` (укажите одноразовую БД, он делает `downgrade base`).
- Линт и формат: `uv run ruff check .`, `uv run ruff format .`

## 8. Фронтенд: планирование (change `frontend-mvp`)

**Принято**
- Стек: React + Vite + TypeScript + Tailwind. Папка `frontend/`, порт 5173, API на `http://localhost:8000`.
- Визуальный референс: тёмный SaaS-стиль (тёмный фон, крупные скруглённые карточки с мягкими градиентами, тонкие заголовки, оранжевый акцент, плашки-метки разделов).
- **Две темы** — светлая и тёмная, переключатель в интерфейсе; по умолчанию тёмная или системная (уточнить).
- **Два языка** — русский и английский, переключатель в интерфейсе. Все тексты через словарь переводов, без строк в компонентах.
- Реклама для Free — заглушка-баннер, скрывается при `plan = pro`; реальная рекламная сеть позже.
- Названия полей API остаются в snake_case; преобразование в camelCase — только в API-клиенте.

**Схема экранов (утверждено)** — вкладки: **Обзор | Подписки | Календарь (Pro, замок на Free) | Аналитика (Pro или позже, уточнить)**.
- **Обзор**: три карточки с цифрами (расход за месяц, за год, число активных подписок), кольцевая диаграмма долей расходов по подпискам, столбцы топ-5 самых дорогих, лента «ближайшие списания» (из `/api/subscriptions/upcoming`).
- **Подписки**: поиск, фильтры-чипсы (активные / неактивные, цикл оплаты), сортировка (по умолчанию по дате ближайшего списания; также по сумме и названию), группы по времени списания («Сегодня», «На этой неделе», «В этом месяце», «Позже»), переключатель «карточки / таблица».
- **Календарь**: заглушка с замком, пока Pro-фичи не реализованы.
- **Добавление и правка подписки**: боковая панель на компьютере, нижняя шторка на телефоне (без перехода на другую страницу).
- Страницы входа и регистрации вне вкладок; блок рекламы-заглушки для Free.

**Категорий нет (утверждено).** Инфографика строится по подпискам и по циклам оплаты (месячные, годовые, недельные, свои интервалы).

**Что бэкенд даёт для этих экранов (реализовано в change `subscriptions-search-and-breakdown`)**
- Разбивка расходов для диаграмм: `GET /api/stats/breakdown`.
- Поиск, фильтр по циклу, сортировка и вычисляемые поля (`monthly_cost`, `charge_date`, `days_until`) в `GET /api/subscriptions`; группы «Сегодня / На этой неделе / В этом месяце / Позже» фронт строит по `days_until`.
- Язык и тема хранятся только в браузере; в профиль пользователя — позже.
