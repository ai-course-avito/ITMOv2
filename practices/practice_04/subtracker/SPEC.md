# SPEC — subtracker

## 1. Продукт

**Проблема.** Люди забывают, за что платят (стриминг, облака, VPN, приложения): списания приходят неожиданно, общая сумма в месяц и в год неизвестна.

**Ценность.** Один экран показывает расход за месяц и за год и заранее предупреждает о списаниях.

**Аудитория.** Физлица с 5–20 подписками. Разработка — соло, ролей и командных тарифов нет.

## 2. Тарифы

| | Free | Pro |
|---|---|---|
| Количество подписок | без лимита | без лимита |
| Список подписок, расход за месяц/год | да | да |
| Реклама | да (показывает фронт) | нет |
| Перетаскивание (ручной порядок подписок) | нет | да |
| Интеграция с календарём (дата списания) | нет | да |
| Прогноз расходов | нет | да |
| Оценка необходимости подписки (рейтинг) | нет | да |
| Подсказки по экономии / оптимизации расходов | нет | да |

Статус реализации: **ни одна Pro-фича пока не реализована.** Реализован только признак `plan` (`free` по умолчанию) и его выдача через `GET /api/auth/me`. Реклама — задача фронта: бэкенд лишь сообщает план. Оплата (Stripe) не делается; тариф переключается вручную в БД. Лимита подписок на Free нет.

## 3. Модель данных

- **User**: `id`, `email` (уникален, хранится в нижнем регистре), `hashed_password` (argon2), `default_currency` (3 буквы), `plan` (`free` | `pro`, по умолчанию `free`).
- **Subscription**: `id`, `owner_id` → User, `name`, `amount` (`Decimal`, 2 знака), `billing_cycle` (`monthly` | `yearly` | `weekly` | `custom_days`), `custom_interval_days`, `is_active`.

Следующие этапы добавят `next_billing_date`, ограничения на `billing_cycle` и `amount`, а также поля для Pro-фич (порядок, оценка необходимости).

## 4. API

Реализовано:
- `GET /api/stats/summary` — расход за месяц/год по активным подпискам текущего пользователя.
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`, `GET /api/auth/me`
- `GET /health`

Планируется: CRUD `/api/subscriptions`, `/api/subscriptions/upcoming`, Pro-эндпоинты (прогноз, рейтинг, подсказки).

## 5. Дорожная карта (этапы, один этап = один change и коммит)

1. `backend-foundation` — миграции, auth, `plan`, запуск без Docker, seed, `/health`, CORS.
2. CRUD подписок + изоляция пользователей + `next_billing_date`.
3. Напоминания о ближайших списаниях (APScheduler).
4. Фронтенд: логин, список, дашборд.
5. Pro-фичи: прогноз, календарь, рейтинг необходимости, подсказки, drag-and-drop.
6. Оплата (Stripe) и реклама.

## 6. Известные ограничения (TODO)

- Refresh-токены не хранятся и не отзываются (stateless JWT) — для продакшена нужен список/ротация.
- APScheduler работает внутри процесса приложения: напоминания могут теряться при перезапуске и не масштабируются на несколько инстансов. Для продакшена нужна очередь задач или cron + таблица статусов. Это решение для MVP, не production-grade.
- Docker/compose пока нет (в `AGENTS.md` они указаны как планируемые); запуск локальный (см. раздел 7).

## 7. Локальный запуск

Нужны: Python-окружение через `uv`, запущенный PostgreSQL и база из `DATABASE_URL`.

```bash
cd backend
uv sync
cp .env.example .env          # один раз; задайте SECRET_KEY (обязателен)
./scripts/dev.sh --seed       # проверка БД -> миграции -> демо-данные -> uvicorn на :8000
```

- Swagger: http://localhost:8000/docs, проверка живости: http://localhost:8000/health
- Демо-пользователь после `--seed`: `demo@example.com` / `demo-password` (план `free`, 5 подписок). Повторный запуск не создаёт дубликатов.
- Без демо-данных: `./scripts/dev.sh`.
- Перевести пользователя на Pro вручную: `UPDATE users SET plan = 'pro' WHERE email = '...';`
- Тесты: `uv run pytest`. Тест миграций на реальном Postgres включается переменной `TEST_POSTGRES_URL` (укажите одноразовую БД, он делает `downgrade base`).
- Линт и формат: `uv run ruff check .`, `uv run ruff format .`
