Skill tdd-feature: устройство, запуск и проверенный результат

Устройство (созданный мной skill)

Процедура из шести шагов: прочитать контракт, пример теста и style guide; написать один падающий тест (перед этим прочитать writing-good-tests.md); запустить fail_first.sh; написать минимальный код; sh scripts/check.sh; посмотреть git diff. Содержательная автоматизация это scripts/fail_first.sh: он запускает один тест и печатает FAIL-FIRST OK только если тест упал по assertion. Если тест прошел сразу, нет тестов, ошибка импорта или сломана фикстура, печатает FAIL-FIRST BAD с причиной.

  • ai-review-api/.claude/skills/tdd-feature/SKILL.md
  • ai-review-api/.claude/skills/tdd-feature/writing-good-tests.md
  • ai-review-api/.claude/skills/tdd-feature/scripts/fail_first.sh

Проверка скрипта на четырех случаях

fail_first.sh tests/test_tmp_ff.py::test_missing_feature_returns_422
  -> FAIL-FIRST OK: ... AssertionError: assert 200 == 422
fail_first.sh tests/test_tmp_ff.py::test_passes_already
  -> FAIL-FIRST BAD: тест прошел сразу
fail_first.sh tests/test_tmp_bad.py
  -> FAIL-FIRST BAD: ошибка сбора тестов ... No module named 'app.nothing'
fail_first.sh nonexist.py
  -> FAIL-FIRST BAD: pytest завершился с кодом 4

Источник: evidence/fail_first_run.txt

Запуск агентом и результат

  • Фича A (50 тестов, CHECK PASS). fail_first.sh дал FAIL-FIRST OK на assert 200 == 422, assert 200 == 413 и KeyError: 'error'. Тест «ровно 100000 байт» прошел сразу, FAIL-FIRST BAD. Агент проверил, что тест что-то проверяет: временно заменил > на >=, hook дал CHECK FAIL, после возврата CHECK PASS.
  • Фича B (54 теста). Тест на таймаут сначала дал FAIL-FIRST BAD: в app.main не было константы LLM_TIMEOUT_SECONDS, тест падал на AttributeError. После добавления константы FAIL-FIRST OK, assert 200 == 502.
  • Исправление замечаний (56 тестов). Тест времени переписан, при временном wait=True FAIL-FIRST OK с assert 5.026 < 2.5, потом wait=False возвращен.

Что проверил я как ревьюер: sh scripts/check.sh дал 50 passed после A и 56 passed после исправлений B, git diff --check без ошибок, контракт и check.sh не тронуты. Через TestClient и настоящий uvicorn с curl прогнаны границы 100000 и 100001 байт (ASCII, кириллица, эмодзи), везде ожидаемый статус, LLM при отказах не вызывался.

Источники: A_run_summary.txt (пункты по skill и fail-first), B_run_summary.txt, B_fix_summary.txt, A_manual_check.txt, B_manual_check.txt.

Свой MCP diff-inspector: полезный tool, успех и ошибочный вход

Зачем: агент работает с git diff, а лимит фичи A считается в байтах UTF-8. Tool inspect_diff(diff, max_bytes=100000) разбирает unified diff и возвращает файлы (путь, статус, added, removed, binary), суммы, размер в байтах, too_large и would_be_accepted. Ошибки разбора превращаются в ToolError, клиент получает isError=true с понятным текстом. Разбор вынесен в чистый Python и покрыт 38 тестами (sh scripts/check.sh: 43 passed на тот момент).

  • ai-review-api/mcp_server/server.py
  • ai-review-api/mcp_server/diff_parser.py
  • ai-review-api/mcp_server/smoke_client.py
  • ai-review-api/tests/test_diff_parser.py
  • ai-review-api/.mcp.json

успех diff на 5 файлов

isError: False
total_files: 5   total_added: 5   total_removed: 4
size_bytes: 716  max_bytes: 100000
too_large: false  would_be_accepted: true
статусы: modified, added, deleted,
         renamed (src/a.py -> src/b.py),
         binary=true (img/logo.png)

Тот же diff при max_bytes=100: too_large: true, would_be_accepted: false, это не ошибка (isError: False).

ошибка шесть плохих входов

  Не нашел ни одного признака unified diff...

  max_bytes должен быть больше 0, получено: 0.
max_bytes=-5       isError: True
  ... получено: -5.

ИТОГ: OK
