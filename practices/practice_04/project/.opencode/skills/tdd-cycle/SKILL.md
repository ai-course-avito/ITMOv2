description: TDD (red-green-refactor) для бэкенда FastAPI в этом проекте; применяй при добавлении/изменении HTTP-эндпоинтов и правил контракта.
---

Пошаговая процедура под этот проект (граф задач по тегам, FastAPI, pytest):

1) Прочитать docs/requirements.md и найти релевантный раздел контракта для фичи.
   - Учитывай модель данных: Задача {id: int, title: str, tags: list[str]}.
   - Пример: «Фича A — входная валидация (POST /tasks)» и правила 201/422.

2) Прочитать tests/test_example.py как эталон стиля тестов.
   - Паттерн Arrange-Act-Assert, один сценарий на тест, HTTP-уровень через TestClient.

3) Red — написать/выбрать фейлящийся тест и зафиксировать падение.
   - Создай новый тест с именем формата tests/test_<feature>_<behavior>.py или используй существующий.
   - Тестируй только публичный HTTP API: from fastapi.testclient import TestClient; client = TestClient(app).
   - Запусти sh scripts/check.sh и зафиксируй вывод (ожидаем красный — падение по правильной причине).

4) Green — реализовать минимальный код, чтобы тест прошёл, и зафиксировать зелёный прогон.
   - Для FastAPI реализуй ровно столько, сколько нужно: например, POST /tasks с pydantic-схемами (TaskIn/Task), in-memory список, 201 при валидном вводе, 422 при невалидном (см. контракт).
   - При необходимости добавь GET /tasks, если тест его использует.
   - Снова запусти sh scripts/check.sh и зафиксируй вывод (все тесты зелёные).

5) Refactor — небольшой рефакторинг без изменения поведения.
   - Наведи порядок в именах, вынеси общие куски, типы. Тесты должны остаться зелёными.
   - При сомнениях — малые шаги: «рефактор — прогон тестов».

6) Границы из AGENTS.md — не трогай без явного поручения:
   - docs/requirements.md, docs/design.md и scripts/check.sh.

Подсказки для этого репозитория:
- Хранилище — in-memory список в процессе; не добавляй внешние БД.
- Поведение API должно строго соответствовать контракту (коды 201/422, структура ответа).
- Тесты должны работать изолированно; не полагайся на порядок запуска, состояние подготавливай через API.
