# Контракт API: ai-review-api

Сервис принимает diff и возвращает ревью от LLM. В проекте LLM заменен детерминированной заглушкой (`app/llm.py`), сеть не используется.

## Эндпоинты

### GET /health

Ответ `200`:

```json
{"status": "ok"}
```

### POST /review

Запрос (`Content-Type: application/json`):

```json
{"diff": "<текст diff>"}
```

Ответ `200`:

```json
{
  "summary": "Файлов в diff: 1",
  "comments": [
    {"file": "unknown", "line": 1, "text": "..."}
  ]
}
```

- `summary`: строка, краткий итог ревью.
- `comments`: список комментариев (`file`, `line`, `text`).
- Если поле `diff` отсутствует или не строка, FastAPI отвечает `422` (стандартная схема валидации).

Ревью выполняет `LLMClient.review(diff: str) -> dict`; клиент подставляется через `Depends(get_llm_client)`, в тестах его заменяют через `app.dependency_overrides`.

## Планируемые фичи

Эти фичи в базовую версию НЕ входят, их делает агент. Сейчас `/review` принимает любой diff любого размера, а ошибка LLM вылетает наружу.

### Фича A: входная валидация

- Пустой diff (пустая строка или только пробельные символы): `422`.
- Размер diff больше `MAX_DIFF_BYTES = 100000` байт (в UTF-8): `413` с телом `{"error": "diff_too_large", ...}` (остальные поля, например `max_bytes`, допустимы).
- При отказе по любой из этих причин LLM НЕ вызывается.
- Diff размером ровно `MAX_DIFF_BYTES` байт допустим.

### Фича B: ошибка зависимости

- Если LLM выбросил ошибку или превысил таймаут: `502` с телом `{"error": "llm_unavailable", ...}` вместо `500` со стектрейсом.
- Сценарии фичи A сохраняются (валидация срабатывает раньше обращения к LLM).
