# Style guide: ai-review-api

Пять правил. Агент читает их перед правкой кода и тестов.

1. **Имена.** Функции и переменные в `snake_case`, константы в `UPPER_CASE` (например `MAX_DIFF_BYTES`), классы в `CamelCase`. Имя теста описывает поведение: `test_review_with_empty_diff_returns_422`.
2. **Тест на каждый код ответа.** Для каждого кода, который эндпоинт может вернуть по контракту (200, 413, 422, 502 и т.д.), есть минимум один тест. Граничные значения проверяем отдельными тестами.
3. **Зависимости только через `Depends`.** Клиент LLM и любые другие внешние зависимости получаем через `Depends(...)`, не создаем внутри эндпоинта и не берем из глобальных переменных. Так их можно подменить через `app.dependency_overrides`.
4. **Ошибки API в одном формате.** Тело любой ошибки, которую мы формируем сами: `{"error": "<код>", "detail": ...}`, где `<код>` это короткий `snake_case` (`diff_too_large`, `llm_unavailable`). Стектрейс в ответ не отдаем.
5. **Без лишних комментариев.** Код и имена должны быть понятны сами. Комментарий нужен только там, где объясняется "почему", а не "что". Закомментированный код и отладочные `print` не оставляем.
