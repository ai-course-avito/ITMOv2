# Как писать хорошие тесты в этом проекте

Коротко, чтобы агент мог быстро подгрузить это перед написанием теста.

## Что тестируем

- Наблюдаемое поведение API из `docs/requirements.md`: код ответа, тело ответа, был ли вызван LLM.
- Не тестируем внутренности (приватные функции, порядок вызовов внутри `app/`), иначе тест ломается при любом рефакторинге.
- На каждый код ответа, который описан в контракте для фичи, нужен минимум один тест (200, 413, 422, 502 и т.д.).

## Один сценарий на тест

- Один тест проверяет одну причину падения. Если в названии хочется написать "и", тестов должно быть два.
- Граничные значения отдельными тестами: ровно лимит проходит, лимит + 1 не проходит.
- Структура: подготовка, один вызов API, проверки результата.

## Имена

- `test_<что делаем>_<что ожидаем>`, например `test_review_with_empty_diff_returns_422`.
- Имя читается как предложение про поведение. Без `test_1`, `test_ok`, `test_new_feature`.

## Мок LLM

- LLM всегда подменяем через `app.dependency_overrides[get_llm_client] = lambda: fake`, как в `tests/test_example.py`.
- Фейк детерминированный и запоминает вызовы (`fake.calls`), чтобы проверять "LLM не вызывался" при отказе по валидации.
- Для ошибки зависимости фейк сам бросает исключение или таймаут в `review`.
- Overrides чистим после теста (фикстура с `yield` и `dependency_overrides.clear()`).
- Сеть и реальный клиент в тестах не используем.

## Плохие тесты

- Тест без assertion или с `assert True`: пройдет всегда.
- Assertion, которая подогнана под текущий вывод (`assert response.text == "..."` целиком, когда важен только код).
- Тест, который проверяет только `status_code != 500`: слишком слабо, проверяй точный код и поле `error`.
- Тест, зависящий от порядка запуска или от состояния прошлого теста (не почищены overrides).
- Тест, который падает по неправильной причине: ImportError, опечатка в URL, забытая фикстура. Для этого и нужен fail-first.
- Огромный тест "на всю фичу" с десятком assertion: непонятно, что именно сломалось.
