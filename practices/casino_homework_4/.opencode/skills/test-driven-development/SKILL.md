# TDD для LuckySpin

## Когда применять
- Новые фичи: лобби автоматов, спин, ежедневный бонус, изменение баланса.
- Рефакторинг критичных мест: расчёт выигрыша, логика бонуса «раз в день», сохранение баланса в localStorage.
- Починки багов: сначала падающий тест, затем фикс.

## Как устроено
- Цикл Red → Green → Refactor.
- Тесты на Vitest + @testing-library/react для UI, чистые unit-тесты для бизнес-логики.
- Данные храним в localStorage, поэтому выделяем «ядро» логики в чистые функции; доступ к localStorage оборачиваем адаптером.
- Случайность и время под контролем: RNG и «часы» инъецируем или мокируем.

## Шаги
1. Сформулировать поведение на языке теста.
2. Написать минимальный падающий тест (Red). Тест должен быть стабильным и описывать пользовательскую ценность.
3. Запустить тесты и убедиться, что падение связано с отсутствующей реализацией.
4. Написать минимальный код для прохождения теста (Green). Без преждевременной абстракции.
5. Рефакторинг: устранить дубли, улучшить имена, вынести чистые функции, оставить поведение неизменным (Refactor).
6. Повторить цикл до покрытия сценария целиком.
7. Для багфикса: сначала регрессионный тест, затем фикс, затем рефактор.

## Запрещено
- Писать «боевой» код без падающего теста.
- Добавлять тесты, зависящие от реального времени/рандома.
- Мокать слишком глубоко UI-детали там, где нужна проверка поведения пользователя.
- Преждевременная оптимизация и сложные абстракции до стабилизации API через тесты.
